# CLAUDE.md — точка входа для LLM

Ты работаешь над **AI Hospitality Platform** — мультитенантной SaaS-платформой, где AI является основным интерфейсом между гостями отеля, персоналом и внутренними сервисами. Это НЕ чат-бот: чат — лишь один из каналов, ядро — оркестрация гостиничных процессов.

## Обязательно перед любой задачей

1. Прочитай [FOUNDATION.md](FOUNDATION.md) — разделы 4 (Принципы P-1…P-12) и 12 (Правила R-1…R-12). Они обязательны, нарушение = блокер.
2. Термины бери из [docs/GLOSSARY.md](docs/GLOSSARY.md) — не изобретай синонимов.
3. Работая с модулем — сначала его `README.md` и `api.py`.
4. Архитектурно значимые решения — только через ADR ([docs/adr/](docs/adr/)).
5. Читай точечно, а не подряд: эта карта → нужные разделы FOUNDATION → README и `api.py` затронутого модуля → канонический пример. Файлы задачи перечислены в её карточке: для скелета — PHASE0.md; задачи Gate B / Phase 1 ведутся в issues майлстоуна «Пилот: первый отель» (скоуп — в теле и комментариях issue). Чтение репозитория «на всякий случай» — расход контекста без пользы.

## Ключевые факты (краткая карта)

- **Архитектура:** модульный монолит (ADR-001). Микросервисы запрещены без ADR.
- **Стек:** Python 3.12 + FastAPI + Pydantic v2 + SQLAlchemy 2 + PostgreSQL(+pgvector) + Redis; фронт — Next.js/TS (ADR-002).
- **Мультитенантность:** `tenant_id` + Postgres RLS в каждой тенантной таблице (ADR-003). Ни одного запроса вне контекста тенанта.
- **Интеграции:** только через порты и адаптеры (`integrations/`). Доменные модули не импортируют интеграции напрямую. У каждого порта — обязательный Fake-адаптер: полноценная локальная реализация для dev/CI/демо, рождается в одном PR с портом (ADR-007).
- **AI:** слой поверх бизнес-логики. Каждая способность AI — декларативный tool-обёртка над сервисом ядра. Промпты — код: версионируются и покрываются evals.
- **AI Gateway:** весь LLM-трафик — только через `ai/gateway` (маршрутизация моделей, лимиты, логирование стоимости и версий промптов). Прямые вызовы провайдеров запрещены.
- **Слои:** kernel (`platform/`, `shared/`) ← доменные модули (`modules/`) ← композиционный слой (`ai/`, `channels/`). Доменные модули никогда не импортируют `ai/`, `channels/` или `integrations/`.
- **Human-in-the-loop:** деньги, документы (АВР), изменение брони — только с подтверждением человека (P-9, NG-4).
- **Наблюдаемость:** структурированные JSON-логи с `tenant_id`/`correlation_id`, OpenTelemetry, коды ошибок из каталога. Код без логов/метрик — незавершён.

## Владельцы фактов (один факт — один документ)

**Упоминать** факт вправе любой документ — но ссылкой. **Утверждать** его, с числом и формулировкой, вправе ровно один. Иначе решение расходится по репозиторию, и при изменении часть экземпляров остаётся устаревшей: на 04.08.2026, до этой правки, «90 дней» стояли в 15 файлах, «Gate B» — в 14, и два issue подряд (#193, #194) были ровно про это — отсылка обновлена в одном месте из двух, правило записано не там, где его прочтут.

Роль каждого документа фундамента задаёт [FOUNDATION.md](FOUNDATION.md) §0 («Реестр документов фундамента») — это его факт, и главная формулировка там. Таблица ниже решает обратную задачу: не «что это за документ», а «где живёт вот этот факт». Её строки — ключи поиска по классу факта, а не определения ролей, и расходиться с §0 они не вправе.

| Класс факта | Владелец |
|---|---|
| Принципы, запреты, правила R-* | [FOUNDATION.md](FOUNDATION.md) |
| Порядок фаз, Exit-критерии, нумерованные правила исполнения | [PROJECT_EXECUTION_PLAN.md](PROJECT_EXECUTION_PLAN.md) |
| Очерёдность работ | [docs/QUEUE.md](docs/QUEUE.md) |
| Одно архитектурное решение и почему именно оно | [docs/adr/](docs/adr/) |
| Устройство одной фичи и её числа | [docs/specs/](docs/specs/) |
| Шаги процедуры, выполняемой руками: деплой, восстановление, реакция на инцидент | [docs/runbooks/](docs/runbooks/) |
| Устройство и публичный контракт одного модуля | `modules/*/README.md` (R-4) |
| Значение термина | [docs/GLOSSARY.md](docs/GLOSSARY.md) |
| Обсуждение без принятого решения | [docs/DISCUSSION_LOG.md](docs/DISCUSSION_LOG.md) |
| Решение, принятое LLM от имени основателя | [docs/founder-review/](docs/founder-review/README.md) — одна запись, один файл; архив до 29.10 — [docs/FOUNDER_REVIEW_QUEUE.md](docs/FOUNDER_REVIEW_QUEUE.md) |
| Мелкая находка, отложенная на потом (не блокер) | [docs/later/](docs/later/README.md) — одна находка, один файл; архив до 29.10 — [docs/LATER.md](docs/LATER.md) |
| Как сессия ведёт себя внутри задачи: что читать, что показывать, как отчитываться | этот файл, раздел «Правила работы» |

Запрещён **второй экземпляр без ссылки** — он расходится с оригиналом молча. Разрешён и нужен **краткий пересказ со ссылкой на владельца**: на нём стоит весь этот файл — «Ключевые факты» и «Жёсткие запреты» пересказывают FOUNDATION, чтобы сессия получила карту на входе, а не читала конституцию целиком. Пересказ без ссылки и есть второй экземпляр, поэтому ссылка обязательна.

Таблица не исчерпывающая, и есть места, которые обязаны нести число сами: юридические тексты ([docs/legal/](docs/legal/) — обещание гостю и договор с отелем не ссылаются на внутреннюю спеку) и обязательные реестры ([docs/PII_REGISTRY.md](docs/PII_REGISTRY.md), [docs/runbooks/errors.md](docs/runbooks/errors.md), [docs/runbooks/secrets.md](docs/runbooks/secrets.md), [docs/RBAC.md](docs/RBAC.md)). Для них правило другое: меняешь факт у владельца — правишь их тем же PR. Перечень таких мест — правило 9 PROJECT_EXECUTION_PLAN, и он открытый; проверка одной командой — `grep -rn "в том же PR"`.

Пишешь число или решение — сначала поищи его по репозиторию (`grep`). Нашёл у другого владельца — ставь ссылку, а не второй экземпляр. Владелец сменился — прежнее место становится ссылкой в том же PR. Пример на «90 днях» выше: владелец срока — [spec 0032](docs/specs/0032-guest-text-retention.md), юрдокументы и реестр ПД несут его числом и правятся тем же PR, остальные упоминают ссылкой.

## Правила работы

- Язык кода и идентификаторов — английский; документации — русский (R-3).
- Файл ≤ ~400 строк, строгая типизация (mypy strict), Pydantic-схемы на границах (R-3, R-6).
- Нетривиальная фича начинается со спеки в `docs/specs/`, а не с кода (R-2).
- Всё, на что основатель будет смотреть глазами, — тексты гостю и персоналу, экраны, надписи на кнопках — показывай абзацем прямо в чате **до** реализации, а не PR'ом после. Вкус, выясненный после написания кода, стоит полного цикла на каждую итерацию: экран согласия переделывался тремя PR за один день (#132 → #141 → #142), тогда как три варианта текста в чате стоили бы одного сообщения. Это показ, а не запрос разрешения: показал — работаешь дальше по своему варианту, не останавливаясь. Ответ основателя пришёл до того, как ты дошёл до этого места в коде, — правишь по ответу; ответа нет — вариант остаётся твоим, и ты вписываешь его записью в [docs/founder-review/](docs/founder-review/README.md) (пока текст не увидел живой гость, несогласие правится дёшево — follow-up PR). Текст, который в рантайме порождает модель, показать абзацем нельзя (сообщение о частичном выполнении собирается моделью на каждый случай — [spec 0030](docs/specs/0030-partial-completion-guest-message.md)): показывай промпт и образец выдачи.
- **Пул окон** (правило 10 [PROJECT_EXECUTION_PLAN.md](PROJECT_EXECUTION_PLAN.md)): когда `make pool` пишет «диспетчер: работает», всё, что этот файл велит показать основателю или спросить у него в чате, — тексты до реализации, план платного прогона, вопрос развилки — окно передаёт файлом через окно-диспетчер; шаги — [docs/QUEUE.md](docs/QUEUE.md), раздел «Пул окон».
- Изменил модуль — обнови его README в том же PR (R-4).
- В БД — только UTC; наивные datetime запрещены. Локальное время — через часовой пояс отеля из конфига тенанта ([FOUNDATION.md](FOUNDATION.md) §9).
- Ревью кода выполняет отдельная LLM-сессия с чистым контекстом (FOUNDATION.md, раздел 13); самопроверка автора ревью не является. **Merge блокирует только находка, ведущая к тяжёлым последствиям** — неправда гостю или отказ ему в помощи, утечка или потеря данных, отказ системы или красный CI (R-5, R-6, R-7, R-9), неконтролируемые траты, закон и договор с отелем, рунбук, буквально ведущий к одному из них; всё прочее — записью в [docs/later/](docs/later/README.md). Список блокеров, уровни ревьюера, один круг доработки и условия merge — у владельца, правило 9 PROJECT_EXECUTION_PLAN (режим пилота, решение основателя 15.10.2026). Многоагентный режим включает человек словом `ultracode` в промпте — сессия сама фан-аут не разворачивает; в режиме пилота он только для аудитов и ревью миграций, входа и прав, изоляции тенанта и денег (правило 7).
- Задача противоречит FOUNDATION.md → остановись и сообщи, не решай молча (R-11).
- Делай ровно то, о чём просили, в том объёме, который просили. Рутинные развилки решай сам; спрашивай, только когда разные прочтения дают разную работу. Не расширяй скоуп молча: увидел **смежную** проблему — серьёзную (список блокеров правила 9 PROJECT_EXECUTION_PLAN) заведи issue, мелкую впиши записью в [docs/later/](docs/later/README.md); в этом же PR не чини. Дефект того, что правит сам этот PR, смежным не является — судьба находки решается правилом 9 PROJECT_EXECUTION_PLAN. Доводи задачу до конца целиком и сообщай о завершении только когда она действительно закончена; не смог часть — сделай остальное и прямо скажи, что осталось и почему.
- Держи документы и ответы по длине задачи. Не раздувай README, спеки и отчёты дублирующими разделами, повторными резюме и «водой»; в коде комментируй только то, чего сам код показать не может.
- **Документы — по потребности пилота** (решение основателя 15.10.2026). Спека — коротко: проблема, решение, контракты, тесты; ориентир — до ~150 строк, крайние случаи и «а что если» — записью в [docs/later/](docs/later/README.md). Рунбук пишется под процедуру, которую человек выполнит в пилоте, а не под гипотетический сценарий. Фича не обязана синхронизировать каждую спеку и рунбук, где упомянута её тема: обязательно то, что перечисляет правило 9 плана («Что автор правит тем же PR»); устаревшее упоминание в чужом документе — запись в `docs/later/`.
- Не перепроверяй себя ритуально: проверка — это прогон `make check` и тестов, а не ещё один проход по собственному тексту.
- **Платный прогон модели — только после явного «да» основателя.** Любой вызов, оплачиваемый с баланса провайдера модели (сейчас — Anthropic Console), — `python -m hospitality.ai.evals.bakeoff`, свои скрипты замеров, повторы N×, smoke руками (`make smoke`, `make smoke-staging`, `gh workflow run smoke.yml`), — сессия запускает, только показав в чате план (какие прогоны, сколько вызовов, цена в $ по прайс-листу шлюза `MODEL_PRICING_USD_PER_MTOK`, что без прогона останется непроверенным) и получив явное согласие. Названная сумма — потолок: дошёл — остановился и отчитался. R-7 и DoD спеки говорят, что мерить, но тратить не разрешают; «нет» судьбу PR само не решает — мержить без прогона (непроверенное названо в теле PR) или ждать, говорит основатель, а не сказал — спроси. Спрашивают до ревью, самое позднее — до approve (ждущий прогона PR стоит в черновике, как стоял PR #344): условия merge после approve задаёт только правило 9 [PROJECT_EXECUTION_PLAN.md](PROJECT_EXECUTION_PLAN.md), и этот пункт к ним ничего не добавляет. Исключение — проба баланса одним вызовом Haiku с `max_tokens=1`. Повод: 26.09.2026 две сессии за утро израсходовали на тестах весь баланс — третье обнуление за месяц (07.09, 11.09, 26.09), и каждое останавливало работу.
- **У автоматической платной проверки цена записана в её спеке.** Проверка, которая платит модели без участия человека (сейчас это workflow `Smoke` на PR и push в `main` — [spec 0019](docs/specs/0019-smoke-and-restore.md)), записывает в спеке цену прогона и условие запуска. Условие запуска — то же «да» основателя из пункта выше, данное на поток прогонов по записанной цене (у `Smoke` — 28.09.2026): новая такая проверка или расширенное условие требуют нового «да», а раз сумма — потолок, пересчёт, поднявший цену, показывается основателю. Пересчитывает цену PR, меняющий модель, которую вызывает проверка, или заметно растящий её промпт, — в том же PR. Повод: spec 0019 писалась под Haiku («доли цента»), модель гостя сменили на Sonnet 5, а до 28.09 цену не пересчитал никто — два месяца smoke тратил деньги и на PR из одних документов.
- **Хука перед коммитом нет** (снят решением основателя 15.10.2026 вместе с режимом пилота). Обязательный щит R-9 — CI: без зелёного required check `check` защита `main` merge не даст. Перед push гоняй тесты затронутого модуля (`.venv/bin/pytest <путь> -q --no-cov`) или полный `make check` (~6 минут: тесты в два процесса, #527), если правка широкая; красный CI на PR — обычная доработка, а не авария. Перед `gh pr ready` — сверка автора: три адресные проверки частых блокеров ревью (правило 9 [PROJECT_EXECUTION_PLAN.md](PROJECT_EXECUTION_PLAN.md), абзац «Сверка автора перед `gh pr ready`»); CI перед ready автор не ждёт — итог `check` смотрит ревьюер (там же).
- Завершая задачу, дай основателю «передачу смены» из трёх частей.
  1. **Что сделано и как проверено** — включая то, что смержено, и что от этого появилось на staging.
  2. **Что требуется лично от основателя.** Только то, чего сессия физически не может (секреты, доступы, оплата, действия в его личных аккаунтах), и то, что требует именно его решения (архитектурная развилка, продуктовый выбор, место новой задачи в очереди). Работу, которую способна выполнить сама, сессия выполняет — merge после approve в том числе (правило 9 PROJECT_EXECUTION_PLAN), — а не выносит списком «сделайте это»; вопрос основателю задаётся, когда разные ответы дают разную работу, а не для подстраховки.
  3. **Промпт для следующего окна — ровно один.** В пуле окон (правило 10) вместо него — «окно свободно, общий промпт»: продолжение несёт комментарий «Передача» в issue. То, что делает другая сессия, оформляется готовым промптом: основатель копирует его целиком и вставляет в новое окно, ничего не дописывая. Рядом с промптом — модель и effort (правило 7 PROJECT_EXECUTION_PLAN: Opus 5 или Fable 5, effort назвать явно); если класс задачи оправдывает многоагентный режим, слово `ultracode` уже стоит в тексте промпта (правило 7) — основатель ничего не дописывает. Сумма в промпте разрешением тратить не является («бюджет — около $10» в промпте доработки PR #344 сессия прочла как согласие): если окну нужен платный прогон, промпт велит показать план с ценой и ждать ответа (пункт о платных прогонах выше). Промпт пишется без просьбы: «напиши промпт для следующего окна» — это работа сессии, а не запрос к основателю.

     **Промпт всегда один, даже когда работы видно на три окна вперёд.** Пишется тот, что обязан случиться следующим; порядок задаёт правило 10 PROJECT_EXECUTION_PLAN (ревью открытого PR, доработка PR со статусом changes requested и merge approve'нутого — раньше нового кода, дальше — верхний **не занятый** пункт раздела 1). Промпт для окна после следующего пишет то окно, которое до него дойдёт: к тому моменту оно будет знать состояние PR и очереди, а сегодняшняя догадка о них устареет. Так основатель просто перекидывает один промпт из окна в окно, а не выбирает из списка, какой сейчас актуален, — выбор был бы работой, требующей знания правила 10, то есть ровно тем, что сессия обязана делать за него.

     **Хвост — это недоделанная часть задачи, а не открытый PR.** Собственный PR, ждущий ревью или доработки по находкам, и есть то, что обязано случиться следующим (правило 10, раздел 0), — он и получает тот самый единственный промпт. Мелочи окна себе не открывают: они — записью в [docs/later/](docs/later/README.md) (правила 9 и 11). Хвост же промптом не становится: серьёзный — issue с обоснованием места в очереди в его теле (строку в [docs/QUEUE.md](docs/QUEUE.md) по нему вписывает окно-диспетчер — правило 10, R-12), мелкий — запись в `docs/later/`. Промпт живёт в чате одного окна, репозиторий — в `main`, и только второе читает сессия с чистым контекстом.

  Каждый пункт «что сделано» и каждое действие основателя сопровождай пояснением простым языком, как пятнадцатилетнему: одно-два предложения — что это за вещь, зачем она нужна и почему сделано именно так; термин при первом употреблении расшифровывай. Основатель — новичок в программировании и учится по этим пояснениям; пункт передачи, который он не понял, — не передан.

## Контекст проекта

Основатель — не профессиональный разработчик; код пишут преимущественно LLM. Поэтому: простота сопровождения важнее элегантности, один канонический паттерн на каждую типовую задачу, никаких скрытых зависимостей и магии.

Текущая фаза: **Gate B — предпилотное закаливание** (Phase 0 закрыта 23.07.2026). Критерии и обоснование — [PROJECT_EXECUTION_PLAN.md](PROJECT_EXECUTION_PLAN.md), раздел «Мост Phase 0 → Phase 1»; задачи ведутся в issues майлстоуна «Пилот: первый отель».

**Режим пилота** (решение основателя 15.10.2026): главное — скорость при достаточной надёжности. До merge чинится только то, что приведёт к тяжёлым последствиям, мелочи — записью в [docs/later/](docs/later/README.md), процесс не правится — правила 9 и 11 PROJECT_EXECUTION_PLAN.

**Очередь работ — одна: [docs/QUEUE.md](docs/QUEUE.md).** Начало сессии — `make queue`; что брать, как заявить пункт и что править в конце — правило исполнения 10 PROJECT_EXECUTION_PLAN (нормативная формулировка — только там). Свою следующую задачу не выбирай и не выводи из issue-трекера.
