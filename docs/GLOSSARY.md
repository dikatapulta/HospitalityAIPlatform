# GLOSSARY — единый словарь терминов

> Ubiquitous Language проекта. Эти термины обязательны в коде (английские имена), документации, схемах БД и разговорах. Обнаружил синоним в коде — приведи к термину словаря.

| Термин (RU) | Термин в коде | Определение |
|---|---|---|
| Тенант | `Tenant` | Один отель (или сеть отелей — уточняется в Фазе 4), подключённый к платформе. Единица изоляции данных и конфигурации. |
| Гость | `Guest` | Человек, проживающий или проживавший в отеле. Идентифицируется в рамках тенанта. |
| Проживание | `Stay` | Период пребывания гостя: заезд, выезд, номер, тариф. Связывает гостя с бронью PMS. |
| Поздний выезд | `late checkout` (`Stay.check_out_at`) | Выезд в день выезда позже расчётного часа отеля (`stay_checkout_hour`), отмеченный ресепшеном. Своего поля нет — это час `check_out_at`, поэтому за ним сами сдвигаются чат гостя и автовыезд ([spec 0060](specs/0060-late-checkout.md)). |
| Снимок PMS | `PmsSnapshot` | Состояние «кто в доме» по данным PMS на один момент: строки `PmsStayRow` (комната, номер брони, даты, число гостей — без имён). Отдаётся портом `PmsPort`; ядро сверяет снимок со своими `Stay` и само выводит заезды, выезды, переселения и продления (ADR-004). |
| Свободные номера PMS | `PmsAvailability` | Второй файл того же отеля из PMS: на каждую ночь ближайших недель — сколько номеров свободно для продажи (`PmsNightAvailability`; ≤ 0 — мест нет). Броней, комнат и гостей в нём нет. Отдаётся портом `PmsPort` (`fetch_availability`); по нему бот говорит гостю, есть ли в отеле места на продление, а подтверждает продление ресепшен ([spec 0059](specs/0059-stay-extension-availability.md)). |
| Сотрудник | `User` | Работник отеля или платформы с ролью (RBAC). Гость — НЕ User. |
| Роль (уровень) | `StaffRole` | Уровень сотрудника в тенанте — что он может делать: `staff` «Сотрудник», `senior` «Старший службы», `manager` «Менеджер отеля». Живёт на `TenantMembership` рядом со службами; роли на службу нет (spec 0045 §2). `platform_admin` — не роль в тенанте, а флаг платформенного оператора на `User` (ADR-008). |
| Служба | `TenantMembership.service_keys` | Над какими заявками работает сотрудник: категория заявок отеля (`RequestCategory.key`) — отдельной сущности «служба» нет. У человека их может быть несколько, у менеджера — ни одной ([spec 0045](specs/0045-services-and-levels.md) §2). |
| Служба ресепшена | `staff_services.RECEPTION_SERVICE_KEY` | Служба с ключом `reception`: её сотрудник любого уровня заселяет гостей и видит заявки всех служб. Не путать со службой эскалаций — та задаётся конфигом и у пилота совпадает с ресепшеном (spec 0045 §2). |
| Лестница невзятой заявки | `staff_portal/ladder.py` (`LadderStep`) | Кого зовёт сигнал кабинета о невзятой заявке: сначала её службу, через срок отеля — «просрочена» той же службе, через два срока — ресепшен и менеджера; срочная, эскалация, заявка службы без сотрудников в кабинете и заявка, поднятая напоминаниями гостя ([spec 0070](specs/0070-guest-request-reminder.md) §5), — им сразу ([spec 0045](specs/0045-services-and-levels.md) §4). |
| Уведомление на телефон (веб-пуш) | `WebPushPort`, `StaffPushSubscription` | Уведомление кабинета, которое приходит на телефон сотрудника, когда кабинет закрыт: сервер шлёт зашифрованное сообщение в службу пуша браузера (Google, Apple), телефон показывает его. Подписка — на телефоне сотрудника в отеле; зовёт тех же людей о том же, что сигнал кабинета ([spec 0050](specs/0050-staff-web-push.md)). Не путать с уведомлением на компьютере — его показывает открытая вкладка (spec 0039 §3). |
| Уборка после выезда | `RoomTurnover` (`modules/housekeeping`) | Путь одного номера от выезда до «готов к заселению»: ресепшен отмечает выезд по номеру комнаты, хаускипинг проверяет (с замечанием или без), убирает, старший хаускипинга принимает. Не заявка (ADR-021) и не статус номера — тот остаётся в OPERA (NG-2). Один открытый путь на номер ([spec 0046](specs/0046-checkout-turnover.md) §3). |
| Служба уборки | `staff_services.HOUSEKEEPING_SERVICE_KEY` | Служба с ключом `housekeeping`: её сотрудники ведут уборку после выезда, старший — принимает номер (spec 0046 §4). |
| Раздача этажей | `FloorAssignment` (`modules/housekeeping`), `floors.FloorRouting` | Какие этажи старшая уборки дала каким горничным; действует, пока её не поменяют. Заявка уборки и выезд из номера, у этажа которого есть горничная, сначала зовут только её. Заявку уборки горничная видит только своих этажей (с #856), через срок отеля её слышит старшая и «Направляет» горничной другого этажа; выезд через срок зовёт всю службу ([spec 0053](specs/0053-housekeeping-floors.md) §2, §4, §4а). |
| Направить заявку | `requests_api.direct_request`, `ServiceRequest.directed_to_*` | Старшая уборки или менеджер называет горничную, которой видна и звучит невзятая заявка уборки с чужого для неё этажа; заявка остаётся невзятой, взять её может любой, кто её видит. Не «Передать» — та меняет службу ([spec 0053](specs/0053-housekeeping-floors.md) §4а). |
| Этаж номера | `housekeeping_api.floor_of_room` | Номер из 3–4 цифр без двух последних: 704 → 7, 1204 → 12. Иначе этажа нет, и заявку слышит вся служба (spec 0053 §3). |
| Список номеров отеля | `TenantConfig.hotel_rooms` | Все номера отеля (номер, код типа из Opera, сторона коридора с румплана) в порядке доски «Номера»; источник — файл профиля онбординга. Не номерной фонд PMS (NG-2): ни статусов, ни цен — только «какие номера есть». Этаж не хранится, его даёт номер ([spec 0061](specs/0061-room-board.md) §2). |
| Заявка | `ServiceRequest` | Единица работы для службы отеля: уборка, ремонт, IT, F&B, жалоба. Один жизненный цикл для всех категорий. |
| Категория заявки | `RequestCategory` | Конфигурируемый тип заявки: маршрутизация в службу, SLA, поля. |
| Передача заявки | `transfer_request` | Смена службы (категории) открытой заявки из кабинета. Взятая при этом возвращается в очередь новой службы. Не путать с возвратом в очередь (`in_progress → new`, та же служба) — оба действия spec 0042. |
| Оценка заявки | `RequestFeedback` (`modules/feedback`) | Палец вверх или вниз, которым гость веб-чата оценивает выполненную заявку своего проживания, и необязательный комментарий к пальцу вниз. Одна на заявку и окончательная; палец вниз заводит карточку в службе эскалаций ([spec 0076](specs/0076-guest-request-feedback.md)). |
| Фото к заявке | `request_photos` (`modules/requests`) | Фото, которое гость веб-чата прислал кнопкой с камерой и которое код приложил к его заявке; служба видит его в карточке. До 5 на заявку; ждущее фото — присланное до заявки, ещё ни к одной не приложенное ([spec 0081](specs/0081-guest-request-photo.md) §3). |
| Диалог | `Conversation` | Переписка гостя (или сотрудника) с платформой в одном канале. |
| Канал | `Channel` | Способ общения: telegram, whatsapp, email, web. |
| Оркестратор | `Orchestrator` | Компонент `ai/`, управляющий диалогом: контекст → решение → ответ/инструмент/эскалация. |
| Инструмент | `Tool` | Декларативная способность AI: типизированные вход/выход, класс подтверждения, права. Обёртка над сервисом ядра. |
| Класс подтверждения | `ConfirmationClass` | `auto` / `confirm_guest` / `confirm_staff` — кто должен подтвердить действие (P-9). |
| База знаний | `KnowledgeBase` | Версионируемые документы тенанта (отель) и общие (город) для RAG. **Не путать с «Фактом об отеле»** (`HotelFact`): тот — одна строка ответа в конфигурации тенанта, база знаний — документы с индексом, до неё платформа ещё не дошла. |
| Факт об отеле | `HotelFact` | Одна пара «тема → ответ гостю», написанная отелем: Wi-Fi, завтрак, парковка. Живёт в `TenantConfig`, уходит блоком в системный промпт (не инструментом) и потому оплачивается каждым ходом диалога — отсюда пределы числа и длины. Необязательный `valid_until` делает факт временным (ремонт, закрытый бассейн): после этой даты он не показывается гостю, но остаётся у отеля (spec 0036). Зеркало `GuestFact`: то — про гостя, это — про отель. |
| Справочник города | `CityGuide` (`modules/concierge`) | Общие знания о городе отеля: что посмотреть, как добраться, сезоны, практичные мелочи. Записи с источником и датой проверки пишет и проверяет платформа, а не отель; отель подключает справочник флагом, город берётся из профиля отеля. Уходит блоком в системный промпт, как факты отеля. **Не путать** с «Фактом об отеле» (строка, написанная отелем) и с «Базой знаний» (документы с индексом) ([spec 0085](specs/0085-city-guide-almaty.md)). |
| Квота бесплатного | `ServiceQuota` (`TenantConfig.service_quotas`) | Норма отеля: сколько штук предмета (вода) гость получает бесплатно в день отеля — на гостя, считается на проживание как норма × число гостей. Сверх нормы бот предлагает платную заявку по цене из конфига ([spec 0056](specs/0056-service-quotas.md)). |
| Room service | `room_service` (модуль) | Заказ в номер: гость собирает корзину на странице «Заказать в номер», заказ уходит заявкой в службу каталога, оплата — сотруднику до выдачи ([spec 0038](specs/0038-room-service.md)). |
| Каталог | `RoomServiceCatalog` (`restaurant`, `shop`) | Витрина room service со своей службой, корзиной, переключателем «принимаем» и сбором: «Ресторан» (служба `fnb`) и «Магазин» (служба `supply`). Разделы и товары ведёт служба каталога на странице «Товары и меню». |
| Товар | `RoomServiceItem` | Позиция каталога — блюдо ресторана или товар магазина: названия на языках отеля, цена — данные тенанта. «Закончилось» (`is_available = false`) гость видит серым; «Скрыт из меню» (`hidden_at`) гость не видит. Ни то, ни другое не удаляет товар. |
| Заказ в номер | `RoomServiceOrder` | Оформленная корзина одного каталога: позиции со снимком названий и цен, сбор, итог. Живёт парой с заявкой (`origin = guest_form`), стадию выводят из заявки ([spec 0038](specs/0038-room-service.md) Р-4). |
| Отметка об оплате | `ServiceRequest.paid_at` | Факт «сотрудник получил деньги» на заявке с оплатой при выполнении (`payment_required`). Ставит только человек из кабинета; без неё такую заявку нельзя закрыть как выполненную. Не финансовая запись: чек — в кассе отеля, платформа денег не принимает (NG-3, spec 0038 Р-2). |
| Сервисный сбор | `RoomServiceCatalogConfig.service_charge_percent` | Процент к сумме позиций заказа, у каждого каталога свой; гость видит его отдельной строкой до «Оформить». Задаётся в конфигурации тенанта, а не в каталоге. |
| Бронь столика | `TableBooking` | Запрос гостя на столик в ресторане отеля из веб-чата: ресторан, дата и час, число гостей. Живёт парой с заявкой в службе ресторана (`origin = guest_form`); «забронирован» — только после «Подтвердить» сотрудника ресторана, до того — «запрос». Не путать с бронью PMS, которая стоит за проживанием ([spec 0064](specs/0064-table-booking.md)). |
| Ресторан отеля | `RestaurantConfig` (`TenantConfig.table_booking`) | Ресторан на территории отеля, куда гость бронирует столик: названия, часы посадки, предел гостей и служба, которая отвечает на запросы. Данные тенанта, а не код (NG-7). |
| 3D-витрина | `showroom` (модуль), `channels/showroom`, `ai/showroom` | Параметрическая 3D-схема здания отеля на домене платформы для посетителей без проживания: агент подбирает номера для группы, частный гость — даты и номер или вид; помощник ведёт камеру и готовит запрос, отправляет его сам посетитель. Три режима: кабинет (всегда при сцене), по коду доступа (до публичного запуска) и публично — флагом `public_enabled` после допсоглашения и письменного «да» отеля ([spec 0069](specs/0069-sales-showroom-3d.md), [ADR-025](adr/ADR-025-public-showroom-without-login.md)). Не 3D для гостя на заселении — та тема открыта (DISCUSSION_LOG). |
| Сцена витрины | `SceneDocument` (`showroom_scenes`) | Данные здания одного отеля для просмотрщика: корпус, этажи с назначением, номера по сторонам, типы и виды, помещения (залы — на вырост). Имён, занятости и цен из PMS в сцене нет и быть не может (NG-2); ориентир цены у типа номера — только если его задал отель. Загружает менеджер файлом JSON; у пилота — вне репозитория (`*.local`). |
| Запрос из витрины | `ShowroomRequest` (`kind = group \| booking`) | Обращение посетителя из 3D-витрины: группа (компания, контакт, размер группы, даты, выбранные номера) или бронирование (даты, гостей, желаемый номер или вид, контакт). Живёт парой с заявкой в службе продаж или бронирования (`origin = showroom_form`); контакты — в модуле, не в заявке, срок — 365 дней. Запрос, а не бронь: наличие и бронь подтверждает человек в Opera и отвечает вне платформы (spec 0069 §2.4). |
| Наставник | `mentor` (модуль), `ai/mentor` | Раздел кабинета для обучения персонала: сотрудник спрашивает о стандартах отеля и получает ответ только по кодексу со ссылкой на статью; «Тренировка» задаёт ситуации и оценивает ответы; «Экзамен» — те же вопросы серией с итогом в процентах и порогом сдачи из настроек отеля ([spec 0048](specs/0048-mentor.md), §12 — экзамен; ADR-023). Не гостевой бот: кодекс гостю не показывается. |
| Кодекс отеля | `Codex` | Стандарты работы персонала одного отеля в разметке «часть → раздел → глава → статья»; данные тенанта, загружает менеджер (spec 0048 §4). **Не путать** с «Кодом отеля» (slug для входа) и с «Фактом об отеле» (`HotelFact`, ответы гостю). |
| Статья кодекса | `CodexArticle` | Единица кодекса с номером («Статья 14», вставка — «Статья 14-1»), пунктами и строкой «Источник: …»; по статьям наставник ищет и на них ссылается в ответе. |
| Тренировка | `MentorQuiz` | Режим наставника: модель по статье задаёт ситуацию, сотрудник отвечает, модель ставит оценку «верно / частично верно / неверно»; оценка — строка статистики «Где ошибаются» (spec 0048 §5). |
| Назначенный экзамен | `MentorExamAssignment` | Экзамен «Наставника», который менеджер назначил всем сотрудникам или службам: тема — весь кодекс или главы, число вопросов и порог — из настроек отеля, срока нет. «Итоги экзаменов» считают только его — сдан однажды — сдан; экзамен с темой на выбор — «Экзамен для себя», в итоги не идёт ([spec 0072](specs/0072-mentor-exam-rollout.md) §3). |
| Идея сотрудника | `MentorIdea` (`kind = idea`), режим `idea` «Наставника» | Предложение сотрудника по продукту Necturn из раздела кабинета «Предложить идею»: ИИ уточняет его вопросами, сверяет с картой возможностей и предлагает пересказ, автор правит и отправляет. Основатель видит карточку с именем и службой автора и пометкой ИИ; руководство отеля — нет ([spec 0071](specs/0071-staff-ideas.md)). |
| Интервью службы | `MentorIdea` (`kind = interview`), режим `interview` | Разговор ИИ со старшим службы или менеджером о работе службы по заданным темам; итог — пересказ, который собеседник правит и отправляет основателю ([spec 0071](specs/0071-staff-ideas.md) §4). |
| Служебная записка | `Memo` (`kind = memo`), модуль `memos` | Запись раздела кабинета «Служебные записки»: автор пишет текст, выбирает подписантов и адресата, отправляет руководителю с теми подписями, что есть, руководитель решает — «Согласовано», «Отказано», «На доработку». После отправки текст не меняется. Внутреннее согласование по положению отеля, не электронный документ с ЭЦП ([spec 0077](specs/0077-staff-memos.md)). |
| Объяснительная | `Memo` (`kind = explanation`), `MemoDemand` | Письменное объяснение работника в том же разделе: по требованию руководителя (фото бумажного требования, подтверждение получения, срок два рабочих дня) или по своей инициативе. Без подписантов и решения; видят автор, затребовавший и адресат ([spec 0077](specs/0077-staff-memos.md) §6). |
| Лист подписей | `MemoSignature` | Строки под записью: автор, подписанты, адресат — образец подписи, ответ («Подписал», «с замечанием», «не ответил к моменту отправки»), способ подтверждения и время. Фиксируется отправкой руководителю ([spec 0077](specs/0077-staff-memos.md) §3). |
| Подтверждение с устройства | `StaffPasskey`, `platform/staff_confirm` | Действие, которым сотрудник подтверждает, что запись делает он сам: ключ WebAuthn (passkey) на его устройстве после Face ID, отпечатка или кода блокировки; запасной путь — пароль кабинета. Привязано к содержимому записи. Не способ входа и не ЭЦП; биометрию платформа не получает (ADR-008 §8). |
| Образец подписи | `MemoSignatureSample` | Подпись, которую сотрудник один раз рисует пальцем на экране «Моя подпись»; показывается в листе подписей рядом с его именем. Сам по себе ничего не подтверждает — подтверждает устройство или пароль ([spec 0077](specs/0077-staff-memos.md) §4). |
| Карта возможностей | `ideas_capability_map` | Текст для промпта идей: что умеет каждый раздел кабинета и гостевой бот и чего Necturn не делает принципиально. По нему ИИ помечает идею «уже есть», «упирается в ограничение» и т. п., но никогда не отказывает окончательно ([spec 0071](specs/0071-staff-ideas.md) §5). |
| Назначение вызова LLM | `LlmPurpose` | Зачем шлюз зовёт модель: `guest` (гостевой диалог и всё на его пути), `mentor`, `documents` (чтение фото реквизитов, spec 0049) или `showroom` (навигация 3D-витрины, spec 0069). От назначения зависят модель и дневной бюджет тенанта ([ADR-024](adr/ADR-024-gateway-purpose-embeddings-stream.md)). |
| Порт | `Port` | Интерфейс внешней возможности, объявленный ядром (PmsPort, TaxiPort…). |
| Адаптер | `Adapter` | Реализация порта для конкретного провайдера (OperaAdapter, KaspiAdapter…). Живёт в `integrations/`. |
| Fake-адаптер | `Fake<Port>Adapter` | Полноценная локальная реализация порта с состоянием в памяти: ведёт себя как реальная система, проходит контрактные тесты порта, выбирается конфигурацией. Не unit-mock и не временная заглушка. Обязателен для каждого порта (ADR-007). |
| Назначение файла | `FilePurpose` | Зачем принят файл: `menu_photo` — фото блюда или товара, `guest_document` — документ гостя (реквизиты для АВР), `request_photo` — фото к заявке, `hotel_logo` — знак отеля в шапке гостевого чата (spec 0066). От назначения зависят допустимые типы, размер и срок хранения (spec 0047 §4). Файлы лежат на томе зашифрованными, в БД — строка `uploaded_files` (ADR-022). |
| Эскалация | `Escalation` | Передача диалога от AI живому сотруднику. У отеля с заданной службой эскалаций (`TenantConfig.escalation_category_key`) эскалация заводит заявку в этой службе — источник `escalation` (spec 0039 §2). |
| Служба эскалаций | `TenantConfig.escalation_category_key` | Категория заявок отеля, которая принимает «гостю нужен человек»: в ней эскалация заводит заявку (у пилота — ресепшен). Не задана — эскалация остаётся только сообщением в staff-чат Telegram; законно лишь по явному выбору отеля «только Telegram» (`escalation_telegram_only`, spec 0039 §2.3). |
| ЧП-перехват | `EmergencyIntercept` | Статическая проверка сообщения гостя на маркеры чрезвычайной ситуации (пожар, медицина, безопасность) ДО вызова модели: персоналу уходит эскалация, гостю — статический текст, отправляющий его на ресепшен (spec 0034 §3). Без LLM намеренно (spec 0034). |
| Срочная заявка | `ServiceRequest.is_urgent` | Заявка, промедление с которой грозит здоровью, безопасности или имуществу. Не статус и не категория, а признак самой заявки: снимает гейт подтверждения (ADR-018) и маркирует заявку персоналу. |
| Источник заявки | `ServiceRequestOrigin` | Чем заявка была при рождении: `guest_chat` (гость через бота), `staff_manual` (сотрудник внёс руками в кабинете), `api` (внешний вызов сервисным токеном), `escalation` (бот не справился и позвал человека: ЧП, ИИ не ответил, бот не смог оформить — эскалация стала заявкой в службе эскалаций отеля, spec 0039 §2), `guest_form` (гость оформил сам формой на странице, без бота и без сотрудника: заказ в номер, spec 0038 Р-7), `showroom_form` (посетитель без проживания — агент или будущий гость — отправил запрос из 3D-витрины, spec 0069 §2.4), `feedback` (гость поставил палец вниз выполненной заявке — карточка в службе эскалаций, spec 0076 §4.3), `remainder` (остаток частично выполненной заявки — новая заявка в очереди той же службы, spec 0079). Обязательное поле заявки без умолчания: из доли `guest_chat` + `guest_form` считается Exit-критерий Phase 1 «≥ 70% заявок без участия ресепшена» (формула — spec 0035 §4); `escalation` и `feedback` входят в знаменатель, но не в числитель; `showroom_form` и `remainder` не входят ни туда, ни туда. |
| Остаток заявки | `parent_request_id`, `origin = remainder` | Новая заявка в очереди той же службы на то, что не сделано: сотрудник закрыл исходную «Готово» с примечанием и оставил остальное «на потом». Исходная — `done` с примечанием (частичное выполнение — исход, не статус), остаток помнит её в `parent_request_id`; гостю остаток не пишется (spec 0079). |
| Привязка заявки к диалогу | `RequestOrigin` | Строка `request_origins`: из какого диалога и канала пришла заявка — адрес для обратной связи гостю (ADR-011). **Не путать с «Источником заявки»** (`ServiceRequestOrigin`): здесь «откуда писать ответ», там «чем заявка была». |
| Реквизиты компании | `CompanyProfile` | Юридические данные корпоративного клиента (БИН, ИИК, адрес…), извлечённые из документов и подтверждённые человеком. Постоянная карточка компании между проживаниями (Phase 3); не путать с реквизитами одного запроса АВР. |
| Запрос АВР | `ActRequest` | То, что гость прислал скрепкой в веб-чате для закрывающих документов: «На кого выставить», текст, до 5 файлов, снимок номера и дат проживания. Живёт парой с заявкой в службе «Бухгалтерия» (`origin = guest_form`); его поля реквизитов (БИН/ИИН, ИИК, БИК, банк, адрес) — строка таблицы «Документы для АВР», «Проверить», пока бухгалтер не отметил «Проверено». Срок — как у текстов гостя ([spec 0049](specs/0049-act-requisites.md)). |
| АВР | `WorkCompletionAct` | Акт выполненных работ — финансовый документ для корпоративных клиентов (стандарт РК). Выпускается только после подтверждения бухгалтером. |
| Доменное событие | `DomainEvent` | Факт, опубликованный модулем (`request.created`). Доставляется через outbox. |
| Онбординг тенанта | `TenantOnboarding` | Процесс подключения нового отеля: профиль → знания → интеграции → персонал → чек-лист. |
| Каталог ошибок | Error Catalog | Реестр кодов ожидаемых ошибок (`ERR-<MODULE>-NNN`) со статьями диагностики в runbooks. |
| Golden set | Golden Set | Эталонный набор диалоговых сценариев для регрессионной проверки качества AI (evals). |
| Идентификатор гостя | `GuestIdentity` | Идентификатор гостя в конкретном канале: телефон, telegram_id, email, профиль PMS. Один `Guest` — много идентификаторов; модель поддерживает слияние дубликатов. |
| Вопрос без ответа | `UnansweredQuestion` | Вопрос гостя об отеле, который справочник (`HotelFact`) не покрыл: модель отвечает честным «не знаю» и объявляет факт служебным инструментом, канал пишет строку. Не эскалация (`Escalation`): человек здесь не нужен сейчас — это список того, чего не хватает в справочнике, и менеджер видит его на той же странице (spec 0036). |
| Факт о госте | `GuestFact` | Структурированная запись памяти о госте (предпочтение, аллергия, привычка) с источником и сроком жизни. Хранится отдельно от базы знаний и RAG. |
| AI-шлюз | `AiGateway` | Единственный компонент, через который проходят все вызовы LLM: маршрутизация моделей, лимиты, приоритеты, логирование стоимости и версий промптов. |
| Способ входа сотрудника | `UserIdentity` | Способ входа / внешний идентификатор `User`: пароль (логин отеля), OIDC, telegram. Один User — много способов входа; зеркало `GuestIdentity` (ADR-008). |
| Суперадмин | `User.is_platform_admin` | Отдельная учётка оператора платформы с членством `manager` в отеле: только она сбрасывает пароль сотрудника и стирает учётки. Входит своей страницей — логин, пароль и код из приложения на телефоне (TOTP) ([spec 0044](specs/0044-superadmin.md)). |
| Логин отеля | — | Короткое имя пользователя сотрудника (`BORM`), с которым он входит в кабинет вместе с паролем: 3–12 латинских букв и цифр, уникально внутри отеля, задаёт менеджер в приглашении ([spec 0037](specs/0037-staff-hotel-login.md) §2). |
| Код отеля | — | Slug тенанта, как его видит и вводит персонал на общем входе `/staff` (spec 0037 §3): по нему открывается страница входа своего отеля. Тот же slug стоит в адресе гостевого QR, поэтому код — не секрет. |
| Членство в тенанте | `TenantMembership` | Связь сотрудника с тенантом и его роль в нём. Many-to-many: у User может быть несколько членств, роль живёт на членстве (ADR-008). |
| Сессия сотрудника | `Session` | Серверная сессия кабинета: opaque-токен (в БД — хэш), принадлежит User; активный тенант — атрибут запроса, проверяемый по членству (ADR-008). |
| Сервисный аккаунт | `ServiceAccount` | Машинный клиент (интеграция, smoke): принадлежит одному тенанту либо платформе, аутентифицируется API-ключом (`ApiKey`); не учётка человека (ADR-008). |
| Код заселения | `StayAccessCode` | Per-stay код привязки гостя: выдаётся при заезде (событие `stay.checked_in`), проверяется тройкой тенант+комната+код, живёт, пока живо `Stay` (ADR-008). |
| Ссылка привязки | `StayBindLink` | QR на листке гостю (и на экране карточки заселения): привязывает гостя к `Stay` без ввода кода. То же право, что у кода заселения, — многоразова, живёт, пока живо `Stay`, гаснет перевыпуском кода и выездом (spec 0033 §6, ADR-008 §3). |
| Листок гостю | — | Бумажный листок 50 × 45 мм, который ресепшен печатает из карточки заселения и отдаёт гостю вместе с ключом: «Room N», QR ссылки привязки, «Code NNN-NNN» (spec 0033 §6). |
| Гостевая сессия | `GuestSession` | Сессия гостя в веб-чате после ввода кода заселения; привязана к `Stay` и `GuestIdentity`, валидность Stay перепроверяется на каждом действии (ADR-008). |
| Согласие гостя | `consent_at` / `consent_version` | Факт согласия гостя на обработку ПД: момент (UTC) и версия показанного текста. | Отметка согласия на ИИ-раздел | `TenantMembership.ai_consents`, `AiRecipient` | Галочка менеджера отеля в «Сотрудниках»: согласие сотрудника на передачу его данных получателю ИИ-раздела (OpenAI — «Наставник», Anthropic — «Предложить идею» и «Оформить») подписано на бумаге. | Consent-gate | `consent gate` | Барьер перед первым диалогом: пока согласие не дано (или его версия устарела), канал не зовёт LLM, не создаёт заявок и не сохраняет содержимое сообщений гостя (spec 0029, вариант A юраудита 22.07). |
