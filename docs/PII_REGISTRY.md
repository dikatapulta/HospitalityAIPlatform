# Реестр персональных данных (PII) — FOUNDATION §9

Каждое поле с персональными данными: где живёт, зачем, срок хранения, как
маскируется в логах. **Обновляется в том же PR, что и миграция, добавляющая
PII** (§9); ревью миграции без строки здесь — блокер. Правовая база — юраудит
22.07.2026 (`docs/audits/2026-07-22-legal-recommendations.md`): Закон РК
«О персональных данных» (локализация — ст. 12), GDPR для иностранных гостей.

Сроки хранения решены юрпакетом (issue #126, 28.07.2026): 90 дней для текстов
сообщений и свободного текста заявок — реализация ретеншна #42; до неё данные
не удаляются автоматически, но удаление по обращению субъекта уже исполняется
вручную (`docs/runbooks/subject-requests.md`). Публичные тексты — в
`docs/legal/` (политика, согласие `consent_version`).

| Поле | Модуль / таблица | Зачем | Срок хранения | В логах |

| `messages.text` | channels (0008) | История диалога гостя; может содержать любые ПД, названные гостем | 90 дней (решение юрпакета #126; реализация ретеншна — #42) | не пишется (логируются только id и метаданные) |

| `service_requests.guest_language` | requests (0012) | Язык уведомлений гостю | как у заявки | пишется (не идентифицирует человека) |

## Не-PII, но секреты (для полноты картины)

`stay_access_codes.code_hash` (bcrypt), `guest_sessions.token_hash` (SHA-256) —
секреты доступа, в открытом виде не хранятся и не логируются никогда
(ADR-008); показываются один раз в момент выдачи.

## Правила

1. Новая PII-колонка → строка в таблице выше в том же PR (§9).
2. PII в логи не пишется; техидентификаторы (chat_id, UUID) — допустимы.
3. Удаление данных гостя по запросу (GDPR/ЗПД РК) проектируется при
   добавлении поля: PII должна быть удаляемой без разрушения агрегатов.
