# QUEUE.md — очередь работ

> **Роль:** единственное место, где живёт **порядок** работ. Что именно делать — в issue;
> зачем и по каким критериям — в [PROJECT_EXECUTION_PLAN.md](../PROJECT_EXECUTION_PLAN.md);
> здесь — только «что раньше, что позже» и кто это берёт.
>
> **Статус:** действующий. Заведён 2026-08-04 (правило исполнения 10). Порядок в разделах
> 1–2 выведен из «Exit Gate B» и списка «Осознанно НЕ в Gate B» того же плана — это не
> свежая расстановка приоритетов, а перенос уже принятых решений в один упорядоченный
> список. Два пункта план прямо не называет (#43, #54) — их обоснование в самих строках.

## Как этим пользоваться

Нормативная механика — правило исполнения 10
[PROJECT_EXECUTION_PLAN.md](../PROJECT_EXECUTION_PLAN.md); здесь — операционная шпаргалка.

- **Начало сессии** — `make queue`: раздел 0 живьём из GitHub, верх раздела 1
  с пометками «занято», расхождения файла с GitHub.
- **Заявка на пункт** — первым действием сессии: ветка, пустой коммит, draft-PR
  с номером issue в заголовке «… (#N)» — по заголовку `make queue` пометит пункт занятым.
  В пуле окон заявка ставится внутри турникета, а у ревью, доработки и merge она своя —
  `ops/pool.sh claim` (раздел «Пул окон» ниже).
- **Конец сессии** — правка этого файла **в том же PR**, что и работа: вычеркнуть
  сделанное, вписать issue, которые породили ревью или аудит; плановую работу без
  номера issue — строкой с обоснованием. Находка, не попавшая ни в один раздел,
  для следующей сессии не существует. Issue заводится только на серьёзное —
  список блокеров правила 9 (режим пилота): то, что в PR не починить, или то,
  чего PR не трогал. Мелочи и правки процесса своей строки здесь не получают —
  они записью в [later/](later/README.md) (правила 9 и 11), и «не попало ни в один
  раздел» на них не распространяется.
  Умолчание места новой строки — **раздел 3**; в раздел 1 она встаёт только
  с обоснованием прямо в строке: неправда гостю или отказ в помощи, данные
  гостя, отказ системы, деньги, закон (правило 9). Умолчание — про место новой
  строки, а не про приоритет: перестановка уже стоящих строк и подъём из
  раздела 3 остаются за основателем.
- **Разметка — контракт для `make queue`:** номер **жирным** (`**#N**`) — пункт очереди,
  обязан быть открытым issue; номер обычным текстом — упоминание в обосновании.
  Порядковых номеров у пунктов нет: порядок — это порядок строк, позицию печатает скрипт.

**Порядок меняет основатель** — перестановка строк здесь и есть решение о приоритете.
LLM-сессия переставляет строки только по явной просьбе; молча — никогда (R-11).

Модель и effort у каждого пункта — по правилу 7 плана; это стартовая оценка, а не приговор:
не решено за два захода — лестница эскалации там же.

## Пул окон

Решение основателя 28.10 (#503), предел пять — его слово 29.10; механика — правило 10 плана.
Основатель открывает сколько угодно окон с одним промптом: работают одновременно не больше
пяти, остальные ждут
номера без трат. Окно берёт ровно одну работу и уходит. Замки — папки в
`/tmp/necturn-windows/` (все окна на одном Mac), их ведёт `ops/pool.sh`, состояние —
`make pool`. Владелец замка — процесс окна: закрытое окно отпускает свои замки само,
перезагрузка Mac сбрасывает все. Чужой замок руками (`ops/pool.sh free`) — только по слову
основателя.

**Промпты** — основатель копирует как есть:
- рабочее окно — Opus 5 `xhigh` на любой пункт (задачу окно узнаёт после старта, а effort
  посреди сессии не меняют — правило 7): «Ты — окно пула. Выполни `git fetch origin`, войди
  в свою копию (EnterWorktree без имени) и работай по разделу «Пул окон» в docs/QUEUE.md.»;
- для пунктов Fable — тот же промпт на Fable 5 `xhigh` (effort выставить руками);
- окно-диспетчер — Opus 5 `high`: «Ты — окно-диспетчер пула. Выполни `git fetch origin`,
  войди в свою копию (EnterWorktree без имени) и работай по разделу «Пул окон» в docs/QUEUE.md.»

**Рабочее окно**
1. **Номер:** `ops/pool.sh slot` печатает N. Код 3 — все номера заняты: `ops/pool.sh wait work`
   в фоне, потом снова. Каждое сообщение основателю начинается с «Окно N:».
2. **Турникет** — только выбор и заявка, пара минут, без работы:
   - `ops/pool.sh enter` (ждёт до 9 минут — в Bash timeout 600000; код 4 — повторить);
   - копия — на свежий `origin/main` (`git fetch origin`, `git checkout --detach origin/main`),
     затем `make queue` и `make pool`;
   - выбор по правилу 10: раздел 0, затем верхние 5 незанятых пунктов раздела 1. Пропустить:
     черновик PR; работу с заявкой в `make pool` и PR из его «очереди слияния»; пункт, который
     по своей строке ждёт другого;
     пункт не своей модели (Opus — всё, кроме пунктов Fable; Fable — только они); пункт, где
     последний комментарий «Передача» в issue говорит, что работа ждёт решения основателя;
   - заявка: код — draft-PR по правилу 10; ревью, доработка, merge — `ops/pool.sh claim
     review-<PR>` (`rework-<PR>`, `merge-<PR>`);
   - `ops/pool.sh leave`.

   Брать нечего — `ops/pool.sh leave`, затем `ops/pool.sh wait work` в фоне (будит при
   изменении PR или замков, не дольше 8 часов) и снова шаг 2.
3. **Работа** — по CLAUDE.md и правилам 9–10. `/verify` — порт 801N и своя база с N в имени:
   окна делят один Mac.
   - **Merge после approve** (правило 9, «Очередь слияния»; и по заявке `merge-<PR>`):
     `make pool` пишет «воркер слияния: работает» — `ops/pool.sh enqueue <PR>`, CI не ждать:
     дальше PR ведёт воркер. Воркера нет — `ops/pool.sh merge-one <PR>` в фоне: ждёт замок
     слияния без трат (до 2 часов; код 4 — повторить), обновляет PR до `main`, ждёт `check`,
     повторный approve ставит сам по правилу 9 и мержит; код 1 — не смержен, причина —
     в его выводе и в комментарии PR. После влитого `main` approve аккаунтом ревьюера руками
     не ставить. Остановить PR в очереди — `gh pr ready <PR> --undo` (черновик) или request
     changes: воркер снимет его без approve.
4. **Вопрос основателю.** `make pool` пишет «диспетчер: работает» — вопрос идёт файлом
   `/tmp/necturn-windows/ask/N-<PR или issue>-<слово>.md`: работа, вопрос простыми словами,
   варианты и что будет при каждом, рекомендация, строка «блокирует: да» или «блокирует: нет».
   Диспетчера нет — вопрос в своём чате, как раньше.
   - Не блокирует (показ текста гостю или персоналу, вкус) — работа идёт дальше по своему
     варианту, вариант — записью в `docs/founder-review/` (CLAUDE.md).
   - Блокирует (платный прогон, развилка с разной работой, секрет или доступ) —
     `ops/pool.sh wait answer N-<…>` в фоне. Ответ — туда, где ему место по CLAUDE.md;
     файлы вопроса и ответа удалить. «Диспетчера нет» (его окно закрыли) — тот же вопрос
     в своём чате.
   - Многоагентный режим (правило 7) включает только основатель словом в этом окне:
     просьба — и файлом, и в чате.
5. **Конец** (и вынужденная остановка):
   - работа продолжается после окна (следующий PR серии, шаг после merge) — комментарий
     в issue, начинающийся словом «Передача»: что сделано, где остановилось, что дальше,
     на что смотреть; без секретов и данных отеля — репозиторий публичный;
   - `ops/pool.sh journal "<работа и состояние PR>" "<сделано — одно предложение простыми
     словами>" "<что нужно лично от основателя или «ничего»>"` — журнал основателя
     `журнал-окон.local` в корне основной папки; задачи из него не берут;
   - `ops/pool.sh release`;
   - передача смены по CLAUDE.md, третья часть — «окно свободно, общий промпт»;
   - последняя строка того же сообщения — ровно `Окно N · <работа и состояние PR> — можно
     закрывать`, текст работы — тот же, что в `journal` (журнал ставит его в заголовок
     записи). Заголовок вкладки окна строится из первого промпта, а он у окон пула общий —
     заголовки совпадают, и нужное окно основатель узнаёт по этой строке. Кавычки в тексте
     работы — «ёлочки»: прямые переписка окна хранит как `\"`, и диспетчер строку не найдёт.

**Окно-диспетчер** — код не пишет, работу из очереди не берёт, номера не занимает.
1. `ops/pool.sh dispatcher` (код 1 — диспетчер уже есть: сказать основателю и остановиться),
   затем `ops/pool.sh merge-worker` в фоне — воркер очереди слияния, без модели (правило 9).
   Живёт, пока живо это окно; закрыто окно — окна мержат сами. Воркер закончился — его
   последние строки: код 5 (повторный approve аккаунтом ревьюера не прошёл) — сказать
   основателю, иначе запустить снова.
2. `ops/pool.sh wait ask` в фоне — будит при новом вопросе или записи журнала, раз в час —
   по времени.
3. Сводка основателю — коротко, как пятнадцатилетнему; нового нет — молчать:
   - вопросы без ответа (`make pool`), блокирующие первыми: окно, о чём, варианты
     и последствия, рекомендация; варианты — кнопками (AskUserQuestion); блокирующий,
     а основателя, похоже, нет рядом, — одно уведомление (PushNotification);
   - новая запись журнала — окно закончило: заголовок его вкладки, его последняя строка
     и «закрывай»; «От тебя» не «ничего» — ещё и это. Номер окна вкладку не находит (окно
     отдаёт его до последнего сообщения, номера переиспользуются), строка — находит:
     `grep -l -F "<строка>" ~/.claude/projects/*HospitalityAIPlatform*/*.jsonl` —
     переписка окна (свою, в папке с именем своей копии, пропустить); в ней последняя
     запись `customTitle` (после /rename), иначе `aiTitle` — это и есть заголовок. Строки
     ещё нет — окно дописывает передачу смены: «закрывай» не говорить, проверить снова
     через пару минут (в фоне);
   - раз в час: копия на свежий `origin/main`, `make queue` — новые issue вне раздела 1
     (поднимать ли — решает основатель), пункты Fable, которые окна пропускают, давно
     стоящие PR, строки воркера «смержен» и «снят из очереди» за час.
4. Ответ основателя — дословно и с тем, как понят, — в `ask/<имя вопроса>.answer`;
   в репозиторий его записывает спросившее окно. Перестановку строк этого файла по слову
   основателя диспетчер делает сам — отдельным PR только с этой правкой; ревьюят и мержат
   его рабочие окна.
5. За основателя не решает: без ответа вопрос остаётся и в следующей сводке стоит первым.
   Слово многоагентного режима основатель вписывает сам — диспетчер говорит, в какое окно.

## 0. Открытые PR — этот раздел ведёт GitHub, не файл

Раздел 0 — живой список открытых PR; его печатает `make queue` прямо из GitHub,
руками он не ведётся. У строки в файле не было бы владельца, который её вычеркнет
(ревьюер пишет в чужую ветку только то, что разрешает правило 9
[плана](../PROJECT_EXECUTION_PLAN.md), — строк этого файла среди этого нет, — а мержащая
сессия правит только свою строку), и она гнила бы
за минуты — «ждёт merge» пережил сам merge через 11 минут после коммита (ревью PR #176).
Что делать с каждым статусом — подписано в выводе `make queue`; приоритеты — правило 10.
Уровень ревью автор указывает в описании PR (правило 9) — смотреть там.

## 3. Отложено осознанно — не блокирует пилот

Решение зафиксировано планом («Осознанно НЕ в Gate B») либо самой issue. Строка здесь —
не «забыли», а «посмотрели и решили после пилота». Возврат в раздел 1 — только явным решением.

**Устойчивость сборки — следствия #302 (порядок внутри раздела за основателем):** **#304** (переезд на `anthropic` SDK 1.x: мажор 1.0.0 от 20.08.2026 переехал с `httpx` на `httpx2`; сегодня нас держит граница `<1`, поставленная PR #303 — **Opus 5 `xhigh`**, уровень A: `ai/gateway` в красной зоне правила 9. Раздел 3 обоснован в теле issue: платформа работает на 0.x, ни одного из трёх оснований подъёма нет, а переезд красной зоны через сутки после мажорного релиза — худший из возможных моментов. **Тем же PR снимается игнор `anthropic` в `.github/dependabot.yml`** (запись `versions: [">= 1"]`, см. ~~#319~~ ниже): пересчитываться после переезда там нечему — форма буквальна, «глушить всё, что `>= 1`», — и после переезда она молча заглушит уже без причины и без срока единственный класс PR, который требование `>=1.x,<2` вообще порождает: сдвиг верхней границы на следующем мажоре, плюс security-фикс, за которым придётся уйти с 1.x.
