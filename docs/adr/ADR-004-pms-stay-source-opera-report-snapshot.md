# ADR-004: источник проживаний из Opera PMS 5.6 — снимок отчёта планировщика Opera, сверка состояния против состояния

- **Статус:** proposed — черновик (PR #591, issue #121). Принимается, когда IT отеля подтвердит
  допущения раздела «Что подтверждает IT отеля»; до этого единственный источник проживаний —
  ручное заселение в кабинете.
- **Дата:** 2026-10-31
- **Автор:** LLM-сессия по #121 (Fable 5.1, безголовое окно пула)

## Контекст

Пилотный отель — 350 номеров, 100–150 заселений в день. Ресепшен уже вводит гостя в Opera, а
платформа просит ввести его второй раз; пропущенный ввод проявляется у гостя: QR → «введите
код» → кода нет → гость без помощи, в логах зелено (DISCUSSION_LOG «Как гость получает доступ
при 310 номерах»; решение основателя 27.07: сначала ручное заселение, выгрузка из Opera —
следующая задача после кабинета). Кабинет v1 и листок гостю сделаны (#48, #354); ручной путь
остаётся всегда — перевыпуск кода, переселение, накладки.

Что известно: Opera **5.6.27.3 on-premise**, у отеля свой IT-отдел, регкарта печатается из Opera
каждому гостю. Состав выгрузки решён основателем 06.08 ([аудит 05.08](../audits/2026-08-05-operational-audit.md)
§12 п. 4): **номер брони, занятость номеров, даты; имена не выгружаются** — ADR пишется под этот
вход, а не выбирает его заново. FOUNDATION §8 правило 6 и §17.6 требуют от ADR-004 стратегию
синхронизации, разрешение конфликтов и reconciliation до первого настоящего PMS-адаптера; контракт
порта — #122, проектируется вместе с этим ADR. Ответов IT отеля (письмо — [рунбук](../runbooks/founder-actions-pilot-launch.md)
§4) ещё нет: ADR решает под явными допущениями и называет, что меняется, если допущение ложно.

Сверено по справке Oracle для OPERA 5.6 (31.10.2026):
- **Reports Scheduler** (Miscellaneous → Reports Scheduler; функция `General → Report Scheduler = Y`):
  повтор «каждые N минут / часов / дней», назначения File/Folder, SFTP, Email; папка по умолчанию
  `..\micros\opera\export\<schema>`; формат — параметр отчёта
  ([reports_scheduler.htm](https://docs.oracle.com/cd/E98457_01/opera_5_6_core_help/reports_scheduler.htm)).
- **Export Files** (Miscellaneous → File Export): колонки из view, но запуск — ночной аудит или
  вручную, не раз в минуты ([export_files.htm](https://docs.oracle.com/cd/E98457_01/opera_5_6_core_help/export_files.htm)).
- **OWS** — отдельная лицензия Oracle; **OXI / Business Events** — лицензируемый слой интерфейсов,
  XML по подписке на события; интерфейс без валидации Oracle поддерживает «только со своей стороны»
  ([partner-integration](https://www.oracle.com/hospitality/partner-integration/)).

## Рассмотренные варианты

**Способ чтения.**
1. **Снимок отчётом планировщика Opera** — отчёт «кто в доме» раз в 5 минут в файл силами IT отеля.
   Плюсы: штатная функция 5.6, без лицензий и вендора; даёт **состояние** — заезды, выезды,
   переселения и продления видны сами; состав колонок задаёт отчёт, имена не выгружаются по
   построению; наш сбой невидим для стойки. Минусы: лаг до интервала; отчёт настраивает IT отеля;
   ещё один поток данных, за которым надо следить.
2. **OWS (OPERA Web Services)** — SOAP, официально. Лицензия Oracle, настройка через вендора, чужой
   бюджет и месяцы; для чтения четырёх полей избыточно. Вернуться, когда понадобится **запись**
   в Opera (self check-in).
3. **Прямое чтение БД Oracle read-only.** Технически проще всего, но интерфейс без валидации, риск
   поддержки для отеля, Oracle-клиент в нашем образе, схема без обязательств; плохая первая просьба
   к IT.
4. **OXI / Business Events** — события в реальном времени, но лицензия и настройка интерфейсного слоя.
   Порт на снимках его не исключает: адаптер событий материализует состояние и отдаёт снимок.
5. **Export Files Opera** — только по ночному аудиту: один снимок в сутки. Как единственный источник
   не годится (заезд виден назавтра); как **план Б** при отсутствии планировщика — да: выезды и
   сверка автоматом, заезды по-прежнему руками.
6. **Перехват печати регкарты (виртуальный принтер).** Источник событий, не состояния: нет выездов и
   переселений, сверка невозможна; через компонент идёт полный набор ПД против решения 06.08; первый
   наш компонент в подсобке отеля, в критическом пути заселения; отказ тихий (DISCUSSION_LOG
   «Гостевая авторизация…» §5). Как источник — нет. Как дополнение «мгновенный заезд» — не раньше
   живого пилота, только в безопасной форме (копия регкарты в папку, разбор у нас) и отдельным ADR.

**Как файл попадает к нам.**
- а) **Задача планировщика Windows на стороне отеля**: взять свежий файл из папки отчёта и отправить
  HTTPS-запросом на наш адрес с токеном. Ни одного нового входа у нас — тот же Cloudflare, TLS,
  лимиты и журнал; соединение исходящее из отеля, входящих в его сеть нет; сбой задачи ничего в
  отеле не ломает. Минус: десять строк на машине отеля, которые ведёт IT.
- б) **SFTP-доставка самого планировщика Opera** на наш сервер: без скрипта в отеле, зато новый
  вход на сервере мимо Cloudflare — sshd/chroot, ключи, allow-list, сторож диска (31.10 диск уже
  заполнялся, #414).
- в) Email-назначение в наш ящик — данные через почту третьей стороны; нет.
- г) Сетевая шара + VPN или pull — входящий доступ в сеть отеля; нет.

## Решение

**Вариант 1 с транспортом (а).** Источник правды о проживаниях для отеля с Opera — **снимок** отчёта
«in-house» из Reports Scheduler раз в 5 минут (IT вправе выставить 3–10); файл доставляет задача
планировщика Windows на маршрут загрузки с токеном тенанта. Отчёт — контракт с IT: только
заселённые на момент выгрузки; колонки `room`, `confirmation_no`, `arrival`, `departure` (даты по
бизнес-дате отеля) и необязательная `guests` (число гостей — не ПД, вход квот #124); формат с
разделителем (Delimited Data), UTF-8; **никаких имён и контактов**. Файл с лишними колонками
адаптер отвергает целиком, а не «вычищает»: решение 06.08 держится кодом, а не договорённостью.

**Порт — источник снимков, не событий.** `PmsPort` в `shared/ports/pms.py` (канон порта —
`file_storage.py`): `fetch_snapshot(tenant_id) -> PmsSnapshot | None` и `check()`. Снимок —
`taken_at`, `source_id` (хэш файла), строки `PmsStayRow`: `room_number`, `booking_ref`, `arrival`,
`departure`, `guests_count | None`. Адаптеры `integrations/pms/`: `FakePmsAdapter` (снимок в
памяти, который тесты и демо двигают: заезд, выезд, переселение, продление — ADR-007) и
`OperaReportPmsAdapter` — принимает файл на своём маршруте (монтирует composition root; §8
правило 4 — идемпотентно, с токеном), разбирает и проверяет его и хранит последний принятый снимок
тенанта в своей тенантной таблице; файл на диск не ложится. Выбор — конфигурация тенанта
`pms_source: manual | opera_report` (§8 правило 3). Снимок, а не `list_events since`: снимок
строится из любого источника (отчёт, Export Files, OXI, OWS), а события из снимка — только
сверкой, которая и есть работа ядра.

**Сверка — в `modules/guests` (владелец Stay), по порту, шагом воркера** (`sync_stays_from_pms()`
рядом с `close_overdue_stays()`), через те же `check_in` / `move_stay` / `extend_stay` /
`check_out` — журнал изменений и события `stay.*` те же, что у ручного пути. Stay получает
`source: manual | pms`, `pms_booking_ref` (уникален среди активных Stay тенанта) и счётчик
пропусков. Правила, снимок против состояния:
1. строка есть, Stay с таким `booking_ref` нет → `check_in` (`source=pms`, `check_in_at` = момент
   первого появления, `check_out_at` = `departure` + расчётный час отеля в его поясе, `guests_count`
   из колонки или 1). Комната занята **ручным** Stay с пересечением дат → он **усыновляется**:
   получает `booking_ref` и `source=pms`, код и сессии гостя живут. Занята чужим PMS-Stay →
   расхождение, не трогать;
2. комната в строке иная → `move_stay`; `departure` иная → `extend_stay` (продление и ранний выезд —
   одно поле); комната занята → расхождение;
3. PMS-Stay есть, строки нет **в двух снимках подряд** → `check_out`; один пропуск — не повод
   (усечённый файл);
4. **ручной Stay снимок не закрывает никогда**: его ведут ресепшен и автовыезд (spec 0043); «нет
   в Opera» — пометка в карточке;
5. **защита от массового закрытия**: снимок, в котором разом исчезло больше 20 % PMS-Stay и больше
   десяти, не применяется — алерт, ждём следующий. Расхождения (п. 1–2) — список в кабинете на
   странице заселения и строка журнала; решает ресепшен руками;
6. один снимок применяется один раз (`source_id`, P-6/P-8), повтор — ноль действий; два
   `booking_ref` одной строки — файл отвергается;
7. Opera — источник правды о комнате и датах **PMS-Stay**: их правка в кабинете перезапишется
   следующим снимком, карточка об этом предупреждает; верный путь — править Opera. Код, ссылки и
   сессии гостя — наши, снимок их не трогает; plaintext кода PMS-Stay никто не видит — листок
   печатается по ссылке привязки, код — перевыпуском;
8. автовыезд по сроку остаётся включённым и у отеля с Opera — страховка на день, когда файл
   перестал приходить (уточнение spec 0043 §2.4). `expected` и `cancelled` не заводятся: нет Stay
   до заселения (P-1).

**Свежесть — видима.** `pms_snapshot_age_seconds` и счётчики применённого — метрики (spec 0018);
нет снимка дольше трёх интервалов — алерт через `shared/alerting` и полоса в кабинете «данные
Opera не обновлялись — заселяйте руками»; форма ручного заселения не прячется никогда. Гость при
промахе идёт обычным путём «введите код»; его текст и текст полосы — спека #122, показываются
основателю до кода.

**Безопасность и данные.** Токен загрузки — на тенанта, в БД хэшем (ADR-008: секреты — только
хэши), выпускается командой онбординга; файл ≤ 1 МБ, лимит частоты; в журналы — только числа.
Снимок без имён — не ПД сам по себе, но `pms_booking_ref` ложится строкой в реестр ПД (связь
с системой отеля) и в состав данных договора п. 4.2.1 — тем же PR, что миграция (#122). Новых
получателей нет: файл идёт из отеля в тот же контур, где база; до переезда в РК (#49) это
Hetzner, как у всех данных гостей (договор п. 4.3).

**Что подтверждает IT отеля** (письмо — рунбук §4) и что меняется без подтверждения:
- планировщик отчётов включён, отчёт без имён с нужными колонками в формате с разделителем
  настраивается — иначе план Б: Export Files по ночному аудиту тем же портом (суточный снимок:
  выезды и сверка — автоматом, заезды — руками), решение — записью основателю;
- IT ставит задачу выгрузки по HTTPS — иначе адаптер SFTP-приёмника (вариант б) при неизменном
  порте, отдельным PR с рунбуком входа;
- имена из отчёта убрать нельзя вовсе — вопрос возвращается основателю: решение 06.08 этот ADR
  не пересматривает.

## Последствия

- Тем же PR: FOUNDATION §17.6 — «черновик ADR-004»; GLOSSARY — «Снимок PMS»; spec 0043 §2.4 —
  автовыезд остаётся; рунбук founder-actions §4 — вопросы письма под это решение.
- #122 (следующий PR серии; ревью A — миграция и токен): порт + Fake + `OperaReportPmsAdapter`
  с маршрутом загрузки, `sync_stays_from_pms` + шаг воркера, миграция (`stays.source`,
  `stays.pms_booking_ref`, счётчик пропусков, таблица принятых снимков адаптера), строка реестра
  ПД, README `guests` и `integrations/pms`, метрики и алерт, список расхождений и полоса в кабинете,
  конфиг тенанта `pms_source`, расчётный час — в `TenantConfig` (сейчас константа
  `CHECKOUT_HOUR` в `staff_portal/checkin.py`, аудит 05.08 Г-9). Спека — коротко; правила 1–8
  покрыты тестами по Fake до первого живого файла.
- Вне репозитория при #122: договор п. 4.2.1 (номер брони) и DPA; инструкция IT отеля (отчёт,
  задача планировщика, токен) — рунбук.
- Проще: заселение без второго ввода; выезд и переселение — сами; групповой заезд перестаёт быть
  особым случаем (DISCUSSION_LOG G-6); v2 «продлить выезд» (#234) читает занятость из того же
  снимка — строки будущих заездов там расширение контракта отчёта, не этот ADR.
- Сложнее: два источника Stay в одной таблице и поток данных, за которым следит алерт.
- Пересмотреть: запись в Opera (self check-in) — OWS/OXI; конец поддержки Opera 5.6 или переезд
  отеля в OPERA Cloud — OHIP; второй отель с другой PMS — второй адаптер того же порта; лицензия
  OXI у отеля — адаптер событий, порт тот же.
