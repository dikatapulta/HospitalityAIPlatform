# ADR-006: Хостинг и резидентность персональных данных (РК)

- **Статус:** accepted (развилка закрыта основателем на стратсессии 27.07.2026,
  зафиксирована в PROJECT_EXECUTION_PLAN §Gate B; этот ADR — проработка следствий)
- **Дата:** 2026-07-28
- **Автор:** LLM-сессия (Fable), по issue #49 и FOUNDATION §17.1

## Контекст

Пилот — это продакшен с реальными персональными данными граждан РК: telegram
`chat_id` / веб-сессия гостя, тексты диалогов и номер комнаты с 11.07.2026
однозначно квалифицируются как ПД (новое определение через «идентификаторы»,
закон № 231-VIII). Правовая рамка — юраудит 22.07.2026
(`docs/audits/2026-07-22-legal-audit-rk.md`, рекомендации —
`2026-07-22-legal-recommendations.md`):

- **ст. 12 закона № 94-V** — база данных с ПД хранится **на территории РК**.
  Согласием субъекта это требование не снимается. Текущий staging — Hetzner
  (Германия): для синтетических диалогов легально, для реальных гостей —
  прямое нарушение. **Локализация блокирует продакшен уже сейчас**; дата
  25.08.2026 — вступление отдельной нормы о реестрах операторов/нарушений,
  а не отсрочка.
- **ст. 16** — трансграничная передача в страны, «не обеспечивающие защиту»
  (США — не участник Конвенции 108), легальна только при согласии субъекта.
  Затрагивает LLM-вызовы в Anthropic — у платформы нет способа их избежать
  (региона РК у Anthropic нет), значит, они легализуются согласием.
- Уведомление об утечке — **1 рабочий день** (приказ № 232/НҚ); невыполнение
  «мер защиты», повлёкшее утечку, — до 750 МРП (~3,2 млн ₸) для малого бизнеса;
  сокрытие — отдельный состав.

Ограничения проекта: инфраструктура v1 = Docker Compose на VPS (FOUNDATION §13,
ADR-001 — без Kubernetes и микросервисов); экономика пилота — самофинансирование
(~$100–200/мес, дешёвые решения); сопровождает не-разработчик (P-1 — минимум
движущихся частей). Весь деплой-контур (`ops/`: `bootstrap-server.sh`,
`deploy.sh`, compose, GHCR-образы, cloudflared-туннель) провайдер-агностичен —
это осознанный актив данного решения.

## Рассмотренные варианты

1. **Гибрид: БД в РК, приложение за рубежом.** Формально закрывает ст. 12,
   фактически — нет: обработка за рубежом остаётся трансграничной передачей
   (нужны те же согласия), а трактовка 2026 года требует первичный контур
   обработки в РК — претензия возможна. Технически плохо: +50–80 мс на каждый
   SQL-запрос app↔БД, десятки запросов на один HTTP-запрос → секунды латентности.
   **Отвергнут** (юраудит, раздел «Оценка гибридной схемы»).
2. **Всё за рубежом, легализовать согласием.** Невозможно: согласие покрывает
   трансграничную передачу (ст. 16), но не локализацию базы (ст. 12).
3. **Продакшен целиком в РК; staging остаётся за рубежом с синтетикой.**
   Один VPS корпоративного класса в РК; нестабильность KZ-хостинга лечится не
   географией, а восстанавливаемостью (шифрованные бэкапы + отрепетированный
   restore + переносимый вход). **Принят.**

Провайдер (развилка закрыта основателем): **Kazteleport** — ЦОД Halyk, Tier III,
SLA 99.9%, договор на юрлицо, автоплатёж. Запасные, на случай отказа/деградации:
Servercore (регион Алматы), VK Cloud KZ. PS.kz для продакшн-БД отвергнут
(класс надёжности). Managed Postgres приемлемого класса в РК на июль 2026 не
найден — самостоятельный Postgres в Docker (как на staging) остаётся.

## Решение

Продакшен-контур разворачивается **целиком в РК на VPS Kazteleport** той же
механикой, что staging (Docker Compose + `deploy.sh` + GHCR + именованный
cloudflared-туннель); **staging остаётся на Hetzner** и никогда не видит
реальных ПД; LLM-вызовы в Anthropic легализуются согласием гостя (consent-gate
до первого вызова LLM) и минимизацией; бэкапы шифруются age fail-closed,
офсайт-копия живёт у второго независимого от Kazteleport провайдера, при этом
**зашифрованная копия за рубежом допустима**: age-шифроблоб без приватного
ключа (ключ — только у основателя) не является доступными персональными
данными, что настоящим ADR и фиксируется.

## Проработка следствий

### 1. Два контура — одна механика, ноль общих секретов

Прод — второй экземпляр staging-контура: `bootstrap-server.sh` → пользователь
`deploy` → `docker-compose.staging.yml`-аналог → идемпотентный `deploy.sh`
(миграции до перезапуска, сид, smoke `/health/ready`). Образы — те же из GHCR:
в образах нет ПД, GHCR субоператором ПД не является.

Правила границы контуров:

- **Реальные данные никогда не покидают прод-контур.** «Скопировать прод-базу
  на staging для отладки» — запрещено; отладка — на синтетике (канон сида).
  Единственный легальный выход данных — шифрованный бэкап (см. §4).
- **Полностью отдельный набор секретов** (раздел «прод» в
  `docs/runbooks/secrets.md` — завести при создании контура): своя SSH-пара CI
  (`PROD_SSH_*` в GitHub Secrets), свои `POSTGRES_PASSWORD`, `SERVICE_TOKEN`,
  `TELEGRAM_WEBHOOK_SECRET`, отдельный прод-бот Telegram, **отдельный
  `ANTHROPIC_API_KEY`** (независимые лимиты и бюджет), отдельный проект Sentry,
  свои cloudflared-креды и **своя пара ключей age** (см. §4). Компрометация
  staging не открывает ничего в проде, и наоборот.
- Механика прод-деплоя (ручной триггер / тег вместо «каждый merge в main») —
  деталь workflow при создании контура; требование ADR — отдельные секреты,
  отдельный job, отдельный `.env` с правами 600.

### 2. Граница данных: что где живёт и на каком основании

| Система | Где | Что там | Основание |
|---|---|---|---|
| Postgres + Redis (прод) | Kazteleport (РК) | диалоги, заявки, Stay, конфиги тенантов | ст. 12 — выполнена |
| Postgres (staging) | Hetzner (Германия) | только синтетика | не ПД |
| Anthropic API | США | тексты хода диалога (минимизированные) | согласие гостя, ст. 16 |
| Telegram Bot API | вне РК | сообщения гостевого/staff-каналов | согласие гостя; канал, выбранный самим гостем |
| Cloudflare | глобальный edge | транзит HTTPS-трафика, TLS-терминация | согласие + перечень субоператоров (см. §3) |
| Sentry (EU-регион) | ЕС | события об ошибках; тексты гостей в события не пишутся | минимизация (Task 0018) |
| GHCR | США | docker-образы без ПД | не ПД |
| Офсайт бэкапов | второй провайдер, не Kazteleport | age-шифроблобы | шифроблоб без ключа ≠ доступные ПД |

Позиция по Cloudflare — фиксируется явно: ст. 12 регулирует **хранение базы
данных**, транзит трафика через зарубежный edge — трансграничная передача в
момент коммуникации, покрываемая согласием и перечнем субоператоров в политике
конфиденциальности (#126). TLS терминируется на edge, то есть Cloudflare
технически видит трафик — осознанный компромисс: взамен порт приложения не
открыт наружу вовсе (туннель держит исходящее соединение) и вход мгновенно
переносится между провайдерами. Отказ от Cloudflare потребовал бы открытого
порта + собственного TLS на KZ-VPS — больше поверхности при меньшей
переносимости; пересматривать, если регулятор истолкует транзит иначе.

### 3. Вход и миграция: туннель как механизм отказоустойчивости

- Прод — **отдельный именованный cloudflared-туннель** со своими кредами и свой
  hostname (имя домена решается при создании контура; staging-туннель и
  `staging.necturn.com` не трогаются).
- Публичный хост не привязан к IP → **смерть провайдера = переезд, а не потеря
  данных**: новый VPS у запасного KZ-провайдера + `bootstrap-server.sh` +
  restore бэкапа + те же креды туннеля — трафик и вебхук Telegram переключаются
  сами. Репетиция restore (Task 0019, 25.07) дала 5м33с на чистой машине;
  целевой RTO 30–60 минут — приемлемо для пилота (заявки в простое принимает
  ресепшен по телефону).
- Права кредов туннеля: staging-компромисс `chmod 644` (UID контейнера ≠
  владелец файла) на проде повторить осознанно либо выровнять UID при
  bootstrap — креды в любом случае живут только на сервере, вне репо.
- Внешний uptime-мониторинг `/health` (бесплатный тир UptimeRobot/
  healthchecks.io) с алертом в Telegram — узнавать о падении раньше отеля.

### 4. Бэкапы: канон переезжает, офсайт обязателен

Канон `ops/backup/backup.sh` (Task 0019 + #81) переезжает на прод без
изменений: pg_dump → проверка `pg_restore --list` → age-шифрование публичным
ключом → retention; fail-closed — нет ключа или age, файл не создаётся.

- **Своя пара ключей age для прода.** Приватный ключ — только на машине
  основателя и в его менеджере паролей (как staging-пара, `restore.md`
  «Ротация ключа»); на сервере — только публичный `BACKUP_AGE_RECIPIENT`.
  Отдельная пара — гигиена контуров при нулевой добавленной сложности.
- **Офсайт — у второго независимого провайдера, никогда у Kazteleport**
  (бэкап не должен умирать вместе с сервером). Приоритетный вариант —
  S3-совместимое хранилище второго KZ-провайдера; **допустимый резерв —
  зарубежное хранилище** (например, Hetzner Storage Box): юридическая позиция
  этого ADR — age-шифроблоб без приватного ключа не является доступными ПД,
  трансграничного нарушения не создаёт. Выбор конкретного хранилища — при
  создании контура (§17.3 FOUNDATION — провайдер объектного хранилища — может
  закрыться тем же решением).
- Репетиция restore повторяется **на прод-контуре** до заезда первых гостей;
  тайминг — в `restore.md`.

### 5. Postgres: роль без суперправ и шифрование диска

- **Выделенная LOGIN-роль приложения без SUPERUSER/BYPASSRLS и без владения
  схемой** (issue #49, п. 2; ревью Task 0009: `SET ROLE hospitality_app`
  обратим `RESET ROLE`). На проде — с первого дня; реализация — code-задача
  волны Security-3 (PEP §Gate B, п. 8), применяется и к staging.
- **Шифрование диска** прод-VPS — LUKS или средствами Kazteleport (что даёт
  тариф — выяснить при заказе): прагматичное закрытие криптотребования СТ РК
  к хранению данных ограниченного доступа.

### 6. LLM и субоператоры

- Consent-gate: без согласия гостя LLM не вызывается вовсе (веб-чат — v0 уже
  живёт, финальные тексты — #126; Telegram — #127, вариант A: inline-кнопка).
  Минимизация уже в конструкции: имена/телефоны/платёжные данные не
  собираются, в LLM-журнале — `prompt_hash`, не тексты.
- Перечень субоператоров для политики и DPA-раздела договора с отелем (#126):
  Anthropic, Telegram, Cloudflare, Kazteleport, провайдер офсайт-хранилища
  бэкапов, Sentry. Hetzner в прод-перечень не входит, пока не выбран как
  хранилище шифроблобов.
- От основателя: проверить условия Anthropic API по ретеншну/DPA
  (zero-data-retention для API-трафика) при оформлении коммерческого аккаунта —
  усиливает «надлежащие меры» по ст. 16.

## Условия соответствия прод-инстанса (DoD issue #49)

До заезда первых реальных гостей прод-контур обязан иметь:

1. VPS Kazteleport, договор на юрлицо (ИП — см. П4 рекомендаций), автоплатёж;
   диск зашифрован (§5).
2. Выделенную LOGIN-роль без суперправ (§5).
3. Зелёный деплой прод-контура с отдельным набором секретов (§1) и записанным
   разделом «прод» в `secrets.md`.
4. Живой cron бэкапов + офсайт вне Kazteleport + репетицию restore на
   прод-контуре с таймингом в `restore.md` (§4).
5. Отдельный туннель/домен + внешний uptime-мониторинг (§3).
6. Consent-gate в обоих каналах и опубликованные юрдокументы (#126, #127).
7. Закрытую публичную поверхность (Security-3: `docs_url=None` вне dev,
   `/health/ready` за auth/облегчён, без `ufw allow 8000`).

## Последствия

- **Проще:** переезд между провайдерами — смена IP в секретах (деплой
  провайдер-агностичен, вход — туннель, данные — бэкап); staging остаётся
  дешёвым полигоном без юридических ограничений; позиция по шифрованным
  зарубежным копиям зафиксирована — офсайт перестаёт быть юридически подвешенным.
- **Сложнее:** два набора секретов/ботов/доменов/ключей age; прод-данные
  недоступны для отладки (только синтетика); **каждый новый внешний сервис
  проходит вопрос «где данные» по умолчанию** — провайдер объектного хранилища
  (§17.3), IdP (ADR-008 §5), WhatsApp BSP (§17.4) наследуют это требование.
- **Сделать** (порядок — «Порядок и упаковка» рекомендаций 22.07): юрпакет
  #126 → комплаенс-код #127/#128/#42 → создание прод-контура (с основателем:
  аккаунт и VPS Kazteleport, bootstrap, секреты, туннель, домен, офсайт) →
  репетиция restore на проде. FOUNDATION §17.1 помечается решённым этим же PR.
- **Пересмотреть, когда:** Kazteleport не держит SLA (запасные — Servercore
  Алматы / VK Cloud KZ, механика переезда отработана); в РК появится managed
  Postgres приемлемого класса (FOUNDATION §13 предпочитает managed); масштаб
  >1 отеля потребует репликации/горячего standby; к 25.08.2026 — сверка с
  порогами реестра операторов (может добавить организационные обязанности, не
  меняя архитектуры); регулятор истолкует транзит через зарубежный edge как
  нарушение локализации (§2); Anthropic откроет приемлемый по юрисдикции регион.
