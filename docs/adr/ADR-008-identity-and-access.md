# ADR-008: Модель идентичности и доступа

- **Статус:** accepted (принят как модель; реализация — Phase 1: веб-чат #79, кабинет v1 / #48, RBAC v1)
- **Дата:** 2026-07-27
- **Автор:** LLM-сессия (Fable), по §17.7 FOUNDATION

## Контекст

Phase 0 сознательно обходится без идентичности: один статический `SERVICE_TOKEN`
на весь HTTP API (`platform/auth.py`), гость — это Telegram `chat_id` в
`Conversation`, персонал — множество staff-чатов из конфига тенанта (spec 0026).
Этого достаточно для walking skeleton и уже недостаточно для Phase 1: веб-чат по
QR (#79) требует per-stay токена, кабинет персонала (#48) — пользователей с
ролями, RBAC v1 — сущности, на которой роль живёт. §17.7 требует зафиксировать
модель ADR-ом **до** этих работ.

FOUNDATION §11 задаёт три инварианта — дешёвых сейчас и дорогих при ретрофите:

- **(а)** сотрудник ↔ тенант — членство (many-to-many): `platform_admin` и сети
  отелей несовместимы с полем `tenant_id` у пользователя;
- **(б)** личность отделена от способа входа (по образцу `Guest`/`GuestIdentity`):
  SSO/OIDC добавляется как способ входа, а не миграцией модели;
- **(в)** машинные клиенты — сервисные аккаунты/API-ключи, не учётки людей.

Прочие ограничения: ADR-003 (tenant_id + RLS в каждой тенантной таблице),
P-1 (сопровождаемость важнее элегантности — код пишут LLM, сопровождает
не-разработчик), P-9/NG-4 (человек в контуре), §9 (Guest/GuestIdentity/Stay уже
объявлены сущностями ядра; «гость = номер телефона» — запрещённое упрощение),
юраудит РК (локализация, consent, retention). Наработанные позиции основателя
зафиксированы в DISCUSSION_LOG: код при заселении (не ссылка/SMS), выдача —
побочный эффект заезда, приглашения вместо раздачи токенов, строгий auth-only
для неавторизованных (решение 22.07). Открытые вопросы операционного аудита
Q7 («что можно до привязки») и Q8 («что после выезда») адресованы сюда.

## Обзор: два мира и один словарь акторов

Модель разделяет два мира, у которых разные жизненные циклы и разное отношение
к тенантности:

```
ПЛАТФОРМЕННЫЙ МИР (вне RLS, как таблица tenants; только код platform/)
  User ──< UserIdentity          (личность сотрудника / её способы входа)
  User ──< TenantMembership >── Tenant     (роль живёт здесь)
  User ──< Session               (сессии кабинета)
  ServiceAccount ──< ApiKey      (машинные клиенты; тенант определяется ключом)

ТЕНАНТНЫЙ МИР (tenant_id + RLS, канон миграции 0002; модуль guests/)
  Guest ──< GuestIdentity        (идентификаторы гостя в каналах)
  Guest ──< Stay                 (проживание; источник истины про доступ гостя)
  Stay  ──< StayAccessCode       (per-stay код, только хэш)
  Stay  ──< GuestSession         (сессии веб-чата)
```

Всякое действие в системе совершает ровно один **актор**:
`user | service_account | guest | system`. Аудит (§9) и RBAC записывают и
проверяют актора, AI-инструменты объявляют минимальную роль (§7.3); AI,
действующий в диалоге гостя, — это актор-гость с правами гостя, не больше (§11).

## Решение

### 1. Сотрудники: User, UserIdentity, TenantMembership, Session

**`User`** — личность сотрудника (отеля или платформы), платформенная сущность
**без `tenant_id`** (инвариант а). Поля минимальны: `display_name`, `status`
(`active | deactivated`), `is_platform_admin`, timestamps. Гость — НЕ User
(GLOSSARY). Деактивация — одно действие: вход закрыт, сессии погашены,
аудит-запись остаётся (DoD #48).

**`UserIdentity`** — способ входа / внешний идентификатор, отдельная сущность
(инвариант б, зеркало `GuestIdentity`): `kind` + `external_id`, уникальность
`(kind, external_id)` на платформе. Стартовые kinds:

- `password` — `external_id` = нормализованный email, рядом `secret_hash`
  (argon2/bcrypt — деталь реализации; в БД только хэш);
- `oidc` — `external_id` = `issuer|subject` (зарезервирован, см. §5);
- `telegram` — Telegram-аккаунт сотрудника (зарезервирован: персональная
  привязка через deep-link инвайта — «может подождать», DISCUSSION_LOG).

Один User — много способов входа; добавление/удаление способа не трогает User.

**`TenantMembership`** — членство: `(user_id, tenant_id)` уникально, `role_key`
из RBAC-матрицы (`docs/RBAC.md`, пишется в RBAC v1 — сама матрица не предмет
этого ADR), `status` (`active | revoked`), `invited_by`, timestamps. **Одна роль
на членство**: нужна комбинация прав — заводится роль в матрице, а не вторая
строка членства (P-1: суперпозиции ролей нечитаемы для не-разработчика).
`platform_admin` — флаг на User, а не членство: оператор платформы вне тенантов;
каждое его действие в данных тенанта — аудит-запись с явной пометкой.

**`Session`** — серверная сессия кабинета: случайный opaque-токен ≥ 256 бит,
в БД **только хэш**; cookie HttpOnly + Secure + SameSite (TTL idle/absolute —
параметры реализации). Сессия принадлежит User, а не членству; **активный
тенант — атрибут запроса** (поддомен/путь кабинета), на каждом запросе
проверяемый по активному членству. Деактивация User гасит все его сессии;
отзыв членства закрывает доступ к тенанту на следующей же проверке запроса.

Приглашение сотрудника (поток #48: менеджер жмёт «пригласить» → одноразовая
ссылка/код с ролью и истечением → сотрудник ставит пароль) — **provisioning-
артефакт, не способ входа**: инвайт не живёт в `UserIdentity`, а по принятии
создаёт User + `UserIdentity(password)` + `TenantMembership`. Механика страницы
«Сотрудники» — скоуп кабинета v1.

**Отвергнуто — stateless JWT.** Мгновенный отзыв (увольнение — DoD #48) всё
равно требует похода в хранилище (denylist), т.е. «stateless» не наступает,
а ротация ключей подписи и класс ошибок валидации добавляются. Одна выборка
по индексу на запрос — приемлемая цена вплоть до масштабов, которых пилот не
достигнет; кэш — когда цифры потребуют.

### 2. Машинные клиенты: ServiceAccount, ApiKey

**`ServiceAccount`** — машинный клиент (инвариант в): `name`, `status`,
`tenant_id` **nullable** — аккаунт принадлежит ровно одному тенанту либо
платформе (NULL: smoke-прогоны, будущие платформенные агенты). Машине не нужно
many-to-many: интеграции двух тенантов — два аккаунта с двумя ключами. Ключевое
свойство наследуется из Phase 0 (§11): **клиент не выбирает себе тенанта —
тенанта определяет ключ**.

**`ApiKey`** — `key_prefix` (открытый, для идентификации в логах) + `key_hash`,
`revoked_at`, `last_used_at` (наблюдаемость: мёртвые ключи видны). Ключей у
аккаунта может быть несколько (ротация без простоя).

Статический `SERVICE_TOKEN` остаётся до реализации: при вводе таблиц он
превращается в сид первого сервисного аккаунта пилотного тенанта, из UI и
документации исчезает (#48). Канон `resolve_tenant_from_service_token` меняет
источник (env → таблица), не контракт.

### 3. Гости: Guest, GuestIdentity, Stay, per-stay код

Все гостевые сущности — **тенантные таблицы с RLS** (канон 0002) в новом
доменном модуле `guests/` (§5.1: «гости, проживания, профили»); гость существует
в границах тенанта, кросс-отельного профиля нет (privacy; см. «Не входит»).

**`Guest`** — человек. **`GuestIdentity`** — идентификатор в канале:
`(tenant_id, kind, external_id)` уникально; kinds: `telegram | web | phone |
email | pms`. Один гость — много идентификаторов; слияние дубликатов —
перевешивание `guest_id` у идентичностей (модель поддерживает с первого дня,
§9; UI/автоматика слияния — не сейчас). `Conversation` канала получает ссылку
на `GuestIdentity` **аддитивно** — ровно так, как обещает docstring
`channels/telegram/models.py`; `RequestOrigin` (ADR-011) со временем вытесняется
резолвом через идентичность, тогда ADR-011 помечается superseded.

**`Stay`** — проживание: `guest_id`, `room_number`, `check_in_at`,
`check_out_at` (UTC; интерпретация — в часовом поясе отеля из конфига тенанта),
`status` (`expected | checked_in | checked_out | cancelled`). В Phase 1 Stay
создаёт кнопка «заселить» в кабинете персонала — ручное подтверждение реального
заезда, а не батч-импорт (решение DISCUSSION_LOG: CSV/Fake PMS не гарантируют
реальное время). Синхронизация с настоящим PMS и конфликтные правила — ADR-004.

**Per-stay код** (`StayAccessCode`) — механизм привязки идентичности канала к
Stay:

- **Код, не ссылка** (решение DISCUSSION_LOG): работает для 100% гостей без
  SMS/email-порта. Короткий, человеко-вводимый (без визуально спутываемых
  символов; формат — реализация), в БД — только хэш.
- **Выдача — побочный эффект события `stay.checked_in`** (outbox, P-6), а не
  отдельная кнопка «сгенерировать токен»: шаг нельзя забыть. Ресепшен видит код
  на карточке заселения и передаёт гостю (печать/показ — UX кабинета).
- **Проверка — тройкой**: тенант (из URL комнатного QR) + комната (оттуда же) +
  код. Статический QR идентифицирует отель/комнату и не является секретом; код
  вне своей комнаты бесполезен. Ввод кода — под rate-limit по канону
  Redis-счётчика (spec 0023), перебор невозможен без LLM-затрат.
- **Код многоразовый в пределах Stay**: семья в номере и второе устройство —
  норма; каждая успешная привязка создаёт свою `GuestIdentity`/сессию.
  Одноразовость отвергнута: она заставила бы ресепшен перевыпускать код на
  каждый чих и не добавляет безопасности при проверке тройкой.
- **Срок жизни — производный от Stay, своего нет.** Код и все гостевые сессии
  валидны, пока Stay в статусе `checked_in` и `now < check_out_at`. Продление
  или ранний выезд правят Stay (кабинет) — доступ следует автоматически;
  отдельного действия «продлить токен» не существует (одно место истины —
  закрывает открытый вопрос DISCUSSION_LOG о судьбе токена при продлении).

**`GuestSession`** — сессия веб-чата после ввода кода: opaque-токен (хэш в БД),
привязана к Stay и GuestIdentity. Валидность Stay перепроверяется **на каждом
действии**, а не при входе: тест-инвариант #79 — «истёкшая сессия не может
действовать» — выполняется конструктивно.

Тот же код работает в любом гостевом канале: гость может ввести его и
Telegram-боту — привязка `GuestIdentity(kind=telegram)` к Stay тем же путём.
Механизм канал-агностичен; политика каждого канала — ниже.

### 4. Неавторизованный гость (Q7) и жизнь после выезда (Q8)

**Q7 — до привязки: строгий auth-only** (решение 22.07, DISCUSSION_LOG).
Неавторизованный контакт получает статический ответ без единого вызова LLM —
«отсканируйте QR в номере / введите код заселения» + телефон ресепшена — и не
может создавать заявки. Никаких «публичных вопросов» до авторизации в Phase 1
нет (формулировка в PROJECT_EXECUTION_PLAN исправлена этим же PR); публичный
дешёвый тир — сознательное решение Phase 2. Это закрывает и деньги (C1
security-аудита: выжигание LLM-бюджета открытым ботом), и самодекларируемую
комнату.

Целевое состояние — auth-only во **всех** гостевых каналах, иначе дыра просто
переезжает в Telegram. Включение per-channel — конфиг тенанта: веб-чат рождается
auth-only сразу; Telegram переключается **после** того, как выдача кодов
заработает в кабинете (иначе включение отрубит текущих гостей пилота до
появления процесса выдачи). Порядок включения — деталь плана Phase 1, не модели.

**Q8 — после выезда: доступ гаснет, канал деградирует до неавторизованного.**
`checked_out` (или наступление `check_out_at`) гасит код и гостевые сессии;
дальнейшие сообщения получают тот же статический ответ с телефоном ресепшена.
Grace-период не вводим: забытые вещи и претензии после выезда — человеческий
канал (ресепшен), это его работа, а у бота после выезда нет способа проверить,
что пишет тот же человек. История диалога остаётся персоналу (retention
`messages` — юр. пакет, рекомендация 90 дней). Пост-выездной запрос отзыва —
модуль `feedback/` со своим одноразовым механизмом; в этот ADR не входит.

### 5. SSO/OIDC — совместимость, не внедрение

На пилоте вход сотрудника — свой минимальный: инвайт → пароль (+ сессии выше).
Никакого внешнего IdP сейчас: Keycloak/Ory/Authentik — отдельный сервис против
ADR-001 без доказанной необходимости, его резидентность в РК не проверена
(ADR-006), а онбординг отеля не должен зависеть от второй системы (P-1).

Совместимость гарантируется конструкцией (инвариант б): будущий SSO/OIDC — это
новый `kind=oidc` в `UserIdentity` (issuer + subject) и шаг в login-flow; ни
User, ни членства, ни сессии не мигрируют. Триггер пересмотра — требование
enterprise-SSO от сети отелей, тогда же — решение про IdP с проверкой
резидентности.

### 6. Как это ложится на RLS (ADR-003)

- **Платформенный мир (User, UserIdentity, TenantMembership, Session,
  ServiceAccount, ApiKey) — вне RLS**, как таблица `tenants`: это механизм,
  который *устанавливает* контекст тенанта, — он по определению работает до
  того, как контекст есть (login, проверка ключа), и поверх тенантов
  (membership many-to-many, platform_admin). Правило ADR-003 «каждая тенантная
  таблица — под RLS» не нарушается: эти таблицы не тенантные, а платформенные.
  Компенсация: доступ к ним — только код `platform/` (граница R-5), наружу
  таблицы не смотрят, изменения членств/ключей — в аудит.
- **Гостевой мир — целиком под RLS** (канон 0002). Для веб-чата контекст
  тенанта устанавливается **из URL комнатного QR** (slug тенанта) до
  аутентификации гостя — вся проверка кода/сессии уже выполняется внутри
  контекста тенанта, чужой Stay недостижим на уровне СУБД.
- Канон `TenantResolver` (middleware) расширяется до цепочки резолверов:
  API-ключ → staff-сессия + запрошенный тенант (проверка членства) →
  гостевая сессия/QR-slug. Контракт прежний: валидная идентичность → tenant_id,
  всё остальное → None; закрыто по умолчанию (`require_authenticated_tenant`).

### 7. Граница staff/guest в Telegram — обобщается, не ломается

Сегодня «кто персонал» решает множество staff-чатов из конфига тенанта
(spec 0026, `config.staff_chat_ids()`); команды из staff-чата обезличены. В
терминах этого ADR staff-чат — **канальный суррогат идентичности**: актор —
не User, а «staff-канал тенанта», аудит несёт `chat_id`. Это остаётся законным
и после ADR: групповой чат — канал уведомлений служб, у группы и не должно
быть личной учётки. Появление User эту границу не мигрирует автоматически;
персональные действия («тебе назначена заявка», `/assign` на конкретного
сотрудника) появятся тогда, когда сотрудник привяжет свой Telegram к своему
User (`UserIdentity(kind=telegram)` через deep-link инвайта) — модель это
поддерживает, срочности нет (DISCUSSION_LOG). Деградация сохраняет направление
spec 0026: ошибка конфигурации превращает сотрудника в гостя, никогда наоборот.

## Рассмотренные варианты (макро-развилки)

1. **`tenant_id` на User + роль на User.** Проще на неделю, ломается на первом
   же `platform_admin` и первой сети отелей; ретрофит членств — миграция всех
   auth-путей. Запрещено инвариантом (а).
2. **Внешний IdP (Keycloak/Ory) сразу.** Закрывает SSO из коробки, но: второй
   сервис (против ADR-001), непроверенная резидентность РК, онбординг отеля
   зависит от чужого UI, а пилоту SSO не нужен. Отложено с гарантией
   совместимости через `UserIdentity` (§5).
3. **JWT-сессии.** См. §1 — отвергнуто в пользу opaque + хэш в БД.
4. **Доставка гостевого токена ссылкой (SMS/email).** Требует порта доставки и
   контакта, которого гость мог не оставить; не работает для 100% заселений.
   Код при заселении работает всегда; SMS/email — возможный запасной канал,
   если порт появится по другой причине (DISCUSSION_LOG).
5. **Собственный срок жизни токена (выдал — живёт N дней).** Расходится со Stay
   при продлении/раннем выезде и требует второго действия персонала. Отвергнуто:
   валидность — производная от Stay (§3).

## Что сознательно НЕ входит

- **RBAC-матрица** (роль × действие, `docs/RBAC.md`) — задача RBAC v1; здесь
  зафиксировано только, что роль живёт на членстве и одна на членство.
- **Механика инвайтов и страница «Сотрудники»** — кабинет v1 (#48).
- **Выбор IdP, 2FA** — не для пилота (P-1); модель не мешает ни тому, ни другому.
- **Кросс-тенантный профиль гостя** — гость существует в границах отеля;
  слияние гостей между тенантами не проектируется (privacy, RLS).
- **OAuth-scopes публичного API** — Phase 4; API-ключей сервисных аккаунтов
  достаточно.
- **PMS-синхронизация Stay** — ADR-004 (до первого настоящего PMS-адаптера).
- **Consent и retention** — юр. пакет (тексты согласий, сроки хранения); модель
  лишь не мешает удалению PII гостя без разрушения агрегатов (§9).

## Последствия

- **Открываются** #79 (веб-чат: QR → код → GuestSession) и #48 / RBAC v1
  (кабинет: User/членства/сессии). Два пласта независимы — гостевой мир не ждёт
  User: веб-чат реализуем раньше кабинета, персонал получает код из сида/CLI до
