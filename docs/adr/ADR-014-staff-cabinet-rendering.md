# ADR-014: Кабинет персонала v1 — server-rendered внутри монолита

- **Статус:** accepted (решение основателя 30.07.2026 на ревью spec 0033,
  развилка Ф-1)
- **Дата:** 2026-07-30
- **Автор:** LLM-сессия (Fable), spec 0033 / issue #48

## Контекст

ADR-002 закрепил за фронтом Next.js/TS. Первый реальный фронт — кабинет
персонала v1 (spec 0033): три мобильных экрана (очередь заявок, заселение с QR,
сотрудники) с умеренной интерактивностью (формы, списки, поллинг). Гостевая
веб-страница (spec 0027) уже отказалась от Next.js для одной страницы — тот
прецедент явно резервировал Next.js «за кабинетом», поэтому отступление для
кабинета требует ADR, а не молчаливого решения (R-11).

Ограничения: P-1 (сопровождаемость важнее элегантности; код пишут LLM,
сопровождает не-разработчик), один деплой-юнит (ADR-001, docker-образ +
deploy.sh на staging), экономика пилота из кармана основателя, mobile-first
(решение 27.07).

## Рассмотренные варианты

1. **Next.js-приложение (по букве ADR-002)** — лучший инструментарий UI
   (shadcn/ui + Tailwind, сильная LLM-генерация), готовый каркас для роста.
   Минусы: вторая кодовая база (TS) и toolchain (node) в CI, второй процесс
   или reverse-proxy в деплое, вторая дисциплина типизации/тестов — постоянный
   налог на каждую LLM-сессию и на не-разработчика при инцидентах.
2. **Next.js static export, отдаваемый FastAPI** — один контейнер, но
   node-сборка и TS-база остаются; SSR/маршрутизация Next.js фактически не
   используются — платим за фреймворк, применяя его как генератор статики.
3. **Server-rendered в монолите** (Jinja2-шаблоны + ванильный JS fetch/поллинг,
   канон — страница `channels/web`) — один язык, один деплой, ноль новых
   toolchain; минус — UI собирается руками (CSS без библиотеки компонентов),
   на насыщенных интерфейсах (живой инбокс, дэшборды) упрётся в предел.

## Решение

Кабинет v1 строится по варианту 3 — server-rendered внутри монолита, пакет
`staff_portal/` в композиционном слое. JSON-эндпоинты действий проектируются
как самостоятельный контракт (session-auth поверх сервисов модулей, P-5), так
что слой представления заменяем: будущий Next.js подключается к тем же
эндпоинтам. ADR-002 не отменяется — Next.js остаётся целевым выбором для
фронта, который перерастёт server-rendered; этот ADR фиксирует, что кабинет v1
до такого порога не дотягивает и налога двух экосистем не окупает (P-1).

## Последствия

- Проще: деплой и CI не меняются; кабинет сопровождается тем же стеком и теми
  же канонами (mypy strict, httpx-тесты страниц); одна сессия LLM держит в
  голове весь вертикальный срез.
- Сложнее: консистентность UI держится своим CSS-каноном (layout в
  `staff_portal/templates/`), без готовой библиотеки компонентов; JS остаётся
  намеренно примитивным (fetch + поллинг, без сборки).
- Сделать: пакет `staff_portal/` + контракт import-linter (spec 0033 §4);
  пометку «Next.js закреплён за кабинетом» в docstring `channels/web/page.py`
  заменить ссылкой на этот ADR.
- Пересмотреть, когда кабинету потребуется первый насыщенный экран — живой
  инбокс WhatsApp-handoff (Phase 2), интерактивные отчёты — либо пилот покажет,
  что качество UI реально мешает принятию персоналом. Тогда Next.js-приложение
  поверх уже существующих JSON-эндпоинтов, ревизия — вместе с ADR-002.
