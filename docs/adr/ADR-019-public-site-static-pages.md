# ADR-019: Публичный сайт necturn.com — статическая страница в `site/`, выкладка Cloudflare Pages

- **Статус:** accepted
- **Дата:** 2026-09-21
- **Автор:** LLM-сессия issue #351 (Opus 5)

## Контекст

`necturn.com` не отвечает вовсе: у домена нет ни A-, ни MX-записей. При этом домен
на виду — гость видит `staging.necturn.com` в адресе веб-чата, отель читает «Necturn»
в договоре, на домене будет корпоративная почта (issue #351). Нужна одна страница о
продукте на kk/ru/en; меняется она редко и ничего о посетителях не собирает.

Ограничения:

- **ADR-002** закрепил за фронтом Next.js/TS. Прецеденты отступления для одной страницы
  уже есть — гостевой веб-чат (spec 0027) и кабинет v1
  ([ADR-014](ADR-014-staff-cabinet-rendering.md)), — и оба оформлены решением, а не
  молча (R-11). Этот ADR — такое же решение для сайта компании.
- **ADR-006:** ПД гостей хранятся в РК; Cloudflare уже в перечне субоператоров как
  транзит HTTPS. Сайт, который ничего не хранит и не собирает, под ст. 12 не попадает, —
  но только пока это так.
- **P-1:** сопровождать страницу будут LLM-сессии и основатель без опыта фронтенда.

## Рассмотренные варианты

1. **Отдавать страницу монолитом** (маршрут `/` приложения). Один деплой, но лицо
   компании живёт на машине с ПД гостей и падает вместе с ней; прод ещё не переехал в
   РК (#49), а staging — не место для публичной страницы; в приложении появляется
   новая анонимная поверхность (уровень A правила 9) ради статического текста.
2. **Отдельный репозиторий.** Изоляция, но вторая точка правды: LLM-сессии, очередь и
   ревью живут здесь, основателю пришлось бы вести ещё один репозиторий.
3. **Next.js-приложение по букве ADR-002.** Сборка, Node и зависимости ради одной
   страницы — отвергнуто тем же доводом, что в ADR-014.
4. **Папка `site/` этого репозитория, один HTML без сборки, Cloudflare Pages с
   Git-интеграцией.** Домен уже в Cloudflare, тариф бесплатный, выкладка — merge в
   `main` без секретов в CI, страница проходит то же ревью, что код.

## Решение

Вариант 4. Страница — `site/index.html` (стили, переводы и скрипт внутри, без сборки)
плюс `site/_headers` (CSP и заголовки безопасности). Pages-проект подключён к этому
репозиторию: production-ветка `main`, команда сборки `exit 0`, каталог вывода `site`,
build watch paths `site/*` (чужие коммиты сборку не запускают), автоустановка
зависимостей выключена (`SKIP_DEPENDENCY_INSTALL=1`, иначе сборщик увидит
`pyproject.toml` в корне), превью веток выключены. Домен `necturn.com` добавляется в
Pages как custom domain — запись DNS создаёт сам Pages. Шаги — рунбук
[public-site.md](../runbooks/public-site.md).

Страница **ничего не собирает и не загружает извне**: ни форм, ни cookies, ни
аналитики, ни внешних шрифтов. Это стерегут CSP в `_headers` и `tests/test_site.py`.
Форма, счётчик или cookie превращают сайт в поверхность обработки данных
посетителей (ADR-006: где хранится, чьё согласие) — поэтому требуют нового ADR, а не
правки страницы.

## Последствия

- **Проще:** выкладка — merge в `main`; откат — одна кнопка в Pages (рунбук, §5);
  хостинг бесплатный и не зависит от серверов приложения.
- **Сложнее:** вторая поверхность выкладки мимо `deploy.sh`; первичная настройка
  Pages-проекта и домена — за основателем, доступ к Cloudflare у него.
- **Отступление от R-3:** `index.html` длиннее ~400 строк. Требование «один файл без
  сборки» (#351) важнее: разбиение на файлы потребовало бы сборки или ещё одного места,
  где живут тексты.
- **FOUNDATION §15:** в структуру репозитория добавлена строка `site/`.
- **Пересмотреть**, если сайту понадобятся формы, аналитика или много страниц (тогда —
  генератор статики или Next.js по ADR-002 и новый ADR про данные посетителей); если
  регулятор истолкует edge-транзит иначе (ADR-006); если Cloudflare выведет Pages из
  поддержки в пользу Workers Static Assets.
