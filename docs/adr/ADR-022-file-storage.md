# ADR-022: где лежат файлы — том Docker рядом с базой, шифрование приложением, антивирус позже

- **Статус:** proposed (PR #496, issue #491)
- **Дата:** 2026-10-27
- **Автор:** LLM-сессия по #491 (Opus 5.5)
- **Закрывает:** FOUNDATION §17.3 «Провайдер объектного хранилища».

## Контекст

Решение основателя 27.10: три направления параллельно, два из них принимают файлы — фото блюд
и товаров (#418) и файлы гостя с реквизитами для АВР (#493); #82 (фото к заявке) ждёт того же.
Устройство узла — [spec 0047](../specs/0047-file-storage.md). Требования FOUNDATION:

- §9 — файлы в объектном хранилище, в БД только метаданные; вирус-скан и валидация типа при
  загрузке;
- §11 — особо чувствительные поля (документы, реквизиты) шифруются на уровне приложения;
  загрузки: ограничение типов и размера, антивирус, изоляция обработки (разбор PDF — в
  воркере, не в веб-процессе);
- §17.3 — провайдер хранилища решается ADR в Phase 1.

Ограничения: ADR-006 (прод — в РК; staging и гостевая копия на Hetzner — временное
отступление), NG-8, P-1. Ответ основателя 27.10 (вопрос 5 FOUNDER_REVIEW_QUEUE): файлы гостя —
только на хостинге в РК, до него — staging на выдуманных данных; хранение — диск сервера, при
переезде том переезжает со стеком; антивирус — решить здесь по рекомендации.

## Решение

**1. Хранилище — именованный том Docker `files_data`** рядом с томом базы, смонтирован в
`app` и `worker` по пути `/var/lib/hospitality/files`. Адаптер `LocalDiskFileStorageAdapter`
за портом `FileStoragePort` (P-3, ADR-007 — с Fake-адаптером в том же PR). Файлы получают тот
же статус, что база с диалогами: тот же сервер, тот же ночной бэкап, шифрованный age; наружу
ничего не уходит. S3-совместимый адаптер не пишется: при переезде в РК (#49) том едет со
стеком. Понадобится второй узел приложения — адаптер добавляется, ядро не меняется.

Отвергнуто: S3 у облачного провайдера сейчас — второй контур ПД вне РК без нужды (ADR-006);
байты файлов в Postgres — раздувают дамп и противоречат §9.

**2. Каждый файл на томе — шифротекст.** AES-256-GCM в сервисе ядра (`platform/files.py`), до
вызова адаптера: адаптер хранит непрозрачные байты, поэтому правило переживёт смену адаптера.
Ключ — `FILE_ENCRYPTION_KEY` (32 байта base64) в `.env` сервера, копия — в менеджере паролей
основателя ([secrets.md](../runbooks/secrets.md)): потеря ключа = потеря всех файлов и их
бэкапов. Дополнительные данные шифра — ключ хранения `{tenant_id}/…`: шифротекст, подложенный
под чужой ключ, не расшифруется. Шифруются все назначения, а не только документы гостя: один
путь кода и один тест; фото блюд от этого ничего не теряют.

Отвергнуто: только шифрование диска — §11 прямо требует уровень приложения для документов;
отступление стоило бы слова основателя (R-11), а выполнение — около сорока строк.

**3. Изоляция обработки — дочерний процесс.** Всё, что разбирает содержимое недоверенного
файла (декодирование картинки Pillow, чтение оглавления DOCX), идёт в короткоживущем дочернем
процессе `python -I -m hospitality.platform.file_sanitizer` с потолками памяти, процессора и
времени и ограничением числа одновременных разборов (числа — spec 0047 §3). Картинка-бомба
или уязвимость декодера убивает дочерний процесс, а не веб-процесс с сессиями гостей. Загрузка
при этом остаётся синхронной: человек сразу видит «принято» или причину отказа. PDF в этом узле
не разбирается вовсе (проверяется только сигнатура `%PDF-`); извлечение текста из PDF и DOCX
(#493) — в процессе `worker`, как требует §11, — обязанность спеки 0049.

Отвергнуто: Pillow в веб-процессе — отступление от §11; очередь воркера для картинок —
асинхронный ответ «файл обрабатывается» без выигрыша в изоляции перед дочерним процессом.

**4. Антивирус откладывается до прод-контура в РК** (рекомендация, принятая основателем 27.10).
Пока его нет, действуют меры, которые закрывают те же пути атаки:

- тип — по содержимому (сигнатура), белым списком: JPEG, PNG, WebP, PDF, DOCX; всё прочее, в
  том числе SVG, HTML и исполняемые файлы, — отказ;
- картинка перекодируется в WebP: исходные байты не хранятся вовсе, метаданные (EXIF с
  геолокацией) не уезжают;
- DOCX с макросами (`vbaProject.bin`, тип `macroEnabled`) — отказ;
- PDF и DOCX отдаются только скачиванием: `Content-Disposition: attachment`,
  `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox` — на нашем домене файл
  не откроется и скрипт внутри PDF не исполнится;
- сервер файлы не исполняет и не открывает: разбор — только в изолированном процессе (п. 3).

ClamAV контейнером — при переезде в РК, если серверу хватит памяти (≈ 1–1,5 ГБ), или раньше,
если файлы начнут уходить третьим лицам (пересылка по почте, выгрузка в 1С).

## Последствия

- FOUNDATION §17.3 получает «Решено: ADR-022».
- Порт `shared/ports/file_storage.py` — первый порт проекта и канон (маркер `CANONICAL`);
  адаптеры — `integrations/file_storage/`, подключает только composition root (контракт 2
  import-linter).
- Новый секрет `FILE_ENCRYPTION_KEY`; пустой — загрузка и чтение отвечают ERR-FILES-006,
  остальное приложение работает. Негодный — процесс не стартует (проверка Settings).
- `backup.sh` архивирует том tar'ом и шифрует age рядом с дампом; восстановлению файлов нужны
  оба ключа — приватный age и `FILE_ENCRYPTION_KEY` ([restore.md](../runbooks/restore.md)).
- На гостевой копии приём файлов гостя выключен до хостинга в РК (выключатель — у #493).
- Пересмотреть: при переезде в РК (антивирус), при втором узле приложения (S3-адаптер), при
  смене ключа шифрования (нужна перешифровка — байт версии формата для неё уже есть).
