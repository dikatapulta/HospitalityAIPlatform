## Вердикт

Фундамент держится и за 149 коммитов не прогнулся: RLS-канон (ENABLE + FORCE + WITH CHECK + индекс)
стоит на всех 17 тенантных таблицах — подтверждено каталогом Postgres, а не чтением миграций; `tenant_id`
недостижим из ввода гостя и сотрудника; фоновые задачи и CLI ставят контекст на каждого тенанта; вход
персонала и сессии сделаны по канону (argon2id, 256-битные токены с SHA-256 в БД, ротация при входе,
CSRF-щит на всех 21 JSON-действиях, TOTP с анти-replay под блокировкой); объект внутри отеля привязан к
актору на трёх уровнях (тенант, уровень, служба — под той же `FOR UPDATE`, что и переход), и мутации это
подтвердили; резерв бюджета LLM атомарен и освобождается на всех исходах; история git (355 коммитов) без
секретов; бэкапы шифрованы fail-closed. **Ни межтенантной, ни внутриотельной IDOR-дыры не найдено.**

Что не чисто. Живая копия сегодня: ввод кода заселения без ступени по IP, с bcrypt на каждую попытку и
ключом лимита на произвольную строку из URL — дешёвое выжигание двух ядер сервера (🟠). Всё, что ждёт
подключения Telegram-бота: гость в Telegram не привязан к Stay (деньги, чужая комната, безлимитный
ЧП-перехват), команды персонала не знают границы службы, токен бота уходит в логи, Sentry, `outbox` и
текст алерта через текст исключения httpx. Вход персонала: общий IP-ключ лимита на весь NAT отеля и
политика пароля «восемь знаков», оба без сигнала. Наружу без аутентификации открыты `/metrics` (с запросами
к БД на каждый scrape), `/health/ready`, `/docs`. Юрдокументы разошлись с кодом в трёх местах. Из 19 находок
21.07 закрыты 9, частично — 6, открыты по решению — 4.

## Находки

### К-1 — ввод кода заселения выжигает процессор живой копии — 🟠

Аноним со slug отеля (он на QR-листках) шлёт `POST /g/{slug}/{любая строка}/session` с любым кодом. Ключ
лимита — `{tenant}:{room_number}`, а `room_number` — произвольный текст пути (`channels/web/service.py:141-147`,
`channels/web/router.py:85-90`); без Stay код всё равно проверяется bcrypt'ом cost 12 для выравнивания
времени (`modules/guests/service.py:379-393`, `:88`). Проба: 30 запросов на 30 строк комнаты при лимите 2 —
ни одного 429, 32 вызова bcrypt по 225–252 мс; bcrypt 5.0 отпускает GIL, четыре потока — четыре ядра.
Сервер копии — 2 vCPU на всё (Postgres, Redis, app, worker): ~9 запросов в секунду с одной машины забирают
весь CPU, в той же `to_thread`-очереди стоят argon2 входа персонала и ходы гостей. Второй ступени нет ни в
middleware (`app.py:55`), ни в `ops/deploy/cloudflared/config.yml` (голый ingress), ни в рунбуках. Канон
IP-ступени уже есть у входа персонала (`shared/config.py:235`, `shared/clientip.py:67`). Дополнение
проверки: строка комнаты длиннее 20 символов даёт **500**, не 422, — `GuestSessionStart.room_number`
(`modules/guests/schemas.py:61`) валидируется после лимитера (`web/service.py:167`): ключ Redis длиной в
тысячи символов создан, а каждый запрос — ERROR-событие Sentry с телом (#433). Без потери данных,
прекращается с флудом; 🟠, не 🔴, потому что атакующий — мотивированный аноним, ущерб обратим.
**Чинить:** IP-ступень по готовому канону на `start_session` + `max_length=20` в роутере до лимитера;
правило rate-limit Cloudflare на `/g/*/session` — без кода, сегодня.

### К-2 / К-3 / О-2 — Telegram-гость не привязан к Stay — 🟠 при подключении бота

Три находки трёх осей с одной причиной: `channels/telegram/guest.py:76-84` зовёт ход гостя без
`verified_room_number` и с ключом лимита `chat_id`; `GuestIdentity(kind=telegram)` в коде не создаётся
(`modules/guests/models.py:30-37`). Следствия: (а) деньги — `guest_chat_daily_budget_share=0.1` × потолок
$10 = $1 на аккаунт в сутки, десять аккаунтов после одной кнопки согласия съедают дневной бюджет отеля →
ERR-AI-002 настоящим гостям (остаток C1; spec 0023 §5 это признаёт для привязанных чатов, в Telegram
привязки нет); (б) комната заявки и эскалации — из аргумента модели, то есть из текста гостя (остаток H4;
проба: заявка в «402» без Stay; с привязкой «305» перезапись работает — `ai/tools/create_service_request.py:286-296`);
(в) ЧП-перехват стоит до лимита (`channels/common/guest_turn.py:100-113`) и под `enable_service_requests`
не гейтится — spec 0034 §4 приняла риск с доводом «гость не аноним, он в номере», верным для веба и неверным
для Telegram: любой аккаунт — безлимитный генератор срочных карточек, строк outbox и сообщений в staff-чат,
делящий квоту Bot API и очередь воркера (#416) с настоящими тревогами. ADR-008 §4 Q7 отложил auth-only в
Telegram «после выдачи кодов в кабинете» — выдача работает, условие наступило; spec 0033 обещала «отдельный
issue после кабинета» — его нет ни среди открытых, ни среди закрытых; #384 (этапы пилота) пункта не содержит.
Сегодня путь закрыт не флагом, а тем, что бота на копии нет и пустой `TELEGRAM_WEBHOOK_SECRET` отвергает
всё (`channels/telegram/router.py:46-55`). Сюда же О-1 / К-5: команды персонала из staff-чата любой службы
переводят заявку любой службы по `#N` и по UUID в `callback_data` (`channels/telegram/staff.py:336-338, 447`;
проба: `/done 1` из чата уборки закрыл заявку техники, гость получил «выполнена») — принятое исключение
spec 0026 «Что сознательно не делаем» с условием «Phase 1 вместе с кабинетом», которое spec 0045 выполнила
для кабинета и не пересмотрела для канала. **Чинить** одним пакетом как предусловие подключения бота:
привязка кодом заселения в чате (ADR-008 §3 «тот же код в любом канале»), `allowed_category_ids` по
обратному правилу «чат → служба» из `staff_chats_by_category`, ЧП-перехват только для привязанных.

### К-4 / И-2 / П-1 / Н-1 — токен бота в тексте исключения httpx — 🟡

`response.raise_for_status()` в `channels/telegram/client.py:98` и `shared/alerting.py:96-98` кладёт в текст
`HTTPStatusError` полный URL `https://api.telegram.org/bot<токен>/sendMessage`. Дальше четыре стока:
`error=str(error)` в WARNING/INFO-логах восьми мест (`channels/telegram/outbound.py:55`, `consent.py:201,231,243`,
`staff.py:215,386,463`, `notifications.py:424`); необёрнутые отправки подписчиков (`notifications.py:239,334,407,497`,
`redelivery.py:203`) → `shared/events.py:368-378` `logger.error(..., exc_info=True)` → ERROR-событие Sentry с
токеном в `exception.value` (воркер шлёт ERROR в Sentry через LoggingIntegration, `shared/sentry.py:19-21`);
`last_error=f"{type}: {error}"[:1000]` (`events.py:381`) — токен в таблице `outbox_events` и в бэкапах;
`shared/outbox_alerts.py:52-57` кладёт первые 160 символов `last_error` в текст алерта dead-letter (токен на
~50-м символе). Пробы четырёх осей: `MockTransport` 400/403 → токен в `str(error)`, в stdout-JSON, в
breadcrumb и событии Sentry (транспорт в памяти), в `last_error` и в тексте алерта. Маскирование есть только
для трёх секретных путей (`shared/logging.py:47-56`); план #433 (`max_request_body_size`, breadcrumb httpx)
эти стоки не закрывает. Триггер рутинный: гость заблокировал бота (403), чат не найден (400), 429. Стоки —
свои (Sentry, логи, алерт-чат основателя, БД), поэтому 🟡. **Чинить** у источника: `TelegramApiError(status,
description)` без URL в `client._post` и `alerting.send_alert`, тест с латинским маркером токена на
`telegram_send_failed`; страховка — маска `/bot[^/]+/` в процессоре логов и `before_send`.

### В-1 / В-2 — вход персонала: общий IP-ключ и политика пароля без сигнала — 🟡

Ключ IP-лимита входа не содержит ни отеля, ни логина (`platform/staff_credentials.py:166-173`), оба ключа
списываются до проверки пароля, несуществующий логин тратит IP-бюджет (`staff_auth.py:227-231`). Проба:
три отказа по случайным логинам с одного адреса, затем верный логин и пароль менеджера → 429. За туннелем в
ключ идёт настоящий IP клиента (`--no-proxy-headers` + `TRUSTED_PROXY_IPS=172.16.0.0/12`; обе docker-сети
сервера внутри диапазона — снимок), так что аноним запирает только свой внешний адрес: NAT отеля, если
гостевой Wi-Fi и стойка выходят через один (вопрос основателю). Сигнала нет: алертер читает только 5xx
(`tools/alerter.py:177-180`), `staff_logins_total{outcome="rate_limited"}` никто не смотрит. Рычаг из
ERR-AUTH-006 «поднять `STAFF_LOGIN_IP_RATE_LIMIT_ATTEMPTS`» на staging и копии мёртв — ни одна `STAFF_LOGIN_*`
не пробрасывается в `environment:` (`ops/deploy/docker-compose.staging.yml:64-127`). Политика пароля —
только `PASSWORD_MIN_LENGTH = 8` (`staff_credentials.py:55-57,120-133`): `12345678`, `password`, `qwerty123`
приняты пробой через приглашение; 10 попыток в 10 минут = 1440 в сутки на учётку, владелец входит раз в
30 дней и 429 не увидит. **Чинить:** несуществующий логин — на отдельный ключ, блок-лист топ-1000 паролей +
«пароль ≠ логин», алерт на всплеск `rate_limited`, проброс `STAFF_LOGIN_*` в compose.

## Проверено и подтверждено сильным

- **RLS:** 17 тенантных таблиц — ENABLE + FORCE + одна политика FOR ALL с USING = WITH CHECK, `tenant_id NOT
  NULL`, индекс; whitelist — `tenant_memberships`, `staff_invites`; `alembic_version` без грантов (каталог,
  две оси независимо). GUC ставится первой командой транзакции (`shared/db.py:145-148`); `row_security = off`
  только в бэкфилле 0025. Фоновые задачи и CLI — `tenant_context` на каждого тенанта, контекст между
  итерациями не течёт (`shared/tenancy.py:117-123`). Сверка RLS-контекста с тенантом действия — в одной точке
  `require_role`.
- **Вход и сессии:** argon2id (t=3, m=64 MiB, p=4), выравнивание по тому же профилю, один ответ на «нет
  логина/неверный пароль»; сессии 256 бит → SHA-256 unique, absolute + idle + revoked + status за один
  запрос, новый токен на каждый вход; отзыв всех сессий при отключении, стирании, сбросе пароля, смене
  фактора; cookie `HttpOnly; Secure; SameSite=lax; Path=/staff`; CSRF — все 21 JSON-действие и все HTML-формы
  (проба пяти вариантов Origin); инвайты и сбросы — 256 бит, TTL 72/24 ч, одноразовость под `FOR UPDATE`,
  маскирование токена в логах и Sentry; TOTP RFC 6238, окно ±1, constant-time, анти-replay под блокировкой,
  бутстрап только CLI после верного кода; `clientip` — заголовок только от доверенного сокета.
- **Объект и актор:** `require_role` + службы под `FOR UPDATE`; ленты режутся в SQL до `limit`; люди и
  инвайты скоупятся членством в тенанте, `ERR-AUTH-008` неразличим; суперадмин — флаг не даёт доступа без
  членства, повторная проверка в транзакции; веб-гость — Stay перепроверяется на каждом действии, выезд и
  перевыпуск гасят сессии и ссылки.
- **AI:** гейт P-9 структурный (класс — свойство модуля инструмента), снятие только у `CONFIRM_GUEST`; отмена
  только из снапшота диалога; резерв бюджета до проверки, снятие в `finally` на всех исходах, параллельные
  вызовы не перелетают (проба: 5 вызовов при бюджете на 1,5 — прошёл 1); fail-fast старта по прайс-листу и
  ключу; import-linter держит SDK в двух файлах; текст гостя в system не попадает; `LlmRequest` и
  `TenantConfig` поля модели не имеют — провайдер из ввода не переключить.
- **Каналы:** вебхук — `compare_digest`, пустой секрет = 403 до разбора тела (мутация поймана); один ключ
  идемпотентности для сообщений и `callback_query`, уникальность в БД; consent-gate в обоих каналах до
  хранения и LLM; граница staff/guest — строгое равенство, деградация в сторону гостя; cookie веб-гостя
  `SameSite=strict; Path=/g/{slug}`; код заселения — bcrypt, единый 403, лимит по (tenant, room); bind-ссылка
  256 бит, срок = Stay, маскируется в логах; демо-страницы без флага 404, с флагом — только за сессией.
- **Доставка:** факт и событие атомарны во всём домене; сеть вне транзакций; `SKIP LOCKED` + аренда 300 с,
  исход своей транзакцией; dead-letter — факт строки, алерт «прочитать → отправить → пометить»; автовыезд,
  ретеншн, сводка идемпотентны при двойном запуске (пробы); Redis недоступен — fail-open ≤ 1 с, Postgres
  недоступен — честный отказ без падения.
- **Секреты и инфраструктура:** история git без секретов; `.env`, `*.local`, `backups/` игнорируются; бэкапы
  — age fail-closed, `pg_restore --list` до шифрования, umask 077, 14 суток в двух точках; деплой — снимок
  перед миграцией доказывается файлом, миграция до `up` под `set -e`; образ non-root; `--no-proxy-headers` во
  всех трёх точках; наружу ни одного порта; CI — секреты только `secrets.*`, чужой PR их не получает, деплой-job
  с минимальными правами; Sentry — `send_default_pii=False`, `include_local_variables=False`, EU-проект.
- **Приватность штатного пути:** access-log без IP/UA/query; валидация не пишет `input`; метрики без ПД;
  `llm_call_log` — только `prompt_hash`; провайдерам уходит минимум (OpenAI `store=False`); журнал кабинета без
  текстов и имён по построению; ретеншн исполняет §7 политики буквально; SQL рунбука обращений исполним
  против схемы.
