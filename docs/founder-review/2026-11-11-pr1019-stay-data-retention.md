- [ ] **11.11.2026 — крупное: данные о проживании удаляются через 90 дней после выезда, запись о согласии живёт 3 года без имени (PR #1019, #948, [spec 0032](../specs/0032-guest-text-retention.md) §6): проверь решения окна.** Срок и сама идея решены раньше — [запись 11.11 по PR #1005](2026-11-11-pr1005-first-letter-positions.md), вопрос 8; этот PR — код. Ниже то, что окно решило по дороге.
  - [ ] **Изменён пункт шаблона договора с отелем о сроках (DPA N.2 п. 4).** Было: «записи о согласии — на срок действия договора и 3 года после». Стало: «имя гостя, номер комнаты, период проживания и идентификатор чата — 90 дней после выезда, затем удаляются; записи о согласии — 3 года с даты согласия, без имени гостя и идентификатора чата: дата, версия текста согласия, канал, номер комнаты и период проживания (доказательная база)». Нормы те же, что в записи по PR #1005: хранить до достижения цели (Закон № 94-V ст. 12 п. 2), доказательство согласия — обязанность оператора (ст. 25 п. 2 пп. 5), три года — исковая давность (ГК ст. 178 п. 1). Подписанный пилотный договор лежит вне репозитория, окно его не читало: если в нём прежняя формула шаблона, новая входит в допсоглашение о функциях веб-чата гостя — строка добавлена в [pilot-copy.md](../runbooks/pilot-copy.md), «Допсоглашение с отелем». До подписи расхождение ничего не ломает: первая запись о согласии удалится не раньше чем через три года.
  - [ ] **Вернувшийся гость не «вылетает» из Telegram.** Чат Telegram у человека один на все приезды, а в базе он привязан к записи о первом приезде. Если бы программа просто стирала старую запись, она заодно стёрла бы и привязку текущего приезда — гостю пришлось бы вводить код заново посреди проживания. Сделано так: привязка чата сначала переезжает к записи текущего приезда, потом старая запись удаляется. Отвергнуто: держать старую запись, пока гость ездит (имя из прошлого приезда пережило бы свой срок).
  - [ ] **Согласия, данные до обновления, тоже получают запись на 3 года.** При обновлении базы программа один раз проходит по уже существующим сессиям и диалогам и для каждого согласия создаёт запись-доказательство. Иначе согласия гостей, заехавших до обновления, исчезли бы через 90 дней вместе с их данными. Комната и даты берутся такими, какие они в базе в момент обновления.
  - [ ] **В Telegram запись-доказательство пишется раньше, чем отметка «согласие дано».** Если запись не удалась, гость увидит экран согласия ещё раз. Обратный порядок мог бы дать согласие, которое потом нечем подтвердить. Когда гость Telegram вводит код заселения, пишется вторая запись — уже с комнатой и датами.
  - [ ] **Удаление начинает работать сразу после выкладки, выключателя нет.** Срок — обещание политики и договора, а не функция отеля: раз в час программа сама удаляет проживания, с выезда которых прошло больше 90 дней. На staging и на копии отеля сразу уйдут старые тестовые проживания; у живых гостей пилота первое удаление — не раньше чем через 90 дней после первого выезда.
  - [ ] **Проживание, которое забыли выписать, тоже удаляется через 90 дней после срока выезда** — так записано в спеке: иначе оно жило бы вечно. Обычно такой случай раньше закрывает автовыезд.
  - [ ] **Срок 3 года нельзя поменять настройкой сервера** (в `.env.example` его нет): число — обещание договора, меняется кодом вместе с текстом. Рунбук обращений гостей (`subject-requests.md`): абзац о записях согласия переписан под новую таблицу.
  - [ ] **Следом — политика 1.5** (следующий PR серии): строка о сроке данных о проживании в §7, название и БИН отеля, срок согласия. Для неё понадобятся точное название и БИН отеля в файле профиля — окно скажет, куда вписать.
