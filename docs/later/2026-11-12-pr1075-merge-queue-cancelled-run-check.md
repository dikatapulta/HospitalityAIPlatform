- [ ] 12.11 — merge PR #1075, окно пула 3; повтор 27.11 — merge PR #1170, окно пула 2 — очередь слияния снимает PR по `check` отменённого прогона. На одну голову GitHub в одну секунду запускает два прогона CI (у #1170 — сразу после `update-branch` воркера); один отменяется (`cancel-in-progress`), но его job `check` с `if: always()` всё равно отрабатывает и пишет failure. `pr_check` в `ops/pool-merge.sh` берёт последний `check` из `statusCheckRollup`, живого ещё нет — и воркер снимает PR как «красный» (у #1075: failure в 21:32:10 UTC, снят в 21:32:36, живой прогон закончился в 21:34:45). Считать такой `check` «pending» мало: 27.11 живой прогон #1170 был зелёным, а GitHub всё равно держал PR — сводный статус головы FAILURE, `mergeStateStatus` BLOCKED, пять `gh pr merge` подряд с отказом «the base branch policy prohibits the merge»; совет из комментария воркера («Повтори: ops/pool.sh enqueue») без перезапуска не помог бы. Сняло `gh run rerun <id отменённого прогона>`: его новый `check` зелёный, статус CLEAN, следующий `enqueue` смержил. Починка — в воркере: если на голове есть отменённый прогон с `check` failure, перезапустить его и ждать, а не снимать PR. `if: always()` у `check` не трогать: пропущенную job GitHub засчитывает required check как успех.
