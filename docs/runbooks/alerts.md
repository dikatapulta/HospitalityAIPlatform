# Runbook: алерты и наблюдаемость (Task 0018, FOUNDATION §10)

Как система сообщает о проблемах и что делать, когда пришёл алерт.

## Устройство (четыре механизма)

1. **Sentry (managed, §10.4, §10.12)** — каждая необработанная ошибка приложения
   и воркера становится событием с тэгами `tenant_id` и `correlation_id`.
   Включается переменной `SENTRY_DSN` (пустая = выключен). Смотреть:
   [sentry.io](https://sentry.io) → проект платформы → Issues (фильтр
   `environment:staging`).
2. **`GET /metrics` (§10.7)** — метрики Prometheus-формата: RED по эндпоинтам
   (`http_requests_total`, `http_request_duration_seconds`), глубина outbox
   (`outbox_pending_events` — очередь на доставку, `outbox_dead_letter_events` —
   похороненные, issue #133), возраст пульса воркера
   (`worker_heartbeat_age_seconds`, issue #136), LLM (`llm_calls_total`, `llm_tokens_total`,
   `llm_cost_usd_total` — по тенантам; `llm_daily_spend_usd` и
   `llm_daily_budget_usd` — расход за текущие UTC-сутки и лимит, issue #103:
   это самый короткий ответ на вопрос «сколько отель уже потратил сегодня»;
   `llm_provider_failure_streak` и `llm_budget_rejection_streak` — отказы модели
   по журналу вызовов, issue #374: «отвечает ли сейчас модель этому отелю»).
   Эндпоинт анонимный (явное решение §11,
   как `/health`). Быстрая проверка: `curl -s https://staging.necturn.com/metrics`
   (порт 8000 наружу закрыт Cloudflare-туннелем; изнутри сервера алертер ходит
   по docker-сети `http://app:8000`).
3. **Алертер (§10.8)** — сервис `alerter` staging-стека
   (`hospitality.tools.alerter`): раз в `ALERT_POLL_INTERVAL_SECONDS` (60 с)
   опрашивает `/health/ready` и `/metrics` приложения и шлёт алерты в
   Telegram-канал команды: ERR-OPS-001 (приложение не отвечает), ERR-OPS-002
   (всплеск 5xx), ERR-OPS-003 (воркер не подаёт признаков жизни), ERR-OPS-004
   (очередь событий растёт), ERR-OPS-006 (дневной бюджет LLM на исходе),
   ERR-OPS-009 (модель не отвечает — чаще всего кончился баланс) и ERR-OPS-010
   (дневной бюджет LLM исчерпан, бот молчит).
   Ещё одна линия смотрит не в HTTP, а на диск: возраст свежайшего ночного бэкапа
   в каталоге `ALERT_BACKUP_DIR` — ERR-OPS-008 (issue #106). Каталог бэкапов
   живёт на хосте (`/opt/hospitality/backups`) и смонтирован в контейнер
   алертера только для чтения — правка `volumes` сервиса `alerter` в
   `ops/deploy/docker-compose.staging.yml`.
   Конфигурация — `TELEGRAM_ALERT_BOT_TOKEN` +
   `TELEGRAM_ALERT_CHAT_ID` в `.env` на сервере (образец —
   ops/deploy/.env.staging.example). Пороги и период опроса — переменные
   `ALERT_*`: у всех есть рабочие умолчания, менять их не нужно, а имена со
   значениями перечислены в `.env.example` в корне репозитория (что каждая
   значит — там же в комментариях); чтобы переопределить на сервере, строку
   `ALERT_...=` дописывают в `.env` и перезапускают сервис `alerter`.
   Алерты состояния (001, 003, 004, 006, 008, 009, 010) приходят по одному разу на вход в
   проблему, и ✅ — на выход; пустая метрика (`NaN` — БД недоступна) для алертера
   означает «не знаю», и он молчит: такой отказ уже покрыт ERR-OPS-001.
   У линии бэкапа правило обратное: «не знаю» (каталог не читается) — тоже
   алерт, потому что молчащий watchdog и есть режим отказа из issue #106.
4. **Воркер** — единственный, кто знает момент, когда доставка события сдалась
   окончательно, поэтому об этом (ERR-EVENTS-002) докладывает он сам, а не
   watchdog снаружи: раз в `WORKER_DEAD_LETTER_ALERT_INTERVAL_SECONDS` (60 с)
   шлёт в тот же канал команды одно сообщение на пачку похороненных событий
   (issue #133, ADR-015). Читает ту же пару `TELEGRAM_ALERT_*` — в сервисе
   `worker`, а не только `alerter`; пустая пара = шаг выключен (WARNING в логах).

Каждый алерт содержит: код ошибки, окружение, детали, тенанта (для
платформенных алертов — `platform`), correlation id (у внешнего опроса его
нет — `—`; у алерта воркера это correlation id публикации события) и ссылку на
этот runbook.

**Не всё в канале команды — алерт.** Раз в сутки туда приходит копия утренней
сводки каждого отеля (issue #301, spec 0035 §8): «🏨 Название · 📊 Вчера, …» и
последней строкой «ИИ за сутки отеля: $N» — той же парой `TELEGRAM_ALERT_*`, но
это отчёт, а не проблема, и кода ошибки у него нет. Отличать по первой строке:
у алерта она начинается с эмодзи состояния и кода (`🔴 [staging] ERR-…`).
Строка расхода уходит только сюда — в сводке, которую видит отель, её нет
(себестоимость платформы — не число отеля).

## ERR-OPS-001

**Алерт:** `/health/ready` недоступен или нездоров N опросов подряд.

1. Зайти на сервер: `ssh deploy@<IP>` (адрес и ключ — docs/runbooks/deploy.md).
2. Что лежит: `cd /opt/hospitality && docker compose -f docker-compose.staging.yml ps`
   — смотреть колонку STATUS у `db`, `redis`, `app`.
3. В тексте алерта есть `checks` из тела ready-ответа:
   - `postgres: error` → `docker compose -f docker-compose.staging.yml logs --tail 50 db`;
     чаще всего контейнер перезапущен/убит OOM или кончилось место (`df -h`).
   - `redis: error` → то же для `redis`.
   - `connection error` в деталях → приложение не отвечает вовсе:
     `docker compose -f docker-compose.staging.yml logs --tail 100 app`.
4. Поднять упавший сервис: `docker compose -f docker-compose.staging.yml up -d <service>`.
   После восстановления алертер сам пришлёт ✅.
5. Если причина неясна — Sentry Issues за последние минуты + логи app по времени алерта.

Ложный случай: деплой, который держит приложение недоступным дольше ~2 минут,
породит алерт и следом ✅ — это нормально и информативно.

## ERR-OPS-002

**Алерт:** всплеск 5xx (прирост ≥ порога за интервал опроса).

1. Открыть Sentry → Issues, отсортировать по последнему событию: каждый 5xx —
   событие с `correlation_id` и стеком. Это самый быстрый путь к причине.
2. Без Sentry: `docker compose -f docker-compose.staging.yml logs app | grep unhandled_error`
   — записи содержат `correlation_id`; полный след запроса —
   `grep <correlation_id>` по логам (docs/runbooks/errors.md, «Как найти ошибку в логах»).
3. Если всплеск начался сразу после деплоя — откат: `./deploy.sh <предыдущий образ>`
   (docs/runbooks/deploy.md).
4. Повторный алерт о продолжающемся всплеске придёт не раньше, чем через
   `ALERT_COOLDOWN_SECONDS` (15 мин) — тишина после первого алерта не означает,
   что всплеск кончился; смотреть метрики/Sentry.

## ERR-OPS-003

**Алерт:** воркер событий не подаёт признаков жизни (пульс старше порога).
Что это значит по существу: **стоит вся доставка событий** — служба не узнаёт о
новых заявках, напоминания и ретеншн не идут. Приложение при этом отвечает, и
кроме этого алерта ничто на проблему не укажет.

1. Жив ли контейнер: `cd /opt/hospitality && docker compose -f docker-compose.staging.yml ps worker`
   — колонка STATUS. `Exited`/`Restarting` → причина в логах:
   `docker compose -f docker-compose.staging.yml logs --tail 100 worker`.
2. Контейнер `Up`, а пульса нет — процесс завис или не пишет в БД:
   - последние строки логов старше нескольких минут → завис (чаще всего в
     сетевом вызове подписчика; с issue #134 сеть идёт вне транзакции, но
     таймаут внешнего сервиса цикл всё равно ждёт);
   - в логах `worker_heartbeat_failed` (ERR-OPS-005) и `worker_iteration_failed`
     (ERR-EVENTS-003) → БД недоступна из воркера, чинить как ERR-OPS-001.
3. Поднять: `docker compose -f docker-compose.staging.yml up -d worker`
   (зависший — `restart worker`). Пульс появится в течение
   `WORKER_HEARTBEAT_INTERVAL_SECONDS` (30 с), и алертер сам пришлёт ✅.
4. Что накопилось за простой: `curl -s https://staging.necturn.com/metrics | grep outbox_pending_events`.
   Очередь разберётся сама — события не теряются (at-least-once, ADR-005), но
   уведомления службе придут задним числом; людей в staff-чате стоит
   предупредить, если простой был долгим.
5. Возраст пульса числом:
   `curl -s https://staging.necturn.com/metrics | grep worker_heartbeat_age_seconds`
   (`NaN` = БД недоступна или строки пульса нет — тогда алерта и не было).

Ложный случай: деплой перезапускает воркер на секунды — до порога в 5 минут
это не доходит. Алерт пришёл сразу после деплоя = воркер не поднялся.

## ERR-OPS-004

**Алерт:** очередь событий выше порога (`outbox_pending_events`).
Вторая линия на тот же симптом: она срабатывает и тогда, когда воркер жив и
пульс свежий, а очередь всё равно не разбирается.

1. Пришёл ли рядом ERR-OPS-003 — если да, причина в мёртвом воркере, разбирать
   по статье выше; эта очередь — его последствие.
2. Воркер жив: смотреть, доставляются ли события вообще —
   `docker compose -f /opt/hospitality/docker-compose.staging.yml logs --tail 200 worker | grep event_delivery_failed`.
   Один и тот же `event_name` с растущим `attempts` = сломан обработчик или его
   зависимость; события уходят в повтор с backoff и копятся.
3. Что именно копится:
   ```sql
   SELECT event_name, count(*), min(occurred_at)
     FROM outbox_events
    WHERE processed_at IS NULL AND dead_lettered_at IS NULL
    GROUP BY event_name ORDER BY 2 DESC;
   ```
4. Починить причину (обработчик или зависимость) — очередь разберётся сама.
   Если она продолжает расти при работающей доставке, воркер не успевает за
   потоком: поднять `WORKER_BATCH_SIZE` в `.env` и перезапустить сервис.
5. Событиям, исчерпавшим повторы, приходит отдельный алерт ERR-EVENTS-002 — это
   уже потери, а не задержка.

Ложный случай: разовая массовая публикация (импорт, онбординг) даёт алерт и
следом ✅, когда очередь разобрана.

## ERR-OPS-006

**Алерт:** дневной бюджет LLM тенанта израсходован на долю порога (80%).
Ничего ещё не сломано: это те несколько часов, за которые нужно решить —
поднимать лимит или разбираться, откуда расход. На 100% бот замолкает
(ERR-AI-002) и каждое сообщение гостя уходит в эскалацию к персоналу — об этом
с первого отказа придёт [ERR-OPS-010](#err-ops-010).

1. Сколько и у кого: `curl -s https://staging.necturn.com/metrics | grep llm_daily_`
   — `llm_daily_spend_usd{tenant_id="…"}` против `llm_daily_budget_usd`.
   Тенант в алерте назван UUID; какой это отель —
   `SELECT id, slug, name FROM tenants;`.
2. Расход нормальный или аномальный: `llm_cost_usd_total{tenant_id="…"}`,
   делённый на `llm_calls_total{tenant_id="…",status="ok"}`, — средняя цена
   хода (оба счётчика — за жизнь процесса `app`). Вызовы — только со
   `status="ok"`: отказы по бюджету (`budget_exceeded`), ошибки и таймауты
   стоят 0, и с ними цена хода занижена, а вызовов больше, чем прошло. Цена
   резко выросла — сменилась модель (`LLM_MODEL`) или раздулся контекст;
   выросло число успешных вызовов — наплыв диалогов или цикл в коде.
3. Один ли промпт крутится в цикле:
   ```sql
   SELECT prompt_hash,
          count(*) FILTER (WHERE status = 'ok') AS calls,
          count(*) FILTER (WHERE status = 'budget_exceeded') AS rejected,
          sum(cost_usd)
     FROM llm_call_log WHERE created_at >= date_trunc('day', now())
    GROUP BY prompt_hash ORDER BY 4 DESC LIMIT 5;
   ```
   `calls` — вызовы, за которые заплачено; `rejected` — сколько раз этот промпт
   уже отверг бюджет (это бесплатно, но цикл виден и по ним). Запрос — из
   тенантной сессии (см. оговорку в статье ERR-AI-002).
4. Расход легитимен → поднять лимит: `LLM_TENANT_DAILY_BUDGET_USD` в `.env` на
   сервере и `docker compose -f /opt/hospitality/docker-compose.staging.yml up -d app worker`.
   Новое значение видно в `llm_daily_budget_usd` на следующем scrape, и алерт
   гаснет сам (✅), как только доля вернётся ниже порога.
5. Расход аномальный → ограничивать источник, а не потолок: лимиты гостевого
   чата (`GUEST_CHAT_RATE_LIMIT_*`, spec 0023) и статья ERR-CHANNEL-003.

Ложный случай: разовый импорт или нагрузочная проверка на staging сжигают
бюджет демо-тенанта — алерт придёт по делу, а ✅ — в начале следующих
UTC-суток. Тишина при пустом `/metrics` (БД недоступна) — не «всё хорошо»,
а «не знаю»: в этот момент уже пришёл ERR-OPS-001.

## ERR-OPS-008

**Алерт:** свежего бэкапа БД нет (или каталог бэкапов не читается).
Что это значит по существу: **восстанавливать в аварии будет нечего**. С issue
#81 бэкап шифруется и потому не создаётся вовсе, если на сервере нет ключа или
бинарника `age`, — до этого алерта такой отказ был совершенно бесшумным.

1. Что лежит в каталоге:
   `ls -lt /opt/hospitality/backups | head`. Ночные бэкапы — файлы
   `hospitality-<UTC-метка>.dump.age`; `pre-migrate-*` — это снимки деплоя,
   бэкапом они не считаются (иначе умерший cron маскировался бы ими).
2. Почему не создался последний: `tail -50 /opt/hospitality/backups/backup.log`
   — там стоит причина словами. Частые: нет `BACKUP_AGE_RECIPIENT` в `.env`, не
   найден `age`, не отвечает контейнер `db`.
3. Место на диске: `df -h /opt/hospitality` (дамп пишется целиком, потом
   шифруется — нужно вдвое больше размера дампа).
4. Жив ли cron: `crontab -l` (строка `0 3 * * * /opt/hospitality/backup.sh …` —
   docs/runbooks/restore.md) и `systemctl status cron`. Строки нет — расписание
   потерялось при пересборке сервера, вернуть по тому же runbook.
5. Прогнать бэкап руками и посмотреть на вывод целиком:
   `/opt/hospitality/backup.sh`. Успешный прогон гасит алерт сам (✅) на
   следующем опросе.
6. Алерт **«каталог бэкапов не виден алертеру»** — это не про бэкапы, а про
   монтирование: `docker compose -f /opt/hospitality/docker-compose.staging.yml exec alerter ls /backups`.
   Команда ответит ошибкой — пустого вывода в этой ветке не бывает: пустой
   каталог виден и алертится другим текстом («нет ни одного файла»).
   `No such file or directory` → в compose нет `volumes` у сервиса `alerter`
   (устаревший файл на сервере — обновить деплоем); `Permission denied` →
   каталог на хосте не читается чужим uid:
   `ls -ld /opt/hospitality/backups` и `chmod o+rx /opt/hospitality/backups`
   (внутри каталога файлы остаются `0600` — читать дампы алертеру не нужно, ему
   нужны только имена и даты).

Ложный случай: сервер поднят час назад и ночного прогона ещё не было — алерт
придёт по делу («нет ни одного файла»), и снимать его нужно ручным прогоном
бэкапа, а не молчанием.

## ERR-OPS-009

**Алерт:** у отеля несколько вызовов модели подряд неуспешны (порог
`ALERT_LLM_FAILURE_STREAK_THRESHOLD`, 3). Бот не отвечает гостям — каждое
сообщение уходит заглушкой и эскалацией к персоналу, и отель видит это как
«гости вдруг все зовут человека». Кроме этого алерта, причину не покажет ничего:
ошибки провайдера пишутся на WARNING, и Sentry их не видит (issue #374).

1. Что именно отвечает провайдер — текст ошибки SDK в событии `llm_call_failed`
   (`Error code: <HTTP-код> - <тело ответа>`, в теле — тип и текст ошибки):
   `docker compose -f /opt/hospitality/docker-compose.staging.yml logs --since 1h app worker | grep llm_call_failed`.
   Сверять по веткам сверху вниз и брать первую совпавшую: у 400 и у 429 по
   несколько причин с одним типом ошибки, различает их только текст. Типы и
   коды — по документации провайдера
   ([ошибки](https://platform.claude.com/docs/en/api/errors),
   [лимиты](https://platform.claude.com/docs/en/api/rate-limits)).
   - `credit balance is too low` (400) — кончился баланс: Console Anthropic →
     Settings → Billing, пополнить. Самый частый случай.
   - `You have reached your specified API usage limits` (400; для лимита
     workspace — `…specified workspace API usage limits`) — сработал лимит
     расходов, который выставили в Console сами. Деньги на счёте при этом есть.
     Console → Settings → Billing → Spend limits: поднять или снять. Когда
     доступ вернётся сам, сказано в тексте ошибки.
   - `enforced_spend_limit_reached` (429, тип `rate_limit_error`) — исчерпан
     месячный потолок расходов тарифа аккаунта. Это не транзитный 429: каждый
     вызов будет отвергнут до 00:00 UTC 1-го числа следующего месяца, ждать ✅
     бесполезно. Доступ раньше вернёт только тариф выше: Console → Settings →
     Limits → Request rate limit increase.
   - `billing_error` (402) — проблема с платёжными данными: Console → Settings →
     Billing, проверить способ оплаты.
   - `authentication_error` (401) / `permission_error` (403) — ключ отозван или
     неверен: Console → API keys, ротация — docs/runbooks/secrets.md.
   - `not_found_error` (404) — провайдер не нашёл запрошенное. Путь запроса
     задаёт SDK, а единственный идентификатор от нас — модель из `LLM_MODEL`:
     сверить её со [статусом моделей](https://platform.claude.com/docs/en/about-claude/model-deprecations).
     Снята с обслуживания или недоступна ключу → сменить `LLM_MODEL` в `.env`
     на действующую модель из прайс-листа шлюза (иначе `app` и `worker` не
     стартуют — таблица неполадок docs/runbooks/deploy.md) и
     `docker compose -f /opt/hospitality/docker-compose.staging.yml up -d app worker`.
     Модель действующая → следующая ветка.
   - Прочий `invalid_request_error` (400) или 404 при действующей модели —
     провайдер отвергает сам запрос, причина с нашей стороны. Смотреть, что
     менял последний деплой (`LLM_MODEL`, промпт, инструменты), и откатить:
     `./deploy.sh <предыдущий образ>` (docs/runbooks/deploy.md).
   - `rate_limit_error` (429) без `enforced_spend_limit_reached` — упёрлись в
     лимит запросов или токенов в минуту: Console → Settings → Limits. Этот 429
     транзитный — проходит сам, как только нагрузка спадает.
   - `overloaded_error` (529) или 5xx — перегрузка или авария у провайдера:
     [status.claude.com](https://status.claude.com); делать ничего не нужно.
   - В тексте алерта только таймауты — провайдер не успевает ответить:
     там же status.claude.com, затем сеть сервера (статья ERR-AI-001).
2. Какой отель: тенант в алерте — UUID, `SELECT id, slug, name FROM tenants;`.
   Серия по всем отелям сразу —
   `curl -s https://staging.necturn.com/metrics | grep llm_provider_failure_streak`.
3. После починки ✅ придёт с первым успешным вызовом — следующим сообщением
   гостя. Дёргать модель ради проверки не нужно: это платный вызов.

Ложный случай: короткая волна перегрузки провайдера (529). Повторов шлюз сегодня
не делает, и в журнале такая волна неотличима от пустого баланса (#409) — алерт
придёт, а через минуты погаснет сам. Если в `llm_call_failed` видно
`overloaded_error`, а не баланс — ждать ✅. Ложным не бывает 429 с
`enforced_spend_limit_reached`: он сам не погаснет до 1-го числа (шаг 1).

## ERR-OPS-010

**Алерт:** дневной бюджет LLM отеля исчерпан — шлюз уже отвергает вызовы
(ERR-AI-002), бот отвечает гостям заглушкой. Это продолжение
[ERR-OPS-006](#err-ops-006): тот предупреждал на 80%, этот приходит с первого
отказа. ✅ — в 00:00 UTC (бюджет дневной) или раньше, когда после поднятого
лимита вызов прошёл; в нём — сколько вызовов было отвергнуто.

1. Расход, лимит и число отказов:
   `curl -s https://staging.necturn.com/metrics | grep -E 'llm_daily_|llm_budget_rejection'`.
2. Легитимен ли расход — шаги 2–3 статьи [ERR-OPS-006](#err-ops-006).
3. Гостям нужен ответ до полуночи UTC → поднять `LLM_TENANT_DAILY_BUDGET_USD`
   в `.env` на сервере и
   `docker compose -f /opt/hospitality/docker-compose.staging.yml up -d app worker`.
   ✅ придёт со следующим сообщением гостя, которое пройдёт бюджет.
4. Расход аномальный — ограничивать источник, а не потолок (шаг 5 ERR-OPS-006).

Ложный случай: у самого края лимита несколько гостей пишут одновременно, резервы
их вызовов в сумме перешагивают лимит, и один вызов отвергается, а следующий
проходит (ADR-017) — 🔴 и ✅ с разницей в минуты. Бюджет при этом всё равно на
исходе: ERR-OPS-006 уже пришёл.

## ERR-EVENTS-002

**Алерт:** событие outbox исчерпало повторы доставки и ушло в dead-letter.
Что это значит по существу: чья-то заявка не дошла до службы и сама уже не
дойдёт. Пока алерт не разобран, гость ждёт ответа, которого не будет.

1. Найти событие по id из алерта (первые 8 символов) — на сервере, в БД:
   ```sql
   SELECT id, event_name, tenant_id, correlation_id, attempts, dead_lettered_at, last_error
     FROM outbox_events WHERE id::text LIKE '<id из алерта>%';
   ```
   `last_error` в алерте обрезан до одной строки — здесь он целиком.
2. Полный след «публикация → попытки доставки» — по correlation id из алерта:
   `docker compose -f /opt/hospitality/docker-compose.staging.yml logs worker | grep <correlation_id>`
   (события `event_published`, `event_delivery_failed`, `event_delivery_exhausted`).
3. Сколько всего похоронено (алерт называет только старейшее из своей пачки,
   до 50 событий):
   `curl -s https://staging.necturn.com/metrics | grep outbox_dead_letter_events`.
   Растёт от алерта к алерту — сломан обработчик, а не одно событие.
   Перечислить остальные поимённо — запросом из статьи ERR-EVENTS-002
   (по `dead_lettered_at`: помеченные рассказанными из выборки алерта уже ушли).
4. Починить причину (обработчик или зависимость), затем вернуть события в
   очередь — SQL (одно событие и пачкой) и объяснение полей в
   docs/runbooks/errors.md, статья «ERR-EVENTS-002».
   Одно уведомление (не восстанавливая событие) быстрее отправить руками из
   staff-чата: гость ждёт минуты, а не деплой.
5. Повторного алерта об этих же похоронах не будет: о каждых рассказывают ровно
   один раз (`dead_letter_alerted_at`). Тишина после алерта = «новых похорон не
   было», а не «разобралось само». Вернули событие в очередь, а фикс не помог —
   похороны новые, и алерт о них придёт заново (код сам снимает пометку).

Ложный случай: во время сознательного эксперимента с недоступной зависимостью
(репетиция отказа, отключённый staff-чат) события хоронятся штатно — алерт
верен, разбирать нечего.

## Проверить тракт алертов вручную

С сервера (значения взять из `.env`):

```bash
curl -s "https://api.telegram.org/bot$TELEGRAM_ALERT_BOT_TOKEN/sendMessage" \
  -d chat_id="$TELEGRAM_ALERT_CHAT_ID" -d text="тест тракта алертов"
```

Сообщение в канале = бот и канал настроены верно. Полная репетиция DoD:
`docker compose -f docker-compose.staging.yml stop db` → алерт ERR-OPS-001 в
течение ~2–3 минут → `... start db` → ✅ о восстановлении.

Та же репетиция для воркера (issue #136):
`docker compose -f docker-compose.staging.yml stop worker` → алерт ERR-OPS-003
в течение ~6 минут (порог 5 минут + интервал опроса) → `... start worker` → ✅.
Дольше нескольких минут держать остановленным не нужно: пока воркер стоит,
события копятся, и уведомления службам придут задним числом.

## Как узнать chat.id канала

Добавить бота администратором канала → отправить в канал любое сообщение →
`curl -s "https://api.telegram.org/bot<токен>/getUpdates"` — в
`channel_post.chat.id` будет отрицательное число вида `-100…` — это и есть id.
Если `getUpdates` пуст — сначала `deleteWebhook` не делать (вебхук нужен
гостевому боту!): взять ОТДЕЛЬНОГО бота для алертов или посмотреть id через
пересылку сообщения боту @userinfobot.

## Известные ограничения (зафиксировано)

- Алертер живёт на том же VPS, что и приложение: смерть всего сервера не
  заалертит. Лечение — внешний managed uptime-сервис (§10.12), опрашивающий
  `https://staging.necturn.com/health/ready` (например, UptimeRobot, бесплатного
  тарифа достаточно). Рекомендуемый ручной шаг после Task 0018, вне её DoD.
- Состояние алертера — в памяти: перезапуск контейнера может повторить
  активный алерт один раз.
- Метрики процесса-воркера не экспонируются (у него нет HTTP): его здоровье
  видно снаружи через отметку пульса в БД, которую `/metrics` приложения отдаёт
  возрастом (`worker_heartbeat_age_seconds`, ERR-OPS-003, issue #136), через
  глубину очереди (`outbox_pending_events`, ERR-OPS-004) и через Sentry
  (ERROR-логи воркера становятся событиями). Алерты воркер шлёт сам
  (ERR-EVENTS-002), но только о dead-letter — о собственной смерти он не
  доложит по построению, поэтому её и стережёт алертер снаружи.
- Пульс — про процесс, а не про полезную работу: воркер, который жив и
  отмечается, но роняет каждую доставку, ERR-OPS-003 не даст. На этот случай и
  стоит вторая линия — ERR-OPS-004 по глубине очереди.
- Реестр Prometheus — на процесс: при нескольких uvicorn-воркерах `/metrics`
  отдаёт счётчики случайного воркера. Поэтому staging бежит с одним воркером
  (override `command` в docker-compose.staging.yml, Task 0019); multiprocess-
  реестр — Phase 1.
