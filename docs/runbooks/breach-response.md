# Runbook: реагирование на утечку персональных данных

> Пакет П1.5 (issue #126). Правовая рамка: уведомление уполномоченного органа —
> **1 рабочий день** с момента выявления (приказ МИИЦР № 232/НҚ от 30.04.2026);
> дальше граждан оповещает «цифровое правительство» по SMS. Сокрытие утечки —
> отдельный состав; невыполнение мер защиты, повлёкшее утечку, — 750 МРП для
> малого бизнеса (юраудит 22.07).
>
> **Главный принцип: сомневаешься, инцидент ли это, — считай инцидентом и
> уведомляй.** Ложная тревога стоит неловкого письма; сокрытие — штраф и
> потеря договора с отелем.

## 1. Что считается инцидентом

Любое из этого — инцидент, запускай регламент:

- несанкционированный доступ к БД, серверу или бэкапам (посторонний вход по
  SSH, чужие запросы с `SERVICE_TOKEN`, взлом аккаунта GitHub/Cloudflare);
- утечка секретов, дающих доступ к данным гостей: `POSTGRES_PASSWORD`,
  `SERVICE_TOKEN`, SSH-ключи, креды cloudflared, `TELEGRAM_BOT_TOKEN`
  (переписка через Bot API), **приватный ключ age** (расшифровывает бэкапы);
- нешифрованный дамп/экспорт данных гостей вне прод-контура (нарушение
  границы контуров ADR-006 §1);
- потеря/кража устройства основателя с доступами (ssh-ключи, менеджер
  паролей, приватный ключ age);
- сообщение третьей стороны («ваши данные продаются», отчёт исследователя).

НЕ инцидент (но фикс и запись): уязвимость без признаков эксплуатации;
падение сервера без признаков доступа; утечка секрета, не дающего доступа к
ПД (например, `TELEGRAM_ALERT_BOT_TOKEN` — там нет данных гостей). Сомнение
трактуется в сторону «инцидент».

## 2. Час 0 — зафиксировать и сдержать

1. **Записать время обнаружения (UTC) и что известно** — в файл-таймлайн
   инцидента (локально у основателя; каждая следующая запись — с временем).
   Этот файл — основа уведомления и защита от обвинения в сокрытии.
2. **Сдержать** — по типу инцидента:
   - скомпрометирован секрет → ротация по таблице
     [secrets.md](secrets.md) (у каждого секрета описана процедура);
   - подозрение на активный доступ к серверу → отключить вход: погасить
     cloudflared (`docker compose stop cloudflared`), при необходимости —
     остановить весь стек (`docker compose down`); заявки в простое отель
     принимает по телефону — это штатный режим (ADR-006 §3);
   - скомпрометирован Bot API → `/revoke` у BotFather (см. secrets.md);
   - утёк приватный ключ age → ротация пары ([restore.md](restore.md),
     «Ротация ключа») + считать содержимое всех живых дампов раскрытым.
3. **Ничего не удалять на сервере** (логи, дампы, docker-журналы) — это
   доказательная база для оценки объёма.

## 3. День 1 — оценить объём и уведомить

### 3.1. Оценка объёма (по логам и БД)

Собрать в таймлайн: период воздействия; какие тенанты (отели) затронуты;
категории данных (тексты сообщений? имена? комнаты?); примерное число
субъектов. Источники: JSON-логи app/worker (`tenant_id`, `correlation_id`),
Sentry, `last_used_at` ключей, журналы SSH (`journalctl -u ssh`).

```sql
-- Число затронутых диалогов/гостей за период (пример; выполняется на сервере:
-- docker compose -f docker-compose.staging.yml exec db psql -U $POSTGRES_USER $POSTGRES_DB)
SELECT count(DISTINCT c.id) AS conversations, count(DISTINCT s.guest_id) AS guests
FROM conversations c
LEFT JOIN guest_sessions gs ON gs.guest_identity_id = c.guest_identity_id
LEFT JOIN stays s ON s.id = gs.stay_id;
```

### 3.2. Уведомление уполномоченного органа — не позднее 1 рабочего дня

Получатель: уполномоченный орган в сфере защиты персональных данных —
Комитет информационной безопасности МИИЦР РК. Канал подачи: [проверить
актуальный на gov.kz при регистрации ИП: портал eOtinish / канцелярия КИБ —
вписать сюда адрес при первом заполнении].

Шаблон текста (состав — по приказу № 232/НҚ):

```
Уведомление о нарушении безопасности персональных данных

1. Оператор: [ИП/ТОО «___»], БИН/ИИН [___], адрес [___].
2. Ответственное лицо: [ФИО], тел. [___], email [___]
   (приказ № [_] от [дата] — docs/legal/responsible-person-order-template.md).
3. Дата и время выявления нарушения: [UTC+05:00 ...].
4. Характер нарушения: [несанкционированный доступ / утечка / потеря],
   обстоятельства: [кратко из таймлайна].
5. Категории затронутых данных: [тексты сообщений чата, имена гостей,
   номера комнат, идентификаторы чатов].
6. Предполагаемое число субъектов: [N], собственник базы: [отель «___»].
7. Принятые меры: [ротация секретов, отключение входа, ...из таймлайна].
8. Планируемые меры: [...].
```

### 3.3. Уведомить отель — не позднее 24 часов (DPA, раздел N.6)

Контакт из договора; приложить пп. 3–7 шаблона. Согласовать коммуникацию с
гостями (SMS-оповещение граждан делает «цифровое правительство» после
уведомления органа — самим гостям писать не обязательно, но отель может
решить иначе).

## 4. После: восстановление и пост-мортем

1. Доротировать **все** секреты контура, не только явно утёкшие (час 0 мог
   недооценить объём); чистый деплой `./deploy.sh`.
2. Проверить целостность данных против последнего бэкапа (`make backup-fetch`
   + восстановление на локальной БД — restore.md).
3. Пост-мортем в `docs/audits/` (дата-breach-postmortem.md): таймлайн, объём,
   корневая причина, что меняем. Закрытие дыры — issue с приоритетом блокера.
4. Запись в лог инцидентов (правило secrets.md: «утечка любого секрета →
   ротация + запись в лог инцидентов») — сам таймлайн и есть эта запись,
   приложить к пост-мортему.
