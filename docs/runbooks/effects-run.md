# Runbook: приёмка кандидата — прогон по эффектам на staging

> Перед каждым обновлением копии отеля (#1051 п. 1). Гонит окно с человеком: нужен вход на
> staging по ssh ([deploy.md](deploy.md)), безголовому окну его не дают. Прогон пишет в базу
> staging (демо-отель) — запускать по «да» основателя, как любую запись на staging (CLAUDE.md,
> «Пул окон»). Модель не платит: скрипт ходит на Fake-адаптерах. Живую модель, телефон и вид
> проверяет основатель — [лист приёмки](founder-acceptance.md), сразу после скрипта.

**Прогон по эффектам** — пройти путь человека на работающем стеке и смотреть, куда пришло
каждое действие, а не как выглядит экран: красивый экран бывает и у действия, которое
никуда не ушло (#785). Так в октябре–ноябре нашлись пять серьёзных дефектов, которых
не видели ни тесты, ни ревью (аудит процесса 11.11, П-6).

## Что проверяет скрипт

`python -m hospitality.tools.effects_run` поднимает приложение в процессе контейнера
staging — на его базе, Redis и настройках демо-отеля — и идёт по HTTP тремя «браузерами»:

- **сотрудник** — приглашение менеджером → принятие → выход и вход логином → «Наставник»
  закрыт без отметки согласия → отметка открывает → экзамен назначен службе «Хаускипинг» →
  сдан → строка «сдан» в «Итогах экзаменов» у менеджера;
- **гость** — заселение в номер `9901` → экран согласия действующей версии → код → вопрос
  по-русски, по-казахски и по-английски доходит до модели → «Пожар в номере, дым!» — телефон
  ресепшена без модели → срочная карточка службы эскалаций с номером и проживанием → она
  в очереди менеджера с пометкой «Срочно»;
- **кабинет** — «Обзор», «Очередь заявок», «Заселение», «Сотрудники», «Итоги экзаменов»
  открываются у менеджера на данных staging.

Те же шаги в CI гоняет `tests/test_launch_path.py` на пустой базе; скрипт добавляет то,
чего тест не видит: настройки и данные демо-отеля, миграции staging, его Redis и воркер.

## Шаги

1. **Образ staging — кандидат.** На сервере, в каталоге staging:
   ```bash
   cd /opt/hospitality && grep '^APP_IMAGE=' .env    # sha — запомнить: он станет меткой
   docker compose -f docker-compose.staging.yml ps    # идёт деплой — ждать: staging отдаёт 502
   ```
2. **Прогон** — там же, минуты две:
   ```bash
   docker compose -f docker-compose.staging.yml --env-file .env exec app \
     python -m hospitality.tools.effects_run --i-know-this-is-staging
   ```
   Таблица: строка на шаг — ✓, ✗ с причиной или ⬜ «не дошли» (путь остановился на ✗);
   в конце «Итог». Код возврата: 0 — все ✓, 1 — есть ✗ или ⬜, 2 — контур не staging.
   Пока идёт прогон, в Telegram-группу персонала staging и в пуш подписанным сотрудникам
   демо-отеля приходит «🚨 ЧП» номера `9901` — это он.
3. **✗ в путях** — метку на этот sha не ставить. Issue «к выпуску» со строкой отчёта и
   шагом воспроизведения, починка — обычным PR в `main`; после её деплоя — шаг 2 заново.
   Частые причины, которые чинятся без кода (затем шаг 2 заново):
   - «службы эскалаций нет» — её задаёт `demo_showcase` без `--reset`; он же перевыпустит
     приглашения демо-сотрудникам, не вошедшим в кабинет ([deploy.md](deploy.md),
     «Демо-картина к показу»);
   - «номер 9901 занят» — прошлый прогон оборвался до уборки: «Заселение» → 9901 →
     «Выселить»;
   - «нет активного менеджера» или «тенанта нет» — команды из [errors.md](errors.md),
     ERR-PLATFORM-010, шаг 2 (`tools.staff_bootstrap`, `tools.seed`).
4. **✗ в «Уборке»** — доделать руками, что написано в строке (кнопки кабинета менеджером).
   Уборка идёт и после упавшего шага: гасит всё, что прогон успел завести.
5. **Лист основателя** — назвать основателю короткий sha и адрес staging; дальше —
   [founder-acceptance.md](founder-acceptance.md), часть 1. Ждать его бланк.
6. **Перед меткой** — снова `grep '^APP_IMAGE=' .env`: пока шёл лист, staging мог получить
   слияние. Тот же sha — метка на нём ([pilot-copy.md](pilot-copy.md), «Выпуск в отель»).
   Другой — шаг 2 на новом образе (бесплатно, минуты), метка — на новом sha; в записи — оба.
7. **Запись** — комментарием «Приёмка pilot-rcN» в issue кандидата (для `pilot-rc1` —
   #897): дата, sha, таблица скрипта целиком, бланк основателя. Данных отеля в нём нет —
   staging синтетический, а репозиторий публичный.

## Чего скрипт не проверяет

- **Живую модель** — язык и смысл ответа гостю, вопросы и оценки экзамена. Это шаги 6 и
  10–11 листа основателя. Платные прогоны сверх листа — bake-off на кандидате, ручной Smoke —
  только по «да» основателя на план с ценой (#1051 п. 4, CLAUDE.md).
- **JavaScript и вид на телефоне** — лист основателя целиком.
- **Шаги #848 про заявки гостя** (полотенца, «Готово» → гостю, заказ в номер, столик):
  у копии их нет — режим «только консультации», room service и бронь выключены. Их
  проверяют, когда раздел включают на копии, — абзацем включения в
  [pilot-copy.md](pilot-copy.md).
- **Копию отеля** — скрипт на ней не запускается (отказ по признакам контура); после
  обновления её смотрит часть 2 листа, без записи данных.

## Что остаётся в демо-отеле

Отключённые учётки `EFM…` и `EFS…` (метка — месяц, день, час и минута запуска), попытка
экзамена в базе (в «Итогах экзаменов» её не видно: назначение снято), отменённая причиной
«дубль» карточка и закрытое проживание `9901` в истории, переписка тестового гостя в «Диалогах».
Так же, как следы прогона #848: история кабинета атрибутируема, удалять её нечем и незачем.
