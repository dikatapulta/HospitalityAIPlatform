# Каталог ошибок (FOUNDATION §10.5)

Каждая **ожидаемая** ошибка платформы имеет код `ERR-<MODULE>-NNN` и статью в этом файле.
Алерт или ответ API содержит код → код содержит диагноз. Это база для «автоматического
определения вероятной причины» без чтения кода.

## Правила

- Код выбрасывается только через `AppError(code=..., message=..., status_code=...)`
  из `hospitality.shared.errors` (канон, R-8). `message` виден клиенту — без секретов
  и внутренних деталей.
- Новый код = константа в коде + статья здесь, **в том же PR**. Код без статьи — блокер ревью.
- Формат: `ERR-<MODULE>-NNN`, где `<MODULE>` — имя модуля заглавными (PLATFORM, REQUESTS, …),
  `NNN` — порядковый номер внутри модуля, начиная с 001. Номера не переиспользуются:
  удалённый код помечается здесь как «изъят», а не заменяется новым смыслом.
- Структура статьи: **что значит → вероятные причины → что проверить**.

## Как найти ошибку в логах

Каждый ответ с ошибкой содержит `correlation_id` (он же — в заголовке ответа
`X-Correlation-ID`). По нему находится весь след запроса:

```bash
# staging (подробности подключения — docs/runbooks/deploy.md)
docker compose -f /opt/hospitality/docker-compose.staging.yml logs app | grep <correlation_id>

# локально
make dev-logs | grep <correlation_id>
```

## ERR-PLATFORM-001 — необработанная внутренняя ошибка

- **Что значит:** запрос упал с исключением, которое не является `AppError`, — программная
  ошибка или отказ инфраструктуры. Клиент получил HTTP 500 без деталей; полная трасса —
  в логах, событие `unhandled_error` с тем же `correlation_id`.
  Под uvicorn на тот же инцидент в логах будет и вторая запись с той же трассой от
  `uvicorn.error` («Exception in ASGI application»): `ServerErrorMiddleware` перевыбрасывает
  исключение после отправки ответа — это дубль, а не второй инцидент. Канонический
  источник для подсчёта и будущих алертов (§10.8) — только событие `unhandled_error`.
- **Вероятные причины:** баг в свежевыкаченном коде; недоступность Postgres/Redis во время
  запроса; несовместимость данных (миграция не применилась).
- **Что проверить:**
  1. Логи по `correlation_id` (см. выше) — событие `unhandled_error` содержит трассу стека.
  2. `/health/ready` — если `postgres`/`redis` в статусе `error`, причина инфраструктурная.
  3. Не совпал ли всплеск ошибок с последним деплоем (`docker compose ps`, тег образа) —
     если да, откат по docs/runbooks/deploy.md.

## ERR-PLATFORM-002 — запрос не прошёл валидацию

- **Что значит:** тело/параметры запроса не соответствуют Pydantic-схеме эндпоинта (P-7).
  Клиент получил HTTP 422; в ответе поле `details` — список нарушений (какое поле, что не так).
  Это ошибка вызывающей стороны, не платформы.
- **Вероятные причины:** клиент (фронт, интеграция, AI-инструмент) отправил устаревший или
  неверный формат; контракт эндпоинта изменился без синхронизации с потребителями.
- **Что проверить:**
  1. `details` в ответе или лог-событие `request_validation_failed` по `correlation_id`
     (в лог пишутся только `loc`/`msg`/`type` — сырой ввод клиента может содержать PII
     и в логи не попадает; сам ввод виден в поле `details` ответа клиенту).
  2. Если ошибки массовые после релиза — сверить версию контракта у клиента и сервера
     (изменение схемы без обратной совместимости — нарушение P-7, фиксировать как инцидент).

## ERR-PLATFORM-003 — HTTP-ошибка фреймворка

- **Что значит:** запрос не дошёл до бизнес-логики — маршрутизация или сам эндпоинт
  ответили стандартным `HTTPException`: неизвестный путь (404), неверный HTTP-метод (405),
  в будущем — 401/403 авторизации. `message` — стандартный текст фреймворка
  («Not Found», «Method Not Allowed»); статус — из исключения. Это ошибка вызывающей
  стороны, не платформы.
- **Вероятные причины:** опечатка в URL у клиента; вызов эндпоинта, который ещё не
  реализован или переименован; неверный метод (GET вместо POST).
- **Что проверить:**
  1. Событие `http_request` по `correlation_id` — фактические `method`, `path`, `status_code`.
  2. Если ошибки массовые после релиза — не переименован ли путь/метод без синхронизации
     с потребителями (см. ERR-PLATFORM-002, тот же протокол).

## ERR-PLATFORM-004 — тенант не найден

- **Что значит:** операция сослалась на `tenant_id`, которого нет в реестре `tenants`
  (`load_tenant_config`/`store_tenant_config`, platform/config.py).
- **Вероятные причины:** устаревший/чужой `tenant_id` у вызывающей стороны (например,
  id из другой среды: dev-идентификатор на staging); тенант удалён оффбордингом.
- **Что проверить:**
  1. Откуда пришёл `tenant_id` — след по `correlation_id`.
  2. Есть ли тенант в реестре: `SELECT id, slug FROM tenants` (доступ — владельцем схемы,
     см. runbook deploy). Демо-тенант пересоздаётся `make seed` (dev) и деплоем (staging).

## ERR-PLATFORM-005 — конфигурация тенанта не задана

- **Что значит:** тенант существует, но `tenants.config` пуст — онбординг не завершён,
  а код уже требует конфиг (часовой пояс, язык и т.д.).
- **Вероятные причины:** тенант создан напрямую в обход онбординга (служебный
  `demo-smoke` из publish_demo_event — ожидаемо без конфига); онбординг прерван.
- **Что проверить:**
  1. Что за тенант: `SELECT slug, config IS NULL FROM tenants WHERE id = '<tenant_id>'`.
  2. Демо-тенант `demo-hotel` — дозаполнит `make seed` (dev) или деплой (staging);
     боевой тенант — завершить онбординг (мастер профиля — Phase 1).

## ERR-PLATFORM-006 — конфигурация тенанта не соответствует схеме

- **Что значит:** JSON в `tenants.config` не проходит схему `TenantConfig`
  (platform/config.py) — данные и код разошлись. Подробности нарушения — в причине
  исключения по `correlation_id`.
- **Вероятные причины:** схему изменили несовместимо без повышения `schema_version`
  и скрипта миграции конфигов (§6) — главный подозреваемый; правка колонки руками
  мимо `store_tenant_config`.
- **Что проверить:**
  1. `schema_version` в БД против `TENANT_CONFIG_SCHEMA_VERSION` в коде.
  2. Если разошлись после релиза — откатить релиз или написать недостающий скрипт
     миграции конфигов всех тенантов (дисциплина §6, как Alembic для БД).

## ERR-PLATFORM-007 — запрос не аутентифицирован

- **Что значит:** запрос к аутентифицированному эндпоинту (`/api/v1/*`) пришёл без
  валидного сервисного токена — контекст тенанта не установлен. Клиент получил
  HTTP 401 с заголовком `WWW-Authenticate: Bearer`. Отсутствующий и неверный токен
  намеренно неразличимы в ответе (не подсказываем подбирающему).
- **Вероятные причины:** нет заголовка `Authorization: Bearer <токен>`; токен клиента
  не совпадает с `SERVICE_TOKEN` окружения (ротация без синхронизации клиентов);
  `SERVICE_TOKEN_TENANT_SLUG` указывает на тенанта, которого нет в реестре
  (сид не выполнен / опечатка) — тогда токен верный, а 401 всё равно возвращается.
- **Что проверить:**
  1. Заголовок запроса: `curl -H "Authorization: Bearer $SERVICE_TOKEN" ...` —
     схема именно `Bearer`, токен без кавычек и переводов строк.
  2. Логи по `correlation_id`: событие `service_token_tenant_missing` означает
     причину №3 — проверить `SELECT slug FROM tenants` и переменную
     `SERVICE_TOKEN_TENANT_SLUG` в `.env`; тенанта досоздаст сид
     (`make seed` локально, деплой — на staging).
  3. Совпадение токена клиента с `SERVICE_TOKEN` в `.env` окружения
     (staging: `/opt/hospitality/.env`, см. runbook deploy).

## ERR-PLATFORM-008 — текст политики конфиденциальности недоступен

- **Что значит:** страница `/legal/privacy` не смогла прочитать
  `docs/legal/privacy-policy.md` (файла нет или он пуст) и отдала HTTP 500. Это
  блокер, а не косметика: на эту страницу ссылается ОБЯЗАТЕЛЬНЫЙ элемент текста
  согласия гостя (ст. 8 Закона РК «О персональных данных», spec 0029 §2) —
  значит, гость соглашается, не имея доступа к политике.
- **Вероятные причины:** образ собран без `COPY docs/legal` (ops/Dockerfile);
  приложение запущено из каталога, где нет `docs/legal/` (нестандартный CWD);
  документ переписали так, что после первой строки `---` не осталось текста
  (публикуется именно эта часть — до неё служебная преамбула).
- **Что проверить:**
  1. Лог по `correlation_id`: событие `privacy_policy_unavailable` печатает
     все проверенные пути — сравнить их с реальным расположением файла.
  2. В контейнере: `docker compose exec app ls docs/legal/` — файл обязан быть
     внутри образа, а не только в репозитории.
  3. `docs/legal/privacy-policy.md`: строка `---` на месте и после неё есть
     текст (см. правило публикации в самом документе).

## ERR-AUTH-001 — неверный email или пароль

- **Что значит:** вход в кабинет персонала (или принятие инвайта существующим
  email) отклонён: учётки нет или пароль не подошёл. Ответы намеренно
  неразличимы (перечисление email по разнице ответов запрещено), HTTP 401.
- **Вероятные причины:** опечатка; сотрудник забыл пароль; email введён не тот,
  на который принимался инвайт.
- **Что проверить:**
  1. Логи `staff.login` по `correlation_id`: `reason=unknown_email` против
     `reason=bad_password` (наружу разница не отдаётся, в логах — есть).
  2. Забытый пароль в v1: сброса НЕТ. Единственный путь — деактивировать
     старую учётку и принять новое приглашение на ДРУГОЙ email (та же
     процедура, что в ERR-AUTH-005): занятый email не освобождается никогда
     (`uq_user_identities_kind_external`), а инвайт на существующий email
     требует доказать владение старым паролем. Сброс пароля — открытый
     продуктовый вопрос (docs/FOUNDER_REVIEW_QUEUE.md).

## ERR-AUTH-002 — сессия кабинета невалидна или истекла

- **Что значит:** запрос страницы/действия кабинета без валидной сессии:
  cookie нет, токен неизвестен, сессия отозвана, вышел absolute-срок
  (`STAFF_SESSION_ABSOLUTE_TTL_DAYS`) или idle-срок
  (`STAFF_SESSION_IDLE_TTL_DAYS` без активности). HTTP 401 → экран логина.
- **Вероятные причины:** штатное истечение; logout на этом устройстве;
  деактивация пользователя (все сессии гасятся разом).
- **Что проверить:** повторный вход. Если сессии «слетают» массово — сверить
  TTL-переменные окружения и `staff_sessions.revoked_at` у пострадавших.

## ERR-AUTH-003 — нет членства или роли в этом отеле

- **Что значит:** сессия валидна, но у пользователя нет АКТИВНОГО членства в
  тенанте из URL (`/staff/{tenant_slug}/…`) либо роль членства не входит в
  требуемые страницей (мини-матрица spec 0033 §3.2). «Нет членства» и «не та
  роль» наружу неразличимы. HTTP 403.
- **Вероятные причины:** членство отозвано; сотрудник открыл сохранённую
  ссылку чужого отеля; странице нужна роль выше (например, «Сотрудники» —
  только `manager`).
- **Что проверить:** лог `staff.role_denied` (user_id, tenant_slug, required);
  строку `tenant_memberships` пользователя — status и role_key. Отдельный
  случай — лог `staff.tenant_context_mismatch`: авторизация прошла, но
  RLS-контекст запроса поставлен другим звеном цепочки (например,
  SERVICE_TOKEN чужого тенанта вместе со staff-cookie) — fail-closed отказ
  `require_role`, «виноват» не пользователь, а сочетание идентичностей.

## ERR-AUTH-004 — приглашение невалидно, истекло или использовано

- **Что значит:** ссылка-инвайт не принята: токен неизвестен, истёк
  (`STAFF_INVITE_TTL_HOURS`), отозван менеджером или уже использован. Причины
  наружу неразличимы; экран предлагает попросить новое приглашение. HTTP 410.
- **Вероятные причины:** штатное истечение (72 ч); менеджер перевыпустил
  ссылку (старая гасится); ссылка открыта второй раз.
- **Что проверить:** строку `staff_invites` по времени создания: `expires_at`
  в прошлом = истёк/отозван, `accepted_at` заполнен = использован. Решение
  всегда одно — новое приглашение из кабинета.

## ERR-AUTH-005 — пользователь деактивирован

- **Что значит:** вход или принятие инвайта от деактивированной учётки
  (`users.status=deactivated`). HTTP 403.
- **Вероятные причины:** сотрудника деактивировали (увольнение); принятие
  инвайта на email бывшего сотрудника.
- **Что проверить:** лог `staff.user_deactivated` (кто и когда). Возврат
  сотрудника — сознательное действие: реактивация учётки в v1 не
  предусмотрена, завести новую учётку на другой email.

## ERR-AUTH-006 — превышен лимит попыток входа

- **Что значит:** rate-limit логина (канон 0023): за окно
  `STAFF_LOGIN_RATE_LIMIT_WINDOW_SECONDS` накопилось больше
  `STAFF_LOGIN_RATE_LIMIT_ATTEMPTS` НЕУДАЧНЫХ попыток по email ИЛИ больше
  `STAFF_LOGIN_IP_RATE_LIMIT_ATTEMPTS` по IP. HTTP 429. Успешный вход бюджет
  не тратит (issue #207) — «слишком много попыток» без единой ошибки пароля
  невозможно.
- **Вероятные причины:** сотрудник перебирает забытый пароль; подбор пароля
  снаружи; общий NAT отеля упёрся в IP-ключ (одна смена — один адрес).
- **Что проверить:** лог `staff.login_rate_limited` (scope: email/ip) и
  метрику `staff_logins_total{outcome="rate_limited"}`. Всплеск по множеству
  email с одного IP — признак перебора, не забывчивости; живая смена, упёршаяся
  в scope `ip`, — повод поднять `STAFF_LOGIN_IP_RATE_LIMIT_ATTEMPTS`.
- **Чей это адрес — видно в ключах счётчика** (в логах адреса нет, issue #173):
  `docker compose exec redis redis-cli --scan --pattern 'ratelimit:staff_login_ip:*'` —
  адрес стоит в имени ключа. Если там адрес вида `172.x` (сосед по docker-сети), значит
  заголовок прокси не разобран — см. следующий пункт.
- **Если в логах есть `client_ip.untrusted_proxy_header`:** приложение не
  доверяет прокси, от которого пришёл запрос, и считает лимит по адресу этого
  прокси — то есть один бюджет на весь отель. Причина — `TRUSTED_PROXY_IPS`
  не покрывает подсеть, из которой пришёл запрос (в записи она в поле `peer`);
  вписать её в переменную и перезапустить app (`ops/deploy/docker-compose.staging.yml`).

## ERR-AUTH-007 — пароль короче минимума

- **Что значит:** при принятии инвайта или бутстрапе задан пароль короче
  8 символов. HTTP 422.
- **Что проверить:** ничего — попросить пароль длиннее; других правил
  сложности в v1 нет (стойкость держат argon2 и rate-limit).

## ERR-AUTH-008 — пользователь не найден

- **Что значит:** операция над сотрудником (смена роли, отключение) получила
  id, которого нет в `users`, ИЛИ у этого пользователя нет активного членства
  в отеле менеджера. Причины намеренно неразличимы: id сотрудника соседнего
  отеля не должен подтверждаться (docs/RBAC.md §3). HTTP 404.
- **Вероятные причины:** гонка двух менеджеров в списке «Сотрудники»;
  устаревшая страница (сотрудника уже отключили); попытка действовать по id
  из чужого отеля.
- **Что проверить:** обновить список; если id пришёл не из UI — источник id;
  строку `tenant_memberships` (tenant_id и status).

## ERR-AUTH-011 — нельзя менять собственную учётную запись

- **Что значит:** одно из двух. Либо менеджер попытался сменить роль самому
  себе или отключить себя на странице «Сотрудники»; либо действующий менеджер
  отеля открыл ссылку-приглашение с ролью ниже своей и ввёл свои email и
  пароль. HTTP 409; ничего не изменилось, приглашение не потреблено.
- **Почему так:** защита от самоблокировки в v1 (spec 0033 §7): сброса пароля
  и реактивации нет, поэтому «снять с себя manager» означало бы потерять
  кабинет отеля насовсем. Путей смены роли три (страница «Сотрудники» — смена
  роли и отключение — и принятие приглашения), поэтому и проверок две:
  `staff_team._forbid_self_action` и `staff_invites._forbid_manager_downgrade`.
- **Что проверить:** ничего — действие выполняет другой менеджер. Приглашение
  цело: его примет тот, кому оно выписано. Менеджеров в отеле нет вовсе
  (единственный ушёл) — новый заводится CLI бутстрапа:
  `python -m hospitality.tools.staff_bootstrap` (docs/RBAC.md §3).

## ERR-AUTH-009 — JSON-действие кабинета отклонено CSRF-щитом

- **Что значит:** POST JSON-действия кабинета (взять/готово/отменить,
  spec 0033 §5) пришёл без `Content-Type: application/json` или без
  НЕПУСТОГО same-origin заголовка `Origin` (CSRF-контракт
  `staff_portal/router.py`). HTTP 403; действие не выполнялось.
- **Вероятные причины:** кросс-сайтовый запрос (собственно CSRF); ручной
  curl/скрипт без нужных заголовков (браузерный fetch страницы кабинета шлёт
  оба всегда); прокси, вырезающий Origin.
- **Что проверить:** лог `staff.action_csrf_rejected` (content_type, origin).
  Массовые отказы у живых пользователей — признак прокси/туннеля, который
  переписывает заголовки, а не атаки.

## «Запрос отклонён: чужой источник (CSRF)» — форма кабинета, без кода

- **Что значит:** тот же щит, но у HTML-ФОРМЫ (вход, выход, заселение,
  принятие приглашения): `Origin` запроса не совпал с `Host`. HTTP 403,
  простым текстом — это отказ навигации, а не ответ API, поэтому кода каталога
  и конверта R-8 у него намеренно нет (`staff_portal/browser.py`).
- **Что проверить:** лог `staff.cross_origin_rejected` — там поле `origin`.
- **`origin` в логе равен `null`** — непрозрачный источник. Разбирается в два
  шага; **сначала масштаб, потом заголовок** — они дают разный диагноз.

  **Шаг 1. Отказ массовый или единичный?** Атака не выглядит как «кабинет лёг
  у всех»: массовые `null` у живых людей — регресс класса #164, наша сторона,
  и трактовать их как атаку нельзя. Единичные у одного человека — почти всегда
  его браузер (см. ниже). Единичные ни у кого из знакомых — то самое, ради
  чего щит и стоит.

  **Шаг 2. Снять политику реферера с той страницы, с которой шлётся форма** —
  ЖИВЬЁМ и с того же контура, где отказ (прод, не staging). Нужен именно GET
  с выводом заголовков; `curl -I` не годится — это HEAD, а `/staff/login`
  отвечает на него `405` вообще без заголовков страницы:

  ```bash
  # хост — того контура, где отказ; staging ниже для примера
  curl -sS -D - -o /dev/null https://staging.necturn.com/staff/login | grep -i referrer
  ```

  - **Там НЕ `strict-origin`** — причина наша: регресс
    `browser.PAGE_HEADERS`; переписывание заголовка зоной Cloudflare
    (Transform Rules / Managed Headers); либо форма шлётся не со страницы
    кабинета — гостевые поверхности `Referrer-Policy` не ставят вовсе
    (долг #158), а браузерное умолчание само по себе `Origin` не обнуляет:
    только на том же понижении схемы, что и `strict-origin` ниже.
  - **Там `strict-origin`, но отказ массовый** — всё равно наша сторона.
    Померена не та страница, с которой реально шлётся форма; либо страница
    открыта по `https`, а форма уходит на `http` — на понижении схемы
    `strict-origin` источник обнуляет, и это единственный случай, когда он это
    делает (Fetch, § append a request Origin header); либо прокси перед
    приложением переписывает `Origin` в строку `null` — заметь, вырезанный
    заголовок дал бы не `null`, а пустой (последний пункт раздела).
  - **Там `strict-origin`, отказ у одного человека** — у клиента действует не
    наша политика реферера: расширение приватности, ручная настройка браузера.
    Симптом тот же, что в #164, но у одного, а не у всех.
  - **Там `strict-origin`, отказы разрозненные и не от своих** — источник и
    правда непрозрачный: форма из песочного iframe, документ после
    кросс-доменного редиректа. **Это может быть атака** — ровно та, ради
    которой щит `null` и отвергает. Смотреть, повторяется ли и идут ли рядом
    неудачные входы (`staff.login` с `outcome=rejected`): IP в
    `staff.cross_origin_rejected` сейчас не пишется — долг #173.

  История: до PR #165 страницы отдавались с `Referrer-Policy: no-referrer`, и
  `null` слали собственные формы кабинета — вылечено, #164 закрыт.
- **`origin` — чужой домен:** собственно CSRF либо неверно настроенный прокси.
- **`origin` пуст:** щит не сработал бы вовсе — значит отказ пришёл не отсюда.

## ERR-TELEGRAM-006 — ответ в чат потерян окончательно

- **Что значит:** платформа отработала ход (заявка создана, токены потрачены,
  служба уведомлена) — а ответ до чата не дошёл и уже не дойдёт. Штатный
  сбой отправки этим кодом НЕ сопровождается: реплика, не ушедшая с первой попытки,
  встаёт в outbox и дожимается воркером (`channels/telegram/redelivery.py`, issue
  #209). Код означает, что дожим исключён. Лог-код (не `AppError`): клиента, которому
  отвечать, здесь нет — вебхуку уже ответили 200.
- **Гостю или персоналу — смотреть по `chat_id`.** Через дожим идут оба направления
  `send_reply`: ответ гостю и ответ персоналу в чат службы (исход `/done`, `/take`,
  ответ на вопрос «что не сделано?»). Имя события (`telegram_reply.undelivered`) и
  этот код одни на оба; адресата различают `chat_id` и `conversation_id` в логе —
  `conversation_id` потерянной реплики персоналу приведёт в групповой чат службы,
  а не к гостю.
- **Два случая, различаются полем `reason` в событии:**
  - `queue_failed` — реплику не удалось даже поставить в очередь (упал `publish`
    в outbox). Ход гостя при этом уже закоммичен; потеряна только доставка.
  - `too_stale` — очередь дожимала дольше `REPLY_MAX_AGE_SECONDS` (10 минут,
    владелец числа — spec 0016), и реплика намеренно НЕ отправлена: ответ на ход,
    случившийся четверть часа назад, дезориентирует сильнее молчания. Значит,
    Bot API или сеть до него были недоступны все эти минуты — смотреть надо туда.
    Уже доставленная И записанная в историю реплика этим кодом не
    сопровождается: подписчик сверяет факт доставки раньше возраста. Остаток
    честнее назвать, чем умолчать: если процесс умер между отправкой и записью
    `Message`, следов доставки нет ни у кого — тогда `too_stale` назовёт
    потерянной реплику, которую гость получил.
- **Третьего пути (dead-letter) у этого события при штатных настройках нет.**
  `telegram_reply.undelivered` не хоронится: попытка, на которой исчерпывается
  `WORKER_MAX_DELIVERY_ATTEMPTS` (10-я), приходится по расписанию backoff на
  810-ю секунду, а там подписчик уже возвращается по сроку годности, а не бросает.
  Поэтому **ERR-EVENTS-002** по этому имени события не приходит; ждать алерта
  бессмысленно — оба живых пути видны только по ERR-TELEGRAM-006: строка в логе
  app (`queue_failed`) или worker (`too_stale`). Оживает dead-letter, как только
  ПОСЛЕДНЯЯ по счёту попытка попадает внутрь срока годности, а расписание задают
  три настройки, не одна: предел попыток `WORKER_MAX_DELIVERY_ATTEMPTS` ≤ 9
  (девятая попытка, 510-я секунда, — последняя внутри срока), потолок
  `WORKER_RETRY_BACKOFF_MAX_SECONDS` ниже ≈ 170 с при нетронутом пределе (при
  100 с десятая попытка приходится на 426-ю секунду) или база
  `WORKER_RETRY_BACKOFF_BASE_SECONDS` ниже ≈ 1,15 с при нетронутых пределе и
  потолке (при 1,15 с десятая попытка приходится на 588-ю секунду). Предел попыток
  назван точно, а обе дробные границы — потолок и база — округлены ВНИЗ, с запасом:
  точная у потолка 173 с, у базы 300/255 ≈ 1,176 с, то есть уже 1,18 с уносит
  десятую попытку за срок годности. Хватает любой одной; трогали любую — считать
  расписание заново, а не полагаться на этот буллет.
- **В самой очереди потеря неотличима от успеха.** Протухшая реплика получает
  `processed_at` — ту же терминальную отметку, что и доставленная (не
  `dead_lettered_at`), поэтому считать потери по `outbox_events` нельзя: считают
  по коду ошибки в логах и Sentry (счётчика `/metrics` у этого пути пока нет —
  #294).
- **Вероятные причины:** `queue_failed` — Postgres недоступен или миграции не
  применены (тот же класс, что ERR-EVENTS-003); `too_stale` — длительная
  недоступность api.telegram.org (сеть, блокировка исходящего трафика), мёртвый
  воркер (проверить ERR-OPS-003), устойчивый 429 при массовой рассылке в один чат.
- **Что проверить:**
  1. Логи по коду: `docker compose -f /opt/hospitality/docker-compose.staging.yml
     logs app worker | grep ERR-TELEGRAM-006` — `reason`, `chat_id`,
     `conversation_id`, у `too_stale` ещё и `age_seconds`.
  2. Рядом по тому же `correlation_id` — `telegram_send_failed` (первая попытка) и
     `telegram_reply_queued` (реплика встала в очередь). Есть первое без второго —
     это `queue_failed`.
  3. Жив ли воркер: `telegram_reply_redelivered` в его логах и пульс (ERR-OPS-003).
     Дожим делает ТОЛЬКО воркер — остановленный воркер превращает каждый сбой
     отправки в `too_stale` через десять минут.
  4. Сколько реплик ждёт прямо сейчас — растущее от минуты к минуте число значит,
     что канал лежит, а не моргнул. Psql открывается каноном subject-requests.md
     (`sh -c` в одинарных кавычках обязателен: `POSTGRES_*` живут внутри
     контейнера db, на хосте их нет):

     ```bash
     docker compose -f /opt/hospitality/docker-compose.staging.yml --env-file .env \
       exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
     ```

     ```sql
     -- по всем отелям сразу: у outbox_events своя политика platform_dispatch,
     -- фильтра тенанта у этого счёта нет и быть не должно
     SELECT count(*) FROM outbox_events
      WHERE event_name = 'telegram_reply.undelivered'
        AND processed_at IS NULL AND dead_lettered_at IS NULL;
     ```
  5. Ответить руками в тот чат, где потерялась реплика: `chat_id`/`conversation_id`
     из лога → чат и текст. Сначала загляните в сам чат: при `too_stale` редкий
     случай (обрыв между отправкой и записью) даёт этот код о реплике, которая
     всё-таки дошла, — тогда отвечать второй раз не надо. Автоматически это уже
     не произойдёт ни на одном из двух путей.

     и трасса с ответом Bot API.
  2. Соседнее событие `daily_summaries_scanned` (`tenants`, `sent`) — работает ли
     прогон в принципе. `sent = 0` при настроенном чате означает либо «время
     рассылки ещё не наступило», либо «сегодня уже отправлено».
  3. Настройки отеля: `python -m hospitality.tools.daily_summary --tenant-slug <slug>`
     (внутри контейнера app) — куда и во сколько уходит сводка. Пустой чат — это
     штатное «отелю не слать», а не поломка.
  4. Повторяется ли код от прогона к прогону: устойчивые 403/400 у `hotel`
     означают неверный чат — исправить тем же инструментом; устойчивые
     `tenant_scan`/`run` чинить как ERR-EVENTS-003.

## ERR-CHANNEL-003 — гостевой чат превысил rate-limit

- До spec 0027 назывался **ERR-TELEGRAM-003**: лимит стал общеканальным вместе
  с выносом хода гостя в `channels/common` (алертер и дашборды старый код не
  использовали — проверено при переносе).
- **Что значит:** один гостевой диалог превысил лимит сообщений
  (issue #41, spec 0023): ступень `guest_chat_window` (`GUEST_CHAT_RATE_LIMIT_MESSAGES`
  за `GUEST_CHAT_RATE_LIMIT_WINDOW_SECONDS`) или `guest_chat_daily`
  (`GUEST_CHAT_RATE_LIMIT_MESSAGES_PER_DAY` за UTC-сутки). Ключ лимита:
  Telegram — `chat_id`, web — `stay_id` (spec 0027 §3.2). Входящее сообщение
  сохранено в историю, **LLM не вызывался** (общий бюджет тенанта защищён), гость
  получил вежливый статический отказ — один раз на окно, дальнейшие сообщения в
  окне дропаются молча. Лог-код, не `AppError` (как ERR-TELEGRAM-002): «клиент» —
  гость, он получает текст, а не HTTP-ошибку.
- **Вероятные причины:** чужой скрипт/спам нашёл публичного бота (штатная работа
  защиты); настойчивый живой гость; слишком низкие значения `GUEST_CHAT_RATE_LIMIT_*`
  для легитимного трафика.
- **Что проверить:**
  1. Логи: события `guest_rate_limited` (`tenant_id`, `chat_id`, `scope`,
     `count`/`limit`) — один ли чат упирается и с какой скоростью растёт `count`
     (сотни за минуты — скрипт, не человек).
  2. Метрика `guest_rate_limited_total{tenant_id, scope}` в `/metrics` — масштаб.
  3. Если трафик легитимный — поднять `GUEST_CHAT_RATE_LIMIT_*` в `.env`
     (значение ≤0 отключает ступень); пер-тенантные значения — Phase 1.
  4. Redis недоступен → лимит **fail-open** (событие
     `rate_limit_backend_unavailable`, диалог работает без защиты): чинить Redis
     по ERR-OPS-001, ложных массовых отказов из-за него не бывает.

## ERR-CHANNEL-004 — ретеншн гостевых текстов упал

- **Что значит:** прогон ретеншна (issue #42, spec 0032) не отработал: либо на
  одном тенанте (в логе есть `tenant_id` — остальные тенанты обойдены), либо
  целиком (лог из `hospitality/worker.py` без `tenant_id`). Данные при этом НЕ
  потеряны — наоборот: старые тексты (`messages`, опустевшие `conversations`,
  свободный текст заявок) не удалены/не обезличены в этом прогоне. Цикл
  воркера жив, доставка событий продолжается; следующий прогон через
  `WORKER_RETENTION_INTERVAL_SECONDS` повторит работу — операции идемпотентны
  (P-8).
- **Вероятные причины:** БД недоступна из воркера (та же природа, что у
  ERR-EVENTS-003); миграции не применены; долгая блокировка удаляемых строк
  чужой транзакцией.
- **Что проверить:**
  1. `docker compose ps` / логи Postgres — жива ли БД (как ERR-EVENTS-003).
  2. Лог `guest_text_retention_completed` предыдущих прогонов: если его нет
     давно, ретеншн не работает вовсе — обещание политики конфиденциальности
     («тексты — 90 дней») нарушается со временем, чинить в приоритете дней,
     а не часов.
  3. Разовый сбой на фоне рестарта БД самочинится следующим прогоном —
     достаточно убедиться, что `guest_text_retention_completed` снова появился.

## ERR-CHANNEL-005 — гость сообщил о ЧП (статический перехват)

- **Что значит:** в сообщении гостя сработал маркер ЧП (пожар/дым/газ,
  медицина, безопасность) — spec 0034, issue #208. Ход оборван ДО модели:
  LLM не вызывался, rate-limit не спрашивался, заявка не создавалась.
  Персоналу ушла эскалация `conversation.escalated` (причина `emergency`) в
  ДЕФОЛТНЫЙ staff-чат тенанта; гость получил статический текст «не ждите
  ответа в чате, позвоните на ресепшен или скажите сотруднику рядом» с
  телефоном ресепшена (`TenantConfig.reception_phone`), если тот задан.
  Номеров экстренных служб в тексте нет намеренно: внешние службы вызывает
  ресепшен (решение основателя 19.08, spec 0034 §3). **Это не ошибка
  приложения** — лог-код операционного события, как ERR-CHANNEL-003: он нужен,
  чтобы ЧП было видно в логах и чтобы было чем измерить срабатывания.
- **Вероятные причины:** настоящее ЧП; ложное срабатывание маркера (список
  намеренно смещён в сторону ложных срабатываний — пропустить пожар дороже);
  гость проверяет бота на прочность.
- **Что проверить:**
  1. Логи: `emergency_intercepted` (`tenant_id`, `conversation_id`, `chat_id`,
     `kind` — fire/medical/security, `language`). Дежурному: сообщение гостя
     целиком видно в самой эскалации в staff-чате.
  2. Эскалация дошла? Ищите в логах worker `staff_escalation_notified` с тем же
     `correlation_id`. Не дошла — смотрите ERR-TELEGRAM-002 (staff-чат не
     настроен) и ERR-EVENTS-001/002 (доставка события).
  3. Строки «📞 Ресепшен» в тексте гостю нет → у тенанта не задан
     `reception_phone`: дозаполнить конфиг (`docs/runbooks/tenant-onboarding.md`,
     аргумент `--reception-phone`). Сам текст при этом действует и без номера —
     инструкция «позвоните на ресепшен или скажите сотруднику рядом» от
     настроек не зависит.
  4. Поток ложных срабатываний из одного чата — это не поломка перехвата:
     своей ступени лимита у ЧП нет намеренно (spec 0034 §4, «принятый риск»),
     иначе она съедала бы вторую настоящую тревогу. Разбирается по-человечески
     через staff-чат.

## ERR-EVENTS-001 — доставка события не удалась (будет повтор)

- **Что значит:** подписчик доменного события упал; событие осталось в `outbox_events`,
  воркер повторит доставку (at-least-once, ADR-005). Лог-событие `event_delivery_failed`
  в логах worker содержит `event_name`, `event_id`, `attempts` и трассу; `correlation_id` —
  тот же, что у публикации.
- **Вероятные причины:** баг в обработчике; временная недоступность зависимости обработчика;
  полезная нагрузка не проходит валидацию схемы события (контракт изменён без совместимости —
  нарушение §13.5).
- **Что проверить:**
  1. Логи worker по `correlation_id`/`event_id` — трасса в `event_delivery_failed`.
  2. Если ошибка повторяется от попытки к попытке — это не «мигание», ждите ERR-EVENTS-002
     и чините обработчик.

## ERR-EVENTS-002 — повторы доставки исчерпаны (dead-letter, алерт)

- **Что значит:** событие не доставлено `worker_max_delivery_attempts` раз и больше
  не берётся в работу НИКОГДА (строка в `outbox_events`: `dead_lettered_at` —
  момент похорон, `processed_at IS NULL`, диагноз — в `last_error`). Эффект
  подписчика НЕ произошёл: уведомление службе о заявке гостя не дойдёт само.
  Об этом приходит алерт в Telegram-канал команды (issue #133, ADR-015) —
  пошаговый разбор: docs/runbooks/alerts.md#err-events-002.
- **Вероятные причины:** устойчивый баг обработчика; «ядовитое» событие
  (нагрузка не соответствует текущей схеме); недоступная зависимость обработчика
  дольше, чем длится лестница backoff (ADR-009).
- **Что проверить:**
  1. `last_error` строки события (доступ — владельцем схемы, см. runbook deploy).
  2. Кто ещё похоронен. Алерт называет id только старейшего события пачки, а
     пометку «рассказано» получает вся пачка (до `worker_batch_size`, 50) —
     поэтому перечисляет похороненные не алерт, а запрос, и смотреть надо на
     `dead_lettered_at`, а не на «о чём ещё не рассказали»:
     ```sql
     SELECT id, event_name, tenant_id, correlation_id, attempts,
            dead_lettered_at, left(last_error, 120) AS reason
       FROM outbox_events
      WHERE dead_lettered_at IS NOT NULL
      ORDER BY dead_lettered_at;
     ```
     Один `event_name` и один `reason` на десятки строк — сломан обработчик,
     чинить его, а не события.
  3. После фикса обработчика вернуть событие в очередь:
     ```sql
     UPDATE outbox_events
        SET attempts = 0, next_attempt_at = NULL, dead_lettered_at = NULL
      WHERE id = '<event_id>';
     ```
     — воркер подхватит его в следующем цикле. Сбрасывать все три поля — канон:
     `dead_lettered_at` и есть терминальность (ADR-015), без его сброса строка
     останется похороненной; `attempts` — иначе первая же неудача снова исчерпает
     предел; `next_attempt_at` (ADR-009) обычно уже в прошлом, но если
     `worker_max_delivery_attempts` понижали — может быть в будущем и задержит
     возврат в работу. Четвёртое поле, `dead_letter_alerted_at`, руками НЕ
     трогают: его сбрасывает сам код в момент повторных похорон
     (`_record_outcome`, ADR-015), поэтому о событии, которому фикс не помог,
     придёт новый алерт — даже если про это поле забыть. Пятое поле,
     `locked_until` (аренда доставки, ADR-016), у похороненной строки всегда
     пусто — код снимает аренду той же транзакцией, что пишет исход.
  4. Вернуть в очередь пачку (сломанный обработчик хоронит события десятками).
     Ограничивать по имени события и окну похорон, а не «всё, что похоронено»:
     ```sql
     UPDATE outbox_events
        SET attempts = 0, next_attempt_at = NULL, dead_lettered_at = NULL
      WHERE dead_lettered_at >= '2026-08-09 00:00:00+00'
        AND event_name = 'request.created';
     ```
     **Перед выполнением понимать:** возврат в очередь запускает обработчиков
     заново, и уведомления уйдут повторно — служба получит сообщения о заявках
     любой давности (вплоть до `outbox_retention_days`, 30 дней). Это штатное
     поведение at-least-once (P-8, ADR-005), а не сбой, но людей в staff-чате
     стоит предупредить заранее. Сначала посмотреть, сколько строк затронет:
     тот же `WHERE` в `SELECT count(*)`.

## ERR-EVENTS-003 — итерация воркера упала целиком

- **Что значит:** цикл воркера не смог прочитать outbox (сбой уровня инфраструктуры,
  а не отдельного обработчика). Процесс жив: логирует `worker_iteration_failed`,
  ждёт период опроса и повторяет.
- **Вероятные причины:** Postgres недоступен; миграции не применены (нет таблицы
  `outbox_events` или роли `hospitality_app`).
- **Что проверить:**
  1. Логи worker (`docker compose ... logs worker`).
  2. `/health/ready` приложения — статус `postgres`.
  3. Применены ли миграции: `docker compose ... run --rm --no-deps app alembic upgrade head`.
- **После падения ПРОЦЕССА воркера** (не итерации) события, которые он успел взять
  в работу, молчат до истечения аренды — `locked_until` в будущем,
  `WORKER_DELIVERY_LEASE_SECONDS`, по умолчанию 5 минут (issue #134, ADR-016).
  Это штатное ожидание, а не залипшая очередь: воркер подхватит их сам. Кто
  сейчас в работе — `SELECT id, event_name, locked_until FROM outbox_events
  WHERE locked_until > now();`. Торопить руками (`SET locked_until = NULL`) можно
  только убедившись, что старый процесс мёртв, — иначе событие доставят двое.

## ERR-EVENTS-004 — retention-очистка outbox упала

- **Что значит:** периодический вызов `cleanup_terminal_events()` (раз в
  `worker_cleanup_interval_seconds`, ADR-009) не смог удалить завершённые строки
  `outbox_events` старше `outbox_retention_days` — доставленные (`processed_at`)
  и похороненные (`dead_lettered_at`, ADR-015). Цикл доставки не затронут: ошибка
  логируется, воркер продолжает доставлять события как обычно и повторит очистку
  на следующем цикле.
- **Вероятные причины:** Postgres недоступен в момент очистки (тот же класс причин,
  что у ERR-EVENTS-003); блокировка удаляемых строк долгой чужой транзакцией
  (с issue #134 доставка такой транзакции больше не открывает: сетевые вызовы
  идут вне транзакций, ADR-016).
- **Что проверить:**
  1. Логи worker (`outbox_cleanup_failed`) — трасса исключения.
  2. `/health/ready` приложения — статус `postgres`.
  3. Если ошибка повторяется от цикла к циклу — таблица `outbox_events` растёт
     быстрее, чем ожидалось retention-политикой; проверить объём строк с
     `processed_at IS NOT NULL` вручную.

## ERR-EVENTS-005 — алерт о dead-letter не ушёл

- **Что значит:** воркер нашёл события, исчерпавшие повторы доставки, но не смог
  рассказать о них человеку (issue #133, ADR-015): лог `dead_letter_alert_failed`.
  Цикл доставки не затронут, пометка «человеку сказано» НЕ ставится — та же пачка
  уйдёт следующим прогоном (раз в `worker_dead_letter_alert_interval_seconds`).
  Опасность здесь двойная: молчит не только алерт, но и то, о чём он молчит, —
  где-то уже лежит недоставленное уведомление службе.
- **Вероятные причины:** Telegram Bot API недоступен или отвечает ошибкой; неверный
  `TELEGRAM_ALERT_BOT_TOKEN`/`TELEGRAM_ALERT_CHAT_ID` (бот удалён из канала, чат
  сменил id при превращении группы в супергруппу); Postgres недоступен в момент
  чтения пачки (тот же класс причин, что у ERR-EVENTS-003).
- **Что проверить:**
  1. Логи worker (`dead_letter_alert_failed`) — трасса и код ответа Telegram.
  2. Тракт алертов вручную (`curl` на `sendMessage`) —
     docs/runbooks/alerts.md#проверить-тракт-алертов-вручную.
  3. Что именно не рассказано:
     `SELECT id, event_name, tenant_id, correlation_id, last_error FROM outbox_events
      WHERE dead_lettered_at IS NOT NULL AND dead_letter_alerted_at IS NULL;`
     — разбирать эти строки по ERR-EVENTS-002, не дожидаясь починки алертов.

## ERR-REQUESTS-001 — категория заявки не найдена

- **Что значит:** `create_request` получил `category_id`, которого нет среди категорий
  ТЕКУЩЕГО тенанта. Чужая и несуществующая категории неразличимы намеренно (RLS, P-4):
  обе дают этот код и HTTP 404.
- **Вероятные причины:** вызывающая сторона (тест, AI-инструмент, будущий HTTP-клиент)
  передала устаревший/чужой идентификатор; категории тенанта ещё не засеяны
  (Task 0011 — сид демо-тенанта); вызов выполнен в контексте не того тенанта.
- **Что проверить:**
  1. Логи по `correlation_id`: `tenant_id` в контексте — тот ли тенант?
  2. Категории тенанта: `SELECT id, key FROM request_categories` из тенантной сессии
     (с Task 0013 — через API списка категорий).

## ERR-REQUESTS-002 — заявка не найдена

- **Что значит:** `change_request_status`/`get_request` не нашли заявку с данным `id`
  у текущего тенанта. Чужая и несуществующая заявки неразличимы (RLS, P-4). HTTP 404.
- **Вероятные причины:** устаревший идентификатор; вызов в контексте не того тенанта.
- **Что проверить:** те же шаги, что у ERR-REQUESTS-001, но по `service_requests`.

## ERR-REQUESTS-003 — недопустимый переход статуса заявки

- **Что значит:** запрошенный переход отсутствует в жизненном цикле
  `new → assigned → in_progress → done/cancelled` (карта — `STATUS_TRANSITIONS`
  в `modules/requests/service.py`): например `new → done`, повторное закрытие
  или любой переход из терминального статуса. Заявка не изменена, событие
  не опубликовано. HTTP 409.
- **Вероятные причины:** гонка двух операторов/процессов (заявку уже перевели);
  клиент показывает устаревший статус; ошибка логики вызывающей стороны.
- **Что проверить:**
  1. Текущий статус заявки и её историю событий `request.status_changed`
     в `outbox_events` по `request_id`.
  2. Если это гонка — повторить операцию от актуального статуса.

## ERR-REQUESTS-004 — ключ категории уже занят

- **Что значит:** `create_category` получил `key`, уже существующий у этого тенанта
  (уникальность пары `tenant_id, key`). HTTP 409.
- **Вероятные причины:** повторный вызов сида без идемпотентности; попытка завести
  категорию-дубликат вручную.
- **Что проверить:** существующие категории тенанта (`request_categories`);
  если нужна та же категория — использовать существующую строку, а не новую.

## ERR-GUESTS-001 — активное проживание не найдено

- **Что значит:** операция персонала (`reissue_access_code`, `check_out`) не нашла
  Stay с данным `id` в статусе `checked_in` у текущего тенанта. Чужой и
  несуществующий Stay неразличимы (RLS, P-4). HTTP 404.
- **Вероятные причины:** гость уже выехал (Stay в `checked_out`); устаревший id;
  вызов в контексте не того тенанта.
- **Что проверить:** активные проживания — `python -m hospitality.tools.checkin --list`;
  логи по `correlation_id` (тот ли `tenant_id`).
- Отказ ПРИВЯЗКИ гостя (неверный код) — не этот код и вообще не `AppError`:
  гость получает штатный auth-only ответ, в логах — WARNING `guest_code_rejected`.

## ERR-GUESTS-002 — комната уже занята активным проживанием

- **Что значит:** `check_in` в комнату, где уже есть Stay в `checked_in`
  (partial unique `uq_stays_tenant_room_checked_in`). HTTP 409. Два активных
  Stay на комнату не поддерживаются (семья = один Stay, код многоразовый,
  ADR-008 §3).
- **Вероятные причины:** вчерашнего гостя не выписали (`--check-out-now`);
  повторное заселение вместо перевыпуска кода (`--reissue`).
- **Что проверить:** `python -m hospitality.tools.checkin --list` (просроченные
  Stay там помечены); если гость реально выехал — оформить выезд и повторить
  заселение.

## ERR-GUESTS-003 — конкурентный перевыпуск кода заселения

- **Что значит:** два перевыпуска кода одного Stay столкнулись; проигравший
  отвергнут partial unique индексом активного кода. HTTP 409.
- **Вероятные причины:** двойной клик/двойной запуск CLI.
- **Что проверить:** ничего чинить не нужно — повторить операцию; действующий
  код — у того, кто успел первым (или у повтора).

## ERR-GUESTS-004 — новый срок выезда в прошлом

- **Что значит:** `extend_stay` получил `check_out_at`, который уже наступил.
  HTTP 422. «Продление в прошлое» — это выезд, для него есть `check_out`.
- **Вероятные причины:** ошибка вызывающего кода (кабинет считает срок сам,
  из UI это состояние недостижимо).
- **Что проверить:** логи по `correlation_id` — какой срок был запрошен.

## ERR-GUESTS-005 — хранилище ссылок привязки недоступно

- **Что значит:** выпуск bind-ссылки не смог записать токен в Redis
  (spec 0033 §6, fail-closed). HTTP 503. Заселение при этом НЕ ломается:
  страница показывает карточку без QR — гость входит по коду.
- **Вероятные причины:** Redis упал/недоступен по сети.
- **Что проверить:** лог `bind_link_backend_unavailable`; здоровье Redis
  (`/health/ready`). После восстановления — «Показать QR» одним нажатием.

## ERR-GUESTS-006 — ссылка привязки истекла или уже использована

- **Что значит:** гость открыл bind-ссылку, чей токен не нашёлся в Redis:
  TTL (120 с) вышел, ссылка уже потреблена (GETDEL одноразов), чужой тенант
  или Redis недоступен — исходы намеренно неразличимы. HTTP 403 с подсказкой
  «попросите показать QR ещё раз или введите код». В spec 0033 §9 код назван
  «ERR-GUESTS-BINDLINK-EXPIRED»; в каталоге — номерной формат R-8.
- **Вероятные причины:** гость замешкался (>2 минут); повторное открытие
  ссылки из истории браузера; рестарт Redis.
- **Что проверить:** это штатный путь — ресепшен перевыпускает QR одним
  нажатием; массовые отказы — лог `bind_link_backend_unavailable` (Redis).

## ERR-WEB-001 — неизвестный отель в адресе веб-чата

- **Что значит:** slug тенанта из URL комнатного QR (`/g/{slug}/…`) не найден в
  реестре. HTTP 404. Slug — публичная строка, не секрет (ADR-008 §6).
- **Вероятные причины:** опечатка при печати QR; QR старого/переименованного
  тенанта; сканеры перебирают адреса (шум).
- **Что проверить:** `SELECT slug FROM tenants`; содержимое напечатанного QR.

## ERR-WEB-002 — веб-чат: строгий auth-only

- **Что значит:** запрос к чату без валидной гостевой сессии (нет cookie,
  сессия отозвана, гость выехал или наступил `check_out_at`). HTTP 401 со
  статическим текстом («отсканируйте QR и введите код» + телефон ресепшена из
  `TenantConfig.reception_phone`) — **LLM не вызывался**, заявок нет (Q7/Q8,
  решение 22.07). Это штатный ответ, не сбой.
- **Вероятные причины:** первый заход гостя (до ввода кода); выезд (Q8);
  чистка cookie; сканеры.
- **Что проверить:** массовые 401 с одного адреса — сканер (шум, лимитов LLM
  не тратит); жалоба живого гостя — проверить Stay комнаты
  (`python -m hospitality.tools.checkin --list`).

## ERR-WEB-003 — код заселения не подошёл

- **Что значит:** привязка тройкой тенант+комната+код не удалась. HTTP 403.
  Причина гостю (и в HTTP-ответе) намеренно не уточняется: «нет активного
  Stay» и «код неверный» неразличимы — иначе по разнице ответов перечисляются
  занятые комнаты. В логах причина есть: WARNING `guest_code_rejected`
  (`reason: no_stay | code_mismatch`).
- **Вероятные причины:** опечатка гостя; код перевыпущен (`--reissue` — старый
  погашен); QR чужой комнаты; гость выехал.
- **Что проверить:** лог `guest_code_rejected` по комнате; активный Stay
  (`checkin --list`); при потере кода — перевыпуск.

## ERR-WEB-004 — превышен лимит попыток ввода кода

- **Что значит:** по паре (tenant, room) исчерпан лимит попыток привязки
  (`GUEST_CODE_VERIFY_RATE_LIMIT_*`, spec 0027 §3.3). HTTP 429. Ключ — комната,
  а не клиент: перебор кода с многих устройств не обходит лимит (ADR-008 §3).
- **Вероятные причины:** подбор кода (вчерашний гость сфотографировал QR);
  гость многократно ошибается.
- **Что проверить:** лог `guest_web_code_rate_limited` и метрика
  `guest_rate_limited_total{scope="guest_code_verify"}`; систематический
  подбор по одной комнате — перевыпустить код и предупредить ресепшен.
  Redis недоступен → fail-open (пространство кода 10⁶ — spec 0033 Ф-2;
  основной путь привязки теперь QR-ссылка вовсе без ввода).

## ERR-WEB-005 — превышен лимит потребления ссылок привязки

- **Что значит:** с одного IP слишком много попыток открыть bind-ссылку
  (`GUEST_BIND_LINK_CONSUME_RATE_LIMIT_*`, spec 0033 §9). HTTP 429. Токен
  непереборный (256 бит) — лимит лишь гасит шум сканеров. Лимит просторный:
  гости за NAT отеля делят один адрес.
- **Вероятные причины:** сканер/бот; в худшем случае — час пик заселений
  за общим NAT (поднять лимит).
- **Что проверить:** лог `guest_bind_link_rate_limited` и метрика
  `guest_rate_limited_total{scope="guest_bind_link_consume"}`; жалобы живых
  гостей в час пик — увеличить `GUEST_BIND_LINK_CONSUME_RATE_LIMIT_ATTEMPTS`.

## ERR-AI-001 — LLM-провайдер не ответил (таймауты исчерпали ретраи)

- **Что значит:** AI Gateway сделал `LLM_MAX_ATTEMPTS` попыток вызова провайдера,
  каждая упала по таймауту (`LLM_TIMEOUT_SECONDS`). В `llm_call_log` осталась
  строка со статусом `timeout`. HTTP 503.
- **Вероятные причины:** деградация/инцидент у провайдера (status.anthropic.com);
  сетевые проблемы между сервером и API; слишком низкий `LLM_TIMEOUT_SECONDS`
  для длинных ответов.
- **Сколько ждал гость:** таймауты плюс паузы между попытками — с issue #46
  попытки идут не подряд: пауза `LLM_RETRY_BACKOFF_BASE_SECONDS × 2^(попытка−1)`
  с разбросом [0.5×, 1×] и потолком в один `LLM_TIMEOUT_SECONDS` (ADR-017;
  формула — канон ADR-009). При умолчаниях это ~3 секунды сверх 90.
- **Что проверить:**
  1. Логи по `correlation_id`: события `llm_call_timeout` (номер попытки) — все ли
     вызовы страдают или единичный.
  2. Статус-страницу провайдера; при инциденте канал обязан деградировать в
     не-AI путь (FOUNDATION §7.8) — заявки создаются без LLM.
  3. Если таймауты только на длинных запросах — поднять `LLM_TIMEOUT_SECONDS`.

## ERR-AI-002 — дневной бюджет LLM тенанта исчерпан

- **Что значит:** записанный расход тенанта за текущие UTC-сутки (сумма
  `cost_usd` в `llm_call_log`) **плюс** резервы вызовов, идущих прямо сейчас
  (`llm_budget_reservation`), перешагнул `LLM_TENANT_DAILY_BUDGET_USD`; вызов
  отвергнут ДО обращения к провайдеру (§7.2: бюджеты и лимиты тенантов).
  HTTP 429 с `Retry-After` до конца UTC-суток. Для гостя это значит: бот
  отвечает заглушкой, а каждое сообщение уходит эскалацией к персоналу
  (деградация §7.8). Сюрпризом это быть не должно — на 80% лимита приходит
  ERR-OPS-006 (issue #103).
- **Вероятные причины:** всплеск диалогов у тенанта; слишком низкий бюджет для
  реальной нагрузки; цикл в вызывающем коде, жгущий токены.
- **Что проверить:**
  1. Сколько потрачено и сколько лимита — прямо в метриках, без SQL и без роли
     в БД: `curl -s https://staging.necturn.com/metrics | grep llm_daily_`
     (по тенанту — `llm_daily_spend_usd` и `llm_daily_budget_usd`).
     **Метрика считает только записанный расход, без резервов** (ADR-017): она
     про потраченные деньги, поэтому в момент отказа показывает чуть меньше
     лимита. Разница — размер резервов вызовов в полёте, порядка цента на вызов.
  2. `SELECT count(*), sum(cost_usd) FROM llm_call_log WHERE created_at >= date_trunc('day', now())`
     из тенантной сессии — на что именно ушло (по `prompt_hash` видно,
     один ли промпт крутится в цикле). **Запрос без фильтра тенанта и потому
     врёт под ролью суперпользователя — issue #252.**
  3. Если расход легитимен — поднять `LLM_TENANT_DAILY_BUDGET_USD` в `.env` и
     перезапустить `app` и `worker` (Phase 0: лимит общий для всех тенантов;
     пер-тенантный — конфиг тенанта, Phase 1 — spec 0014).
  4. Отказ держится, а расход в метрике мал — посмотреть резервы:
     `SELECT count(*), sum(amount_usd) FROM llm_budget_reservation WHERE reserved_until > now()`
     из тенантной сессии. Живых резервов там столько, сколько вызовов идёт
     прямо сейчас; истёкшие бюджет не держат и удаляются следующим вызовом
     сами. Ничего перезапускать и чистить руками не нужно — аренда короткая
     (`LLM_MAX_ATTEMPTS × LLM_TIMEOUT_SECONDS` + паузы + 30 с, ADR-017).

## ERR-AI-003 — ошибка LLM-провайдера (не таймаут)

- **Что значит:** провайдер ответил ошибкой API (401/403/429/5xx, невалидный запрос,
  сеть). Не ретраится (ретрай — только по таймауту); в `llm_call_log` — строка со
  статусом `error`. HTTP 502.
- **Вероятные причины:** невалидный/отозванный `ANTHROPIC_API_KEY`; исчерпан
  rate limit аккаунта у провайдера; инцидент провайдера.
- **Что проверить:**
  1. Логи по `correlation_id`: событие `llm_call_failed` содержит текст ошибки SDK.
  2. Ключ и лимиты в консоли провайдера (docs/runbooks/secrets.md — ротация).

## ERR-AI-004 — вызов инструмента не соответствует контракту

- **Что значит:** модель попросила вызвать AI-инструмент (Task 0015, §7.3) с
  аргументами вне его контракта — неизвестный `category_key` (не из enum,
  выданного модели), `request_id` вне снапшота открытых заявок этого диалога
  (`cancel_service_request`, spec 0025: попытка отменить чужую или уже закрытую
  заявку), невалидные поля или несуществующий инструмент. HTTP 422.
  Оркестратор НЕ отдаёт эту ошибку гостю: он превращает её в эскалацию к
  сотруднику (`needs_human`), заявка при этом не создаётся (и не отменяется).
- **Вероятные причины:** у тенанта не настроены категории заявок (пустой enum);
  рассинхрон: категорию удалили между сборкой инструмента и исполнением; модель
  отклонилась от enum (низкоресурсный язык, слабая модель — риск, который ловит
  golden-set §7.7).
- **Что проверить:**
  1. Логи по `correlation_id`: события `tool_execution_failed` / `unknown_tool_call`
     (имя инструмента и код).
  2. Есть ли у тенанта категории заявок (`list_categories`); при пустом наборе —
     завести категории (сид демо-тенанта / кабинет персонала Phase 1).
  3. Если код повторяется на конкретном языке — это сигнал для ревизии выбора
     модели/промпта по данным bake-off'а (spec 0015).

## ERR-OPS-001 — /health/ready недоступен (алерт)

- **Что значит:** алертер (`hospitality.tools.alerter`, Task 0018) несколько опросов
  подряд (порог `ALERT_READY_FAILURE_THRESHOLD`) не получил 200 от `/health/ready`:
  либо недоступна зависимость (Postgres/Redis — какие именно, видно в `checks` в
  тексте алерта), либо приложение не отвечает вовсе (`connection error`).
  Код выбрасывается не через `AppError` — это алерт платформенного уровня,
  correlation id у внешнего опроса нет.
- **Вероятные причины:** упал контейнер `db`/`redis`/`app`; кончилось место на
  диске; VPS перегружен; деплой дольше пары минут (после него придёт ✅).
- **Что проверить:** пошаговая диагностика — docs/runbooks/alerts.md#err-ops-001.

## ERR-OPS-002 — всплеск ошибок 5xx (алерт)

- **Что значит:** прирост суммы `http_requests_total{status="5xx"}` из `/metrics`
  за один интервал опроса достиг порога `ALERT_ERROR_SPIKE_THRESHOLD`. Приложение
  живо, но какая-то доля запросов падает необработанными ошибками.
- **Вероятные причины:** баг свежего деплоя; недоступная интеграция на горячем
  пути; см. связку с ERR-PLATFORM-001 (каждый 5xx оставил след в логах и Sentry).
- **Что проверить:** пошаговая диагностика — docs/runbooks/alerts.md#err-ops-002.

## ERR-OPS-003 — воркер не подаёт признаков жизни (алерт)

- **Что значит:** метрика `worker_heartbeat_age_seconds` из `/metrics` (возраст
  отметки, которую воркер обновляет каждым кругом цикла) превысила
  `ALERT_WORKER_HEARTBEAT_MAX_AGE_SECONDS` — по умолчанию 5 минут, то есть
  десять пропущенных пульсов. Процесс воркера мёртв, завис или не может писать
  в БД. По существу: **вся доставка событий стоит** — уведомления службам о
  новых заявках, напоминания о невзятых и ретеншн молча не идут, при том что
  API отвечает и `/health/ready` зелёный (issue #136). Алерт шлёт алертер, а
  не воркер: о собственной смерти процесс доложить не может.
- **Вероятные причины:** контейнер `worker` упал или остановлен (OOM, неудачный
  деплой, `docker stop`); процесс жив, но завис в сетевом вызове подписчика;
  Postgres недоступен из воркера (тогда рядом в логах — ERR-OPS-005 и
  ERR-EVENTS-003, а `/health/ready` красный и пришёл ERR-OPS-001).
- **Что проверить:** пошаговая диагностика — docs/runbooks/alerts.md#err-ops-003.

## ERR-OPS-004 — очередь событий растёт (алерт)

- **Что значит:** метрика `outbox_pending_events` (события, не доставленные и не
  похороненные) выше `ALERT_OUTBOX_DEPTH_THRESHOLD` — по умолчанию 100 при
  рабочем фоне в единицы. Вторая линия того же симптома, что ERR-OPS-003, и
  ловит она случай, которого пульс не видит: цикл жив и отмечается, но очередь
  не разбирается — доставки падают по кругу (backoff, ADR-009) или воркер не
  успевает за потоком.
- **Вероятные причины:** сломан обработчик или его зависимость (Telegram Bot
  API, LLM-шлюз) — события уходят в повтор и копятся; массовая публикация
  событий (импорт, разовый всплеск) — тогда очередь разберётся сама и придёт ✅;
  воркер стоит (в этом случае раньше пришёл ERR-OPS-003).
- **Что проверить:** пошаговая диагностика — docs/runbooks/alerts.md#err-ops-004.

## ERR-OPS-005 — пульс воркера не записался

- **Что значит:** цикл воркера не смог обновить свою отметку «я жив» в таблице
  `worker_heartbeats` (лог-событие `worker_heartbeat_failed`). Цикл при этом не
  падает: доставка событий важнее отметки о ней. Последствие — отметка стареет,
  и через `ALERT_WORKER_HEARTBEAT_MAX_AGE_SECONDS` придёт ERR-OPS-003 про
  «мёртвый» воркер, который на самом деле жив. Это не ложная тревога: воркер без
  БД всё равно ничего не доставляет.
- **Вероятные причины:** Postgres недоступен из воркера (тот же класс причин,
  что у ERR-EVENTS-003); миграции не применены (нет таблицы `worker_heartbeats`
  — код старше миграции 0022 быть не может, но откат образа без отката БД
  такое даёт).
- **Что проверить:**
  1. Логи worker: `worker_heartbeat_failed` — трасса; рядом почти наверняка
     `worker_iteration_failed` (ERR-EVENTS-003) — причина общая.
  2. `/health/ready` приложения — статус `postgres`.
  3. Отметка на месте:
     `SELECT name, beat_at, now() - beat_at AS age FROM worker_heartbeats;`
     Строки нет (удалена руками, восстановление из старого дампа) — следующий
     успешный круг воркера заведёт её заново, отдельных действий не нужно;
     до этого момента ERR-OPS-003 не придёт (пустая метрика = «не знаю»).

## ERR-OPS-006 — дневной бюджет LLM на исходе (алерт)

- **Что значит:** расход тенанта за текущие UTC-сутки (`llm_daily_spend_usd`)
  достиг доли `ALERT_LLM_BUDGET_RATIO` (по умолчанию 80%) от его дневного лимита
  (`llm_daily_budget_usd`). Пока ничего не сломано — это предупреждение о том,
  что будет: на 100% gateway начнёт отвергать вызовы (ERR-AI-002), и бот молча
  перестанет отвечать гостям до конца UTC-суток, переводя каждое сообщение в
  эскалацию к персоналу. Алерт заведён именно для того, чтобы у команды были
  часы на реакцию, а не жалобы гостей постфактум (issue #103).
- **Вероятные причины:** обычный высокий день отеля (лимит просто мал); всплеск
  диалогов или наплыв ботов в веб-чате; цикл в коде, жгущий токены на одном и
  том же промпте; смена модели на более дорогую.
- **Что проверить:** пошаговая диагностика — docs/runbooks/alerts.md#err-ops-006.

## ERR-OPS-008 — свежего бэкапа БД нет (алерт)

> Номер 007 зарезервирован за issue #264 (алертер перестал видеть `/metrics`) —
> номера каталога не переиспользуются, поэтому эта статья 008.

- **Что значит:** алертер смотрит в каталог бэкапов сервера (`ALERT_BACKUP_DIR`,
  смонтирован в контейнер только для чтения) и не видит там ни одного файла
  `hospitality-*.dump.age` свежее `ALERT_BACKUP_MAX_AGE_HOURS` (по умолчанию 30
  часов — суточный cron в 03:00 UTC плюс запас). Значит, восстанавливать в
  аварии нечего или почти нечего: RPO ≤ 24 ч (§10.10) уже не выполняется.
  Снимки перед миграцией (`pre-migrate-*.dump.age`) в счёт не идут намеренно —
  иначе умерший ночной cron маскировался бы снимками деплоя (docs/runbooks/restore.md).
- **Вероятные причины:** на сервере нет публичного ключа `BACKUP_AGE_RECIPIENT`
  или бинарника `age` — с issue #81 бэкап тогда не создаётся вовсе (fail-closed:
  открытый дамп с перепиской гостей недопустим); кончилось место на диске; не
  запускается cron; контейнер `db` мёртв, и `pg_dump` падает; каталог бэкапов
  переехал, а `ALERT_BACKUP_DIR` или его монтирование в compose остались старыми.
- **Что проверить:** пошаговая диагностика — docs/runbooks/alerts.md#err-ops-008.

Отдельный случай того же кода — **«каталог бэкапов не виден алертеру»**: каталог
не открывается из контейнера (нет монтирования, каталог удалён, нет прав). Это не
«данных нет, значит всё хорошо», а такая же слепота, как отсутствующий бэкап,
поэтому код тот же, а причина названа прямо в тексте алерта.
