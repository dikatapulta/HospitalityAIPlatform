# Выгрузка Opera: подключение отеля (токен, отчёт, задача планировщика, включение)

> **Роль:** шаги процедуры — что делает IT отеля и что делаем мы, чтобы отчёт Opera раз в
> несколько минут сам попадал в платформу. Контракт файла, коды ответов и числа — у владельца,
> [spec 0058](../specs/0058-pms-stay-sync.md) §2.4; решение и его причины —
> [ADR-004](../adr/ADR-004-pms-stay-source-opera-report-snapshot.md). Коды ошибок —
> [errors.md](errors.md), `ERR-PMS-*`.

Порядок: токен (мы) → отчёт и задача (IT отеля) → проверка кодом 409 → включение (мы, по
слову основателя). До включения файлы не сохраняются — так IT проверяет всё заранее, а номера
броней не ложатся в базу раньше допсоглашения к договору.

## Токен

Выпускает тот, у кого есть доступ к серверу, — внутри контейнера `app` своего контура. Гостевая
копия:

```bash
cd /home/deploy/hospitality-pilot
docker compose -f docker-compose.staging.yml --env-file .env exec app \
    python -m hospitality.tools.pms_token <код-отеля>
```

Staging — то же из `/opt/hospitality`. Команда печатает токен **один раз**; в базе остаётся
только его хэш. Передать IT отеля так, как передаются пароли (не в рабочий чат и не в
репозиторий), — строка в [secrets.md](secrets.md), раздел 4. Перевыпуск — та же команда:
прежний токен перестаёт работать сразу, задача со старым получает 401 (`ERR-PMS-002`), пока IT
не впишет новый.

## Шаг 1. Отчёт в Opera (IT отеля)

В Reports Scheduler — отчёт «гости в доме» (in-house: только заселённые на момент выгрузки),
формат Delimited Data, кодировка UTF-8, раз в 5 минут (допустимо от 3 до 10; другой интервал —
сказать нам: его же ставим в профиль отеля, `pms_snapshot_interval_minutes`).

- Первая строка — заголовок. Колонки — **ровно** `room`, `confirmation_no`, `arrival`,
  `departure` и, если можно, `guests` (число гостей в номере); порядок любой.
- **Никаких имён, телефонов, почты и других колонок.** Файл с лишней колонкой отвергается
  целиком (`ERR-PMS-001`, `reason: extra_column`) — это решение о составе данных, а не
  придирка формата.
- Разделитель — запятая, точка с запятой или табуляция; даты — `2026-11-02` или `02.11.2026`.
- Файл больше 1 МБ не принимается — отчёт «в доме» на 350 номеров весит десятки КБ.

Образец:

```
room;confirmation_no;arrival;departure;guests
305;123456;02.11.2026;04.11.2026;2
410;654321;01.11.2026;06.11.2026;1
```

## Шаг 2. Адрес

`POST https://<домен контура>/integrations/pms/<код-отеля>/opera-report`, заголовок
`Authorization: Bearer <токен>`, тело — файл как есть. Домен гостевой копии —
`app.necturn.com`, staging — `staging.necturn.com`.

## Шаг 3. Задача планировщика Windows (IT отеля)

На компьютере, куда Opera кладёт отчёт: задача в «Планировщике заданий» каждые 5 минут, «Выполнять
вне зависимости от входа пользователя». Действие — PowerShell-скрипт (образец; путь к папке
отчёта — тот, что задан в Reports Scheduler):

```powershell
$maxAgeMinutes = 10   # два интервала отчёта из шага 1
$report = Get-ChildItem "D:\OperaReports\inhouse*" |
    Sort-Object LastWriteTime -Descending | Select-Object -First 1
if ($null -eq $report -or
    $report.LastWriteTime -lt (Get-Date).AddMinutes(-$maxAgeMinutes)) {
    Write-Output "no fresh Opera report"; exit 1
}
Invoke-RestMethod -Method Post `
    -Uri "https://app.necturn.com/integrations/pms/<код-отеля>/opera-report" `
    -Headers @{ Authorization = "Bearer <токен>" } `
    -InFile $report.FullName -ContentType "text/csv"
```

Старый файл скрипт не шлёт: платформа считает снимком момент приёма, и если Opera перестала
писать отчёт, а задача продолжит слать последний файл, остановку не заметит никто. Без отправки
снимок стареет, и срабатывает алерт «данные не обновляются». Интервал не 5 минут —
`$maxAgeMinutes` вдвое больше него.

Скрипт с токеном — доступ на чтение только учётной записи задачи. Повтор того же файла в
течение минуты платформа считает повтором, а не новым снимком; больше 30 файлов в час
отвергаются (`ERR-PMS-004`).

## Проверка (до включения)

Запустить скрипт руками в консоли PowerShell и прочитать ответ там: журнал задачи показывает
только код завершения, без ответа платформы.

| Ответ | Что значит |
|---|---|
| 409 `ERR-PMS-005` | Всё настроено верно: токен работает, файл дошёл, приём у отеля ещё не включён — файл не сохранён |
| 401 `ERR-PMS-002` | Токен или код отеля в адресе не тот |
| 400 `ERR-PMS-001` | Файл не по шагу 1 — в ответе номер строки и причина |
| 413 / 429 | `ERR-PMS-003` / `ERR-PMS-004` — [errors.md](errors.md) |
| `no fresh Opera report` | Запроса не было: в папке нет отчёта моложе `$maxAgeMinutes` — проверить путь в скрипте и расписание отчёта (шаг 1) |

## Включение (наша сторона, только по слову основателя)

Предусловия: подписанное допсоглашение (номер брони — в составе данных договора) и письмо отелю
о новой функции (spec 0058 §4); в образе контура — кабинет PR 5 серии #122 (полосы «данные из
Opera…» и расхождения на странице заселения): без него ресепшен не увидит, что выгрузка
остановилась или не сходится с кабинетом.

Включает ключ профиля отеля `"pms_source": "opera_report"`. Профиль `pilot-hotel.local.json` —
копия `ops/onboarding/pilot-hotel.json` того коммита, на котором стоит копия, плюс этот ключ (и
`"pms_snapshot_interval_minutes"`, если IT поставил интервал не 5 минут); квоты и room service
из прежнего конфига онбординг переносит сам. Файл основатель кладёт в каталог копии, затем —
команда онбординга с этим файлом из абзаца «Квоты бесплатного» [pilot-copy.md](pilot-copy.md)
(её предусловия — про квоты, здесь они не нужны); файл после прогона удалить с сервера. Профили
без ключа `pms_source` его дальше не меняют. Сразу после — первый же файл отвечает
`{"accepted": true, "rows": N}`, через минуту воркер применяет снимок: гости из Opera появляются
на странице заселения, в журнале изменений — «Заселение из Opera».

Выключение — тот же путь с `"pms_source": "manual"`: файлы снова получают 409, заведённые из
Opera проживания остаются и дальше ведутся руками (и автовыездом по сроку, spec 0043).

Остановилась выгрузка — алерт `ERR-GUESTS-010` ([alerts.md](alerts.md#err-guests-010)).
