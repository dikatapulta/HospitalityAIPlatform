# Runbook: гостевая копия (пилот) на staging-сервере

> Временный контур для живых гостей пилотного отеля — решение основателя
> 29.09.2026, отступление от [ADR-006](../adr/ADR-006-hosting-data-residency-kz.md)
> (раздел «Временное отступление») до переезда в РК (#49). Этапы пилота — #384.

## Что это и где живёт

Вторая копия стека на том же сервере, что staging (Hetzner, `deploy@<IP>` —
[deploy.md](deploy.md)). Код тот же, образ тот же из GHCR; своё — база, Redis,
секреты, адрес и расписание обновлений.

| Что | Staging | Гостевая копия |
|---|---|---|
| Каталог | `/opt/hospitality` | `/home/deploy/hospitality-pilot` (в `/opt` у `deploy` нет прав, `sudo` нет) |
| Compose-проект (префикс контейнеров) | `hospitality` | `hospitality-pilot` |
| Адрес | `staging.necturn.com` | `app.necturn.com` — туннель `hospitality-pilot` |
| Снаружи наблюдает | проверка UptimeRobot `staging` | проверка UptimeRobot `app (гости)` — первая и главная ([founder-actions-pilot-launch.md](founder-actions-pilot-launch.md) §6; упала — [alerts.md](alerts.md), «Внешний монитор») |
| Данные | синтетика | живые гости пилотного отеля |
| Обновление | само, на каждый merge в `main` (CI) | только по слову основателя, руками (ниже) |
| Ночной бэкап | cron 03:00 | cron 03:15 с путями копии — строка в «[Ночной бэкап](#ночной-бэкап)» |
| Копия вне сервера | `make backup-fetch` → `backups/` | `make backup-fetch-pilot` → `~/necturn-pilot-backups`, 14 суток — «[Копия вне сервера](#копия-вне-сервера-раз-в-неделю)» |
| Telegram-бот | есть | **нет** (решение основателя 29.09): персонал работает в кабинете |

Код отеля (slug) — только в `.env` копии (`TELEGRAM_TENANT_SLUG`), в
репозиторий не пишется (решение основателя 20.09). Гостевой адрес —
`https://app.necturn.com/g/<код-отеля>/<номер>`, кабинет —
`https://app.necturn.com/staff`.

**Без Telegram-бота** эскалации («🚨 ЧП», «гостю нужен сотрудник», «ИИ
недоступен») адресата не имеют, пока не включён этап 3 (раздел
«[Этап 3](#этап-3-заявки-только-в-кабинете)» — с ним они приходят карточками в
кабинет): подписчик пишет в лог `ERR-TELEGRAM-002` и помечает событие
доставленным. Гостя о ЧП текст перехвата отправляет звонить на
ресепшен (spec 0034 §3); при сбое ИИ до этапа 3 — тоже: звать некому, и вместо
«уже зову сотрудника» гость читает «позвоните на ресепшен» (spec 0051), с этапом 3
зовёт карточка в кабинете (spec 0039 §6). Алерты основателю идут отдельным алерт-ботом
(`TELEGRAM_ALERT_*`) в тот же чат, что у staging, с префиксом «[pilot]» — когда в `.env`
копии есть строка `SENTRY_ENVIRONMENT=pilot` (#389, абзац «Метка контура» в «Обновить
копию»); без неё — «[staging]», как у staging.

## Обновить копию (только по слову основателя)

Ставится версия, которую основатель уже проверил на staging.

```bash
ssh deploy@<IP>
cd /home/deploy/hospitality-pilot
# 1. Скрипты и compose-файл CI обновляет только в /opt/hospitality — взять оттуда:
cp /opt/hospitality/deploy.sh /opt/hospitality/backup.sh /opt/hospitality/docker-compose.staging.yml .
# 2. Образ — тот, что сейчас на staging (строка APP_IMAGE= в /opt/hospitality/.env):
grep '^APP_IMAGE=' /opt/hospitality/.env
./deploy.sh ghcr.io/dikatapulta/hospitality-app:<sha>
```

`deploy.sh` снимает шифрованный снимок базы копии перед миграцией, применяет
миграции, поднимает стек и проверяет `/health/ready`. Снаружи:
`curl -s -o /dev/null -w '%{http_code}' https://app.necturn.com/health/ready` → `200`.
С compose-файлом #407 `deploy.sh` ждёт и туннель копии: не соединился с Cloudflare —
деплой падает строкой `container hospitality-pilot-cloudflared-1 is unhealthy`
([deploy.md](deploy.md), часть D). Лучшее время — днём между заездом и выездом. **Обновление на образ с #399** —
переход персонала на логины: войти по email после него не сможет никто,
порядок — «Первый менеджер кабинета» ниже. **Обновление на образ с #472**
(миграция `0033`, [spec 0045](../specs/0045-services-and-levels.md) §7): бывший
ресепшен сам становится «Сотрудником» со службой «Ресепшен» и заселяет, как
раньше; остальным сотрудникам менеджер в тот же день отмечает службы на
«Сотрудниках» («Изменить» у строки с пометкой «Служба не выбрана — заявок не
видит»). **Образ с разделением очереди** (PR 2 #472, spec 0045 §4–§5) — каждый
видит и ведёт только заявки своих служб, ресепшен и менеджер — все. Сотрудник
без службы с этим образом не видит ни одной заявки: если копия обновляется
сразу на него (минуя образ одного PR 1), менеджер отмечает службы сразу после
обновления. Сигнал кабинета: заявки службы, у которой на «Сотрудниках» нет ни
одного активного сотрудника, ресепшен и менеджер слышат сразу, как раньше;
когда у службы появляется сотрудник, её обычные заявки они слышат только через
два срока напоминания (`request_reminders` показывает сроки), срочные и
эскалации — по-прежнему сразу. **Образ с доской «Выезды и уборка»** (#476):
обновление раздел не включает, и служба «Уборка» у сотрудников — тоже; включение —
«Доска „Выезды и уборка“» ниже.
**Образ с хранилищем файлов** (#491, [spec 0047](../specs/0047-file-storage.md),
миграция `0036`): у копии появляется свой том `hospitality-pilot_files_data`
(свой каталог — свой проект compose), его архив кладёт ночной `backup.sh`
рядом с дампом. Ключ `FILE_ENCRYPTION_KEY` в `.env` копии **не заводится**,
пока на копии нет приёма файлов: без ключа файлы отвечают ERR-FILES-005, всё
остальное работает. Файлы гостя на копии — только после переезда в РК
(решение основателя 27.10); фото блюд — вместе с room service (#418): тогда
ключ генерируется на сервере (`openssl rand -base64 32`) и сразу кладётся в
менеджер паролей основателя ([secrets.md](secrets.md), раздел 2а).
**Образ с PR #344** (28.10) сам, без флага, начинает наполнять менеджеру блок «Гости
спрашивали, а ответа не было» пересказами вопросов гостей: обновлять копию на него —
только после подписанного допсоглашения, абзац «Вопросы без ответа» ниже.
**Метка контура** (#389): compose-файл берёт имя контура из `.env`. Без строки
`SENTRY_ENVIRONMENT=pilot` алерты копии приходят с префиксом «[staging]», её ошибки
помечены в Sentry как staging — и алерт о живом отеле не отличить от алерта синтетики.
Один раз, в каталоге копии до обновления:

```bash
grep '^SENTRY_ENVIRONMENT=' .env     # пусто — дописать; другое значение — исправить на pilot
echo 'SENTRY_ENVIRONMENT=pilot' >> .env
```

Действует с первого обновления, взявшего compose-файл с #389 (шаг 1 выше). Приёмка после
него: `docker compose -f docker-compose.staging.yml --env-file .env exec alerter env | grep
SENTRY_ENVIRONMENT` → `SENTRY_ENVIRONMENT=pilot`.

**Откат** — [deploy.md](deploy.md), часть C, в каталоге копии:
`./deploy.sh ghcr.io/dikatapulta/hospitality-app:<прежний-sha>`. Восстановление
базы из снимка — [restore.md](restore.md), случай В, из каталога копии: там
`<каталог>` — `/home/deploy/hospitality-pilot`, том БД — `hospitality-pilot_db_data`
(staging на том же сервере — `hospitality_db_data`, его не трогать). Приёмка —
`curl` адреса копии из «Обновить копию», а не `make smoke-staging` из шага 7
случая А: он проверяет staging. Откат ниже
образа, записавшего в конфиг тенанта новое поле, молча лишает бота справочника:
старый образ поля не знает и не читает конфиг целиком (#387). У копии такие
поля — `reception_room_dial` с `5907bcc` и `escalation_category_key` — с
первой записи конфига образом с #292, любой (справочник из кабинета,
онбординг): без службы поле пишется как `null`, и старый образ его так же не
прочтёт; перед откатом на образ старше PR #693 (#387) ключ снимают из
`tenants.config`, образ с PR #693 незнакомое поле читает ([deploy.md](deploy.md),
часть C, абзац «Поле конфига тенанта»). Так же —
`room_service` с образа с #508 и `mentor_enabled` с образа с #512: рецепты «Откат на
образ старше #508» и «… #512» в [deploy.md](deploy.md), часть C. Откат
ниже образа с #292 — только по рецепту «Откат на образ старше #292» в
[deploy.md](deploy.md), часть C, с psql из этого каталога: снятие ключа, правка
карточек эскалаций (старый образ не читает `origin = 'escalation'`, и кабинет
не откроется) и подъём старого образа мимо `deploy.sh` — через него откат
встанет на миграции `0029`.

## Ночной бэкап

Строка в `crontab -l` пользователя `deploy`. Все три переменные обязательны: у
`backup.sh` `COMPOSE_FILE` и `ENV_FILE` по умолчанию смотрят в
`/opt/hospitality`, и строка с одним `BACKUP_DIR` каждую ночь клала бы в каталог
копии дамп базы **staging**. Алерт ERR-OPS-008 проверяет только свежесть файлов
в каталоге и промолчал бы.

```
15 3 * * * COMPOSE_FILE=/home/deploy/hospitality-pilot/docker-compose.staging.yml ENV_FILE=/home/deploy/hospitality-pilot/.env BACKUP_DIR=/home/deploy/hospitality-pilot/backups /home/deploy/hospitality-pilot/backup.sh >> /home/deploy/hospitality-pilot/backups/backup.log 2>&1
```

Проверка — как у staging ([restore.md](restore.md), «Разовая настройка
расписания»): свежий `backups/hospitality-*.dump.age` и строка `OK: бэкап
создан…` в конце `backups/backup.log`. С образа #491 рядом с дампом лежит
`hospitality-*.files.tar.age` — архив тома файлов копии, и строка `OK: архив
тома файлов…` следом.

### Копия вне сервера (раз в неделю)

С машины основателя, из корня репозитория:

```bash
make backup-fetch-pilot
```

Забирает свежайший `hospitality-*.dump.age` копии в `~/necturn-pilot-backups`
(другой каталог — `PILOT_BACKUP_LOCAL_DIR`) и расшифровывает его в поток
ключом основателя — тем же, что у staging. Успех — последняя строка
`OK: бэкап расшифровывается ключом основателя и содержит дамп Postgres.`;
любая другая концовка — код выхода 1 и причина в тексте (нет ключа, нет `age`,
дамп не зашифрован) — разбор как у staging, [restore.md](restore.md),
«Шифрование».

**Срок — 14 суток, как обещано гостю** (политика §7, договор с отелем
п. 4.3.4). Файлы старше удаляет агент launchd
`com.necturn.pilot-backup-retention` — каждый час и при входе в систему, даже
если `make backup-fetch-pilot` давно не запускали. Агента ставит (и обновляет)
сам `make backup-fetch-pilot` при каждом прогоне; что удалено — в
`~/necturn-pilot-backups/retention.log`. Возраст считается от времени записи
дампа на сервере (`scp -p`), а не от скачивания. Каталог — не в `~/Desktop`:
туда macOS агенту доступа не даёт. Только macOS: на другой машине скрипт
остановится до скачивания.

Проверить агента: `launchctl print gui/$(id -u)/com.necturn.pilot-backup-retention | grep -E 'state|last exit'`.
Снять (после переезда в РК, когда копия больше не нужна):
`launchctl bootout gui/$(id -u)/com.necturn.pilot-backup-retention && rm ~/Library/LaunchAgents/com.necturn.pilot-backup-retention.plist ~/necturn-pilot-backups/*.dump.age`.

## Отель в копии

Заведён 29.09 онбордингом ([tenant-onboarding.md](tenant-onboarding.md)) с
профилем `ops/onboarding/pilot-hotel.json`, внутри контейнера копии:

```bash
docker compose -f docker-compose.staging.yml --env-file .env run --rm --no-deps -T app \
    python -m hospitality.tools.onboard_tenant ops/onboarding/pilot-hotel.json \
    --tenant-slug <код-отеля> --reception-phone "<мобильный ресепшена>" --reception-room-dial 0
```

Образ копии старше PR #763 (#181) знает этот флаг как `--slug` и на `--tenant-slug`
отвечает `unrecognized arguments` — тогда во всех командах `onboard_tenant` этого
рунбука пиши `--slug`.

Повторный запуск идемпотентен: справочник и чаты служб он переносит из прежнего
конфига всегда, телефон и цифру ресепшена (`0` — в тексте ЧП, spec 0034 §3) —
если их флаг не передан. В базе копии цифра записана 29.09, повтором после
обновления на `5907bcc`.

С образа с #786 повтор без выбора службы эскалаций в конфиге копии откажет
(«Не выбрана служба эскалаций», ничего не записано), а менеджер копии видит на
главной кабинета плашку «Не выбрана служба…». Пока не пройден шаг 5 раздела
«Этап 3: заявки только в кабинете», к команде добавлять
`--escalation-telegram-only` — копия так и работала, только молча; после шага 5
— ничего: служба переносится. Флаг снимает и плашку.

**Новые службы профиля** («Швейцар» и «Банкетный зал», #475) — только по слову
основателя. Профиль команда читает из образа, поэтому сначала копия обновляется
на образ с #475, затем — команда выше **без** `--reception-phone` и
`--reception-room-dial` (телефон, цифра и служба эскалаций переносятся из
конфига). В отчёте — «Категории: создано 2 (doorman, banquet)». Заодно меняются
подсказки ИИ у ресепшена, инженерии и IT (сейф, такси, ключ и настройка
телевизора уходят швейцару) — пока заявки на копии выключены, гость этого не
заметит. Пока у новой службы нет сотрудника на «Сотрудниках», её заявки сразу
слышат ресепшен и менеджер (spec 0045 §4).

**Справочник отеля** загружен 29.09 из локального файла основателя
(`ops/onboarding/*.local`, в репозиторий и в образ не попадает) через
`platform.config.mutate_tenant_config`. С образа `08d33f9` (21.10) его правит
менеджер на странице «Справочник отеля» в кабинете (#335).

**Первый менеджер кабинета** — `tools/staff_bootstrap` без `-T` (пароль
вводит основатель, getpass), из каталога копии и её compose-файлом — команда
шага 5 [tenant-onboarding.md](tenant-onboarding.md) с `/opt/hospitality/…`
отправила бы её в контейнер staging:

```bash
cd /home/deploy/hospitality-pilot
docker compose -f docker-compose.staging.yml --env-file .env exec app \
    python -m hospitality.tools.staff_bootstrap <ЛОГИН> --name "Имя" --tenant-slug <код-отеля>
```

Дальше персонал приглашается из кабинета. **После обновления копии на образ с
#399** email-учётки войти больше не могут: менеджер переходит путём (а) или (б)
шага 5 рунбука онбординга (для (б) — команда выше), остальных он отключает и
приглашает заново с логином — в «Сотрудниках» они помечены «без логина». Их
открытые сессии работают до своего срока, поэтому переприглашать лучше в тот же
день, а не когда человек упрётся в форму входа.

**`STAGING_ALL_FEATURES`** (#940) в `.env` копии не ставится никогда: он включает
разом все разделы и модели разделов, а в копии каждый раздел включается своим абзацем
ниже, по слову основателя. Строку, перенесённую из `.env` staging, — удалить.

**Допсоглашение с отелем** (#947, слово основателя 10.11) — предусловие каждого абзаца ниже, где
раздел даёт отелю новое: функцию, данные работников или гостей, получателя данных. Писем отелю
и сроков возражения как предусловия нет: новое обсуждается с отелем устно и закрепляется
подписанным дополнительным соглашением к договору (п. 7.3; договор вне репозитория). Разделы
кабинета персонала — одно рамочное соглашение с перечнем разделов (шаблон — юрпакет #948):
подпись отеля заменяет уведомления пп. 1.3 и 4.4.4, раздел включается с даты из перечня;
раздела нет в подписанном перечне — не включать. Функции веб-чата гостя (квоты, бронь столика,
оценки, выгрузка Opera, документы для АВР, 3D-витрина) меняют данные гостей и политику —
отдельное соглашение по тому же образцу; в него же — пункт о сведениях для уведомления гостей
при утечке (шаблон DPA N.6 п. 4, #948). Порядок — подпись, затем включение; включить можно
в день подписи. Подписывает основатель, реквизиты — вне репозитория.

**Касса передачи смены** (#469, решение основателя 24.10) — в копии только
ручной бланк: в `.env` копии `ENABLE_HANDOVER_MANUAL=true`, `ENABLE_DEMO_HANDOVER`
не ставится (демо с выдуманными суммами живым сотрудникам не показывается).
Флаг читает только `app`: после правки `.env` —
`docker compose -f docker-compose.staging.yml --env-file .env up -d app`.
Проверка — у ресепшена и менеджера в меню «Передача смены» без пометки «демо».

**Демо «Забытые вещи»** (#604) — в копии не включается никогда: `ENABLE_DEMO_LOST_FOUND`
в `.env` копии не ставится. Находки в нём выдуманы, а живая горничная, записав туда
настоящую вещь, потеряла бы её при обновлении страницы. Настоящая база находок —
новые данные (фото вещей) и отдельное решение (docs/DISCUSSION_LOG.md, «Забытые вещи»).

**Доска «Выезды и уборка»** (#476, [spec 0046](../specs/0046-checkout-turnover.md) §5) — в
копии выключена, пока отель её не согласовал. Её нет в составе сервиса по договору,
и она пишет новые данные: кто из работников проверил, убрал и принял номер, и
замечания хаускипинга (могут пересказывать гостя). Предусловие —
раздел в подписанном допсоглашении (абзац «Допсоглашение с отелем» выше).
До этого `ENABLE_TURNOVER_BOARD` в `.env` копии не ставится. После — строка
`ENABLE_TURNOVER_BOARD=true` в `.env` копии и
`docker compose -f docker-compose.staging.yml --env-file .env up -d app worker`
(воркер рассылает пуш «704 — выезд»).
Проверка — у ресепшена в меню «Выезды и уборка».

**Доска «Номера»** (#666, [spec 0061](../specs/0061-room-board.md) §7) — в копии выключена:

## Этап 3: заявки только в кабинете

Пилотный отель получает заявки только в кабинете (#384): бота у копии нет, и
каждая эскалация — ЧП, «ИИ не ответил», «бот не смог оформить» — приходит в
кабинет заявкой в службу «Ресепшен» ([spec 0039](../specs/0039-cabinet-only-staff-alerts.md) §2).
ЧП — срочной, с бейджем «🚨 срочно».

**Предусловия.** Образ на staging содержит эскалацию заявкой (#292) и сигнал
кабинета (#381): без сигнала кабинет не зовёт, и карточку в фоновой вкладке
никто не увидит. Ещё #101 ([spec 0040](../specs/0040-escalate-to-staff.md)):
без него на «позовите сотрудника» модель обещает человека текстом, и кабинет
такого гостя не видит; с ним модель зовёт инструментом — тем же флагом
`ENABLE_SERVICE_REQUESTS`, что включает заявки (шаг ниже), — и в кабинете
появляется карточка «Гость просит сотрудника». И #382: «мне плохо», «плохо с сердцем», «I feel sick»
ловит ЧП-перехват — гость получает «позвоните 0», в кабинете срочная карточка. Список предусловий — решение
основателя 13.10.2026 в #384.

1. **Заявки в подписанном допсоглашении** — строкой перечня с датой (абзац
   «Допсоглашение с отелем» выше): подпись отеля снимает уведомление за 2 рабочих
   дня по п. 1.3 договора, письма нет (слово основателя 10.11, #947). Отдельного
   согласия на карточки эскалаций с текстом гостя не ждём — решение основателя
   13.10.2026 (spec 0039 §2.9).
2. **Обновить копию** на проверенный образ — «[Обновить копию](#обновить-копию-только-по-слову-основателя)».
   **Сделано 21.10** заранее, до ответа отеля (решение основателя): копия на
   `08d33f9`, в образе #292, #381, #101 и #382. Это был и переход на логины
   (#399) — «Первый менеджер кабинета» выше. Первый прогон автовыезда (#225)
   закрыл 3 забытых проживания. Повторять шаг перед шагом 5, только если в
   `main` с тех пор вышли правки, нужные этапу.
3. **Инструктаж на стойке** (spec 0039 §3.4). Кабинет `app.necturn.com/staff`
   всегда открыт отдельной **закреплённой** вкладкой в **Chrome**, звук включён
   (первое нажатие на странице), уведомления разрешены (кнопка «Уведомления на
   компьютере»), а сайт кабинета внесён в список исключений сна — без этого
   браузер усыпляет фоновую вкладку, и кабинет молчит:
   - **Chrome:** Settings → Performance → «Always keep these sites active» →
     Add → `app.necturn.com`. Это главный шаг: одного закрепления вкладки мало.
   - **Edge** (стоит на том же компьютере ради Opera — если кабинет откроют в
     нём): Settings → System and performance → Performance → «Always keep these
     sites active» (в прежних версиях Edge — «Never put these sites to sleep») →
     Add site → `app.necturn.com`.

   Названия настроек меняются от версии к версии — брать их с экрана
   компьютера ресепшена.
4. **Проверка двухчасовым фоном** на компьютере ресепшена — **до** включения
   заявок: ни служба эскалаций, ни флаг ей не нужны, а провал после включения
   оставил бы карточки живых гостей неуслышанными. Кабинет в фоне дольше двух
   часов, пока работают в Opera; затем с другого устройства — заявка формой
   «Новая заявка» в службу «Ресепшен» (заявку службы с сотрудниками ресепшен
   слышит только через два срока, spec 0045 §4), и на стойке должен прозвучать
   сигнал. Тестовую заявку
   закрыть «Отменить» с причиной «тест». Не прозвучал — вкладку усыпили:
   вернуться к шагу 3. Шаги 5–6 — только после того, как сигнал прозвучал.
5. **Повторить онбординг со службой эскалаций.** Только после сигнала в шаге 4:
   не знаешь, прошёл ли он, — спроси основателя, сам шаг 4 с сервера не
   проверить. Телефон и цифру ресепшена не передавать — они переносятся из
   конфига:
   ```bash
   cd /home/deploy/hospitality-pilot
   docker compose -f docker-compose.staging.yml --env-file .env run --rm --no-deps -T app \
       python -m hospitality.tools.onboard_tenant ops/onboarding/pilot-hotel.json \
       --tenant-slug <код-отеля> --escalation-category reception
   ```
   В отчёте — строка «Служба эскалаций: reception — …». Откат копии ниже
   этого образа идёт по рецепту «Откат на образ старше #292» (абзац «Откат»
   выше) не с этого шага, а с первой записи конфига образом с #292 — она могла
   случиться уже после шага 2 (справочник из кабинета).
6. **Включить заявки:** в `.env` копии `ENABLE_SERVICE_REQUESTS=true`, затем
   `docker compose -f docker-compose.staging.yml --env-file .env up -d app`
   (флаг читает только `app`; `up -d` пересоздаёт контейнер с новым окружением).

Карточку эскалации без модели проверяет ЧП-сообщение в веб-чате тестового
номера при персонале: «пожар, тест» → в кабинете срочная «ЧП — сообщение
гостя: «пожар, тест»» у «Ресепшена»; закрыть её «Отменить» с причиной «тест».
Это настоящая заявка: в сводке дня она останется слагаемым «бот позвал
сотрудника» и войдёт в знаменатель доли заявок без ресепшена (spec 0035 §4) —
одна на весь пилот, при подсчёте её вычесть.

Вызов сотрудника моделью (#101) проверяет после шага 6 сообщение «Позовите,
пожалуйста, сотрудника — это тест» с того же номера: в кабинете несрочная
«Гость просит сотрудника: «…»» у «Ресепшена», гостю — «передал вашу просьбу»
без обещания ответа в чате. Закрыть так же, причиной «тест», и так же вычесть.
Это обычный ход модели гостя (около цента). Карточки нет, а гость прочёл
обещание сотрудника — флаг из шага 6 не доехал до `app`: повторить шаг 6.

## Известные отличия от прода по ADR-006

- Сервер в Германии: база с данными граждан РК вне РК (ст. 12) — то самое
  отступление; выход — #49.
- Общий сервер со staging: SSH-ключ CI (`deploy`, группа `docker`) достаёт и до
  базы копии.
- Общие со staging `ANTHROPIC_API_KEY`, `SENTRY_DSN`, ключ age бэкапов, алерт-бот
  ([secrets.md](secrets.md), раздел 2а).
- Алерты копии приходят тем же алерт-ботом в тот же чат, что у staging, и
  ошибки — в тот же проект Sentry; различает их только метка контура «[pilot]»
  (абзац «Метка контура» в «Обновить копию»). Пока копия не обновлена на compose
  с #389 или в её `.env` нет строки метки, алерт «[staging] …» может быть и про
  живой отель — проверять оба контура: `docker compose ps` в `/opt/hospitality`
  и в каталоге копии, `health/ready` обоих адресов.
- `deploy.sh` пишет в конце «staging здоров» — про копию тоже.
- Диск у копии и staging общий: чистка образов в конце `deploy.sh` (#380) у любого
  из двух удаляет неиспользуемые образы обоих, образы работающих контейнеров не
  трогает. Откат копии скачивает свой образ из GHCR заново.
- `deploy.sh` гоняет сид: в базе копии есть демо-тенант `demo-hotel` с
  минимальным демо-конфигом (город, пояс, язык), без персонала и заселений —
  гость без кода привязки получает отказ без вызова модели.

## Переезд в РК (после пилота, #49)

Креды туннеля `hospitality-pilot` работают только на одном сервере за раз. Два
`cloudflared` с одними кредами — реплики одного туннеля: Cloudflare делит
запросы между ними, и гости попадали бы то в старую базу, то в новую. Поэтому
новый сервер получает креды последним, а старый к этому моменту уже не
принимает запросы.

1. Сервер в РК по ADR-006 (`bootstrap-server.sh`, [deploy.md](deploy.md) часть A)
   со своими секретами — пока без кредов туннеля `hospitality-pilot`.
2. Здесь, в каталоге копии, остановить приём:
   `docker compose -f docker-compose.staging.yml --env-file .env stop cloudflared app worker`.
   С этого шага до шага 5 гостевой адрес не отвечает — делать в тихий час;
   алертер заалертит, это ожидаемо.
3. Снять свежий бэкап — строкой cron из «[Ночной бэкап](#ночной-бэкап)» без
   расписания, руками. Ночной не годится: всё, что гости и персонал записали
   после 03:15, в нём нет, а шаг 7 сотрёт это окончательно.
4. Восстановить этот дамп на новом сервере по [restore.md](restore.md), случай А:
   шаг 1, шаг 3 (вариант «том потерян»), шаги 4–5, шаг 6 — только `up -d --wait`.
   В команде восстановления шага 4 — IP нового сервера и его `<каталог>` (после
   `bootstrap-server.sh` — `/opt/hospitality`); дамп — из `backups/` копии: `scp`
   того же шага — со старого IP и из каталога копии. Сервер
   после части A уже работает, а его база создана миграциями его образа —
   обычно новее образа копии. Без шага 1 воркер пишет в базу во время
   `pg_restore`; без шага 3 таблицы новее дампа остаются, и `alembic upgrade
   head` на шаге 5 падает. `curl` из шага 6 restore.md смотрит на staging —
   здесь его заменяет шаг 6 ниже.
5. Креды туннеля и `cloudflared/config.yml` копии — на новый сервер, поднять там
   `cloudflared`. Адрес `app.necturn.com` прежний, напечатанные QR работают.
6. Проверить не только `health/ready`: войти в кабинет
   `app.necturn.com/staff` и найти последнее заселение, сделанное до шага 2.
7. Только после этого здесь: `docker compose … down -v`, удалить каталог и
   бэкапы копии, убрать строку cron.

До шага 7 перенос откатывается: на новом сервере `stop cloudflared` и вернуть
его в состояние шага 1 — удалить там JSON кредов `hospitality-pilot`, в `.env`
вернуть прежний `CLOUDFLARED_CREDS_FILE`, в `cloudflared/config.yml` — прежний
конфиг. Одного `stop` мало: первый же `up -d` или `./deploy.sh` там поднимает
все сервисы, и с кредами пилота встала бы вторая реплика туннеля, пока копия
обслуживает гостей. Здесь —
`docker compose -f docker-compose.staging.yml --env-file .env up -d`; записанное
на новом сервере после шага 5 при этом не вернётся.

## Ротация кредов туннеля

Новый туннель — это новый id: CNAME `app.necturn.com` смотрит на старый, и без
правки DNS и `tunnel:` в конфиге копии адрес не поднимется. Гостевой адрес
лежит с шага 1 до шага 4 — делать в тихий час.

1. На сервере, в каталоге копии, остановить коннектор:
   `docker compose -f docker-compose.staging.yml --env-file .env stop cloudflared`.
   `tunnel delete` не удаляет туннель с живым соединением.
2. На Mac основателя (нужен `~/.cloudflared/cert.pem`; нет — `cloudflared
   tunnel login`, зона `necturn.com`):
   ```bash
   cloudflared tunnel delete hospitality-pilot    # жалуется на соединения — сначала tunnel cleanup hospitality-pilot
   cloudflared tunnel create hospitality-pilot    # печатает новый id, кладёт ~/.cloudflared/<новый-id>.json
   cloudflared tunnel route dns --overwrite-dns hospitality-pilot app.necturn.com
   ```
   `--overwrite-dns` обязателен: CNAME со старым id остаётся после `delete`.
3. Новый JSON — на сервер поверх `cloudflared/creds.json` копии с правами 644
   ([deploy.md](deploy.md) A4b); в `cloudflared/config.yml` копии строку
   `tunnel:` — на новый id. Путь в `.env` прежний.
4. Поднять коннектор:
   `docker compose -f docker-compose.staging.yml --env-file .env up -d cloudflared`
   и снаружи `curl -s -o /dev/null -w '%{http_code}' https://app.necturn.com/health/ready`
   → `200`. Старый `<id>.json` на Mac удалить.
