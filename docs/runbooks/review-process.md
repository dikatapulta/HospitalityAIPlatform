# Ревью PR вторым GitHub-аккаунтом

> FOUNDATION §13.1: «ревью — отдельной LLM-сессией с чистым контекстом». Этот
> документ — только механика *как* независимая сессия оставляет реальный,
> зачитываемый GitHub'ом approve, а не просто текстовый вердикт в комментарии.

## Как запускать ревью-сессию

1. **Новое окно/чат**, не продолжение того, где писался код — иначе «чистый
   контекст» нарушен: сессия не должна помнить рассуждений автора, только
   читать diff, README и FOUNDATION с диска.
2. Модель — Opus 5, effort по уровню ревью: `xhigh` для уровня A, `high` для
   уровня B (правило 7 PROJECT_EXECUTION_PLAN). Дешёвые модели в ревью не
   используются: ревью в одном классе с канонами и ADR, цена ошибки выше, чем
   в рутинной копии паттерна.
3. Промпт ставит роль ревьюера явно (что читать, какие правила блокирующие) —
   см. пример в истории PR #20/PR #19.
4. **Промпт требует полноты, а не фильтрации по важности.** Формулировка
   «сообщай только блокирующее» исполняется буквально и роняет реальные баги:
   модель находит дефект, оценивает его ниже планки и молчит. Правильно —
   «сообщи все находки, включая те, в которых не уверен, у каждой укажи
   уверенность и серьёзность»; отсечение блокирующих от рекомендаций (R-5,
   R-6, R-7, R-9 — блокирующие) делается отдельным шагом уже по списку.
5. Сессия сама вызывает `gh pr review` под вторым аккаунтом (ниже) — вердикт
   пишется прямо в теле review, а не в отдельный комментарий.
6. **У PR от робота зелёный `smoke` — не сигнал.** PR'ам Dependabot не
   подставляются секреты репозитория (у бота своё хранилище), поэтому guard
   видит пустой `ANTHROPIC_API_KEY` и пропускает все шаги job'а, оставляя его
   зелёным. То же и с `deploy-staging`: на любом PR он пропущен по своему `if:`.
   Поведение таких изменений проверяет прогон CI на main **после** merge —
   смотреть туда, а не на галки PR (найдено ревью PR #188, issue #190).
7. **У каждой находки — метка «чинить сейчас», «issue» или «косметика», прямо
   в вердикте.** Умолчание, четыре основания и определения меток — правило 9
   PROJECT_EXECUTION_PLAN; здесь только механика. Метка обязательна у каждой
   находки: без неё выбор молча делает автор PR — и делает его в сторону issue,
   потому что так дешевле сегодня и дороже потом. Есть хоть одна метка «чинить
   сейчас» → вердикт `--request-changes`, а не approve со списком «на потом»:
   approve переживает push (#198), и отложенное не увидит никто. Метку «issue»
   ревьюер закрывает сам — заводит issue и ставит её номер прямо в находке.
8. **Повторный проход читает дельту, а не весь diff заново.**
   Доработку автор кладёт отдельным коммитом поверх — без `--amend` и
   force-push, иначе прежний head исчезает из ветки и сравнивать не с чем.
   Ревьюер второго прохода читает `git diff <последний коммит, который видел
   предыдущий проход>..<head>` плюс список находок предыдущего прохода
   (`gh pr view <N> --comments`). Что делать с находкой о нетронутой части diff
   и какие находки блокируют merge независимо от прохода — правило 9
   PROJECT_EXECUTION_PLAN.
   Базу дельты называет автор доработки — явной командой
   `git diff <база>..<head>` в комментарии к PR. Без неё ревьюер границу не
   восстановит: подсказка — время `gh api …/reviews --jq '.[].submitted_at'`
   против дат коммитов.

## Почему нужен второй аккаунт

GitHub не даёт аккаунту формально approve-ить свой же PR. Все PR в этом
репозитории открываются от `dikatapulta`, поэтому реальный approve обязан
прийти от другой личности — `supertazick-oss`. Без этого «ревью отдельной
сессией» оставалось бы вежливой конвенцией, а не машинной гарантией.

## Как это работает технически

- `supertazick-oss` — коллаборатор репозитория с правами **Write**.
  Read/Triage недостаточно: GitHub засчитывает approve в
  `required_pull_request_reviews` только от аккаунтов с правом push
  (задокументированное поведение, не наша прихоть) — Write шире, чем хотелось
  бы для чисто ревьюерской роли, но это минимальный уровень, на котором approve
  вообще учитывается веткой main.
- Авторизация изолирована от основного `gh`: отдельная конфиг-директория
  `GH_CONFIG_DIR=~/.config/gh-reviewer`, токен — в системном keychain (не файл).
  Обычный `gh auth status` (аккаунт `dikatapulta`) это не трогает.
- Токен — classic PAT со скоупами `repo` + `read:org`. `gh auth login
  --with-token` требует оба скоупа для валидации; сами API-вызовы ревью
  используют куда меньше. Срок — 90 дней (таблица секретов —
  [secrets.md](secrets.md)).
- Защита `main` (`branches/main/protection`) требует
  `required_pull_request_reviews.required_approving_review_count: 1` — без
  approve `gh pr merge` физически заблокирован (`mergeStateStatus: BLOCKED`).

## Как ревьюер оставляет вердикт

```
GH_CONFIG_DIR=~/.config/gh-reviewer gh pr review <N> --approve --body-file <файл>
# или при блокирующих находках:
GH_CONFIG_DIR=~/.config/gh-reviewer gh pr review <N> --request-changes --body-file <файл>
```

Содержательный вердикт (что проверено, R-5/R-6/R-7/R-9, DoD) пишется в теле
review так же, как раньше писался в комментарий текстом — поменялся только
механизм регистрации, не содержание ревью.

## Мерж

Approve снимает блокировку `main`, после чего PR мержит сессия-автор своим
аккаунтом (`gh pr merge <N> --squash --delete-branch`) — ждать основателя не
нужно. Действие необратимо и делается в общей ветке, поэтому условия закрытые
(правило 9 PROJECT_EXECUTION_PLAN): живой approve, зелёный CI, подтверждённая
ревьюером косметика. Стекованные PR — исключение, требующее внимания: squash
базового PR закрывает надстроенный вместо ретаргета, поэтому такую пару мержат
снизу вверх и после каждого merge сверяют базу оставшегося PR.

## Ротация / компрометация токена

См. [secrets.md](secrets.md) — раздел «Локальные токены». При подозрении на
утечку: Revoke токена на странице `supertazick-oss` → выпустить новый с теми
же скоупами → `GH_CONFIG_DIR=~/.config/gh-reviewer gh auth login --with-token`.
