# Ревью PR вторым GitHub-аккаунтом

> FOUNDATION §13.1: «ревью — отдельной LLM-сессией с чистым контекстом». Этот
> документ — только механика *как* независимая сессия оставляет реальный,
> зачитываемый GitHub'ом approve, а не просто текстовый вердикт в комментарии.

## Как запускать ревью-сессию

1. **Новое окно/чат**, не продолжение того, где писался код — иначе «чистый
   контекст» нарушен: сессия не должна помнить рассуждений автора, только
   читать diff, README и FOUNDATION с диска.
2. Модель — Opus 5, effort по уровню ревью: `xhigh` для уровня A, `high` для
   уровня B (правило 7 PROJECT_EXECUTION_PLAN). Дешёвые модели в ревью не
   используются: ревью в одном классе с канонами и ADR, цена ошибки выше, чем
   в рутинной копии паттерна. Уровень B ревьюится пачкой: до 3–4 PR уровня B
   в одном окне, по одному проходу на PR; уровень A — по одному PR на окно
   (правило 9).
3. Промпт ставит роль ревьюера явно (что читать, какие правила блокирующие) —
   см. пример в истории PR #20/PR #19.
   Для уровня A на крупных diff ревьюеру рекомендован многоагентный прогон —
   Workflow-субагенты: искатели по осям (корректность, изоляция тенанта, каноны,
   секреты) плюс адверсариальная проверка каждой находки (правило 9); вердикт
   и approve пишет сама сессия-ревьюер, субагенты его не ставят. **Режим
   включает человек, а не сессия:** словом `ultracode` в тексте промпта,
   который набирает сам (правило 7; в промпте через `-p`, из планировщика или
   из комментария к PR слово не срабатывает, а выключенные в `/config`
   workflow или триггер слова снимают его действие целиком). Значит,
   слово должно стоять уже в промпте ревью-окна — не потому, что позже его
   не набрать (набрать можно: слово работает в любом промпте, который человек
   набрал сам, хоть в пятом сообщении окна), а потому, что оркестрируется
   только работа **после** слова: половину PR, прочитанную соло, workflow
   не переразберёт, а переделывать её дороже, чем начать в режиме сразу.
   Посреди сессии не переключают другой механизм —
   `/effort ultracode`, это значение effort (правило 7, «Механика effort»).
4. **Промпт требует полноты, а не фильтрации по важности.** Формулировка
   «сообщай только блокирующее» исполняется буквально и роняет реальные баги:
   модель находит дефект, оценивает его ниже планки и молчит. Правильно —
   «сообщи все находки, включая те, в которых не уверен, у каждой укажи
   уверенность и серьёзность»; отсечение блокирующих от рекомендаций (R-5,
   R-6, R-7, R-9 — блокирующие) делается отдельным шагом уже по списку.
5. Сессия сама вызывает `gh pr review` под вторым аккаунтом (ниже) — вердикт
   пишется прямо в теле review, а не в отдельный комментарий.
6. **У PR от робота зелёный `smoke` — не сигнал.** PR'ам Dependabot не
   подставляются секреты репозитория (у бота своё хранилище), поэтому guard
   видит пустой `ANTHROPIC_API_KEY` и пропускает все шаги job'а, оставляя его
   зелёным. То же и с `deploy-staging`: на любом PR он пропущен по своему `if:`.
   Поведение таких изменений проверяет прогон CI на main **после** merge —
   смотреть туда, а не на галки PR (найдено ревью PR #188, issue #190).
7. **У каждой находки — метка «чинить сейчас», «issue» или «косметика», прямо
   в вердикте.** Умолчание, четыре основания и определения меток — правило 9
   PROJECT_EXECUTION_PLAN; здесь только механика. Метка обязательна у каждой
   находки: без неё выбор молча делает автор PR — и делает его в сторону issue,
   потому что так дешевле сегодня и дороже потом. Есть хоть одна метка «чинить
   сейчас» → вердикт `--request-changes`, а не approve со списком «на потом»:
   approve разрешает смержить ветку как есть, ничего в ней не трогая, и момент,
   в который отложенное обязаны сделать, дальше не наступает. Метку «issue»
   ревьюер закрывает сам — заводит issue и ставит её номер прямо в находке.

   **Косметика до конца Gate B не правится в ветке, стоящей под живым или
   ожидаемым approve** (правило 9): защита `main` снимает approve любым push'ем
   (`dismiss_stale_reviews` + `require_last_push_approval` при
   `enforce_admins: true` — #198), и одна опечатка стоила цикла «правка + CI +
   новое окно ревьюера + повторный approve». Вместо этого ревьюер вписывает
   косметику строкой в issue процесс-батча #275 (правило 11) и, если находок
   «чинить сейчас» нет, ставит approve и мержит — merge косметики не ждёт.
   Исключение — вердикт `--request-changes`: снимать там нечего, автор пушит
   доработку в любом случае, поэтому косметику из того же вердикта он правит
   заодно с ней (правило 9). Прежняя механика «правка + повторный approve»
   пересматривается после пилота.
8. **Повторный проход читает дельту, а не весь diff заново.**
   Доработку автор кладёт отдельным коммитом поверх — без `--amend` и
   force-push, иначе прежний head исчезает из ветки и сравнивать не с чем.
   Ревьюер второго прохода читает `git diff <последний коммит, который видел
   предыдущий проход>..<head>` плюс список находок предыдущего прохода
   (`gh pr view <N> --comments`). Что делать с находкой о нетронутой части diff
   и какие находки блокируют merge независимо от прохода — правило 9
   PROJECT_EXECUTION_PLAN.
   Базу дельты называет автор доработки — явной командой
   `git diff <база>..<head>` в комментарии к PR. Без неё ревьюер границу не
   восстановит: подсказка — время `gh api …/reviews --jq '.[].submitted_at'`
   против дат коммитов.

## Почему нужен второй аккаунт

GitHub не даёт аккаунту формально approve-ить свой же PR. Все PR в этом
репозитории открываются от `dikatapulta`, поэтому реальный approve обязан
прийти от другой личности — `supertazick-oss`. Без этого «ревью отдельной
сессией» оставалось бы вежливой конвенцией, а не машинной гарантией.

## Как это работает технически

- `supertazick-oss` — коллаборатор репозитория с правами **Write**.
  Read/Triage недостаточно: GitHub засчитывает approve в
  `required_pull_request_reviews` только от аккаунтов с правом push
  (задокументированное поведение, не наша прихоть) — Write шире, чем хотелось
  бы для чисто ревьюерской роли, но это минимальный уровень, на котором approve
  вообще учитывается веткой main.
- Авторизация изолирована от основного `gh`: отдельная конфиг-директория
  `GH_CONFIG_DIR=~/.config/gh-reviewer`, токен — в системном keychain (не файл).
  Обычный `gh auth status` (аккаунт `dikatapulta`) это не трогает.
- Токен — classic PAT со скоупами `repo` + `read:org`. `gh auth login
  --with-token` требует оба скоупа для валидации; сами API-вызовы ревью
  используют куда меньше. Срок — 90 дней (таблица секретов —
  [secrets.md](secrets.md)).
- Защита `main` (`branches/main/protection`) требует
  `required_pull_request_reviews.required_approving_review_count: 1` — без
  approve `gh pr merge` физически заблокирован (`mergeStateStatus: BLOCKED`).
  С 05.08.2026 к этому добавлены `dismiss_stale_reviews` и
  `require_last_push_approval` при `enforce_admins: true` (#198): approve обязан
  относиться к последнему push'у, любой новый коммит его снимает, и обойти это
  не может никто, включая владельца репозитория.

## Как ревьюер оставляет вердикт

```
GH_CONFIG_DIR=~/.config/gh-reviewer gh pr review <N> --approve --body-file <файл>
# или при блокирующих находках:
GH_CONFIG_DIR=~/.config/gh-reviewer gh pr review <N> --request-changes --body-file <файл>
```

Содержательный вердикт (что проверено, R-5/R-6/R-7/R-9, DoD) пишется в теле
review так же, как раньше писался в комментарий текстом — поменялся только
механизм регистрации, не содержание ревью.

## Мерж

Approve снимает блокировку `main`, после чего PR мержит сессия основным
аккаунтом (`gh pr merge <N> --squash --delete-branch`) — ждать основателя не
нужно. Обычно это сама сессия-ревьюер, следующим шагом после approve; кто ещё и
при каких условиях — правило 9 PROJECT_EXECUTION_PLAN (там же список условий:
живой approve и зелёный CI), здесь только
механика. Практическое следствие новой защиты `main`: любая правка после
approve снимает его, и `gh pr merge` отвечает `BLOCKED`, пока не появится
новый approve, — поэтому косметика не пушится в ветку, стоящую под живым или
ожидаемым approve (правило 9; при вердикте `--request-changes` снимать нечего,
и там косметику из того же вердикта автор правит заодно с доработкой — п. 7
выше), а содержательная доработка идёт через повторный проход. Стекованные PR —
исключение, требующее внимания: squash базового PR закрывает надстроенный вместо
ретаргета, поэтому такую пару мержат снизу вверх и после каждого merge сверяют
базу оставшегося PR.

### Что закрывает issue при merge

Знание нужно и автору (что писать в теле PR), и мержащей сессии (проверить, что
issue закрылся). Механизмов ровно два, и оба держатся на **английском**
ключевом слове `Closes #N` — русское «Закрывает #N» GitHub не парсит вовсе:

1. **Слово в теле PR** создаёт связь PR↔issue: она видна в панели Development и
   в `gh pr view <N> --json closingIssuesReferences`, а issue закрывается в
   момент merge. Проверяется **до** merge — пустой список значит, что связи нет.
   В таймлайне issue у такого закрытия `commit_id` пуст.
2. **Слово в сообщении коммита ветки.** При squash-мерже тело PR в коммит **не**
   попадает: репозиторий настроен `squash_merge_commit_message = COMMIT_MESSAGES`,
   и GitHub собирает сообщение из коммитов ветки. Поэтому `Closes #N`, написанное
   в теле коммита, доедет до `main` и закроет issue даже при пустом
   `closingIssuesReferences`. В таймлайне у такого закрытия стоит `commit_id`
   squash-коммита — по нему два механизма и различаются.

Так закрылся #302: тело PR #303 говорило «Закрывает #302» (не сработало,
`closingIssuesReferences` был пуст), а закрыл его `Closes #302` из тела коммита
ветки, приехавший в squash-сообщение. Префикс conventional-commit тут ни при
чём: `fix` в заголовке закрывающим словом не работает — GitHub требует, чтобы за
ключевым словом **сразу** шла ссылка на issue.

Отсюда практика: пишем `Closes #N` по-английски в теле PR — оно и создаёт
видимую связь, — и не пишем ключевое слово там, где закрывать не собираемся,
**даже с отрицанием**: «Не Closes #49» в теле PR #130 закрыло гейт переезда #49,
потому что русского «не» сканер не видит. И ставим его только в PR, который
работу действительно заканчивает: у докс-PR issue закрывается раньше кода.

## Ротация / компрометация токена

утечку: Revoke токена на странице `supertazick-oss` → выпустить новый с теми
