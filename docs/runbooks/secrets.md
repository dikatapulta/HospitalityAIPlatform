# Чеклист секретов (staging)

> Task 0006. FOUNDATION §11: секретов в репозитории нет — только в секрет-хранилище
> (GitHub Secrets) и в переменных окружения на сервере (`.env`). Этот чеклист —
> единый список: что за секрет, где живёт, как ротировать. Обновляется при
> появлении каждого нового секрета (интеграции, LLM-ключи — в следующих задачах).

## 1. GitHub Actions Secrets (репозиторий → Settings → Secrets and variables → Actions)

Нужны job'у `deploy-staging` (см. [deploy.md](deploy.md)).

| Секрет | Что это | Обязателен | Ротация |
|---|---|---|---|
| `STAGING_SSH_HOST` | IP/хост VPS staging. Пока пуст — деплой пропускается. | да | при смене сервера |
| `STAGING_SSH_USER` | Пользователь деплоя на VPS (`deploy`). | да | редко |
| `STAGING_SSH_KEY` | **Приватный** SSH-ключ для деплоя (отдельная пара, только для CI). | да | при подозрении на утечку — перегенерировать (A3 в deploy.md), заменить `authorized_keys` и секрет |
| `STAGING_SSH_PORT` | SSH-порт, если не 22. | нет | — |
| `ANTHROPIC_API_KEY` | Ключ Anthropic для job `smoke` (spec 0019: smoke гоняет живую модель). Пуст — job грациозно пропускается. | нет | пере-выпустить в консоли Anthropic → обновить секрет (и копии в `.env` сервера и локальном) |

`GITHUB_TOKEN` — встроенный, отдельно заводить не нужно: им job логинится в GHCR
для push образа (`packages: write` в workflow).

## 2. Секреты на сервере (`/opt/hospitality/.env`, шаблон — [ops/deploy/.env.staging.example](../../ops/deploy/.env.staging.example))

Живут **только** на VPS, не в репозитории и не в GitHub Secrets.

| Переменная | Что это | Ротация |
|---|---|---|
| `POSTGRES_PASSWORD` | Пароль БД staging. Сгенерировать: `openssl rand -hex 24`. | сменить в `.env` → `deploy.sh` пересоздаст контейнер app с новым паролем; для существующей БД пароль менять и в Postgres |
| `POSTGRES_USER`, `POSTGRES_DB` | Имя пользователя/БД. | редко |
| `APP_PORT` | Порт приложения на VPS (по умолчанию 8000). | — |
| `SERVICE_TOKEN` | Сервисный токен HTTP API (Task 0013, §11): аутентифицирует запросы к `/api/v1/*`. Сгенерировать: `openssl rand -hex 32`; dev-значение из кода не использовать. | сменить в `.env` → `deploy.sh` пересоздаст app; обновить токен у всех клиентов API (пока это только ручные curl/скрипты) |
| `TELEGRAM_WEBHOOK_SECRET` | Секрет вебхука Telegram (Task 0016, §8.4): Telegram шлёт его в заголовке на каждом запросе; пустой = вебхук закрыт. Сгенерировать: `openssl rand -hex 32`. | сменить в `.env` → `deploy.sh` пересоздаст app; **обязательно** переустановить вебхук с новым `secret_token` (иначе все апдейты → 403), см. [telegram.md](telegram.md) |
| `TELEGRAM_BOT_TOKEN` | Токен бота от BotFather (Task 0016): для отправки ответов гостю через Bot API. | пере-выпустить у BotFather (`/revoke`) → обновить в `.env` → `deploy.sh` пересоздаст app |
| `ANTHROPIC_API_KEY` | Ключ Anthropic для app/worker (живые ответы гостям, issue #73; у воркера ещё и фото реквизитов для АВР, если задан `LLM_MODEL_DOCUMENTS` — spec 0049 Р-13). | пере-выпустить в консоли Anthropic → обновить в `.env` → пересоздать app и worker |
| `OPENAI_API_KEY` | Ключ OpenAI для app/worker — второй провайдер (ADR-020). Нужен, только если `LLM_MODEL` — модель OpenAI или задан `LLM_MODEL_MENTOR` («Наставник», ADR-024): тогда без него app и worker не стартуют. Пустой — штатно. На staging — только синтетика (ADR-006). | пере-выпустить в OpenAI Platform (API keys) → обновить в `.env` → пересоздать app и worker |
| `SENTRY_DSN` | DSN проекта Sentry `hospitality-staging` (EU-регион, Task 0018): куда app, worker и alerter (с issue #229) шлют события об ошибках. Пустой = Sentry выключен. DSN позволяет только отправлять события, не читать. | пере-выпустить в настройках проекта Sentry (Client Keys) → обновить в `.env` → пересоздать app, worker и alerter |
| `TELEGRAM_ALERT_BOT_TOKEN` | Токен **отдельного** алерт-бота (Task 0018; не гостевого — у того вебхук, `getUpdates` конфликтует). | пере-выпустить у BotFather (`/revoke`) → обновить в `.env` → пересоздать alerter |
| `TELEGRAM_ALERT_CHAT_ID` | id Telegram-группы/канала алертов (отрицательное число; как узнать — alerts.md). Апгрейд группы до супергруппы меняет id — алерты замолчат, обновить значение. | при смене группы/канала — обновить в `.env` → пересоздать alerter |
| `ALERT_HEARTBEAT_URL` | Ping URL проверки healthchecks.io `alerter staging` (`https://hc-ping.com/<uuid>`, issue #229): по нему алертер отмечается «жив и сторожит». С адресом кто угодно держал бы проверку зелёной за мёртвого алертера — поэтому секрет, в лог не пишется. Пусто — пульса нет. Как завести — [alerts.md](alerts.md), «Сторож сторожа». | завести новую проверку и удалить старую → новый адрес в `.env` → пересоздать alerter → новая проверка зелёная ([alerts.md](alerts.md), «Сторож сторожа», шаги 1–4) |
| `BACKUP_AGE_RECIPIENT` | **Публичный** ключ age (`age1…`), которым `backup.sh` шифрует дампы БД (issue #81). Сам не секрет, но без него бэкапы **не создаются вовсе** (fail-closed), а деплой останавливается на снимке БД перед миграцией (issue #135). Приватной половины на сервере нет и быть не должно. | новая пара ключей у основателя ([restore.md](restore.md), «Ротация ключа») → новый публичный ключ в `.env`; старый приватный хранить, пока живы дампы, зашифрованные им |
| `FILE_ENCRYPTION_KEY` | Ключ AES-256-GCM файлов на томе `files_data` — фото, документы гостя ([spec 0047](../specs/0047-file-storage.md), ADR-022, FOUNDATION §11) — **и** реквизитов в таблице `act_requests` ([spec 0049](../specs/0049-act-requisites.md) Р-3): запрос может прийти одним текстом, без файлов. Сгенерировать **на сервере**: `openssl rand -base64 32`; копия — **обязательно** в менеджере паролей основателя: архив тома в бэкапе без ключа не прочитать, потеря ключа = потеря всех файлов и реквизитов `act_requests`. Пусто — файлы отвечают ERR-FILES-005, остальное работает: заводится PR'ом, включающим первый приём файлов на контуре. | без ротации: новый ключ не читает файлы, записанные старым (перешифровки нет — NG-8); подозрение на утечку — сначала issue «перешифровать том», ключ не менять вслепую |
| `STAFF_PUSH_VAPID_PRIVATE_KEY` | Приватный ключ VAPID — подпись веб-пуша на телефоны персонала ([spec 0050](../specs/0050-staff-web-push.md) §8): службы пуша Google и Apple принимают уведомление, только если подпись сходится с ключом, на который подписался телефон. Сгенерировать **на сервере**: `docker compose -f /opt/hospitality/docker-compose.staging.yml exec app python -m hospitality.tools.generate_vapid_key`; копия — в менеджере паролей основателя. Пусто — пуша нет (кнопки на телефоне нет), остальное работает; негодное значение валит старт. Шаги — [staff-push.md](staff-push.md). | новый ключ обрывает все подписки: телефоны переподписываются сами, когда сотрудник откроет кабинет; утечка — сменить ключ сразу (чужой с ключом и адресом подписки может слать уведомления персоналу) |

от ADR-006 (раздел «Временное отступление»). Переменные те же, что в разделе 2;
здесь — только чем они отличаются.

| Переменная | Своё или общее со staging | Ротация |
|---|---|---|
| `POSTGRES_PASSWORD`, `SERVICE_TOKEN`, `TELEGRAM_WEBHOOK_SECRET` | **свои**, сгенерированы на сервере 29.09 (`openssl rand -hex`), нигде больше не хранятся | как в разделе 2, в каталоге копии |

## 3. Локальные токены (машина основателя, вне репозитория)

| Секрет | Что это | Где живёт | Ротация |
|---|---|---|---|
| Classic PAT `supertazick-oss` (`repo`, `read:org`) | Токен второго GitHub-аккаунта — независимый ревьюер PR (см. [review-process.md](review-process.md)) | Системный keychain через `GH_CONFIG_DIR=~/.config/gh-reviewer gh auth login`; сырого файла с токеном нет | каждые 90 дней (срок токена) — перегенерировать на странице токена, перелогинить тем же `gh auth login --with-token` |
| Пароль и код из приложения суперадмина ([spec 0044](../specs/0044-superadmin.md)) | Вход учётки, которая сбрасывает пароли и стирает учётки персонала. Код — шесть цифр из приложения-аутентификатора; его секрет живёт в приложении на телефоне и в БД (`staff_second_factors`), пароль — только хэш | Пароль — менеджер паролей основателя; секрет кода — приложение на телефоне (в репозитории и `.env` их нет) | потерян телефон — `superadmin reset-factor`, забыт или утёк пароль — `superadmin set-password`; обе команды закрывают сессии суперадмина ([superadmin.md](superadmin.md)) |
| **Приватный ключ age бэкапов БД** (`AGE-SECRET-KEY-1…`) | Единственный ключ, которым расшифровываются дампы БД (issue #81). На сервер **не попадает никогда**; публичная половина — `BACKUP_AGE_RECIPIENT` в разделе 2 | `~/.config/age/hospitality-backup.key` (права 600) + **обязательная копия в менеджере паролей**: потеря ключа = потеря всех бэкапов (§10.11) | смена пары — [restore.md](restore.md), «Ротация ключа»; старый ключ не удалять, пока живы зашифрованные им дампы (retention 14 дней + локальные копии в `backups/`) |
| Сертификат Cloudflare `cert.pem` и креды туннеля `hospitality-pilot` (`<id>.json`) | `cert.pem` — право управлять туннелями и DNS зоны `necturn.com` (выдан `cloudflared tunnel login` 29.09); JSON — ключ туннеля гостевой копии, его копия на сервере (раздел 2а) | `~/.cloudflared/` на Mac основателя | `cert.pem` после настройки можно удалить — понадобится снова, выпускается повторным `cloudflared tunnel login`; при подозрении на утечку — отозвать в панели Cloudflare (Zero Trust → Tunnels / API Tokens) |
| `OPENAI_API_KEY` | Ключ OpenAI для bake-off моделей OpenAI против модели гостя (ADR-020): прогон платный — только с согласия основателя (CLAUDE.md, «Правила работы») | локальный `.env` в корне репозитория (в `.gitignore`) | пере-выпустить в OpenAI Platform (API keys) → обновить локальный `.env`; если ключ задан и на сервере — там тоже (раздел 2) |

| Секрет | Что это | Где живёт | Ротация |
|---|---|---|---|
| Токен загрузки выгрузки Opera ([spec 0058](../specs/0058-pms-stay-sync.md) §2.4) | Пускает файл отчёта Opera на маршрут загрузки отеля: с ним кто угодно подменил бы «кто сейчас в доме» — сверка заселила бы и выселила гостей по чужому файлу. ## Правила
- Ничего из этого **никогда** не коммитится: `.env` — в `.gitignore`, приватные ключи — только в GitHub Secrets и на сервере.
- Ключ деплоя — **отдельная** пара, не личный ключ разработчика; компрометация → перегенерация, а не общий доступ.
- Утечка любого секрета → ротация по таблице выше + запись в лог инцидентов.
- Новый секрет в проекте (LLM-ключ, токен Telegram, ключ интеграции) → строка в этом чеклисте в том же PR.
- Гигиена `.env` на сервере: права `600` (`chmod 600 /opt/hospitality/.env`), страховочные копии (`.env.bak*`) удалять сразу после проверки — каждая забытая копия это ещё один файл с секретами, который никто не ротирует.
