# Runbook: суперадмин кабинета

Суперадмин — отдельная учётка основателя со своим логином: только у неё в
«Сотрудниках» есть «Стереть учётку» и «Сбросить пароль» у менеджера (сотруднику
и старшему пароль сбрасывает и менеджер отеля, #944). Входит она
своей страницей — логин, пароль и код из приложения на телефоне, — сессия
живёт час, о каждом входе и действии приходит уведомление алерт-ботом в
Telegram. Устройство и почему так — [spec 0044](../specs/0044-superadmin.md).

Все команды ниже — на сервере по SSH-ключу (`deploy@<IP>`, [deploy.md](deploy.md)),
внутри контейнера `app` и **без `-T`**: без терминала пароль виден на экране.
Каталог и compose-файл — своего контура:

| Контур | Каталог | Префикс команды |
|---|---|---|
| Staging | `/opt/hospitality` | `docker compose -f docker-compose.staging.yml --env-file .env exec app` |
| Гостевая копия | `/home/deploy/hospitality-pilot` | тот же, но из каталога копии ([pilot-copy.md](pilot-copy.md)) |

## Завести суперадмина

Нужны: телефон с приложением-аутентификатором (Google Authenticator,
Microsoft Authenticator и аналоги) и логин, которого в отеле ещё нет (3–12
латинских букв и цифр, первой — буква; например `ADMN`, не `BORM`).

```bash
ssh deploy@<IP>
cd /home/deploy/hospitality-pilot          # или /opt/hospitality для staging
docker compose -f docker-compose.staging.yml --env-file .env exec app \
    python -m hospitality.tools.superadmin create <ЛОГИН> --name "Имя" --tenant-slug <код-отеля>
```

1. Пароль — дважды (не короче 8 символов, не частый и без логина и имени — иначе
   ERR-AUTH-016; сохраните в менеджере паролей).
2. На экране появится QR. В приложении: «Добавить» → «Сканировать QR». Не
   сканируется (мелкое окно терминала) — «Ввести ключ вручную», ключ напечатан
   под QR группами по четыре знака.
3. Введите шестизначный код из приложения. Код не подошёл — **ничего не
   записано**: проверьте, что время на телефоне ставится автоматически, и
   запустите команду заново.
4. Сохраните в закладки адрес, который напечатает команда:
   `https://<адрес>/staff/<код-отеля>/superadmin`. На обычной странице входа
   суперадмин не войдёт — «Неверный логин или пароль».
5. Проверка: войти по закладке; в Telegram придёт «🛠 На сервере заведён
   суперадмин» и «🔐 Вход суперадмина».

## Сотрудник забыл пароль

Сотруднику и старшему ссылку выдаёт менеджер отеля сам — теми же шагами в своём
кабинете; основателю придёт уведомление (раздел «Менеджер сбросил пароль»).
Пароль менеджера — только суперадмином:

1. Войти суперадмином по закладке → «Сотрудники».
2. У сотрудника — «Сбросить пароль» → подтвердить.
3. Появится ссылка (действует 24 ч, один раз) — «Поделиться» в WhatsApp или
   «Скопировать». Пока ею не воспользовались, старый пароль работает.
4. Сотрудник открывает ссылку, задаёт новый пароль и сразу попадает в кабинет;
   на остальных его устройствах кабинет попросит войти заново. Логин тот же.

Ссылка «больше не действует» — выдать новую тем же нажатием (она же гасит
прежнюю).

## Потерян телефон

```bash
docker compose -f docker-compose.staging.yml --env-file .env exec app \
    python -m hospitality.tools.superadmin reset-factor <ЛОГИН> --tenant-slug <код-отеля>
```

Новый QR и подтверждение кодом — как при заведении. Код старого телефона
перестаёт работать, все сессии суперадмина закрыты.

## Забыт пароль суперадмина

```bash
docker compose -f docker-compose.staging.yml --env-file .env exec app \
    python -m hospitality.tools.superadmin set-password <ЛОГИН> --tenant-slug <код-отеля>
```

Новый пароль дважды; все сессии суперадмина закрыты.

## Если вход или действие не ваши

Уведомление о входе, сбросе или стирании пришло, а вы ничего не делали.
«⚠️ пароль верный, код из приложения — нет» значит: пароль суперадмина знает
кто-то ещё.

1. **Сразу закрыть дверь** — обе команды выше, `set-password` и
   `reset-factor`: новый пароль, новый код, все сессии суперадмина закрыты.
2. **Посмотреть, что успели** — события в логах приложения по времени
   уведомления (логинов в логах нет, только `user_id`):
   ```bash
   docker compose -f docker-compose.staging.yml --env-file .env logs app --since 24h \
     | grep -E 'staff.superadmin_login|staff.password_reset|staff.member_erased'
   ```
   Кто стоит за `user_id` — запросом только на чтение (вход в psql — канон
   [subject-requests.md](subject-requests.md) §2, из каталога своего контура):
   ```sql
   SELECT display_name, status FROM users WHERE id = '<user_id>';
   ```
   `staff.password_reset_accepted` — по ссылке уже задан пароль чужой учётке:
   войти ею мог тот, кто выдал ссылку. Выдайте владельцу учётки новую ссылку —
   когда он задаст пароль, чужие сессии закроются.
3. **Стёртую по ошибке учётку не вернуть**: пригласите человека заново под
   другим логином.

## Менеджер сбросил пароль

Уведомление «🔑 … Менеджер отеля выдал ссылку сброса пароля сотруднику с ролью …»
— обычное дело отеля: сотрудник забыл пароль, менеджер выдал ему ссылку. Делать
ничего не нужно.

Неожиданно — сбросов много подряд, или сотрудник жалуется, что его выкинуло из
кабинета и пароль не подходит: ссылкой мог воспользоваться не он.

1. **Кто и кому** — лог по времени уведомления (логинов в логах нет):
   ```bash
   docker compose -f docker-compose.staging.yml --env-file .env logs app --since 24h \
     | grep -E 'staff.password_reset_(issued|accepted)'
   ```
   `actor_user_id` — менеджер, `user_id` — сотрудник. Имена — тем же запросом
   только на чтение, что в шаге 2 раздела выше (там же — как войти в psql).
2. **Вернуть вход сотруднику** — новая ссылка ему лично (суперадмином или другим
   менеджером): когда он задаст пароль, чужие сессии закроются. Подписи паролем,
   сделанные после сброса, лист подписей помечает временем сброса
   ([spec 0077](../specs/0077-staff-memos.md) §4).
3. Сброс был не по просьбе сотрудника — разговор с руководством отеля: доступ
   менеджера отключают в «Сотрудниках».
