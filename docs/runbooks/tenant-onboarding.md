# Runbook — онбординг отеля v0 (issue #123)

> FOUNDATION §6 «Онбординг отеля», P-11 (различия отелей — данные, а не код).
> Версия v0: выполняется разработчиком/основателем вручную командами; мастер
> self-service — Фаза 4 (PROJECT_EXECUTION_PLAN).

## Что должно получиться

У отеля есть тенант, шесть (или сколько у него есть) служб-адресов доставки
заявок, осознанные сроки напоминаний по каждой службе, телефон ресепшена и
подсказки, по которым модель отличает «кофе в пакетиках» от «сваренного кофе».
Гость пишет в чат → заявка приземляется в нужную службу → невзятая заявка
подсвечивается по сроку этой службы, а не по общему получасу.

---

## Шаг 0. Собрать данные у отеля (до всякой команды)

| Что спросить | Куда попадёт |
|---|---|
| Юридическое/маркетинговое название | `--name` (`tenants.name`, от его лица говорит бот) |
| Город и часовой пояс | `city`, `timezone` профиля (в БД всё в UTC, §9) |
| Язык по умолчанию | `default_language` — язык ответа, когда язык гостя неизвестен |
| **Список служб**: кто разные люди со своим старшим | `categories` профиля |
| По каждой службе: **через сколько минут невзятая заявка — уже проблема** | `reminder_after_minutes` |
| Телефон ресепшена, который можно показывать гостю | `--reception-phone` |
| **Предметы, которые выдают ДВЕ разные службы** | `hints` (см. шаг 2) |

**Принцип набора служб:** категория — это адрес доставки, а не тема разговора.
Категорий столько, сколько разных групп людей. Категорию «жалоба» не заводим:
жалоба почти всегда содержит конкретную проблему, а эмоциональная формулировка
увела бы заявку к менеджеру вместо техника; «позовите человека» закрыто
эскалацией (#36).

**Минимальный список неоднозначных предметов**, который надо проговорить с
отелем (проверено на пилоте, дальше — дописывать по живым случаям):

| Предмет | Служба А | Служба Б |
|---|---|---|
| кофе, чай | в пакетиках — housekeeping | сваренный, в номер — fnb |
| вода | бесплатная бутилированная — housekeeping | платная сверх нормы — fnb |
| чайник, фен | принести в номер — housekeeping | сломан — maintenance |
| утюг, глажка | принести утюг — housekeeping | погладить вещи — laundry |
| полотенца, халат | свежие от отеля — housekeeping | стирка личных вещей — laundry |

## Шаг 1. Заполнить файл профиля

Профиль пилота — `ops/onboarding/pilot-hotel.json` (шесть служб, сроки и
подсказки уже заполнены). Для другого отеля — копия файла рядом.

В файле НЕТ идентичности отеля (slug, название, телефон): репозиторий
публичный, название и телефон живого отеля в нём не место — они приходят
аргументами команды. Перед первым запуском **сверить с отелем**: `city`,
`timezone`, `default_language` и состав `categories`.

```json
{
  "key": "fnb",
  "name": "Ресторан и room service",
  "reminder_after_minutes": 10,
  "hints": "готовые еда и напитки в номер, сваренный кофе ..."
}
```

- `key` — латиница/цифры/дефисы, стабильный: на него ссылаются конфиг,
  AI-инструмент и маршрутизация уведомлений. Переименование `key` = новая
  категория, старые заявки останутся в старой.
- `name` — то, что видит персонал в кабинете и уведомлениях.
- `reminder_after_minutes` — **не оставлять на умолчании**: без своего срока
  служба получает базовые 30 минут, и кабинет пометит просроченным всё, что
  висит дольше получаса (spec 0028).
- `hints` — короткий список типовых предметов (до 300 символов): он уходит в
  описание инструмента каждым ходом диалога, то есть оплачивается токенами.
  Предмет, который выдают две службы, называется у **обеих** — так модель видит
  неоднозначность сама и, по канону промпта, спрашивает гостя, вместо того
  чтобы угадывать.

## Шаг 2. Выполнить онбординг

Локально (из корня репозитория) или на сервере — тогда через
`docker compose exec app`, файл профиля уже внутри образа:

```bash
python -m hospitality.tools.onboard_tenant ops/onboarding/pilot-hotel.json \
    --slug pilot-hotel --name "Название отеля" --reception-phone "+7 727 000 00 00"
```

Команда идемпотентна: создаёт тенанта (если его нет), добавляет недостающие
категории, пересобирает конфиг из профиля. Существующие категории не трогает и
не удаляет; `staff_chats_by_category` переносит как есть. В конце печатает
отчёт — прочитать его целиком: там видно, что реально создано, какой телефон
записан и какие сроки действуют.

Частые отказы:

- `Тенанта со slug 'x' нет` — опечатка в `--slug` либо первый запуск без
  `--name` (создать тенанта без имени команда откажется намеренно).
- `Конфигурация тенанта не соответствует схеме (ERR-PLATFORM-006)` — дрейф
  данных, разбирать по `docs/runbooks/errors.md`, не перезаписывать вслепую.

## Шаг 3. Чаты служб (пока персонал в Telegram)

Уведомления службы уходят в её чат; чата нет — в общий чат инсталляции
(`TELEGRAM_STAFF_CHAT_ID`), это штатное поведение (spec 0026):

```bash
python -m hospitality.tools.staff_routing housekeeping=-100… fnb=-100…
```

Основная поверхность персонала с пилота — кабинет (`/staff`, spec 0033),
доступы сотрудникам выдаются приглашениями из самого кабинета (`docs/RBAC.md`).

## Шаг 4. Проверить живьём (чек-лист приёмки)

- [ ] `python -m hospitality.tools.onboard_tenant … ` отработал, в отчёте
      столько категорий, сколько служб у отеля;
- [ ] гость пишет просьбу по каждой службе → заявка создаётся и приземляется в
      нужную (в кабинете видно категорию);
- [ ] **неоднозначная просьба** («принесите кофе») → бот **уточняет**, а не
      выбирает службу молча;
- [ ] неавторизованный гость в веб-чате получает отказ **с телефоном
      ресепшена** (шаг 2 без `--reception-phone` его не запишет);
- [ ] невзятая заявка службы с коротким сроком помечается просроченной в
      кабинете раньше, чем заявка службы с длинным (spec 0028);
- [ ] дневной бюджет LLM на тенанта поднят под объём отеля (issue #125) и алерт
      на 80% включён (issue #103) — иначе исчерпание видно только по жалобам.

## Что НЕ входит в онбординг v0

Знания отеля/RAG, политики обслуживания и квоты (issue #124), источник
проживаний из PMS (issue #122) — Фаза 1; самообслуживание отеля — Фаза 4.
Заселение гостей и выдача кодов — страница заселения кабинета (spec 0033) или
`python -m hospitality.tools.checkin`.
