# Спека 0018 — Наблюдаемость: Sentry, метрики, минимальный трейсинг

- **Задача:** Task 0018 (PHASE0.md); FOUNDATION §10.4, §10.7, §10.8, §10.12;
  R-2/R-7/R-8. Класс ревью — A (kernel `shared/`, `ai/gateway`, новый эндпоинт,
  staging-конфигурация).
- **Открывает:** 0019.

## Проблема

Система не сообщает о своих проблемах сама. Логи есть (§10.1–10.2), но их
никто не читает непрерывно: упавший на staging Postgres, всплеск 500-х или
сгоревший дневной бюджет LLM обнаружатся только при ручной проверке. До
первого пользователя (Phase 1) нужны три вещи: автоматический сбор
необработанных ошибок с контекстом, метрики в стандартном формате и активный
алерт в Telegram-канал команды.

## Решение — четыре части

### 1. Sentry (managed, §10.4 + §10.12)

Зависимость `sentry-sdk`; новый модуль `shared/sentry.py` с единственной
функцией `init_sentry(settings)`, вызываемой из обоих composition root'ов —
`app.py` (`create_app`) и `worker.py` (`main`). Пустой `SENTRY_DSN` — Sentry
выключен (канон «пустой секрет валиден», как `ANTHROPIC_API_KEY`): dev/CI
работают без внешнего сервиса, лог `sentry_disabled` фиксирует это явно.

- **Контекст события (§10.4):** глобальный `before_send`-хук читает
  `structlog.contextvars.get_contextvars()` и проставляет тэги `tenant_id` и
  `correlation_id`. Один механизм покрывает оба процесса: в HTTP-запросе
  contextvars биндят `CorrelationIdMiddleware`/`TenantContextMiddleware`, в
  воркере — `tenant_context()` на каждое событие. Ничего не дублируется в
  каждом обработчике.
- **Что уходит в Sentry:** только необработанные исключения (интеграции
  Starlette/FastAPI и штатный `sys.excepthook`). Ожидаемые `AppError`
  перехватываются `register_error_handlers` и в Sentry не попадают — они
  диагностируются каталогом ошибок (§10.5), а не трекером.
- **PII:** `send_default_pii=False` (умолчание SDK); тела запросов не
  отправляются. `traces_sample_rate` не задаётся (0) — производительность
  трассирует OTel в Phase 1, не Sentry.
- **Окружение:** `SENTRY_ENVIRONMENT` (умолчание `dev`, staging ставит
  `staging`) — события staging и будущего prod разделяются в одном проекте.
- Для тестов `init_sentry` принимает необязательный `transport` — события
  перехватываются в память, реальный DSN не нужен.

### 2. `/metrics` в Prometheus-формате (§10.7)

Зависимость `prometheus-client`; новый модуль `shared/metrics.py`:
объявления метрик, функции записи и роутер `GET /metrics`
(`text/plain; version=0.0.4`). Prometheus-сервера в Phase 0 нет и не
появляется (без Grafana-стека): формат стандартный, потребитель сегодня —
алертер (часть 3) и `curl` основателя, завтра — любой managed-scraper.

| Метрика | Тип | Лейблы | Откуда пишется |
| --- | --- | --- | --- |
| `http_requests_total` | Counter | `method`, `route`, `status` | `CorrelationIdMiddleware` — тот же `finally`, что пишет `http_request` |
| `http_request_duration_seconds` | Histogram | `method`, `route` | там же |
| `llm_calls_total` | Counter | `tenant_id`, `model`, `status` | `ai/gateway/service._log_call` — единая точка всех исходов (ok/timeout/error/budget_exceeded — последний с issue #374) |
| `llm_tokens_total` | Counter | `tenant_id`, `model`, `direction` | там же (только ok) |
| `llm_cost_usd_total` | Counter | `tenant_id`, `model` | там же (только ok) |
| `outbox_pending_events` | Gauge | — | запрос `COUNT(*) WHERE processed_at IS NULL AND dead_lettered_at IS NULL` в момент scrape — только очередь на доставку (dead-letter из неё выбывает, ADR-015) |
| `outbox_dead_letter_events` | Gauge | — | там же: `COUNT(*) WHERE dead_lettered_at IS NOT NULL` — события, доставку которых система прекратила (issue #133, ADR-015) |
| `worker_heartbeat_age_seconds` | Gauge | — | отдельный запрос по первичному ключу к `worker_heartbeats` в момент scrape: секунд с последней отметки воркера; `NaN` — БД недоступна или отметки нет (issue #136) |
| `llm_daily_spend_usd` | Gauge | `tenant_id` | снимок в момент scrape: сумма `cost_usd` тенанта за текущие UTC-сутки — то же число, по которому gateway отказывает на ERR-AI-002 (issue #103) |
| `llm_daily_budget_usd` | Gauge | `tenant_id` | там же: дневной лимит, с которым это число сравнивается (`LLM_TENANT_DAILY_BUDGET_USD`) |
| `llm_provider_failure_streak` | Gauge | `tenant_id`, `status` | снимок в момент scrape по `llm_call_log` (`ai/gateway/outcomes.py`): вызовы провайдера со статусом `error` / `timeout` после последнего `ok` (issue #374) |
| `llm_budget_rejection_streak` | Gauge | `tenant_id` | там же: строки `budget_exceeded` после последнего прошедшего бюджет вызова в текущих UTC-сутках; больше нуля — бот молчит (issue #374) |
| `llm_mentor_failure_streak` | Gauge | `tenant_id`, `status` | там же, у «Наставника» (`purpose = 'mentor'`): серия по каждой его модели из настроек, в метрике худшая (issue #911) |
| `llm_mentor_budget_rejection_streak` | Gauge | `tenant_id` | там же: отказы дневного потолка наставника подряд, худшая из его моделей; больше нуля — сотрудники без ответа (issue #911) |
| `guest_text_oldest_age_seconds` | Gauge | `tenant_id` | снимок в момент scrape (`channels/common/retention.py`): `min(messages.created_at)` под контекстом каждого тенанта; без сообщений — 0; БД недоступна — серий нет (issue #410) |

Решения:

- **`route` — шаблон маршрута** (`/api/v1/requests/{request_id}`), не сырой
  путь: сырой путь взрывает кардинальность (UUID в URL, сканеры). Немэтчнутые
  запросы (404 от сканеров) собираются под константой `unmatched` — след
  сканирования виден, кардинальность ограничена.
- **RED-статус** — класс `2xx`/`4xx`/`5xx`, не точный код: алертеру и человеку
  нужен именно класс, точный код есть в логах `http_request`.
- **`tenant_id` как лейбл LLM-метрик** — требование §10.7 («по тенантам»);
  кардинальность = число отелей, это десятки. RED-метрики по тенантам не
  режутся (роутов × тенантов не нужно никому в Phase 0).
- **Глубина outbox считается в момент scrape** через `platform_session_scope()`
  (outbox — кросс-тенантная инфраструктурная таблица, как в
  `deliver_pending_events`). Недоступная БД не роняет `/metrics` (алертер
  обязан продолжать читать счётчики 5xx): gauge выставляется в `NaN`, ошибка
  логируется. Своего HTTP у процесса-воркера нет, поэтому его здоровье видно
  тем же способом: он пишет отметку пульса в БД, а `/metrics` приложения
  отдаёт наружу её возраст (`worker_heartbeat_age_seconds`, issue #136);
  вторая линия — глубина outbox (растёт = воркер стоит или не успевает),
  третья — Sentry (ERROR-логи воркера становятся событиями).
- **Расход к лимиту считает владелец данных, а не kernel** (issue #103):
  `llm_call_log` — тенантная таблица под RLS, платформенная сессия не видит в
  ней ни строки (ADR-003), а исключение диспетчера `outbox_events` в
  бизнес-таблицы не копируется. Поэтому снимок собирает `ai/gateway`
  (`refresh_budget_metrics`) — запросом на тенанта внутри его контекста, — и
  кладёт сюда через `set_llm_daily_budget()`. Kernel импортировать `ai/` не
  вправе (R-5), поэтому зависимость обратная: `shared/metrics.py` держит реестр
  обновляторов, а подключает их composition root — единственный, кому видны оба
  слоя. Пара публикуется и стирается **вместе**: доля от лимита имеет смысл,
  только если оба числа из одного снимка; недоступная БД оставляет метрики
  пустыми, и для алертера это «не знаю», как `NaN` у gauge без лейблов.
  Запросов на scrape — по числу тенантов инсталляции (единицы, запрос
  индексный); когда их станут сотни, лечится счётчиком-агрегатом, а не
  ослаблением изоляции.
- **`/metrics` анонимен** — явное решение (§11: «анонимный доступ — явное
  решение, а не умолчание»), симметрично `/health/*`: PII в метриках нет,
  секретов нет; токен для алертера — лишняя связность Phase 0. Пересмотр — при
  выходе в прод (reverse-proxy/allowlist), фиксируется в «Известных
  отступлениях» README `shared`.

### 3. Алертер → Telegram-канал команды (§10.8)

Новый entrypoint `hospitality/tools/alerter.py` — простейший watchdog-цикл,
запускается как четвёртый сервис staging-стека **тем же образом приложения**
(канон «один образ, другая команда», §5.3, как `worker`). Отступление от буквы
карточки («`ops/` алертинг»): скрипт в `ops/` потребовал бы отдельного
механизма доставки файла на сервер; в образе он приезжает существующим
деплоем. В `ops/deploy/docker-compose.staging.yml` добавляется сервис
`alerter`; сам код — в `tools/` (композиционный слой, там же живут `seed` и
`publish_demo_event`).

Цикл раз в `ALERT_POLL_INTERVAL_SECONDS` (60):

1. `GET {ALERT_TARGET_BASE_URL}/health/ready` (таймаут 5 c). Не-200 или
   сетевая ошибка — счётчик подряд неудач; на
   `ALERT_READY_FAILURE_THRESHOLD`-й (2) подряд — алерт **ERR-OPS-001**
   (однократно, до восстановления). Первый же успех после алерта — сообщение
   о восстановлении, счётчик сбрасывается. DoD-арифметика: падение Postgres →
   алерт через ~2–3 минуты.
2. `GET {ALERT_TARGET_BASE_URL}/metrics`, суммируются `http_requests_total`
   со `status="5xx"`. Прирост с прошлого опроса ≥
   `ALERT_ERROR_SPIKE_THRESHOLD` (5) — алерт **ERR-OPS-002**, не чаще
   `ALERT_COOLDOWN_SECONDS` (900). Недоступный `/metrics` — пропуск шага. Сам
   отказ — не-200 или сетевая ошибка `/metrics` при ответившем `/health/ready`
   `ALERT_READY_FAILURE_THRESHOLD` опросов подряд — алерт **ERR-OPS-007**
   (однократно, ✅ на выход; issue #264): без метрик молчат все шаги ниже,
   кроме бэкапа и диска. Не ответили оба — лежит всё приложение, это
   ERR-OPS-001; счёт ERR-OPS-007 тогда стоит, второго алерта нет.
3. Оттуда же `worker_heartbeat_age_seconds` старше
   `ALERT_WORKER_HEARTBEAT_MAX_AGE_SECONDS` (300) — алерт **ERR-OPS-003**:
   воркер мёртв или завис, вся доставка событий стоит молча (issue #136).
   Смотрит именно watchdog снаружи — о собственной смерти процесс не доложит.
4. И `outbox_pending_events` выше `ALERT_OUTBOX_DEPTH_THRESHOLD` (100) — алерт
   **ERR-OPS-004**, вторая линия на тот же симптом: она ловит случай, которого
   пульс не видит, — цикл жив и пульс свежий, а очередь не разбирается.
5. И пара `llm_daily_spend_usd` / `llm_daily_budget_usd` по каждому тенанту:
   доля расхода от лимита достигла `ALERT_LLM_BUDGET_RATIO` (0.8) — алерт
   **ERR-OPS-006** (issue #103). Состояние алерта — своё на каждого тенанта: у
   каждого отеля свой лимит и свой день. Тенанта нет в снимке — шаг о нём
   молчит; тенант с нулевым расходом в снимке ЕСТЬ (нулём), иначе алерт о
   вчерашнем расходе некому было бы погасить в новых UTC-сутках. Считать
   прирост `llm_cost_usd_total` самим алертером было бы дешевле, но неверно:
   счётчик обнуляется рестартом приложения, а базовая линия суток теряется
   рестартом алертера — оба отказа молчаливые, ровно того рода, против
   которого заводится этот алерт.
5а. И отказы модели по каждому тенанту (issue #374) — пара gauge, которую
   считает `ai/gateway` по журналу `llm_call_log` (`refresh_call_outcome_metrics`,
   подключение — как у пары бюджета). `llm_provider_failure_streak{status=
   error|timeout}` — неуспешные вызовы провайдера после последнего успешного;
   сумма достигла `ALERT_LLM_FAILURE_STREAK_THRESHOLD` (3) — алерт
   **ERR-OPS-009** (кончился баланс, отозван ключ, провайдер лежит), ✅ — когда
   вызов снова прошёл. `llm_budget_rejection_streak` — отказы по бюджету подряд
   в текущих UTC-сутках; больше нуля — алерт **ERR-OPS-010**: бот уже молчит,
   порога нет. Серия, а не окно времени: при трафике отеля «сообщение в час
   ночью, в минуту днём» любое окно глухо для одного или шумно для другого.
   По журналу, а не по `llm_calls_total`: счётчик живёт в памяти процесса,
   вызовы воркера в `/metrics` приложения не попадают, рестарт его обнуляет.
   Отказ по бюджету для этого пишет свою строку журнала (`budget_exceeded`,
   стоимость 0) — до #374 он бросался до цикла попыток и следа не оставлял.
   Обе ошибки шлюз логирует на WARNING, Sentry их не видит: эта линия —
   единственная. Транзитные 429/529 провайдера сегодня неотличимы от пустого
   баланса (#409), поэтому текст ERR-OPS-009 называет и этот случай.
5в. Те же две серии «Наставника» (issue #911, ADR-024 §7) — своими метриками
   `llm_mentor_*` и своими текстами: ERR-OPS-018 на том же пороге, ERR-OPS-019 с
   первого отказа потолка. Серия — по каждой модели наставника (`LLM_MODEL_MENTOR`,
   `LLM_EMBEDDING_MODEL`): вопрос — эмбеддинг и ответ, и при снятой модели ответа
   общую серию обнулял бы проходящий эмбеддинг.
5г. Отказы хода ИИ сотруднику по любой причине (issue #1050) — счётчик процесса
   `mentor_turn_failures_total{flow, reason}`: исключение кода, незаданная модель
   (отказ до журнала, серии нет), провайдер «через раз» (серия гаснет на успехе),
   незагруженный кодекс, неразобранная оценка ответа. `ALERT_MENTOR_TURN_FAILURES_THRESHOLD`
   (3) отказов у тенанта за скользящие 10 минут или одна неразобранная оценка — алерт
   **ERR-OPS-021**; поштучный и с паузой, как 5б, отказы паузы не теряются. Счётчик, а не
   журнал: ход идёт в процессе приложения (один uvicorn-воркер), а исключения кода и
   оценки в журнале шлюза нет.
5б. И счётчик `escalation_requests_total{outcome="failed"}` по тенантам (issue
   #434): эскалация не стала карточкой в кабинете (spec 0039 §8). Прирост с
   прошлого опроса больше нуля — алерт **ERR-OPS-015**: первый случай сразу,
   дальше по тенанту не чаще `ALERT_COOLDOWN_SECONDS`, случаи паузы — числом в
   следующем сообщении; ✅ нет, алерт поштучный, как ERR-OPS-002. Серия счётчика
   появляется только с первым отказом после старта приложения, поэтому тенант,
   которого нет в ответившем `/metrics`, — ноль, а не «не знаю». Рестарт
   приложения алертер узнаёт по спутнику `escalation_requests_created` (время
   рождения серии) и тогда считает новым всё значение: деплой или откат образа —
   главный повод отказа, и «один до рестарта, один после» по одному «значение
   меньше прошлого» дал бы тишину. Первый снимок после старта алертера — только
   базовая линия. Отказ шаг пишет на WARNING: эта линия для него единственная.
5д. И счётчик `escalations_unaddressed_total{reason}` (issue #1050, часть 4): бот позвал
   человека, а адресата нет — ни карточки в кабинете (служба эскалаций не выбрана или
   карточка не завелась), ни `TELEGRAM_STAFF_CHAT_ID`; гость получил «позвоните на
   ресепшен» (spec 0051), отель о нём не знает. Пишет `escalate` до публикации — её
   исключение случай не прячет. Прирост — алерт **ERR-OPS-024**, поштучный, правила чтения
   серии — как у 5б. ЧП (`reason="emergency"`) — на каждом опросе с новым ЧП, без паузы:
   ЧП редки, и второе в паузе первого — другой гость. Остальные причины — с паузой
   `ALERT_COOLDOWN_SECONDS` по отелю и разбивкой по причинам. Отдельный счётчик, а не
   исход `disabled` у 5б: «службы нет» при заданном чате — норма. Карточка не завелась у
   отеля без чата — придут оба, 015 с причиной и 024 со следствием. Устройство —
   `tools/alerter_unaddressed.py`.
6. И единственная линия не по HTTP: возраст свежайшего `hospitality-*.dump.age`
   в каталоге `ALERT_BACKUP_DIR` старше `ALERT_BACKUP_MAX_AGE_HOURS` (30), файлов
   нет вовсе или каталог не читается — алерт **ERR-OPS-008** (issue #106).
   Каталог бэкапов лежит на хосте и монтируется в контейнер алертера только для
   чтения. Снимки деплоя (`pre-migrate-*`, issue #135) за бэкап не считаются:
   иначе умерший ночной cron маскировался бы ими — той самой тишиной, ради
   которой линия и заводится.
6а. В том же каталоге — метка `offsite-copy.stamp`: её ставит забор копии вне
   сервера с машины основателя (`ops/backup/fetch.sh`, агент раз в час), проверив
   дамп ключом, со временем этого дампа. Метки нет или она старше
   `ALERT_OFFSITE_BACKUP_MAX_AGE_HOURS` (у копии отеля 48; 0 — выключено, умолчание)
   — алерт **ERR-OPS-023** (issue #1061). Сторожит сервер, а не ноутбук: о своём
   отказе ноутбук не скажет. Устройство — `tools/alerter_offsite.py`.
7. Снова из `/metrics`: прирост `guest_rate_limited_total` по scope входа в
   чат — ссылка с листка и ввод кода, без лимитов самого чата — за интервал
   ≥ `ALERT_GUEST_DOOR_THRESHOLD` (1) — алерт **ERR-OPS-014** (issue #415), не
   чаще `ALERT_COOLDOWN_SECONDS`, как ERR-OPS-002: гость получил 429 и в чат не
   попал, а 429 — не 5xx. Устройство — `tools/alerter_guest_door.py`.
8. И `guest_text_oldest_age_seconds` по тенантам (issue #410): самому старому
   сообщению больше `MESSAGES_RETENTION_DAYS` плюс
   `ALERT_GUEST_TEXT_RETENTION_GRACE_HOURS` (48) — алерт **ERR-OPS-017**: ретеншн
   не удаляет, обещание политики «тексты — 90 дней» нарушается (spec 0032 §5).
   Смотрит на результат, а не на маркер прогона: тот пишется и при сбое, а
   «удалено 0 строк» неотличимо от «нечего удалять». Пустой снимок — «не знаю».
8а. Только на контуре `pilot` — невзятые заявки дольше **срока команды** (issue #1050,
   часть 4): `service_requests_forgotten{tenant_id, kind=urgent|regular}` и
   `service_requests_forgotten_oldest_age_seconds`, считает обновлятор scrape кабинета
   (`staff_portal/unclaimed_watch.py`). Срок команды: срочная или эскалация — **10 минут**
   (лестница зовёт ресепшен и менеджера с первой минуты, spec 0045 §4); остальные —
   **три срока службы** `d` (`reminder_delay_for`, тот же, что у метки «просрочена»), то есть
   через `d` после третьей ступени лестницы; выключенный срок — `d` по умолчанию платформы
   (30 мин): выключенные напоминания снимают ступени кабинета, а не страховку команды.
   Больше нуля у отеля — алерт **ERR-OPS-025**, состояние по отелю, ✅ — когда таких
   заявок не осталось. Зачем: сигнал кабинета звучит только из открытой вкладки (§3.4
   spec 0039), уснувшая вкладка молчит, а другого пути к персоналу у отеля «только
   кабинет» нет. Почему только `pilot`: демо-отель staging держит невзятые заявки нарочно,
   а алертер перезапускается каждым деплоем — один и тот же алерт десятки раз в сутки.
   Устройство — `tools/alerter_unclaimed.py`.

Алерты состояния (1, 3, 4, 5, 6, 8, 8а) устроены одинаково: одно сообщение на вход в
проблему и ✅ на выход, а не лента каждую минуту. Пустая метрика (`NaN` — БД
недоступна, или `/metrics` не ответил) для алертера значит «не знаю», а не
«всё хорошо»: шаг молча пропускается; о не ответившем `/metrics` говорит
ERR-OPS-007 (шаг 2).

**Напоминание на контуре `pilot`** (issue #1050, часть 3; `tools/alerter_repeat.py`).
Пропущенное одно сообщение — ночью, в суете на стойке — делает алерт состояния тишиной.
Поэтому на копии отеля (`SENTRY_ENVIRONMENT=pilot`), пока ✅ нет, алертер раз в
`ALERT_STATE_REPEAT_SECONDS` (3600) шлёт «🔁 [pilot] ERR-…: без ✅ уже N ч — что
сломано» с отелем и ссылкой на статью; 0 выключает. Час: пропущенный днём алерт всплывает
в пределах часа, ночь копит 6–7 напоминаний, а не ленту. Первое сообщение не повторяется
слово в слово — его числа устаревают. Перечень открытых алертов линия берёт у машины
(`AlertMonitor.active_state_alerts`), отсчёт — с опроса, на котором алерт открылся.
Пропавшая метрика алерт не закрывает, и напоминание идёт: текст говорит «✅ не было», а не
«проблема на месте». Не напоминаются ERR-OPS-006 (прогноз до конца UTC-суток; вред —
ERR-OPS-010) и поштучные алерты. На staging напоминаний нет: чат общий, проблемы чинят
днём по очереди, и ежечасная лента там приучила бы не смотреть в канал.

Сообщение обязано содержать (§10.8): код ошибки, тенанта (для платформенных
алертов — `platform`), correlation id (для опросов — `—`), детали
(`checks` из тела ready / величину всплеска) и ссылку на
`docs/runbooks/alerts.md`. Отправка — прямой `sendMessage` Telegram Bot API
через `httpx`: канал гостевого бота (`channels/telegram`) сознательно **не**
переиспользуется — тракт алертов обязан работать, даже когда код каналов
сломан (алерт о поломке не может зависеть от поломанного).

Состояние — в памяти процесса (перезапуск = чистый лист, худший случай —
один повторный алерт); никакой БД, Redis и Grafana-стека. Логика цикла —
чистые функции (парсер метрик + машина состояний `AlertMonitor.evaluate()`),
покрываются юнит-тестами без сети.

Состояние линии переключается только после доставки (issue #288): цикл зовёт
`AlertMonitor.deliver()`, который перед каждой линией снимает копию машины и
возвращает её, если Telegram не принял сообщение из-за временного сбоя (сеть,
таймаут, 429, 5xx) — следующий опрос решает заново. Отказ 4xx не повторяется:
повтор того же запроса его не лечит. ERROR `alert_send_failed` — на вход в серию
временных сбоев и на каждый отказ 4xx (`tools/alerter_delivery.py`).

Конфигурация: `TELEGRAM_ALERT_BOT_TOKEN` (можно тот же токен, что у
гостевого бота), `TELEGRAM_ALERT_CHAT_ID` (канал команды). Оба пустые —
алертер логирует `alerting_disabled` (WARNING, повтор раз в час) и пассивно
спит: деплой без настроенных алертов остаётся зелёным, а неконфигурация
видна в логах. Частично заполненная пара — ошибка конфигурации, немедленное
падение с внятным сообщением (fail-fast, как `Literal` у `LOG_LEVEL`).

Известное ограничение (в runbook): алертер живёт на том же сервере — смерть
всего VPS Telegram-алерта не даст. Лечится бесплатным внешним uptime-сервисом на
`/health/ready` (managed, §10.12) — ручной шаг основателя после этой задачи,
в DoD не входит.

**Сторож сторожа (issue #229, аудит 05.08 Д-1).** Самого алертера внутри не
стережёт никто: падение, рестарт-луп на полузаполненной паре, пассивный режим и
смерть VPS одинаково немы. Поэтому:

- `main()` алертера зовёт `init_sentry`, как app и worker; DSN пробрасывает
  compose. Падение цикла и ERROR-логи (`alert_send_failed`) — события Sentry.
  `SystemExit` полузаполненной пары Sentry не видит (excepthook его не получает).
  `alert_send_failed` пишется без `exc_info`: в тексте исключения httpx — адрес
  запроса с токеном бота; вместо трассы — код ответа и описание от Telegram.
- Активный цикл после каждого круга шлёт пульс на `ALERT_HEARTBEAT_URL` —
  проверку healthchecks.io (`tools/alerter_heartbeat.py`), не чаще раза в
  минуту: сервис не записывает больше 5 пульсов в минуту. Пассивный режим пульса
  не шлёт — снаружи «алерты выключены» и «алертер мёртв» неразличимы намеренно.
  Пусто — пульса нет (dev/CI). Адрес — секрет, у каждого контура свой.
- Успех пульса — тело ответа `OK`: на неизвестный адрес healthchecks.io отвечает
  `200 OK (not found)`, а проверка без единого пульса стоит в New и не
  тревожит. Сбой — **ERR-OPS-011**, ERROR один раз на вход в сбой, без адреса.
- Смерть одного туннеля пульс не видит (алертер ходит внутрь docker-сети) —
  это внешний монитор публичного адреса, #407.

### 4. OTel — только заготовка (R-11: трактовка зафиксирована)

Карточка: «OTel — только заготовка, полный трейсинг не раньше Phase 1, чтобы
не перепроектировать». Трактовка: **ни зависимостей, ни no-op-кода** —
мёртвый код хуже отсутствующего. Заготовка = зафиксированные точки
подключения:

- поле `trace_id` уже обязательно в каждой лог-записи (§10.1, `logging.py`) и
  ждёт значения;
- `init_sentry` и `configure_logging` вызываются из одних и тех же двух
  composition root'ов — `init_tracing()` Phase 1 встанет рядом одной строкой;
- план Phase 1 описан в `docs/runbooks/alerts.md` (раздел «Что дальше»):
  `opentelemetry-instrumentation-{fastapi,sqlalchemy,redis,httpx}` + процессор
  structlog, пишущий `trace_id` из активного span.

## Коды ошибок (§10.5, R-8)

- **ERR-OPS-001** — `/health/ready` недоступен или нездоров N опросов подряд.
- **ERR-OPS-002** — всплеск 5xx: прирост ≥ порога за интервал опроса.
- **ERR-OPS-003** — пульс воркера старше порога: доставка событий стоит (#136).
- **ERR-OPS-004** — глубина `outbox_pending_events` выше порога (#136).
- **ERR-OPS-005** — воркеру не удалось записать свой пульс: только лог-событие
  `worker_heartbeat_failed`, алерта нет — о последствии скажет ERR-OPS-003.
- **ERR-OPS-006** — расход LLM тенанта дошёл до доли дневного лимита (#103).
- **ERR-OPS-007** — `/metrics` не ответил N опросов подряд при живом
  `/health/ready`: линии из метрик молчат (#264).
- **ERR-OPS-008** — свежего бэкапа БД нет либо каталог бэкапов не читается (#106).
- **ERR-OPS-009** — вызовы провайдера LLM у тенанта неуспешны серией (#374).
- **ERR-OPS-010** — дневной бюджет LLM тенанта исчерпан, вызовы отвергаются (#374).
- **ERR-OPS-011** — пульс алертера наружу не дошёл: только лог-событие
  `alerter_heartbeat_failed`, алерта нет — пропавший пульс заметит сам
  healthchecks.io (#229).
- **ERR-OPS-012** — на диске сервера свободного меньше доли
  `ALERT_DISK_MIN_FREE_RATIO` (#414).
- **ERR-OPS-013** — workflow `CI` или `Smoke` на `main` красный: сообщение шлёт не
  алертер, а последняя job workflow (#413).
- **ERR-OPS-014** — гости упираются в лимит у входа в чат: отказы 429 у двери
  (ссылка с листка, ввод кода) за интервал опроса (#415).
- **ERR-OPS-015** — эскалация не стала карточкой в кабинете: прирост
  `escalation_requests_total{outcome="failed"}` у тенанта (#434).
- **ERR-OPS-017** — самый старый текст гостя у тенанта старше срока ретеншна с
  запасом (#410).
- **ERR-OPS-018** — вызовы провайдера «Наставника» у тенанта неуспешны серией (#911).
- **ERR-OPS-019** — дневной потолок «Наставника» тенанта выбран (#911).
- **ERR-OPS-021** — ИИ в кабинете отказывает сотрудникам: отказы хода за 10 минут или
  неразобранная оценка ответа (#1050).
- **ERR-OPS-023** — свежей проверенной копии бэкапа вне сервера нет дольше порога (#1061).
- **ERR-OPS-024** — ЧП или эскалация без адресата: ни карточки в кабинете, ни чата
  персонала (#1050).
- **ERR-OPS-025** — невзятая заявка дольше срока команды, только `pilot` (#1050).

Статьи — в `docs/runbooks/errors.md`; новый runbook `docs/runbooks/alerts.md`:
что значит каждый алерт, что проверить по шагам (docker compose ps / logs,
`/health/ready` изнутри сервера, Sentry), как проверить тракт алертов вручную,
ограничение «алертер на том же VPS», план OTel Phase 1.

## План тестов (R-7)

1. **Метрики отдаются (DoD):** TestClient — запрос к существующему эндпоинту →
   `GET /metrics` — 200, `text/plain`, содержит `http_requests_total` с
   лейблом `route` = шаблон (не сырой путь с UUID) и классом статуса.
2. Немэтчнутый путь (`/no/such/route`) → лейбл `route="unmatched"`.
3. **LLM-метрики:** `complete()` на `MockLlmProvider` внутри
   `tenant_context` → `llm_calls_total{status="ok"}` и `llm_cost_usd_total`
   выросли; ошибка провайдера → вырос `llm_calls_total{status="error"}`.
4. **Глубина outbox:** опубликованное недоставленное событие →
   `outbox_pending_events` ≥ 1 в выдаче `/metrics`; похороненное событие
   (`dead_lettered_at`) уходит из `outbox_pending_events` в
   `outbox_dead_letter_events` — очередь возвращается к нулю (issue #133).
5. **Sentry (DoD):** `init_sentry` с in-memory transport; необработанная
   ошибка в эндпоинте внутри контекста тенанта → событие захвачено, тэги
   `tenant_id`/`correlation_id` совпадают с ответом; `AppError` 4xx события
   НЕ порождает.
6. **Алертер (машина состояний, без сети):** порог подряд-неудач → один
   алерт ERR-OPS-001 + одно восстановление; всплеск 5xx → ERR-OPS-002 с
   cooldown; недоступный `/metrics` не алертит; парсер метрик на образце
   реальной выдачи prometheus_client. Пульс и глубина (issue #136): устаревший
   пульс → один ERR-OPS-003 + ✅, очередь выше порога → ERR-OPS-004; выдача
   `/metrics` с обоими значениями за порогом проходит весь тракт цикла
   (`MockTransport` → парсер → машина → отправка) и даёт оба алерта.
7. **Бюджет LLM (issue #103):** снимок `refresh_budget_metrics` содержит
   расход каждого тенанта (в том числе нулевой у молчавшего) и лимит;
   недоступная БД оставляет метрики пустыми. Машина: переход через долю →
   один ERR-OPS-006 с процентом и суммой, возврат ниже → ✅; состояние по
   тенанту (алерт одного отеля не глушит другой); пустой снимок состояния не
   меняет; доля вне (0; 1) выключает линию. Тракт `/metrics` → парсер → машина
   → отправка на выдаче с двумя тенантами. Подключение обновлятора в
   `create_app()` и живучесть `/metrics` при падении одного обновлятора.
8. **Свежесть бэкапа (issue #106):** машина состояний — старый дамп даёт один
   ERR-OPS-008 и ✅ на свежий; пустой и нечитаемый каталог алертят (в отличие от
   пустой метрики: «не знаю» про бэкап — тоже алерт); пустой `ALERT_BACKUP_DIR`
   выключает линию. Чтение каталога — на настоящей файловой системе (`tmp_path`):
   снимки деплоя `pre-migrate-*` игнорируются, обрывки `.part` и `backup.log`
   тоже, берётся свежайший из ночных. Тракт «каталог на диске → машина →
   отправка» проходит цикл целиком.
9. Существующие тесты `shared`/gateway — зелёные без правок утверждений.
