# Spec 0022 — Эскалация к человеку: staff-чат узнаёт о каждом «зову сотрудника»

- **Статус:** implemented
- **Дата:** 2026-07-25
- **Источник:** issue #36 (блокер пилота, найден полным ревью Фазы 0): два пути
  кода обещают гостю человека, но персонал не узнаёт об этом ничего.
- **Связанные решения:** P-6 (события для побочных эффектов), P-8
  (идемпотентность), P-9 (human-in-the-loop), §7.8 (деградация), ADR-005
  (outbox, at-least-once), ADR-011 (доставка уведомлений каналом).

---

## Проблема

Гость слышит «зову сотрудника» — и никто не приходит. Два пути:

1. **`TurnKind.NEEDS_HUMAN`** (`ai/orchestrator.py`): модель вызвала
   неизвестный инструмент или исполнение инструмента упало (ERR-AI-004 —
   например, у тенанта нет категории, которую назвала модель). Гость получает
   «Секунду, я подключу сотрудника отеля» — и всё.
2. **Деградация §7.8** (`channels/telegram/guest.py`): провайдер LLM недоступен
   (ERR-AI-001/002/003), канал отвечает `DEGRADED_REPLY` («…уже зову сотрудника
   отеля») — тоже никого не зовёт.

Подписчики уведомлений существуют только для `request.created` и
`request.status_changed`. Обещание бота — ложь; это подрывает доверие к боту
до пилота (milestone «Пилот: первый отель»).

## Развилка: доменное событие через outbox VS прямой send из канала

Issue оставляет выбор: событие `conversation.escalated` от композиционного слоя
либо прямое уведомление из канала («у канала уже есть sender»).

**Выбрано: событие через outbox.** Аргументы:

1. **Надёжность — суть задачи.** Прямой `sender.send_message` из обработчика
   вебхука при сбое отправки (сеть, Telegram 5xx) теряет эскалацию: молча
   (`send_reply` best-effort — тот самый класс лжи, который чиним) или вместе с
   вебхуком (500 → ретрай Telegram гасится дедупом `update_id` → эффект потерян
   навсегда). Через outbox сбой отправки пробрасывается воркеру, который
   ретраит с backoff (ADR-009): эскалация, закоммиченная в outbox, доставится.
2. **Канон уже существует (P-12, R-10).** «Сообщить в staff-чат» уже делается
   подписчиком события (`request.created` → `notify_staff_on_request_created`).
   Прямой send создал бы второй паттерн той же типовой задачи.
3. **Аудит.** Строка outbox — журнал эскалаций (P-6: «естественный аудит»),
   без отдельной таблицы.
4. **Цена — секунды поллинга воркера** — неважна: сотрудник реагирует минутами.
   Воркер и так обязателен для уведомлений о заявках (тот же процесс).

Аргумент «у канала уже есть sender» отклонён: у подписчиков sender тоже есть
(замыкание `notifications.register()`), новой проводки не требуется.

Слои не нарушены: событие публикует и потребляет композиционный слой
(`channels/telegram`), шина (`shared/events`) — kernel, доменные модули не
затронуты. Прецедент «событие композиционного слоя» допущён самим issue.

## Решение

### 1. Оркестратор отдаёт контекст эскалации (P-7)

`OrchestratorTurn` получает поле `escalation: EscalationContext | None` —
задано ⟺ `kind is NEEDS_HUMAN` (инвариант обоих return-путей):

- `reason` — enum `EscalationReason`: `unknown_tool` | `tool_execution_failed`
  | `llm_unavailable` (последний ставит канал, не оркестратор — деградация §7.8
  остаётся заботой канала);
- `error_code` — код каталога (ERR-AI-001…004) для логов и диагноза;
- `tool_name`, `action_summary`, `room_number` — что гость просил (из
  аргументов инструмента, когда известны): на ходе подтверждения последняя
  реплика гостя — «да», и без summary персонал не поймёт, о чём речь.

### 2. Событие `conversation.escalated` (`channels/telegram/events.py`, новый файл)

Копия канона `platform/events.py` (анатомия §5.2): наследник `DomainEvent`.
Нагрузка: `conversation_id`, `inbound_message_id` (естественный ключ
идемпотентности эффекта), `chat_id`, `guest_message` (последняя реплика),
`reason`, `error_code`, `tool_name?`, `action_summary?`, `room_number?`.
Там же — `publish_escalation()`: публикация в собственной транзакции
(бизнес-записи, с которой можно разделить транзакцию, здесь нет: сам факт
эскалации и есть полезная нагрузка).

### 3. Публикация в `guest.py` — оба пути, обещание после коммита

- `AppError` от оркестратора (ERR-AI-001/002/003) → `publish_escalation(...)`
  с `reason=llm_unavailable`, затем `DEGRADED_REPLY`;
- `turn.escalation is not None` (NEEDS_HUMAN) → `publish_escalation(...)`,
  затем реплика гостю.

**Инвариант порядка: реплика-обещание уходит только после коммита эскалации в
outbox.** Если публикация упала (БД умерла посреди запроса), гость получает
молчание, а не ложное обещание; вебхук отвечает 5xx. Ретрай Telegram будет
погашен дедупом `update_id` — эффекты этого хода потеряны; это ранее принятый
компромисс канала Phase 0 (см. `outbound.py`), мы его не расширяем и не чиним.

### 4. Подписчик `notify_staff_on_conversation_escalated` (`notifications.py`)

Канон подписчика-уведомления (как `notify_staff_on_request_created`):

- идемпотентность (P-8) — ключ `staff:escalated:<inbound_message_id>` через
  `notification_already_sent` / `record_outbound_message`;
- **без LLM**: перевода последней реплики нет — в случае `llm_unavailable`
  причина эскалации и есть недоступность ИИ; путь эскалации обязан не зависеть
  от ИИ вовсе. Персонал видит оригинал реплики гостя и `action_summary`
  (он по контракту инструмента уже на языке гостя); резерв — встроенный
  переводчик Telegram;
- текст: шапка «🆘 Гостю нужен сотрудник», `Чат`, `Комната` (или «—»),
  `Просьба` (если известна), `Последняя реплика` (обрезается до 400 символов —
  длинная реплика не должна упереть сообщение в лимит Telegram 4096 и
  зациклить ретраи доставки), строка причины по-русски;
- staff-чат не настроен → warning-лог с кодом **ERR-TELEGRAM-002** (новый код
  каталога; тот же код добавляется существующему пропуску в
  `notify_staff_on_request_created`) и выход без исключения (ретраить нечего —
  конфигурация не появится от повтора);
- сбой отправки пробрасывается — воркер ретраит (ключ гасит дубль).

Регистрация — внутри `notifications.register()`; `worker.py` не меняется.

### 5. Идемпотентность — два эшелона (P-8)

1. **Вход:** повтор вебхука (тот же `update_id`) гасится
   `insert_inbound_message` до всякой обработки — вторая публикация события не
   рождается (существующий механизм).
2. **Эффект:** повторная доставка события (at-least-once, ADR-005) гасится
   естественным ключом `staff:escalated:<inbound_message_id>` — второе
   сообщение в staff-чат не уходит.

### 6. Наблюдаемость (P-10)

Структурированные логи на всех шагах (`escalation_published`,
`staff_escalation_notified`, `staff_escalation_skipped_duplicate`,
`telegram_staff_chat_not_configured` + `error_code`), `tenant_id` — из
контекста тенанта, `correlation_id` вебхука протаскивается outbox'ом в
доставку (существующий механизм §10.2) и пишется в `Message`. Новый код
ERR-TELEGRAM-002 — статья в `docs/runbooks/errors.md` в этом же PR.

## Вне скоупа (зафиксировано, не потеряно)

- **Модель «эскалирует словами»** (`TurnKind.REPLY`): промпт `concierge_v3`
  разрешает «offer to bring in a staff member» свободным текстом — это третий
  путь обещания без эффекта, структурно не детектируемый. Лечится отдельным
  AI-инструментом `escalate_to_staff` (+ prompt v4 + evals) — заведён
  follow-up issue (см. PR).
- Кнопки под эскалацией («взять гостя»), staff→guest переписка через бота —
  Phase 1.
- Комната гостя в деградационном пути неизвестна (нет модуля `guests/`) —
  честное «—».

## План тестов (DoD #36)

1. **«Инструмент упал → уведомление ушло»** (E2E через вебхук, канон
   walking-skeleton): модель предлагает заявку с категорией, которой нет у
   тенанта → гость подтверждает → ERR-AI-004 → NEEDS_HUMAN; гость получил
   «Секунду, я подключу сотрудника отеля», `deliver_pending_events()` →
   в staff-чате сообщение с чатом, просьбой (`action_summary`), последней
   репликой; `Message` с ключом `staff:escalated:<id>` и `correlation_id`
   вебхука.
2. **«Деградация LLM → уведомление ушло»** (E2E): провайдер таймаутит все
   попытки → ERR-AI-001 → `DEGRADED_REPLY`; после доставки — сообщение в
   staff-чате с причиной «ИИ недоступен».
3. **«Дубликат вебхука → ровно одно уведомление»** (E2E): тот же update дважды
   + доставка — один входящий, одна публикация, одно сообщение в staff-чате.
4. **Повторная доставка события → один эффект** (юнит подписчика, канон
   `test_notifications.py`): второй вызов с тем же событием — скип по ключу.
5. **Staff-чат не настроен** (юнит): warning + выход без исключения.
6. **Оркестратор** (юнит, расширение существующих): оба NEEDS_HUMAN-пути
   возвращают заполненный `escalation` (reason/error_code/summary).
