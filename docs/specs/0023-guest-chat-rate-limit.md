# Spec 0023 — Rate-limit гостевого чата: один чат не выжигает LLM-бюджет тенанта

- **Статус:** implemented
- **Дата:** 2026-07-25
- **Источник:** issue #41 (ревью Фазы 0 + аудит карты продукта 18.07): дневной
  LLM-бюджет (`LLM_TENANT_DAILY_BUDGET_USD`, ERR-AI-002) — общий на отель;
  один настойчивый гость или чужой скрипт, нашедший публичного бота, исчерпывает
  его за вечер — и честные гости остаются без AI до конца UTC-суток. Это не
  только про деньги: фактически DoS на весь отель.
- **Связанные решения:** §6 («лимиты на тенанта: rate limits… защита от noisy
  neighbor закладывается сразу»), P-1 (простота), P-8 (идемпотентность),
  P-10 (наблюдаемость), P-11 (конфигурация, а не форки), P-12 (канон),
  §7.8 (деградация), ADR-002 (Redis в стеке).

---

## Проблема

Бюджет LLM защищает тенанта от перерасхода, но не защищает гостей тенанта друг
от друга: лимитов на уровне чата нет. Бот публичный (авторизации гостя в
Phase 0 нет — она появится с per-stay токеном веб-чата, #79), поэтому сценарий
«скрипт шлёт сообщения, пока gateway не начнёт отвечать ERR-AI-002 всем» — не
гипотетический. Экономика пилота оплачивается основателем — каждый впустую
сожжённый вызов буквально стоит денег.

Требование §6 (rate limits на тенанта) в коде не реализовано нигде; Redis в
стеке с Task 0004, но бизнес-кодом не использовался — счётчик этой задачи
станет **каноническим паттерном работы с Redis** (P-12).

## Решение

### 1. Канонический счётчик — `shared/ratelimit.py` (новый файл, CANONICAL)

Fixed-window счётчик в Redis, единственный канон rate-limit'а платформы:

```python
decision = await consume_rate_limit(
    scope="guest_chat_window",      # имя лимита: часть ключа, логов и метрик
    key=f"{tenant_id}:{chat_id}",   # чей лимит; tenant_id обязателен (P-4)
    limit=20,
    window_seconds=600,
)
# RateLimitDecision: allowed, count, limit, available, first_rejection
```

Устройство: ключ `ratelimit:{scope}:{window_seconds}:{key}:{bucket}`, где
`bucket = int(time.time() // window_seconds)` — окно фиксировано по сетке
времени, `INCR` + `EXPIRE` (2 окна, гигиена). Свойства:

- **Просто и атомарно достаточно** (P-1): гонка между `INCR` и `EXPIRE`
  безвредна — счёт ведёт `INCR`, а смена `bucket` сама «обнуляет» окно;
  потерянный `EXPIRE` оставляет лишь мусорный ключ, который не влияет на счёт.
  Без Lua и без требований к версии Redis.
- **Известный компромисс fixed-window:** на границе окон допустим всплеск до
  2N за 2 окна. Для защиты бюджета это приемлемо — точность не цель, потолок
  расхода в худшем случае держит бюджет тенанта (ERR-AI-002). Sliding window —
  усложнение без выгоды здесь (P-1).
- **UTC-сутки бесплатно:** окно 86400 даёт бакет, выровненный по UTC-суткам
  (epoch кратен суткам) — дневная ступень не требует отдельного механизма.

Клиент Redis — `create_redis_client()` в том же файле, **на один вызов** (как
`health.check_redis`), таймаут операций 1 секунда: счётчик стоит на горячем
пути диалога и не имеет права заметно задерживать ответ гостю. Клиент намеренно
не синглтон: пул redis-py привязан к event loop'у создания — кэшированный
клиент ломается при нескольких loop'ах на процесс (по одному на каждый тест
pytest-asyncio); цена TCP-connect'а на сообщение гостя незаметна, loop-безопасный
пул — задача первого горячего потребителя. Подмена в тестах — протокол
`RateLimitRedis` (тот же приём, что `sender`/`provider` в канале).

### 2. Fail-open при недоступном Redis — осознанное решение

Redis упал/недоступен → `consume_rate_limit` возвращает `allowed=True,
available=False` и пишет WARNING `rate_limit_backend_unavailable`. Обоснование:

- Отказ в обслуживании хуже перерасхода: упавший Redis при fail-closed выключил
  бы диалог **всем гостям всех тенантов** — сам rate-limit стал бы DoS-вектором.
- Перерасход при этом ограничен сверху: дневной бюджет тенанта (ERR-AI-002)
  продолжает действовать — worst case и без rate-limit'а стоит
  `LLM_TENANT_DAILY_BUDGET_USD`, как сегодня.
- Недоступность видна: WARNING в логах + `/health/ready` уже мониторит Redis
  (алерт ERR-OPS-001 придёт независимо от этого кода).

При недоступном Redis вторая ступень в том же ходе не проверяется (не ждать
таймаут дважды).

### 3. Две ступени лимита в гостевом чате (`channels/telegram/guest.py`)

Проверка — **до оркестратора** и **после** идемпотентной записи входящего
(история диалога честная: сообщение гостя сохранено, даже если отклонено).
Считаются только TEXT-сообщения гостевого чата — то, что рождает LLM-вызов;
staff-чат, callback-кнопки и UNSUPPORTED (статический ответ без LLM) не
считаются и не ограничиваются.

| Ступень | scope | Лимит (env, дефолт) | Окно |
| --- | --- | --- | --- |
| Всплеск | `guest_chat_window` | `GUEST_CHAT_RATE_LIMIT_MESSAGES` = 20 | `GUEST_CHAT_RATE_LIMIT_WINDOW_SECONDS` = 600 |
| Дневной потолок | `guest_chat_daily` | `GUEST_CHAT_RATE_LIMIT_MESSAGES_PER_DAY` = 200 | UTC-сутки (86400, не настраивается) |

- Значение `≤ 0` отключает ступень (страховочный люк на staging без выкатки).
- Обе ступени инкрементятся на каждое входящее (сообщения, отклонённые
  всплеск-ступенью, продолжают наполнять дневной счётчик — иначе спамер получал
  бы свежий дневной запас после каждого окна).
- Превышение любой ступени → LLM **не вызывается**, гость получает вежливый
  статический двуязычный отказ (ru+en, канон `UNSUPPORTED_REPLY`): для всплеска —
  «подождите пару минут или позовите сотрудника», для дневного потолка —
  «на сегодня лимит исчерпан, обратитесь к сотруднику». Тексты честные:
  обещание «пара минут» не используется там, где ждать до завтра.
- **Отказ отправляется один раз на окно** (на первом превышении,
  `count == limit + 1`); дальнейшие сообщения в окне дропаются молча — иначе
  спам в 1000 сообщений породил бы 1000 исходящих (расход Bot API и такой же
  спам в ответ). Ответ выбирает только первая сработавшая ступень (порядок —
  от жёсткой к мягкой): после дневного потолка window-ступень молчит, а не шлёт
  «подождите пару минут» на каждое новое окно (ревью PR #104). Повтор вебхука
  Telegram не шлёт второй отказ и не двигает счётчик — дубль отсеян
  идемпотентной записью раньше (P-8).
- Значения per-tenant — Phase 1: поля `TenantConfig` (platform/config.py) с
  чтением вместо `Settings` (P-11; тот же путь миграции, что у пер-тенантного
  бюджета LLM — README gateway).

### 4. Наблюдаемость (P-10) и код ошибки

- Каждое отклонение — WARNING `guest_rate_limited` с `error_code=ERR-TELEGRAM-003`,
  `scope`, `chat_id`, `count`, `limit`; `tenant_id` и `correlation_id` — из
  контекста логирования автоматически (canary DoD: tenant_id + chat_id в логе).
- **ERR-TELEGRAM-003** — статья в `docs/runbooks/errors.md`. Лог-код, не
  `AppError` (как ERR-TELEGRAM-002): вебхук обязан отвечать Telegram 200,
  «клиент» здесь — гость, и он получает текст, а не HTTP-ошибку.
- Метрика `guest_rate_limited_total{tenant_id, scope}` (`shared/metrics.py`,
  та же схема, что `llm_calls_total`) — видно и всплеск спама, и слишком
  агрессивный лимит.

## Вне скоупа (зафиксировано, не потеряно)

- **Алерт при ~80% дневного бюджета тенанта** (второй пункт из обсуждения #41) —
  отдельная задача в алертере (механика Task 0018), не смешивается с лимитом
  чата: вынесено в отдельный issue.
- **Авторизация гостя per-stay токеном** — #79 (веб-чат, Phase 1); пер-чатовый
  лимит нужен и после неё (Telegram остаётся публичным).
- **Пер-тенантные значения лимитов** — Phase 1, конфиг тенанта (см. выше).
- **Rate-limit HTTP API (`/api/v1/*`)** — другой вход с другой моделью угроз
  (аутентифицированный сервисный токен); канон `consume_rate_limit` готов к
  переиспользованию там.

## План тестов (DoD #41)

1. **`tests/test_ratelimit.py`** (канон, на fake-Redis): N-е сообщение
   разрешено, (N+1)-е отклонено и только оно `first_rejection`; смена окна
   (параметр `now`) обнуляет счёт; недоступный Redis → fail-open
   (`allowed=True, available=False`); `EXPIRE` ставится при создании ключа.
2. **`channels/telegram/tests/test_rate_limit.py`** (вебхук, DoD):
   при лимите 2 — третье сообщение **не создаёт LLM-вызов** (`provider.calls`
   не растёт), гость получает текст отказа, входящее при этом сохранено в
   `messages` (история честная); четвёртое — молча (нет нового исходящего);
   дневная ступень с лимитом 1 отклоняет второе сообщение своим текстом;
   fail-open — при падающем Redis сообщения продолжают доходить до оркестратора;
   UNSUPPORTED-сообщения не тратят лимит.
