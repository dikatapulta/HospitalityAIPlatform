# Spec 0024 — Шифрование бэкапов БД: дамп с перепиской гостей нечитаем без ключа основателя

- **Статус:** implemented
- **Дата:** 2026-07-26
- **Источник:** issue #81 (гейт пилота). Task 0019 сознательно оставил дампы
  нешифрованными («в БД только демо-данные», отступление от §11 зафиксировано в
  [spec 0019](0019-smoke-and-restore.md)). «До реальных данных гостей» наступает
  в первый день пилота: в дампе — вся переписка гостей (`messages`), то есть
  персональные данные по Закону РК.
- **Связанные решения:** §11 (шифрование бэкапов), §10.10–10.11 (бэкап и
  восстановление, bus factor = 1), P-1 (простота), P-12 (один канон),
  NG-8 (не строить впрок), issue #44 (PII_REGISTRY — рядом по смыслу).

---

## Проблема

Дампы лежат открытым текстом в двух местах: `/opt/hospitality/backups` на VPS и
локальный каталог `backups/` на машине основателя (`make backup-fetch`).
Модель угроз, от которой защищаемся:

1. **Утечка носителя.** Снапшот диска VPS, доступ к панели Hetzner, украденный
   или потерянный ноутбук основателя, чужая резервная копия ноутбука в облаке.
2. **Компрометация сервера.** Взлом даёт доступ и к БД, и к дампам — шифрование
   от этого не спасает *текущие* данные, но спасает **историю**: дампы за 14
   дней (retention) не должны увеличивать урон.
3. **Передача файла.** Дамп по пути «сервер → ноутбук → возможный второй
   носитель» перестаёт быть проблемой, если он зашифрован в точке создания.

Отсюда требование: **на диске дамп существует открытым только внутри одного
прогона `backup.sh`, секунды**; дальше — только шифртекст.

## Решение

### 1. `age` с публичным ключом, а не парольное шифрование

Выбран [age](https://github.com/FiloSottile/age) (асимметричное шифрование,
X25519): на сервере лежит **публичный** ключ (`age1…`), приватный ключ —
только на машине основателя и в его менеджере паролей.

`gpg --symmetric` (вариант из issue #81) **отвергнут**: пароль симметричного
шифрования одновременно является ключом расшифровки, значит он должен быть на
сервере рядом с дампами — ровно та ситуация, от которой мы уходим (угрозы 1–2).
Асимметричный GPG (`gpg --encrypt -r`) модель угроз закрывает так же, как age,
но требует keyring'а на сервере (состояние, которое надо восстанавливать на
новом сервере) и работы с fingerprint'ами; age — одна строка `age1…` в `.env`
и никакого состояния. Второй путь не реализуется (P-12: один канон; NG-8).

Цена решения зафиксирована честно: **потеря приватного ключа = потеря всех
бэкапов**. Поэтому ключ обязан лежать в менеджере паролей основателя рядом с
`.env` staging — это единственная копия, которая переживёт потерю ноутбука
(§10.11, bus factor = 1). В runbook'ах это написано прямым предупреждением.

### 2. Порядок шагов в `backup.sh` — проверка читаемости до шифрования

```
pg_dump -Fc → <stamp>.dump.part      (открытый текст, umask 077, только владелец)
  ├─ файл не пуст?
  ├─ pg_restore --list читает архив?   ← проверка читаемости на открытом дампе
  ├─ age -r <recipient> → <stamp>.dump.age.part
  ├─ шифртекст не пуст и начинается с заголовка age-encryption.org/v1?
  ├─ rm открытого .part                ← открытого дампа на диске больше нет
  └─ mv → <stamp>.dump.age             ← боевое имя получает только шифртекст
```

Инварианты, которые это даёт:

- **Боевое имя = зашифрованный файл.** Как и в Task 0019, «боевое» имя означает
  «файл проверен и годен»: упавший `pg_dump`, битый архив или сбой шифрования
  не оставляют файла, который `make backup-fetch` заберёт как свежайший.
- **Читаемость проверяется до шифрования**, а не вместо неё: `pg_restore --list`
  по-прежнему видит битый дамп в день создания. Проверить читаемость *после*
  шифрования сервер не может — у него нет приватного ключа, и это правильно.
- **`umask 077`** в скрипте: и открытый временный файл, и шифртекст — `0600`
  (до этой задачи дампы были `0664`, читаемы любым пользователем сервера).
- **Fail-closed:** нет публичного ключа / нет бинарника `age` / ключ не похож на
  публичный (`age1…`) → бэкап падает с понятной ошибкой и **не создаёт файла**.
  Молча положить открытый дамп — недопустимо (это и есть issue #81).
- Отдельная защита от типовой ошибки: если в `BACKUP_AGE_RECIPIENT` попал
  **приватный** ключ (`AGE-SECRET-KEY-1…`), скрипт останавливается и требует
  убрать его с сервера и ротировать — приватный ключ на сервере обнуляет смысл
  всей задачи.

Публичный ключ читается из `BACKUP_AGE_RECIPIENT` в `/opt/hospitality/.env`
(канон чтения `.env` — `env_value` из `deploy.sh`) или из одноимённой
переменной окружения (локальный прогон и тесты). Публичный ключ — не секрет, но
живёт он вместе с остальной конфигурацией сервера: одно место, где основатель
правит настройки, и ротация не требует PR.

### 3. Бинарник `age` на сервере — без root

У пользователя `deploy` нет sudo, вход root по ключу закрыт (проверено на
staging), поэтому `apt install age` для **существующего** сервера недоступен.
`age` — статический бинарник Go, поэтому канон такой:

- **новый сервер:** `bootstrap-server.sh` (работает под root) ставит `age` из
  apt, а если пакета нет — скачивает статический бинарник в `/usr/local/bin`;
- **существующий сервер:** основатель кладёт бинарник в
  `/opt/hospitality/bin/age` (каталог деплоя, права `deploy`, root не нужен) —
  однострочник с проверкой sha256 в [restore.md](../runbooks/restore.md).

`backup.sh` ищет бинарник в четырёх местах: `AGE_BIN` (явное указание) → `age`
в `PATH` → `/usr/local/bin/age` → `<каталог скрипта>/bin/age`. Два последних
пути — про cron: у него `PATH=/usr/bin:/bin`, поэтому ни бинарник из
`bootstrap-server.sh`, ни положенный вручную в каталог деплоя иначе не нашлись
бы — и ночной бэкап падал бы там, где ручная проверка по ssh (PATH шире)
показывает зелёный.

### 4. `make backup-fetch` заодно проверяет, что ключ основателя подходит

Худший провал этой задачи — обнаружить в день аварии, что дампы шифровались
ключом, к которому нет приватной половины. Проверить это может только машина
основателя, и она это делает: `fetch.sh` после скачивания расшифровывает
дамп своим приватным ключом и убеждается, что первые байты — `PGDMP`
(магия `pg_dump -Fc`). Это сквозное доказательство «шифровано тем ключом,
которым я умею расшифровывать, и внутри настоящий дамп».

- Приватный ключ ищется в `BACKUP_AGE_KEY` (env или локальный `.env`), по
  умолчанию `~/.config/age/hospitality-backup.key`.
- Ключа нет / `age` не установлен → скачивание считается успешным, но печатается
  понятное «проверка расшифровки пропущена» с инструкцией.
- Проверка не прошла → **ошибка**: нерасшифровываемый бэкап хуже отсутствия
  бэкапа, про такое надо знать сразу.

`fetch.sh` берёт свежайший файл среди `*.dump.age` **и** `*.dump`, но
нешифрованный свежайший дамп — это **ошибка**, а не совместимость: открытые
дампы Task 0019 удалены с сервера 26.07 при внедрении, поэтому появление такого
файла означает, что шифрование отвалилось. Файл при этом скачивается (копия
лучше её отсутствия), но код возврата — ненулевой.

`backup.sh` тоже предупреждает (не падая), если рядом остались нешифрованные
дампы старого формата, и печатает команду удаления — retention сам вычистит их
через 14 дней, но переписку гостей не стоит ждать две недели.

### 5. Восстановление: расшифровка на машине основателя, поток по SSH

Приватного ключа на сервере нет — значит расшифровка происходит **только** у
основателя. Канон восстановления (runbook restore.md):

```
age -d -i <ключ> backups/<дамп>.dump.age | ssh deploy@<IP> 'docker … pg_restore …'
```

Открытый дамп при этом вообще не касается диска сервера — он живёт в потоке.
Вариант «расшифровать в файл, потом scp» задокументирован как запасной (очень
большой дамп, рвущийся канал), с обязательным удалением открытого файла после.

### 6. Раннее предупреждение о молчаливой поломке

Fail-closed рождает новый режим отказа: «шифровать нечем → бэкапов нет вообще».
Дешёвые сигналы, чтобы это не осталось незамеченным до аварии:

- `deploy.sh` в конце деплоя предупреждает, если в `.env` нет
  `BACKUP_AGE_RECIPIENT` (деплой при этом не падает: бэкап и деплой —
  независимые контуры);
- еженедельный `make backup-fetch` падает, если дампов нет вовсе, и печатает
  предупреждение, если свежайший нешифрован;
- строка `backup.log` на сервере остаётся первым источником правды.

Автоматический алерт на «бэкап не создался N часов» — не в этой задаче
(нужен отдельный чек в алертере): **issue #106**.

## Вне скоупа (зафиксировано, не потеряно)

- **Алерт «бэкапа нет»** в алертере (Task 0018) — issue #106 (Phase 1).
- **Шифрование дисков БД** (§11, «шифрование дисков БД и бэкапов»): вторая
  половина требования; решается вместе с хостингом прода в РК (юраудит 22.07,
  дедлайн локализации 25.08.2026), не на staging Hetzner.
- **Несколько получателей** (`-r` несколько раз, второй ключ в сейфе) — не
  нужно, пока копия ключа в менеджере паролей закрывает потерю ноутбука.
- **Шифрование на уровне полей** (документы, реквизиты) — §11, отдельная задача
  вместе с #44 PII_REGISTRY.
- **RPO ≤ 1ч через WAL** — как и в 0019, Phase 1.

## План тестов (DoD #81)

Автотестов у shell-контура нет (и не появляется — канон проекта: bash-скрипты
проверяются прогоном, Python — pytest). Проверки — прогонами:

1. **Локально, `make dev`:** `backup.sh` с тестовой парой ключей →
   на выходе только `*.dump.age`, открытого `.part` не осталось;
   расшифровка приватным ключом даёт архив, который читает `pg_restore --list`.
2. **Локально, негативные:** пустой `BACKUP_AGE_RECIPIENT` → падение без
   создания файла; приватный ключ вместо публичного → падение с требованием
   ротации; несуществующий `age` → падение с инструкцией установки.
3. **Staging:** прогон нового `backup.sh` вручную → `*.dump.age` в
   `/opt/hospitality/backups`; `make backup-fetch` забирает его и подтверждает
   расшифровку ключом основателя (`PGDMP`).
4. **Репетиция восстановления с шифрованным дампом** (случай А, staging): поток
   `age -d | ssh … pg_restore` → сверка контрольных счётчиков до/после →
   `make smoke-staging` зелёный. Результат и тайминги — в журнал restore.md
   (проведена 2026-07-26: счётчики совпали до строки, шаг восстановления — 1 с).
5. **Старые нешифрованные дампы** удалены с сервера после первого успешного
   шифрованного бэкапа.
6. `make check` и CI (включая job smoke) зелёные — контур Python не затронут.
