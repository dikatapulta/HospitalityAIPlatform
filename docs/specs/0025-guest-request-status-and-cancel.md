# Spec 0025 — «Мои заявки»: статус и отмена по запросу гостя

- **Статус:** implemented
- **Дата:** 2026-07-26
- **Источник:** issue #40 (ревью Фазы 0 + дополнение из аудита карты продукта
  18.07): единственная способность AI — создать заявку. На «ну что там с
  уборкой?» и «отмените, уже не надо» модель эскалирует к человеку, хотя данные
  уже есть в системе. Вторая дыра — дубли: гость, попросивший полотенце второй
  раз, создаёт вторую заявку, и служба идёт дважды.
- **Связанные решения:** P-5 (AI — слой поверх ядра, инструменты — тонкие
  обёртки), P-9 (подтверждение действий гостем), §7.3–§7.4 (декларативные
  инструменты, анти-галлюцинация enum'ом), P-4 (RLS), P-6/§13.5 (события —
  контракты, аддитивные изменения), ADR-011 (`request_origins` — привязка
  заявки к диалогу принадлежит каналу), экономика пилота (память проекта:
  токены оплачивает основатель).

---

## Проблема

Гость спрашивает о статусе своей заявки или хочет её отменить. Оба факта уже
в БД (`service_requests` + привязка к диалогу `request_origins`), но модель о
них не знает: в контексте хода нет заявок, а инструмента отмены не существует.
Итог — ручной труд персонала там, где данных достаточно, и дубли заявок.

Issue предлагает два инструмента: `list_my_requests` (класс `auto`) и
`cancel_service_request` (класс `confirm_guest`). При проектировании выявлены
два обстоятельства, которые меняют форму первого:

1. **В оркестраторе Phase 0 нет цикла «tool result → модель».** Обычный ход —
   ровно один вызов LLM; результат инструмента модель не видит (`_execute_tool`
   отвечает гостю текстом из ПЕРВОГО ответа модели). `LlmMessage` гейтвея —
   плоский текст, tool_result-блоков в контракте провайдера нет. Read-инструмент
   без такого цикла бесполезен: модель не сможет пересказать его результат.
   Строить цикл ради списка из 1–3 строк — второй вызов LLM на каждый вопрос о
   статусе и заметная переделка канонического gateway (экономика пилота против).

2. **Анти-дубли требуют, чтобы модель видела открытые заявки ДО решения.**
   Инструмент модель зовёт, когда сама сочтёт нужным — перед созданием дубля ей
   незачем «проверять список». Комментарий в issue формулирует это прямо: «если
   модель видит открытые заявки диалога в контексте, она может ответить „ваша
   заявка #5 уже в работе“ вместо создания дубля».

## Решение

Способность «мои заявки» реализуется **контекстом хода, а не read-инструментом**;
отмена — инструментом по канону `create_service_request`.

### 1. Граница слоёв: кто резолвит «заявки этого диалога»

`request_origins` принадлежит каналу (ADR-011), инструменты живут в `ai/`.
Направление импортов зафиксировано жизнью: `channels → ai` (guest.py зовёт
оркестратор), обратного нет и не появится — AI-слой не знает, что такое
Telegram и диалог.

**Решение:** канал резолвит привязку и передаёт в `orchestrator.handle_message`
снапшот открытых заявок диалога аргументом хода:

```
guest.py:  request_origins(conversation) → ids
           → requests_api.list_open_requests_by_ids(ids)   # RLS, P-4
           → [ActiveRequest(id, daily_number, status, room_number, summary), ...]
           → orchestrator.handle_message(..., active_requests=...)
```

`ActiveRequest` — контракт хода, объявлен в `ai/tools/base.py` (рядом с
`ConfirmationClass`): его заполняет канал, читают оркестратор и инструменты.
Альтернатива «ai читает request_origins сам» отвергнута: появился бы импорт
`ai → channels` (новое направление связи слоёв-сиблингов) либо дублирование
таблицы канала в ядре — оба хуже одного лишнего аргумента.

Снапшот читается на каждом гостевом ходу (2 индексированных SELECT — по
`conversation_id` и по PK). Плата приемлема; у диалога открытых заявок единицы.

### 2. Статус: снапшот в системном промпте (инструмента нет)

Оркестратор добавляет к системному промпту блок (только когда список непуст):

```
# Active service requests in this conversation
- request_id: <uuid> | #5 | status: in_progress | room: 305 | summary: <суть>
```

Промпт `concierge_v4` (версия — новая строка, §7.5) получает правила:

- на вопрос о статусе отвечай ИЗ ЭТОГО СПИСКА, ничего не выдумывая;
- просьба, уже покрытая открытой заявкой, — не дубль: скажи, что заявка #N уже
  в работе, и создавай новую только если гость настаивает, что это другая нужда;
- заявка, которой нет в списке, — честное «не вижу» и предложение позвать
  сотрудника (список — единственный источник правды);
- отмена — только инструментом `cancel_service_request` и только для заявок из
  списка.

DoD «„Где моя заявка?“ → ответ со статусом без участия персонала» проверяется
на scripted-провайдере: тест утверждает, что провайдер получил системный промпт
со снапшотом СВОЕГО диалога (и без чужого), а ответ модели дошёл до гостя.

### 3. Отмена: `cancel_service_request` (класс `confirm_guest`)

Тонкая обёртка над `requests_api.change_request_status` по канону
`create_service_request`:

- **Схема:** `request_id` — строка с **enum из id открытых заявок ЭТОГО
  диалога** (тот же приём анти-галлюцинации, что enum `category_key`, §7.4:
  модель не изобретает id, а выбирает из закрытого списка, который видит и в
  снапшоте); `confirmation_question` — обязательный вопрос-подтверждение на
  языке гостя (UX-поле гейта P-9, как у создания).
- **Состав инструментов хода:** инструмент включается только когда у диалога
  есть открытые заявки (пустой enum бессмыслен и провоцирует галлюцинации).
- **Гейт P-9** — тот же, что у создания: первый ход — `AWAITING_CONFIRMATION` с
  `pending_action`, ход подтверждения — структурный вердикт
  `resolve_confirmation`, исполняется СОХРАНЁННОЕ действие.
- **Валидация на исполнении, не только в схеме:** `execute` повторно проверяет
  `request_id` по снапшоту ТЕКУЩЕГО хода (`ToolTurnContext.active_requests`).
  Id вне списка (чужая заявка, устаревший/подделанный `pending_action`,
  галлюцинация фейка) → `ERR-AI-004` → `NEEDS_HUMAN` с эскалацией. Тенантную
  изоляцию, как всегда, держит RLS (P-4); диалоговую — этот allowed-список.
  Заявка, закрытая персоналом между ходами, выпадает из снапшота и отменена не
  будет — честная эскалация вместо тихой гонки.
- **Исполнение:** `change_request_status(id, CANCELLED,
  resolution_note="Отменена гостем через чат.", initiator=GUEST)`. Причина
  отмены остаётся в заявке для аудита и будущего кабинета персонала.

### 4. Событие `request.status_changed`: аддитивное поле `initiator` (§13.5, Уровень B)

Служба обязана УВИДЕТЬ отмену гостя (DoD), а гость НЕ должен получить абсурдное
«к сожалению, вашу заявку пришлось отменить» в ответ на собственную отмену.
Инициатор перехода — факт о действии, из состояния БД не выводится, поэтому
едет в событии:

```python
class RequestInitiator(enum.StrEnum):
    GUEST = "guest"
    STAFF = "staff"

class RequestStatusChanged(DomainEvent):
    ...
    initiator: RequestInitiator | None = None   # None — не указан (легаси-пути)
```

Поле опциональное с дефолтом `None`: старые строки outbox и существующие
вызовы (`staff.py`, HTTP-роутер) десериализуются/работают без изменений —
их поведение НЕ меняется в этой задаче.

Подписчики (`channels/telegram/notifications.py`):

- `notify_guest_on_request_closed`: `cancelled` + `initiator=GUEST` → пропуск
  (гость уже получил ответ модели «отменил»; извинение персонала — ложь).
  `done` и отмены персонала — как раньше.
- **Новый** `notify_staff_on_request_cancelled_by_guest`: `cancelled` +
  `initiator=GUEST` → сообщение в staff-чат («🚫 Гость отменил заявку #N
  (категория, комната)») + best-effort перерисовка клавиатуры исходного
  уведомления (терминальный статус → кнопки снимаются — персонал не жмёт
  «Готово» по отменённой). Идемпотентность (P-8) — исходящий `Message` с ключом
  `staff:request_cancelled_by_guest:<request_id>`; без LLM (перевод не нужен).

### 5. Ход подтверждения: генерализация под второе действие

`confirmation_gate_v1` и описание поля `reply` в схеме `resolve_confirmation`
писались под единственное действие («acknowledge that the request has been
passed to hotel staff»). Появилось второе — формулировки генерализуются:
`confirmation_gate_v2` + описание `reply` («подтверди, что ОЖИДАВШЕЕСЯ действие
выполнено: заявка передана службе / заявка отменена — по pending action»).
Резервные реплики оркестратора (`_DONE_TEXT`) остаются: в норме текст даёт
классификатор на языке гостя.

### 6. `OrchestratorTurn.created_request_id` — только про созданную заявку

Канал по этому полю записывает `request_origins`; отмена ничего не создаёт.
Модуль инструмента объявляет `CREATES_REQUEST: bool` (create — `True`, cancel —
`False`), оркестратор заполняет `created_request_id` только для создающих
инструментов. Реестр переходит с if/elif на словарь `имя → модуль` — третий
инструмент станет одной строкой.

## Что сознательно НЕ делаем

- **Read-инструмент `list_my_requests` и цикл tool_result.** Снапшот закрывает
  обе потребности (статус + анти-дубли) одним вызовом LLM. Цикл появится, когда
  возникнет инструмент, чей результат нельзя предвычислить до хода (RAG, FAQ).
- **Отмена заявок не из этого диалога** (созданных с ресепшена/по телефону):
  идентичности гостя в Phase 0 нет (§9, Phase 1) — связать «этого гостя» с
  «той заявкой» нечем. Модель честно предлагает сотрудника.
- **Изменение поведения staff-путей**: `staff.py` и HTTP-роутер `initiator` не
  передают (None) — их уведомления и тексты не меняются. Проставить
  `initiator=STAFF` можно будет отдельной косметикой, когда появится
  потребитель этого значения.
- **Свободная причина отмены от гостя** (`reason` в схеме): +1 поле контракта
  ради поля, которое некому читать в Phase 0. `resolution_note` фиксированный.

## DoD (из issue #40) → тесты

| DoD | Тест |
|---|---|
| «Где моя заявка?» → ответ со статусом без персонала | telegram walking-skeleton: снапшот своего диалога в системном промпте scripted-провайдера, ответ дошёл гостю |
| «Отмените» → подтверждение → `cancelled`, служба видит | telegram-тест: гейт P-9 → заявка `cancelled` в БД, staff-чат получил «Гость отменил #N», клавиатура уведомления снята |
| Чужую заявку не увидеть | снапшот диалога A не содержит заявку диалога B (тот же тенант) |
| Чужую заявку не отменить | scripted tool_call с чужим `request_id` → ERR-AI-004, `NEEDS_HUMAN`, заявка осталась открытой |
| Гость не получает «пришлось отменить» на свою отмену | тест подписчика: `cancelled`+`GUEST` → гостю не отправлено, `cancelled`+`None` → отправлено как раньше |

Плюс юниты: enum/состав инструментов по снапшоту, валидация id на исполнении,
`initiator` в событии, `list_open_requests_by_ids` (открытые, порядок, RLS).

## Миграции

Не требуются: новые таблицы/колонки не появляются (`request_origins`,
`pending_action`, `resolution_note` уже есть; поле события — аддитивное).

## Наблюдаемость

Существующие логи оркестратора/реестра покрывают путь (`tool_awaiting_confirmation`,
`pending_action_confirmed`, `tool_executed`, `tool_execution_failed`).
Добавляются: `active_requests_in_context` (сколько заявок в снапшоте хода),
`staff_cancel_notified` у нового подписчика. Коды ошибок новые не нужны:
нарушение контракта инструмента — существующий `ERR-AI-004`, доменные отказы —
`ERR-REQUESTS-002/003`.

## Ограничения и будущее

- Промпт `concierge_v4` проверяется golden-set'ом на scripted-провайдере;
  прогон bake-off на живых моделях (`ai/evals/bakeoff.py`) — ручной шаг
  основателя, как для v3 (замер в докстринге оркестратора).
- Снапшот отдаёт только ОТКРЫТЫЕ заявки. О только что закрытой модель может
  рассказать по истории диалога (уведомление о закрытии — в истории канала).
- В Phase 1 (веб-чат #79, идентичность гостя §9) снапшот естественно меняет
  источник: «заявки этого гостя» вместо «заявки этого диалога» — контракт
  `ActiveRequest` при этом не меняется.
