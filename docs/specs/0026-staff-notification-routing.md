# Spec 0026 — Маршрутизация уведомлений по службам

- **Статус:** implemented
- **Дата:** 2026-07-26
- **Источник:** issue #80 (аудит карты продукта 18.07): все уведомления идут в
  один `TELEGRAM_STAFF_CHAT_ID`. На пилоте (~100 заселений/день) уборка,
  инженерия и IT читают общую ленту: никто не чувствует ответственность за
  «свои» заявки, релевантные тонут в чужих.
- **Связанные решения:** P-11 (различия отелей — конфигурация, не код), §6
  (конфиг тенанта и эволюция его схемы), P-8 (идемпотентность уведомлений),
  P-6 (уведомления — подписчики событий), ADR-011 (staff-чат — заглушка
  кабинета персонала Phase 1), spec 0021 П-2 (кнопки под уведомлением),
  spec 0022 (эскалация), spec 0025 (отмена гостем).

---

## Проблема

Один staff-чат на весь отель — это лента, в которой службы читают чужое.
Разные службы (housekeeping / maintenance / IT) обслуживают разные категории
заявок и физически сидят в разных группах Telegram.

Одновременно один чат — это ещё и граница «кто персонал»: диспетчер вебхука
считает staff'ом ровно один чат (`chat_id == TELEGRAM_STAFF_CHAT_ID`) и только
в нём трактует текст как команды (`/done 5`), а не как реплику гостя. Как
только чатов становится несколько, эта развилка перестаёт быть сравнением
строк — и становится местом, которое обязано быть безопасным.

## Решение

### 1. Где живёт маппинг: конфиг тенанта (P-11, §6)

Новое **необязательное** поле `TenantConfig`:

```python
staff_chats_by_category: dict[str, str] = {}   # category_key → id staff-чата
```

- Ключ — `key` категории заявок (`request_categories.key`: `housekeeping`,
  `maintenance`, …): стабильный идентификатор, который уже используют
  AI-инструменты и сиды. Не `category_id`: UUID у каждого тенанта свой,
  конфиг стал бы нечитаемым и непереносимым.
- Значение — внешний id чата канала уведомлений персонала (Phase 0 — Telegram
  `chat.id` строкой, как `Conversation.external_id`).
- Поле необязательное со значением по умолчанию → `schema_version` остаётся `1`
  (§6: аддитивное изменение схемы не требует миграции конфигов). Пустой
  маппинг = сегодняшнее поведение: всё в дефолтный чат.
- Валидация (иначе опечатка молча выключает маршрутизацию): ключ обязан
  соответствовать формату ключа категории (`^[a-z0-9]+(-[a-z0-9]+)*$`),
  значение — непустая строка. Формат самого chat_id намеренно НЕ проверяется:
  kernel не знает синтаксиса конкретного канала.

Дефолтный чат остаётся в окружении (`TELEGRAM_STAFF_CHAT_ID`): это свойство
инсталляции бота, а не отеля, и он уже там. Категория без маппинга и все
уведомления вне категории → дефолтный чат.

Правило фолбэка и состав множества staff-чатов живут в самом `TenantConfig` —
двумя чистыми методами, чтобы у правила было ровно одно место (P-12):

```python
config.staff_chat_for(category_key, default=...) -> str          # маршрут уведомления
config.staff_chat_ids(default=...) -> frozenset[str]             # граница «кто персонал»
```

### 2. Подписчики: чат выбирается по категории заявки

`channels/telegram/notifications.py`:

| Подписчик | Куда шлёт | Почему |
|---|---|---|
| `notify_staff_on_request_created` | чат категории заявки → дефолтный | заявка принадлежит службе |
| `notify_staff_on_request_cancelled_by_guest` | тот же чат категории → дефолтный | служба, которая видела «Новая заявка #N», обязана увидеть отмену |
| `notify_staff_on_conversation_escalated` | **всегда дефолтный** | у эскалации нет категории |

Про эскалацию — решение осознанное, а не «не успели». `ConversationEscalated`
не несёт категории и не может её нести: половина эскалаций — это `llm_unavailable`,
где именно классификация и не состоялась. Гадать категорию по тексту гостя
означало бы звать LLM на пути, который обязан работать без LLM (spec 0022).
Дефолтный чат — это чат «уровнем выше», ровно тот адресат, который issue #80
называет заготовкой SLA-эскалаций Phase 1.

Категория резолвится через `requests_api.list_categories()` (id → key) — тем же
чтением, что уже делает `_category_name` для текста уведомления; на одно
уведомление приходится один такой вызов, а не два.

**Деградация.** Конфиг недоступен (онбординг не завершён, дрейф схемы) или
категория не найдена → дефолтный чат + WARNING в лог. Уведомление важнее
маршрутизации (§7.8): служба прочитает его в общей ленте, а не потеряет.

**Идемпотентность не меняется** (P-8): ключи уведомлений уже содержат
`request_id`/`inbound_message_id` и от адреса чата не зависят. Смена маппинга
между доставками не порождает дубль в новом чате — ключ уже занят.

### 3. Кнопки под уведомлением едут в свой чат

`edit_message_reply_markup(chat_id, message_id, …)` требует чат, в котором
лежит сообщение. Пока чат был один, годился любой источник chat_id; теперь
`message_id` уведомления и чат команды могут принадлежать разным чатам
(команда `/done 5` из чата уборки по заявке, уведомление о которой ушло
инженерам).

Поэтому `store.load_staff_notification_message_id` заменяется на
`store.load_staff_notification_target(request_id) -> (chat_id, message_id) | None`:
чат берётся из `Conversation` того самого исходящего сообщения-уведомления.
Оба потребителя (`staff._refresh_notification_keyboard`, `notifications`)
переходят на него. Путь нажатия кнопки не меняется: callback приходит из того
же чата, где кнопка (`normalized.chat_id`).

Перерисовка кнопок остаётся best-effort (сбой пишется в лог и не отменяет
переход) — маршрутизация этого не меняет.

### 4. Граница «кто персонал»: множество чатов, а не строка

`channels/telegram/service.py`:

```python
is_staff = normalized.chat_id in await _staff_chat_ids()
# {TELEGRAM_STAFF_CHAT_ID} ∪ значения staff_chats_by_category, без пустых
```

Это единственное место в системе, где решается, чьё сообщение — команда
персонала (двигает чужие заявки), а чьё — реплика гостя. Меры:

- **Множество, а не строка.** Проверка — `in frozenset[str]`, точное равенство
  элементов. Подстрочное совпадение (`"100" in "-100123"`) невозможно
  конструктивно; тест фиксирует это как контракт, а не как случайность.
- **Пустые значения отсеиваются** при сборке множества: ненастроенный
  `TELEGRAM_STAFF_CHAT_ID=""` не делает staff'ом чат с пустым id (а схема
  конфига пустых значений и не пропустит).
- **Деградация — в сторону гостя.** Конфиг не читается → множество из одного
  дефолтного чата. Ошибка конфигурации превращает сотрудника в гостя (бот
  ответит ему как консьерж — заметно и безвредно), но никогда наоборот:
  гость, получивший права персонала, — это привилегия, а не неудобство.
- **Множество закрыто.** Staff-чатом становится ровно то, что основатель
  вписал в конфиг тенанта; никакого вывода «этот чат похож на служебный» из
  истории сообщений, ролей Telegram или входящих данных нет. Записать конфиг
  можно только через `store_tenant_config` (сид и CLI ниже) — HTTP-пути записи
  конфига в Phase 0 не существует.

Цена — один SELECT в `tenants` на входящее обновление, внутри уже открытого
`tenant_context`. Приемлемо на пилотных объёмах; кэш конфига тенанта — общая
задача (не только для этого пути) и появится, когда появится потребность.

### 5. Как основатель задаёт маппинг

Без пути записи фича мертва: `make seed` заполняет конфиг только у тенанта
БЕЗ конфига, а HTTP-эндпоинта настройки в Phase 0 нет. Поэтому —
`python -m hospitality.tools.staff_routing`:

```
python -m hospitality.tools.staff_routing                                  # показать текущий
python -m hospitality.tools.staff_routing housekeeping=-1001 it-support=-1002
python -m hospitality.tools.staff_routing --clear                          # вернуть всё в общий чат
```

Живёт в `tools/` (склейка вне контрактов, как `tools/seed.py`): нужны и kernel
(`load/store_tenant_config`), и модуль requests (проверить, что такая категория
у тенанта есть). Маппинг задаётся ЦЕЛИКОМ — тем же принципом «конфиг это
значение», что и `store_tenant_config`. Неизвестный ключ категории — отказ с
ненулевым кодом возврата и списком доступных ключей: молча принятая опечатка
хуже отказа.

## Что сознательно НЕ делаем

- **RBAC и «служба видит только свои заявки».** Сотрудник из чата уборки
  по-прежнему может закрыть заявку инженерии по номеру `#N`: команды идут в
  `requests.change_request_status` без проверки принадлежности. Это Phase 1
  вместе с кабинетом персонала (§17.7, ADR-011); сейчас важнее, чтобы каждая
  служба ВИДЕЛА своё.
- **Маршрутизация по не-категорийным признакам** (VIP-гость, ночная смена,
  этаж): без данных пилота это выдумывание.
- **Хранение дефолтного чата в конфиге тенанта.** Он свойство инсталляции бота
  (Phase 0 — один бот, один отель). Пер-тенантный дефолт естественно появится
  вместе с пер-чатовым маппингом тенантов (Phase 1).
- **Маршрутизация гостевых сообщений/уведомлений.** Гость по-прежнему получает
  ответы в свой диалог; спека только про staff-адресата.
- **Ретроспективная переадресация.** Смена маппинга не переносит уже
  отправленные уведомления и их кнопки.

Плюс юниты схемы (`tests/test_tenant_config.py`): дефолт-пустой маппинг,

Плюс тест CLI (`tests/test_staff_routing_tool.py`): запись, отказ на неизвестной
категории, `--clear`.

## Миграции

Не требуются: колонок и таблиц не появляется, поле конфига аддитивное
(§6, `schema_version` = 1). Существующие конфиги читаются как есть — с пустым
маппингом.

## Наблюдаемость

- `staff_notification_routed` (INFO): `category_key`, `chat_id`, `routed`
  (нашёлся маппинг или ушло в дефолтный) — по нему видно, доходит ли заявка до
  своей службы.
- `staff_routing_config_unavailable` (WARNING, с `error_code` конфига) —
  деградация к дефолтному чату.
- Существующий `ERR-TELEGRAM-002` («staff-чат не настроен») теперь означает
  «не настроен ни чат категории, ни дефолтный».

Новых кодов ошибок не заводится.

## Ограничения и будущее

- Маппинг — плоский `категория → чат`. SLA-эскалации Phase 1 («не взяли за
  15 минут → чат уровнем выше») получают отсюда обе половины: адрес службы и
  адрес «уровня выше» (дефолтный чат).
- Множество staff-чатов читается из БД на каждое входящее; кэш конфига тенанта
  — отдельная задача Phase 1.
- Смена канала персонала (веб-инбокс, §17) заменит значения маппинга, но не его
  форму: «категория → адрес службы» останется.
