# Spec 0028 — Напоминание о невзятой заявке

- **Статус:** draft
- **Дата:** 2026-07-27
- **Источник:** issue #57 (живая проверка пути персонала 17.07.2026,
  `docs/runbooks/staff-ux-check.md`, сценарий С-9): на staging пять заявок висят
  в `new` вторые сутки, одна — пятые. Ни одна никого ни о чём не уведомила.
  Заявка без срока и без владельца — заявка, которой не существует: она принята,
  гостю обещано, и потеряна.
- **Связанные решения:** P-11 (различия отелей — конфигурация, не код), §6
  (конфиг тенанта и эволюция его схемы), P-8 (идемпотентность), P-1/NG-8 (не
  строим машинерию впрок), ADR-005 (воркер и фоновые задачи), ADR-009
  (`cleanup_terminal_events` — канон периодической задачи), ADR-011 (staff-чат —
  заглушка кабинета персонала Phase 1), ADR-013 (жизненный цикл заявки без
  `assigned`), spec 0021 П-2 (кнопки под уведомлением), spec 0026 (адресат
  staff-уведомления: чат службы по категории → дефолтный «уровень выше»).

---

## Проблема

Уведомление о новой заявке уходит в чат службы один раз. Дальше система молчит:
понятия «просрочено» в ней нет, повторного сигнала нет, эскалации нет. Заявка,
которую в этот момент никто не прочитал (смена, всплеск, ночь), исчезает из поля
зрения навсегда — гость получает «отель принял заказ и забыл», а виноватым
выглядит отель, а не платформа. Это главный риск пилота: доверие персонала к
системе (DISCUSSION_LOG).

Персональной эскалации («не взяли за N минут → менеджеру») сегодня сделать
нельзя: `/start` меняет статус, но исполнителя не записывает — записывать некуда,
сущности `User` нет (ADR-008 написан, реализация — Phase 1). Эскалировать некому,
пока нет владельца. Поэтому issue #57 задаёт порядок: **сначала видимость**, а
персональная эскалация — после ADR-008.

## Решение

Фоновая задача воркера раз в несколько минут ищет заявки, которые никто не взял
дольше срока тенанта, и присылает в чат службы повторное уведомление с кнопками.
Один раз на заявку. Ни SLA-движка, ни новых таблиц, ни новых статусов.

### 1. Что значит «невзятая»

По ADR-013 жизненный цикл — `new → in_progress → done/cancelled`. «Никто не
взял» — это ровно `status = new`: переход в `in_progress` и есть осознанное
действие человека «беру» (P-9). Возраст считается от `created_at` заявки.

Заявки в `in_progress`, висящие сутками (в issue такая одна — комната 101),
эта спека НЕ трогает — см. «Что сознательно НЕ делаем».

### 2. Срок — конфигурация тенанта (P-11, §6)

Два новых **необязательных** поля `TenantConfig`:

```python
request_reminder_after_minutes: int | None = 30          # базовый срок; None = напоминания выключены
request_reminder_minutes_by_category: dict[str, int] = {} # category_key → свой срок
```

- Единица — **минуты**: ими выражается и «15 минут» для прорыва трубы, и «4 часа»
  для смены белья. Отдельного поля «в часах» не заводим — два способа задать одно
  число нарушают P-12.
- Ключ пер-категорийного словаря — `key` категории заявок
  (`request_categories.key`), ровно как в `staff_chats_by_category` (spec 0026):
  UUID у каждого тенанта свой, конфиг стал бы нечитаемым. Валидация ключа — тот же
  паттерн `^[a-z0-9]+(-[a-z0-9]+)*$`. Диапазон `1 ≤ minutes ≤ 10080` (неделя)
  действует на ОБА поля — и на базовое, и на значения словаря: опечатка
  «5000000» не должна выглядеть рабочей настройкой, а `0` не должен означать
  «мгновенно» (это шум, а не напоминание; выключение выражается `null` базового
  поля или отсутствием ключа).
- Оба поля необязательные со значениями по умолчанию → `schema_version` остаётся
  `1` (§6: аддитивное изменение схемы не требует миграции конфигов). Конфиги,
  уже лежащие в БД, читаются как есть и получают базовые 30 минут.

**Почему дефолт — 30 минут, а не «выключено».** Сегодняшнее поведение (тишина) и
есть дефект, ради которого заведена issue. Отель, который ничего не настроил,
обязан получать защиту по умолчанию; отель, которому напоминания не нужны, ставит
`null` явно. Осознанное следствие: на первом прогоне после деплоя staging получит
по одному напоминанию на каждую из шести висящих заявок — это и есть живая
проверка DoD.

Правило «какой срок у этой категории» живёт в самом `TenantConfig` — тем же
приёмом, что `staff_chat_for` (P-12: у правила ровно одно место):

```python
config.reminder_delay_for(category_key) -> timedelta | None   # None = напоминаний нет
config.min_reminder_delay() -> timedelta | None               # самый ранний срок тенанта
```

`reminder_delay_for` отдаёт пер-категорийный срок, если он задан, иначе базовый;
`min_reminder_delay` — минимум из всех заданных (нужен, чтобы одним запросом
отсечь заведомо свежие заявки). Пер-категорийный срок работает и при `null` в
базовом поле: «напоминаем только про инженерию» — валидная настройка.

### 3. Запрос — в модуле requests, политика — в композиционном слое

Новая функция публичного интерфейса `modules/requests/api.py`:

```python
list_unclaimed_requests(*, created_before: datetime, limit: int) -> list[ServiceRequestRead]
```

Заявки текущего тенанта в статусе `new`, созданные раньше `created_before`.
Модуль не знает ни про сроки, ни про напоминания, ни про чаты — он отвечает на
доменный вопрос «что ещё никто не взял с такого-то момента». Порог и адресат —
дело композиционного слоя (P-5: та же дисциплина, что у AI-инструментов).

Порядок — `created_at DESC, id` (новые сверху, как `list_requests`), срез —
`limit`. `limit` — страховка от неограниченного скана, а не настройка: значение
задаёт константа `_SCAN_LIMIT = 200` в `reminders.py` (переменной окружения не
заводим — крутить её незачем, а видеть упирание надо). Направление сортировки
выбрано намеренно: при DESC в срез попадают самые свежие просроченные, то есть
те, кому напоминание ещё не слали; при ASC накопившийся хвост давно напомненных
висяков однажды занял бы весь срез, и новые заявки перестали бы получать
напоминания молча. Гарантии «всегда» DESC не даёт: после долгого простоя воркера
или всплеска, где просроченных больше `limit`, часть срезается — но срезается
видимо, WARNING'ом в лог (скрытая усечённая выборка хуже видимой).

### 4. Фоновая задача — в цикле воркера (канон ADR-009)

`channels/telegram/reminders.py`:

```python
async def remind_unclaimed_requests(*, sender, default_staff_chat_id) -> int
```

Воркер зовёт её из своего цикла раз в `worker_reminder_interval_seconds`
(новая настройка окружения, по умолчанию `300.0`) — тем же способом, что
`cleanup_terminal_events()` (ADR-009): отдельная джоба, планировщик или
Celery не заводятся (NG-8). Как и очистка, первый прогон — сразу на старте
процесса, иначе воркер, рестартующий чаще интервала, не напомнит ни разу.
Сбой скана логируется с кодом каталога и не роняет цикл доставки событий.

Обход тенантов (P-4 — кросс-тенантного запроса к бизнес-таблице не существует):

1. платформенной сессией — список тенантов с заполненным конфигом. Функции для
   этого в ядре нет: заводится **новая** `platform.config.list_configured_tenant_ids(session)
   -> list[uuid.UUID]` (тенант без конфига = онбординг не завершён, напоминать
   ему нечего и некуда). Место выбрано по смыслу: «у кого завершён онбординг» —
   вопрос к конфигу тенанта, а `config.py` уже единственный канонический путь
   работы с ним;
2. для каждого — `load_tenant_config`, затем `tenant_context(tenant_id)` и вся
   работа внутри него: RLS видит ровно одного тенанта. `tenant_id` попадает в
   лог-контекст автоматически (`tenant_context` биндит его, §10.1); в логах ДО
   входа в контекст (недоступный конфиг тенанта) он биндится явно — иначе
   непонятно, о каком отеле речь.

Внутри тенанта: срок выключен (`min_reminder_delay() is None`) → тенант
пропускается без единого запроса к заявкам. Иначе — один запрос кандидатов
(`created_before = now - min_reminder_delay()`), одно чтение категорий
(`list_categories`, оно же даёт `key` для срока и имя для текста), и по каждому
кандидату — точный срок его категории: `created_at + reminder_delay_for(key) > now`
→ пропуск (кандидат попал в срез по чужому, более короткому сроку).

Скан получает собственный `correlation_id` (§10.2): у периодической задачи нет
входящего запроса, а связать между собой логи одного прогона и записанные им
сообщения надо.

**Изоляция сбоев.** Ошибка на одном тенанте (недоступный конфиг, дрейф схемы) —
WARNING и переход к следующему; ошибка на одной заявке (Bot API ответил 429) —
ERROR `ERR-TELEGRAM-004` и переход к следующей; прогон, упавший целиком (БД
недоступна), — ERROR `ERR-TELEGRAM-005` из цикла воркера, который от этого не
останавливается. Проглатывания нет (R-8): всё попадает в лог с кодом, а Sentry
ловит ERROR (§10.4). Ретрай не нужен конструктивно: ключ идемпотентности пишется
только после успешной отправки, поэтому неудачное напоминание будет повторено
следующим сканом само.

### 5. Уведомление: адресат, текст, кнопки, идемпотентность

**Адресат** — чат категории заявки, фолбэк — дефолтный чат (spec 0026): напомнить
обязана та же служба, которая видела «Новая заявка #N». Ни чата категории, ни
дефолтного — WARNING `ERR-TELEGRAM-002` (тот же код, что у остальных
staff-уведомлений).

**Текст** — без LLM, намеренно (канон `notify_staff_on_request_cancelled_by_guest`):
фоновая задача не должна ни стоить токенов, ни зависеть от доступности модели.
Категория и комната уже по-русски, суть — оригиналом гостя (перевод персонал уже
видел в исходном уведомлении; резерв — встроенный переводчик Telegram).

```
⏳ Заявку #12 никто не взял — 45 мин
Категория: Уборка
Комната: 305
Суть: нужны полотенца
Ход: /start 12 (взять в работу) · /done 12 · /cancel 12
```

Возраст — короткой строкой («45 мин», «2 ч 10 мин»): сокращения вместо слов
избавляют от склонений. Доскелетная заявка без `daily_number` (до миграции 0010)
— фолбэк на id, как в остальных уведомлениях.

**Кнопки** — `keyboards.keyboard_for_status(...)` для статуса `new`, то есть
«Взять в работу» / «Отменить» (spec 0021 П-2: ноль ручного ввода). Нажатие на
кнопку под напоминанием безопасно: обработчик callback'а перерисовывает клавиатуру
ТОГО сообщения, где нажали (`normalized.reply_to`), а устаревшие кнопки под
исходным уведомлением гасит карта переходов + тост — это уже действующий контракт
`keyboards.py`, напоминание его не меняет.

**Реплай-команды.** Ключ идемпотентности напоминания добавляется в белый список
`load_request_id_for_staff_message` (`staff:request_unclaimed:%`): третий сегмент
ключа — id заявки, поэтому `/done` реплаем на напоминание резолвится так же, как
реплаем на исходное уведомление. Без этого сотрудник, ответивший на последнее
сообщение о заявке, получал бы «не понял, о какой заявке речь».

**Идемпотентность (P-8)** — существующим механизмом, новых таблиц и колонок нет:
ключ `staff:request_unclaimed:<request_id>` на исходящем `Message`
(`notification_already_sent` перед отправкой, `record_outbound_message` после).
Отсюда — **одно напоминание на заявку**: повторные сканы её больше не трогают.
Гонка двух воркеров закрыта уникальным ограничением `(tenant_id,
idempotency_key)`: проигравший получит IntegrityError, она попадёт в лог как сбой
одной заявки и ничего не сломает.

### 6. Общий адресат staff-уведомлений выносится из notifications.py

Выбор чата по категории (`_category`, `_category_name`, `_staff_chat_for_category`,
`_log_routing`, `_current_correlation_id`) сейчас живёт приватными функциями в
`channels/telegram/notifications.py`. Напоминание — четвёртый потребитель того же
правила. Копировать канон в новый файл нельзя (P-12: у правила одно место),
импортировать приватные имена — тоже.

Поэтому эти функции переезжают в новый маленький модуль
`channels/telegram/routing.py` («адресат staff-уведомления») и становятся
публичными для пакета; `notifications.py` переходит на него в том же PR,
отдельным коммитом — чистый вынос без смены поведения читается ревьюером
отдельно от фичи. Это предусловие фичи, а не попутный рефакторинг: без него
у правила выбора чата стало бы два места.

Побочно `notifications.py` худеет примерно на 60 строк (575 → ~515). В рамки R-3
(≤ ~400) это его не возвращает — файл давно за границей, и лечится он разделением
подписчиков по файлам, а не этим выносом. Отдельной задачей, не здесь.

### 7. Как основатель задаёт срок

Без пути записи фича настраиваема только в теории: `make seed` заполняет конфиг
лишь у тенанта БЕЗ конфига, HTTP-эндпоинта настройки в Phase 0 нет. Поэтому —
`python -m hospitality.tools.request_reminders`, точная копия канона
`tools/staff_routing.py` (spec 0026 §5):

```
python -m hospitality.tools.request_reminders                        # показать текущее
python -m hospitality.tools.request_reminders --after-minutes 20     # базовый срок
python -m hospitality.tools.request_reminders maintenance=10 housekeeping=45
python -m hospitality.tools.request_reminders --off                  # выключить напоминания
```

Как и в 0026: пер-категорийные сроки задаются ЦЕЛИКОМ («конфиг — это значение»),
неизвестный ключ категории — отказ с ненулевым кодом возврата и списком
доступных ключей (молча принятая опечатка выглядит рабочей настройкой и потому
хуже отказа).

Семантика флагов фиксируется явно, чтобы «выключил» не оказалось половинчатым:

- `--off` обнуляет ОБА поля (`request_reminder_after_minutes = null` и пустой
  словарь) — «напоминаний у этого отеля нет» без остатков в пер-категорийных;
- `--after-minutes N` меняет только базовый срок, пер-категорийные не трогает;
- пары без `--after-minutes` меняют только словарь, базовый срок не трогают;
- `--off` вместе с парами или `--after-minutes` — отказ с кодом 2: это два
  разных намерения (канон `staff_routing`: `--clear` + пары запрещены).

## Что сознательно НЕ делаем

- **Повторные напоминания и эскалацию «уровнем выше».** Одно напоминание на
  заявку. Лестница «через 15 → через 30 → менеджеру» — это и есть SLA-движок,
  который issue #57 просит не проектировать; а «менеджеру» без сущности `User`
  (ADR-008, Phase 1) адресовать некому.
- **Заявки в `in_progress`, висящие сутками.** Тот же механизм закроет и их
  (добавится второй порог и второй ключ идемпотентности), но у issue #57 DoD
  ровно про «невзятую», а «взял и не сделал» — это вопрос к владельцу, которого
  пока нет. При мерже спеки заводится отдельная issue в бэклог Gate B со ссылкой
  сюда — иначе пункт растворится в тексте.
- **Рабочие часы служб и тихие часы.** Напоминание в 03:00 разбудит ночного
  портье — но заявка в 03:00 тоже создана гостем в 03:00, и она реальна.
  Расписание служб — конфиг тенанта Phase 1, вместе с кабинетом персонала.
- **Просроченность как состояние заявки** (колонка `reminded_at`, статус
  `overdue`, витрина «просрочено»). Напоминание — факт канала, а не домена;
  хранится там же, где остальные уведомления (`messages`).
- **Метрику «доля просроченных» и отчёты.** Данных пилота ещё нет; считать по
  логам можно уже сейчас.
- **Ретроспективность настройки.** Смена срока не отзывает и не переигрывает уже
  отправленные напоминания.

| Напоминания выключаемы | `test_reminders`: `request_reminder_after_minutes = null` и пустой словарь → ни одного запроса к заявкам |
| Одно напоминание на заявку (P-8) | `test_reminders`: два скана подряд → ровно одно сообщение |
| Взятая заявка напоминаний не получает | `test_reminders`: `new → in_progress` до скана → тишина |
| Кнопки под напоминанием действуют | `test_reminders`: в отправленном сообщении клавиатура статуса `new`; `test_staff`: реплай `/done` на напоминание резолвит заявку |
| Ошибка на одной заявке не отменяет остальные | `test_reminders`: отправитель падает на первой из двух → вторая уведомлена, ключ первой не записан (повторится) |

| Усечение среза видно | `test_reminders`: кандидатов больше `_SCAN_LIMIT` → WARNING `unclaimed_request_scan_truncated` |
| Тенант без конфига пропускается | `test_reminders`: тенант с `config = NULL` не даёт ни запроса, ни лога отправки |

## Наблюдаемость

- `unclaimed_request_reminded` (INFO): `request_id`, `daily_number`,
  `age_minutes`, `category_key`, `chat_id` — по нему видно, доходит ли напоминание
  до своей службы и с какой задержкой.
- `unclaimed_requests_scanned` (INFO, один на прогон): `tenants`, `candidates`,
  `reminded` — доказательство, что задача вообще работает (у периодической задачи
  «тишина» и «сломалась» иначе неразличимы).
- `unclaimed_request_scan_truncated` (WARNING): срез упёрся в `_SCAN_LIMIT`.
- `unclaimed_request_reminder_failed` (ERROR, **`ERR-TELEGRAM-004`**) —
  напоминание по конкретной заявке не отправлено; повторится следующим сканом.
- `unclaimed_request_scan_failed` (ERROR, **`ERR-TELEGRAM-005`**) — прогон упал
  целиком (класс причин ERR-EVENTS-003: БД недоступна, миграции не применены).
  Два кода, а не один, — по образцу ERR-EVENTS-003/004: у них разный диагноз и
  разное действие дежурного (Bot API против инфраструктуры).
- `ERR-TELEGRAM-003` **занят и переиспользованию не подлежит**: до spec 0027 так
  назывался гостевой rate-limit (ныне `ERR-CHANNEL-003`), и в логах и Sentry до
  27.07.2026 этот код означает именно его. Обе статьи (004, 005) добавляются в
  `docs/runbooks/errors.md` в том же PR (§10.5, R-8: код без статьи не заводится).
- `ERR-TELEGRAM-002` переиспользуется без изменений: ни чата категории, ни
  дефолтного не настроено.
- `staff_notification_routed` — тот же лог маршрутизации, что у остальных
  staff-уведомлений (общий `routing.py`).

## Ограничения и будущее

- Одно напоминание на заявку. Вторая ступень («не взяли и после напоминания →
  чат уровнем выше») получает от spec 0026 готовый адрес — дефолтный чат, — но
  включается только вместе с владельцем заявки (ADR-008, Phase 1).
- Скан читает конфиг каждого тенанта каждые 5 минут: кэш конфига тенанта —
  общая задача Phase 1 (та же оговорка, что в spec 0026).
- Срез скана ограничен `limit`; на пилотных объёмах (десятки заявок в сутки) он
  недостижим, но при росте его упирание видно в логах.
- Порог измеряется от `created_at`, а не от «часов работы службы»: отель, у
  которого уборка работает с 8 до 22, увидит ночные напоминания. Расписание
  служб — Phase 1.
