# Spec 0032 — Ретеншн 90 дней: тексты сообщений и свободный текст заявок

- **Статус:** draft
- **Дата:** 2026-07-30
- **Источник:** issue #42 — юрпакет П2.3 (решение основателя в разноске
  стратсессии 27.07: 90 дней для `messages`/`conversations`, заявки не удалять —
  анонимизировать свободный текст).
- **Связанные решения:** FOUNDATION §9 («таблицы с неограниченным ростом
  получают retention в момент создания»), P-4 (tenant-изоляция), P-8
  (идемпотентность фоновых задач), ADR-009 (канон периодической задачи
  воркера — `cleanup_terminal_events`), spec 0028 §4 (канон обхода тенантов
  фоновой задачей), spec 0031 «Что сознательно не делаем» (немаскированную
  staging-историю доедает этот ретеншн), `docs/legal/privacy-policy.md` п. 7 и
  `docs/legal/dpa-hotel-template.md` п. 4 (публичное обещание сроков),
  `docs/PII_REGISTRY.md` (строки `messages.text`, `service_requests.*`).

---

## Проблема

Опубликованная политика конфиденциальности обещает: «Тексты сообщений —
90 дней, затем удаляются; свободный текст заявок обезличивается через
90 дней». Механизма, который это исполняет, нет:

1. `messages` — таблица с неограниченным ростом; в докстринге модели с
   Task 0016 висит пометка «retention — Phase 1» (§9 требует политику с
   момента создания).
2. `conversations` копят `external_id` (chat id гостя) и `pending_action`
   давно умерших диалогов.
3. `service_requests.summary/details/resolution_note` — свободный текст
   гостя и персонала — живут вечно.
4. Staging-история содержит немаскированные номера карт, записанные до
   spec 0031: маскирование задним числом сознательно не делали, потому что
   их «доедает ретеншн 90 дней» — то есть эта спека.

До реализации обещание политики — юридический долг (юраудит 22.07.2026,
дедлайн локализации/комплаенса 25.08.2026).

## Решение

Периодическая задача в цикле воркера — по канону ADR-009
(`cleanup_terminal_events`) и канону обхода тенантов spec 0028
(`remind_unclaimed_requests`). Ни планировщика, ни отдельной джобы (NG-8).

### 1. Срок — настройка инсталляции, не тенанта

`MESSAGES_RETENTION_DAYS=90` в `shared/config.py` — прямая копия канона
`OUTBOX_RETENTION_DAYS` (решение основателя в issue #42). Частота прогона —
`WORKER_RETENTION_INTERVAL_SECONDS=3600` (раз в час, как очистка outbox:
суточная гранулярность срока не требует более частых прогонов).

Это НЕ нарушение P-11 (различия отелей — конфигурация тенанта): 90 дней —
обещание опубликованной политики конфиденциальности, единое для платформы.
Пер-тенантный срок потребовал бы пер-тенантного текста политики — отдельное
решение, если появится отель с другим требованием.

Тот же срок управляет и анонимизацией заявок: политика называет одно число
для обоих обещаний, две настройки могли бы разъехаться с опубликованным
текстом.

### 2. Что удаляем и что анонимизируем

| Данные | Действие | Критерий |
| --- | --- | --- |
| `messages` | удаление строки | `created_at` старше срока |
| `conversations` (+ каскад `request_origins`) | удаление строки | `updated_at` старше срока И не осталось ни одного сообщения |
| `service_requests.summary` | замена на плейсхолдер `[обезличено: срок хранения истёк]` | `created_at` старше срока |
| `service_requests.details`, `resolution_note` | `NULL` | `created_at` старше срока |

Порядок внутри тенанта: сначала сообщения, потом диалоги — диалог, чьё
последнее сообщение только что удалено, становится пустым и уходит в этом же
прогоне (его `updated_at` не моложе последнего сообщения: запись сообщений
`updated_at` не трогает).

Что при этом сознательно происходит:

- **Согласие умирает вместе с диалогом.** `conversations.consent_at/_version` —
  доказательная запись «как у диалога» (PII_REGISTRY); гость, вернувшийся в
  Telegram после 90+ дней тишины, проходит consent-gate заново — это
  корректно, а не баг.
- **Живой диалог не трогается.** Сообщения свежее срока держат диалог
  (условие «не осталось сообщений»); свежий `pending_action`/согласие держат
  его через `updated_at`.
- **Заявка остаётся для отчётов.** Категория, статус, комната, времена,
  `daily_number`, `guest_language` не трогаются — агрегаты и статистика живут
  (решение основателя: «не удалять — анонимизировать»). `room_number`
  остаётся: структурированное поле, само по себе человека не идентифицирует
  (тот же довод, что у логов в PII_REGISTRY), а связка «комната → человек»
  живёт в Stay и имеет свой срок.
- **Статус заявки не важен.** Анонимизируется и заявка, зависшая в `new`/
  `in_progress` дольше 90 дней: обещание политики сильнее удобства — открытая
  три месяца заявка мертва и без текста.

### 3. Слои: политика — в композиционном слое, своя таблица — у своего модуля

Тот же разрез, что в spec 0028 §3:

- `channels/common/retention.py` (новый) — `enforce_guest_text_retention()`:
  обход тенантов, удаление `messages`/`conversations` (таблицы канального
  ядра — его собственные), вызов анонимизации заявок через публичный API
  модуля requests. Импорт `channels → modules.requests.api` разрешён
  направлением слоёв (прецедент — reminders.py).
- `modules/requests/service.py` — `anonymize_expired_request_texts(
  created_before) -> int`: домен сам правит свою таблицу; экспорт через
  `api.py` (R-5).

Обход тенантов — по канону spec 0028, но списком **всех** тенантов, а не
только с завершённым онбордингом: данные (и юр-обязанность) есть и у тенанта
без конфига. В `platform/config.py` добавляется `list_tenant_ids(session)`
рядом с `list_configured_tenant_ids` с задокументированным отличием.

### 4. Идемпотентность (P-8)

Ни новых таблиц, ни колонок, ни миграций. Идемпотентность — свойство самих
операций: удаление по `created_at < cutoff` повторно не находит строк;
анонимизация фильтрует уже обезличенные (`summary != плейсхолдер OR details
IS NOT NULL OR resolution_note IS NOT NULL`) — повторный прогон обновляет
0 строк. Гонка двух воркеров безопасна: обе стороны выполняют одинаковые
идемпотентные DELETE/UPDATE.

### 5. Наблюдаемость (§10)

- Прогон получает собственный `correlation_id` (канон spec 0028).
- Итоговый лог `guest_text_retention_completed`: `tenants`,
  `messages_deleted`, `conversations_deleted`, `requests_anonymized` —
  нулевые счётчики отличают «нечего удалять» от «джоба не ходила».
- Сбой на одном тенанте логируется `ERR-CHANNEL-004` и не отменяет остальных
  (канон ERR-TELEGRAM-005); тот же код — на падении прогона целиком в
  воркере. Статья в `docs/runbooks/errors.md`.
- Первый прогон — сразу на старте воркера (канон: частые рестарты не должны
  отменять ретеншн, ревью PR #19).

## Что сознательно НЕ делаем

- **Пер-тенантный срок** — см. §1.
- **Архив/экспорт перед удалением** — удаление и есть цель (обещание
  политики); бэкапы БД живут своим циклом и шифруются (spec 0024).
- **Ретеншн `llm_call_log` и аудита** — текстов там нет (`prompt_hash`
  вместо промпта, §7.6), это рост без PII-обещания; отдельный долг §9, не
  этот issue.
- **Ретеншн `stays`/`guests`/`guest_sessions`** — сроки «как у Stay/сессии»
  решаются юрпакетом отдельно; удаление по обращению субъекта уже исполняется
  runbook'ом `subject-requests`.
- **Суммаризацию удаляемой истории** — NG-8, не строим впрок.

## Известные следствия

- Вместе со старыми исходящими `messages` уходят их ключи идемпотентности
  уведомлений (`staff:*`): напоминание по заявке-зомби старше 90 дней может
  уйти повторно — к этому моменту её текст уже обезличен, повтор безвреден.
- LLM-контекст не меняется: окно истории и так 20 сообщений (#74).

## Контракты

- `hospitality.channels.common.retention.enforce_guest_text_retention()
  -> RetentionRunStats` (счётчики прогона).
- `hospitality.modules.requests.api.anonymize_expired_request_texts(
  *, created_before: datetime) -> int` + константа
  `REQUEST_TEXT_ANONYMIZED_PLACEHOLDER`.

- Настройки: `messages_retention_days: int = 90`,

## План тестов

1. **Сообщения:** старше срока — удалены, свежие — нет; граница по
   `created_at`.
2. **Диалоги:** пустой и давно не обновлявшийся — удалён (каскадом ушёл
   `request_origin`); диалог со свежими сообщениями — жив; пустой, но недавно
   обновлённый (`pending_action`) — жив; диалог, опустевший в этом же
   прогоне, — удалён.
3. **Заявки:** старые `summary/details/resolution_note` обезличены, свежие
   нетронуты; агрегатные поля (статус, категория, комната, номер) целы;
   повторный прогон — 0 обновлений (идемпотентность); статус не влияет.
4. **Изоляция тенантов (P-4):** данные тенанта B не тронуты прогоном по A;
   обходятся и тенанты без конфига.
5. **Устойчивость:** сбой на одном тенанте не отменяет остальных
   (ERR-CHANNEL-004).
6. **Воркер:** джоба зовётся из цикла с интервалом, первый прогон на старте,
   сбой логируется с кодом и не роняет цикл (канон test_worker).
