# Spec 0033 — Кабинет персонала v1 (условие запуска пилота)

- **Статус:** draft — на ревью основателя ДО кода (R-2)
- **Дата:** 2026-07-30
- **Источник:** issue #48 (тело + комментарии 27–28.07), ADR-008 (модель
  идентичности — этот документ реализует его staff-половину), DISCUSSION_LOG
  темы «Профиль пилотного отеля», «Как гость получает доступ при 310 номерах»,
  «UI-дизайн кабинета персонала», «Доступ персонала: приглашения и отзыв»,
  «Кабинет персонала: веб/PWA vs нативное приложение».
- **Связанные решения:** ADR-003 (RLS; платформенные таблицы — вне RLS по
  ADR-008 §6), ADR-008 (§1 User/Session/инвайты, §3 per-stay код, §6 резолвер),
  ADR-013 (жизненный цикл заявки без `assigned`), ADR-014 (рендеринг кабинета —
  черновик в этом же PR), spec 0023 (канон Redis rate-limit), spec 0026
  (уведомления службам — остаются), spec 0027 (guests/, канал web), spec 0029
  (consent-строка), P-1, P-4, P-5, P-9, P-11, P-12; FOUNDATION §11
  («каждый эндпоинт рождается аутентифицированным»).

---

## 1. Проблема

Пилотный отель — ~310 номеров, 6 служб, ~50–120 заявок в сутки, ~100–150
заселений в день. Текущий staff-интерфейс — Telegram-группы: при таком объёме
это уведомление каждые 10–15 минут круглосуточно, лента без фильтров и «моих
заявок» (#56 — заявка существует только пока её сообщение видно в чате).
Персонал координируется в WhatsApp, куда staff-уведомления официально
недоставимы (Cloud API не поддерживает группы; неофициальные API — Non-Goal).
Выдача гостевого доступа (веб-чат по QR, ADR-008) держится на CLI — у стойки
им пользоваться нельзя. Поэтому **кабинет v1 — условие запуска пилота, а не
улучшение после него** (решение основателя, #48).

**Критерий приёмки v1 — удобство** (требование основателя 28.07): персонал
*предпочитает* кабинет, а не обходит его. Обход = гость без кода при зелёных
логах — главный риск ручного заселения.

## 2. Скоуп v1

Три экрана + вход. **Mobile-first**: горничные и техники закрывают заявки с
этажа, ресепшен показывает QR со своего телефона; десктоп — тот же макет шире.

1. **Очередь заявок** — лента открытых, «взять в работу», «готово»/«отменить»
   (закрывает #56).
2. **Страница заселения** — один ввод с клавиатуры (комната), остальное
   кнопками; QR одноразовой ссылки + код крупными цифрами; индикация «гость
   подключился»; перевыпуск, переселение, продление, выселение из карточки.
3. **Страница «Сотрудники»** — пригласить/деактивировать (модель ADR-008;
   деактивация гасит сессии немедленно).

**Вне скоупа v1** (фиксируется, чтобы не расползтись):

- Назначение заявки на конкретного сотрудника и персональные уведомления
  («тебе назначена») — ждёт привязки Telegram к User (ADR-008 §7); v1 пишет
  только «кто взял».
- Отчёты/аналитика, онбординг категорий (#123), конфиг квот (#124) — свои
  задачи; кабинет даёт им каркас (вход, роли, навигация).
- Перевод SERVICE_TOKEN в сид сервисного аккаунта (ADR-008 §2) — follow-up
  issue после серии: кабинету не нужен, а трогает smoke/deploy.
- Включение auth-only в Telegram (ADR-008 §4) — отдельный issue **после** того,
  как выдача кодов заработает в кабинете на staging.
- 2FA, SSO/IdP — не для пилота (ADR-008 §5).

## 3. Пользователи и вход (реализация ADR-008 §1)

### 3.1. Таблицы (платформенный мир, вне RLS — ADR-008 §6)

Пять таблиц в `platform/` (доступ — только код `platform/`, граница R-5):

| Таблица | Поля (кроме id/created_at) | Ограничения |
|---|---|---|
| `users` | `display_name`, `status` (`active\|deactivated`), `is_platform_admin BOOL`, `updated_at` | — |
| `user_identities` | `user_id FK→users`, `kind VARCHAR(16)` (`password\|oidc\|telegram`), `external_id VARCHAR(255)`, `secret_hash VARCHAR(255) NULL` | UNIQUE `(kind, external_id)` |
| `tenant_memberships` | `user_id FK→users`, `tenant_id FK→tenants`, `role_key VARCHAR(32)`, `status` (`active\|revoked`), `invited_by FK→users NULL`, `updated_at` | UNIQUE `(user_id, tenant_id)` |
| `staff_sessions` | `user_id FK→users`, `token_hash VARCHAR(64)`, `last_used_at`, `expires_at`, `revoked_at NULL` | UNIQUE `(token_hash)` |
| `staff_invites` | `tenant_id FK→tenants`, `role_key`, `invited_name VARCHAR(255)`, `token_hash VARCHAR(64)`, `invited_by FK→users`, `expires_at`, `accepted_at NULL`, `accepted_user_id NULL` | UNIQUE `(token_hash)` |

- `kind=password`: `external_id` — нормализованный email (trim + lowercase),
  `secret_hash` — argon2id (`argon2-cffi`; в БД только хэш). `oidc`/`telegram` —
  зарезервированные значения контракта, веток кода в v1 нет (P-1).
- Таблица сессий названа `staff_sessions` (не `sessions`) — симметрия с
  `guest_sessions` и отсутствие конфликтов имён. В ADR-008 это `Session`.
- `tenant_memberships` несёт `tenant_id` без RLS — **whitelist-исключение из
  P-4**, явно зафиксированное ADR-008 §6; список исключений — в docstring
  миграции (будущий линтер обязан знать его явно).
- Инвайт — provisioning-артефакт, не способ входа (ADR-008 §1): по принятии
  создаёт User + `UserIdentity(password)` + membership; если email уже есть на
  платформе — добавляет только membership (сеть отелей, ADR-008 инвариант а).

### 3.2. Роли v1 — минимум, совместимый с RBAC v1

Полная матрица — `docs/RBAC.md`, задача RBAC v1 (не этот спек). Кабинету v1
достаточно трёх `role_key` и мини-матрицы:

| Действие | `staff` | `receptionist` | `manager` |
|---|---|---|---|
| Очередь: смотреть, взять, готово, отменить | ✅ | ✅ | ✅ |
| Заселение и карточки Stay | — | ✅ | ✅ |
| Сотрудники: пригласить, деактивировать | — | — | ✅ |

- «Кто вправе приглашать» (открытый вопрос #48): **v1 — только `manager`**
  (предложение, развилка Ф-3 в §11).
- Фильтр очереди по категориям — UI-фильтр, не право: любой сотрудник видит
  всю очередь (маленькая команда службы сама знает своё; привязка роль →
  категории — RBAC v1, когда появится боль).
- Проверка роли — одна функция в `platform/` (`require_role(request, ...)`),
  копируемая как канон всеми страницами кабинета (§11 FOUNDATION: эндпоинт
  рождается аутентифицированным).

### 3.3. Сессии и вход

- Логин: email + пароль → `staff_sessions`: opaque-токен ≥ 256 бит, в БД хэш
  (SHA-256), cookie `HttpOnly + Secure + SameSite=Lax`. TTL: idle 30 дней
  (продлевается активностью), absolute 180 дней — параметры `shared/config.py`.
  Сессии окажутся на личных телефонах (DISCUSSION_LOG): частый re-login убьёт
  удобство, отзыв решается деактивацией.
- Rate-limit логина — канон Redis-счётчика spec 0023: по email и по IP
  (дефолт 10 попыток / 10 минут).
- **Активный тенант — атрибут запроса** (ADR-008 §1): URL кабинета —
  `/staff/{tenant_slug}/…`; на каждом запросе membership проверяется заново.
  Одно членство → редирект сразу в тенанта; несколько — выбор после логина.
- Цепочка `TenantResolver` расширяется третьим звеном (ADR-008 §6): API-ключ →
  **staff-сессия + slug из пути (проверка членства)** → гостевая сессия.
  Контракт прежний: валидная идентичность → tenant_id, иначе None.
- Деактивация (`manager` в кабинете): `users.status=deactivated`, все
  `staff_sessions` revoked, memberships revoked — одна транзакция, одно
  действие в UI. Аудит: структурированный лог-событие с actor
  (`staff.user_deactivated`); отдельная таблица аудита — RBAC v1.
- **Бутстрап**: первого `manager` создаёт CLI `tools/staff_bootstrap`
  (onboarding-шаг платформы, по образцу `tools/checkin`); дальше — только
  приглашения из UI. Ничего через env/разработчика (§6 FOUNDATION).

### 3.4. Приглашение сотрудника

Менеджер вводит имя + роль → одноразовая ссылка `/staff/invite/{token}`
(TTL 72 ч, в БД хэш). Ссылку менеджер передаёт сам (WhatsApp/лично) — email-порт
не нужен, email используется как логин, а не как канал доставки. Сотрудник
открывает ссылку → вводит email + пароль (согласие на обработку — той же
строкой-строчкой, что consent v3) → попадает в очередь. Истёкший/использованный
инвайт → понятный экран «попросите новое приглашение». Повторное приглашение —
новая ссылка, старая гасится.

## 4. Рендеринг кабинета — развилка (ADR-014, черновик в этом PR)

ADR-002 закрепил за фронтом Next.js; spec 0027 переиспользовать его для
гостевой страницы отказалась (вторая сборка ради одной страницы). Для кабинета
v1 предлагаю **вариант A — server-rendered внутри монолита** (Jinja2-шаблоны +
ванильный JS fetch/поллинг, канон — страница `channels/web`):

- Один язык, один деплой-юнит, ноль node-toolchain в CI — P-1 в чистом виде
  для репозитория, который сопровождают LLM и не-разработчик.
- Скоуп v1 — формы и списки с поллингом; Tailwind/shadcn не окупают вторую
  экосистему на трёх экранах при экономике пилота из кармана основателя.
- JSON-эндпоинты действий (взять/закрыть/заселить/поллинг) одинаковы в обоих
  вариантах — если кабинет перерастёт (живой инбокс WhatsApp, отчёты), Next.js
  подключается к тем же эндпоинтам, выброшенными окажутся только шаблоны.

Альтернатива B — Next.js static export, отдаваемый FastAPI (один контейнер,
но + node-сборка и TS-кодовая база). Решение — за основателем на ревью этой
спеки (развилка Ф-1 в §11); принятие варианта A фиксируется ADR-014 (иначе он
помечается rejected и серия строится по B — структура спеки не меняется).

Размещение кода: новый composition-layer пакет `src/hospitality/staff_portal/`
(FOUNDATION §5.1 «Web (персонал/админ)») — импортирует `platform/` и `api.py`
доменных модулей, сам не импортируется никем; контракт import-linter
расширяется рядом с `ai/`/`channels/`. Структура: `router.py` (страницы),
`api_router.py` (JSON-действия), `templates/`, `static/styles.css`, `tests/`.
QR — серверный SVG (`segno`, pure-python, без бинарных зависимостей).

## 5. Очередь заявок (закрывает #56)

`/staff/{slug}/requests` — лента открытых (`new` + `in_progress`), новые
сверху; карточка: `#дневной_номер`, комната, категория, текст, статус, возраст,
«взял: Имя». Обновление — поллинг каждые 15 с (без WebSocket — P-1).

- Кнопка **«Взять»** (`new → in_progress`) — одно нажатие, пишет «кто взял».
- Кнопка **«Готово»** (`in_progress → done`) — опциональная заметка
  (resolution_note, spec 0021/0030); **«Отменить»** — заметка обязательна.
- Фильтры-чипсы: по категории, «мои»; вкладка «закрытые за сегодня»
  (граница суток — полночь отеля, Q3). «Мои» — фильтр, не замок: закрыть чужую
  заявку можно (как сегодня в Telegram).
- Все действия — через `requests_api.change_request_status` (P-5): те же
  переходы `STATUS_TRANSITIONS`, те же события, гость получает те же
  уведомления, что при действиях из Telegram.

**Изменения модуля `requests/`:**

- Колонка `service_requests.claimed_by_user_id UUID NULL` (FK на платформенных
  `users` — по образцу FK на `tenants`) + `claimed_by_display_name VARCHAR(255)
  NULL` (денормализованный снапшот имени: список заявок не ходит в платформенные
  таблицы, имя на момент взятия — честная история).
- `change_request_status(...)` получает опциональный `acting_user`
  (id + display_name); при `new → in_progress` заполняет колонки. Telegram-путь
  передаёт None (staff-чат — канальный суррогат, ADR-008 §7) — колонки пусты,
  деградация невидима.

## 6. Страница заселения

`/staff/{slug}/checkin` — роль `receptionist`/`manager`.

**Форма — секунды у стойки:** комната (единственный ввод с клавиатуры,
фокус при открытии) → ночи кнопками `1/2/3/7` (+ «другое» — число) → гостей
кнопками `1/2/3+` → «Заселить». `check_out_at` = дата заезда + ночи, 12:00 по
поясу отеля → UTC (расчётный час — правило про заезд/выезд, Q3).

**Изменения модуля `guests/`:** колонка `stays.guests_count SMALLINT NOT NULL
DEFAULT 1` (`3+` хранится как 3) — вход квот #124 («лимит × guests_count»);
`StayCheckIn` получает поле. Плюс операции `move_stay` (переселение; занятая
комната → ERR_GUESTS_ROOM_OCCUPIED — partial-unique уже держит БД),
`extend_stay` (правка `check_out_at`; доступ гостя следует автоматически —
ADR-008 §3, отдельного действия с кодом нет).

**Карточка после заселения (и по поиску комнаты):**

- **QR одноразовой ссылки привязки** + тот же код заселения **крупными
  печатными цифрами** рядом (гость без интернета фотографирует или
  переписывает). Ссылка живёт 120 с, одноразова; истекла — перевыпуск одним
  нажатием (повторное открытие страницы ничего не ломает).
- Механика ссылки: Redis (канон-инфраструктура уже есть), ключ
  `bindlink:{tenant}:{sha256(token)}` → stay_id, TTL 120 с, потребление —
  атомарный GETDEL; таблица не нужна (эфемерность — свойство, потеря при
  рестарте Redis лечится перевыпуском). Маршрут — в `channels/web`:
  `/w/{slug}/b/{token}` → consent-строка v3 → по нажатию токен потребляется →
  `start_guest_session` тем же путём, что ввод кода (P-12); истёкший токен →
  «попросите показать QR ещё раз» + переход на обычный ввод кода.
- **Индикатор «гость подключился»**: карточка поллит (каждые 3 с, пока
  открыта) счётчик привязок Stay; после успешной привязки — зелёное
  «подключился» — обратная связь до жалобы гостя.
- Действия карточки: перевыпустить код (`reissue_access_code` — уже есть),
  переселить, продлить, выселить (`check_out`). Всё — по одному нажатию +
  подтверждение для выселения.

## 7. Страница «Сотрудники»

`/staff/{slug}/team` — роль `manager`. Список членств (имя, роль, статус,
активность), «Пригласить» (имя + роль → ссылка с кнопкой «поделиться»),
«Деактивировать» (подтверждение; §3.3). Ожидающие инвайты видны и отзываемы.

## 8. Что остаётся в Telegram

Кабинет **добавляется, не заменяет** — оба пути живут на всём пилоте:

- Уведомления о заявках в чаты служб (spec 0026), inline-кнопки и
  reply-команды (spec 0021), напоминания о невзятых (spec 0028), эскалация
  (#36) — без изменений. Telegram — канал push-уведомлений; очередь и
  заселение — кабинет (DISCUSSION_LOG).
- Действие из Telegram и из кабинета сходится в одном сервисе (P-5) — гонок
  статусов нет сверх существующих (`ERR-REQUESTS-003` на недопустимый переход,
  кабинет показывает «уже взята»).
- Гостевой Telegram-канал не трогаем; auth-only — follow-up (§2).

## 9. Наблюдаемость, безопасность, ошибки

- Коды ошибок (каталог): `ERR-AUTH-001` неверные креды, `-002` сессия
  невалидна/истекла, `-003` нет членства/роли, `-004` инвайт
  невалиден/истёк/использован, `-005` пользователь деактивирован,
  `ERR-GUESTS-BINDLINK-EXPIRED` — ссылка привязки истекла.
- Структурированные логи с `tenant_id`/`correlation_id` + actor `user_id` на
  каждом действии кабинета; лог-события: `staff.login`, `staff.invite_created`,
  `staff.invite_accepted`, `staff.user_deactivated`, `staff.request_claimed`,
  `staff.stay_checked_in`, `staff.bind_link_issued/consumed`.
- Метрики: логины, взятия из кабинета vs Telegram (мерило «персонал
  предпочитает кабинет»), заселения, доля привязок по QR-ссылке vs ввод кода.
- Rate-limits (канон 0023): логин (§3.3); выпуск bind-ссылок — по (tenant,
  stay); consume bind-ссылки — по IP.
- `docs/PII_REGISTRY.md`: email и имя сотрудника (users/user_identities/
  invites), `claimed_by_display_name` в заявке.

## 10. План тестов

- **Unit (platform):** нормализация email; argon2-хэш; login/logout; idle- и
  absolute-истечение; инвайт одноразов/истекает/гасится перевыпуском; принятие
  инвайта существующим email → второе членство; деактивация гасит сессии в той
  же транзакции; require_role по мини-матрице.
- **Резолвер:** staff-сессия + slug без членства → None/403; revoked membership
  закрывает доступ следующим запросом; порядок звеньев не ломает API-ключ и
  гостевую сессию (регресс web-чата).
- **Requests:** «взять» пишет claimed_by; повторное «взять» → ERR-REQUESTS-003
  и дружелюбное «уже взята»; Telegram-путь оставляет колонки пустыми.
- **Guests/bind-link:** одноразовость (второй GETDEL — отказ); TTL; ссылка
  чужого тенанта бесполезна (тройка контекста); привязка создаёт GuestSession
  тем же путём, что код; guests_count сохраняется; move/extend/checkout.
- **Интеграционный сценарий:** бутстрап → логин → заселение → bind по QR →
  гость пишет в чат → заявка → в кабинете «взять» → «готово» → гость получил
  уведомление; деактивация → та же сессия получает 401.
- **Страницы:** httpx-смоук (аутентифицированность каждой, ключевые элементы,
  без сессии → редирект на логин). Evals не нужны (AI-слой не меняется).

## 11. Развилки основателю (решить на ревью спеки)

- **Ф-1. Рендеринг кабинета** (§4): предлагаю A — server-rendered в монолите
  (ADR-014); альтернатива — Next.js static export. Влияет только на слой
