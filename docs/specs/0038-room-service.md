## 1. Зачем и что получается

Гость открывает меню кнопкой «Меню» на странице веб-чата, собирает корзину,
видит итог с сервисным сбором и оформляет заказ. Заказ уходит **заявкой** в
службу F&B. Сотрудник нажимает «Принял», идёт в номер за оплатой (наличные
или терминал отеля), отмечает «Оплачено», пробивает заказ в кассе ресторана,
кухня готовит, сотрудник отмечает «Доставлено». Гость получает сообщение в
чате на каждом шаге. Оплата до готовки защищает от ложных заказов: при ошибке
теряется ходка сотрудника, а не блюдо и не чек (довод основателя — DISCUSSION_LOG).

Меню ведёт сам F&B в разделе кабинета «Меню»: блюда, разделы, цены, фото,
стоп-лист и переключатель «Заказы в номер: принимаем / не принимаем». AI в
основе заказов не создаёт: заказ оформляет гость кнопкой.

## 2. Что видит гость

Экраны и поведение — прототип (шапка спеки). Обязательное:

- **Меню.** Разделы-чипсы с прокруткой; карточки блюд в две колонки: фото
  или заглушка с первой буквой, цена, название, описание; «+» превращается в
  «− N +». Блюдо в стоп-листе видно серым с меткой «Закончилось», добавить
  его нельзя. Удалённое блюдо не видно. Внизу — липкая полоса корзины
  (число порций и сумма блюд). В шапке — переключатель языка EN / RU / KK из
  языков отеля (§4.4).
- **Корзина.** Позиции со степпером, «Очистить», суммы, кнопка «Далее».
  Позиция, попавшая в стоп-лист после добавления, помечена «Закончилось —
  уберите из корзины», и «Далее» неактивна.
- **Итог.** Номер комнаты из привязки, «Как можно скорее», «Оплата при
  получении», состав, пожелания (до 200 знаков, необязательно), суммы
  «Блюда / Сервисный сбор N% / Итого». Суммы присылает сервер (§3, Р-5), а
  не JavaScript страницы. Кнопка «Оформить заказ · {итого}»; повторное
  нажатие не создаёт второй заказ.
- **Статус заказа.** Шкала «Отправлен → Принят → Оплачен → Доставлен» с
  временем шагов, текст текущего шага, состав и суммы. «Отменить заказ»
  есть только на шаге «Отправлен», с подтверждением на странице. Отменённый
  заказ показывает причину; доставленный и отменённый — кнопку «Заказать ещё».
- **«Заказы не принимаются».** Меню видно, «+» нет, полоса корзины —
  неактивная «Заказы сейчас не принимаются» с подсказкой «Обратитесь на
  ресепшен — {цифра} с телефона в номере» (`reception_room_dial` из конфига;
  без него — «Обратитесь на ресепшен»).
- **Активный заказ** виден плашкой над разделами меню («Заказ #12 · Принят»).

## 3. Архитектурные решения

**Р-1. Заказ — это заявка в F&B плюс модуль `room_service`.** Новый доменный
модуль `modules/room_service/` владеет меню, настройкой «принимаем / не
принимаем» и заказами (позиции, суммы, причина отмены). Заказ рождает
`ServiceRequest` в категории F&B и живёт его жизненным циклом: дневной номер,
маршрут в чат службы (spec 0026), напоминания (spec 0028), очередь кабинета,
сводка дня. Так требует FOUNDATION §5.2 («единый конвейер заявок») и вход
#418. Почему не внутри `requests/`: меню — каталог, а не заявка, а канонический
модуль не должен знать про блюда. Почему не отдельный жизненный цикл у заказа:
пришлось бы второй раз строить номер, маршрутизацию, напоминания и сводку.
Зависимость односторонняя: `room_service` → `requests.api`; `requests` о
заказах не знает.

**Р-2. «Оплачено» — отметка на заявке, а не новый статус.** В `requests`
появляются признак `payment_required` (ставится при создании и не меняется)
и отметка `paid_at` + `paid_by_*` — по образцу `claimed_*`/`closed_*`
(spec 0035). Правило живёт в домене: заявку с `payment_required` нельзя
перевести в `done` без отметки (`ERR-REQUESTS-005`), из какого бы канала ни
пришло «Готово» — кабинет, кнопка Telegram, `/done N`, HTTP API. Статусов по-прежнему четыре
(ADR-013 не меняется); стадию заказа для глаз выводит `room_service` (Р-4). Почему
отметка, а не статус: «оплачено» — факт о деньгах, а не стадия работы службы.
Новый статус пришлось бы учесть в очереди, сводке, напоминаниях и всех
клавиатурах. Так же ADR-013 и spec 0034 решили со срочностью. Отметка обобщена
на любую заявку с оплатой при выполнении. Когда до него дойдёт очередь, её
переиспользует #124 (вода за деньги), но заводится она сейчас ради room service.

**Р-3. Атомарность заказа и заявки.** Сервисные функции модулей сами
открывают транзакцию (`session_scope`), общей транзакции на два модуля в
проекте нет и не заводится. Поэтому id заявки задаёт `room_service` заранее:
1. одной транзакцией пишет заказ и позиции с `request_id = uuid4()`;
2. зовёт `requests.create_request(request_id=…)`. Создание по заданному id
   идемпотентно (P-8): если заявка с этим id уже есть, она возвращается без
   второго события и второго номера.

Сбой между шагами оставляет заказ без заявки. Его не видит ни персонал, ни
страница (заказ показывается, только если заявка есть). Повтор «Оформить» с
тем же ключом клиента (§5.3) доводит дело до конца. Брошенный недооформленный
заказ удаляет ретеншн (§4.5).

**Р-4. Стадия заказа выводится, а не хранится** — одна функция
`room_service.order_stage(request)`:

| Заявка | Стадия | Гость видит |
|---|---|---|
| `new` | `sent` | Отправлен |
| `in_progress`, `paid_at` пуст | `accepted` | Принят |
| `in_progress`, `paid_at` есть | `paid` | Оплачен, готовим |
| `done` | `delivered` | Доставлен |
| `cancelled` | `cancelled` | Отменён |

**Р-5. Деньги.** Суммы — целые числа в минимальных единицах валюты (`*_minor`,
тиын для KZT). Валюта в основе одна, `KZT`: схема конфига принимает только её,
вторая валюта — расширение `Literal` и таблицы округления. Цена блюда задаётся
в кабинете целыми тенге. Сбор = сумма блюд × процент / 100, округление до
целого тенге, половина — вверх; процент и сбор пишутся в заказ снимком.
Итог, который видит гость, считает сервер (`quote`), и тот же итог гость
присылает при оформлении (`expected_total_minor`). Разошёлся с пересчётом
(цену поменяли, блюдо ушло в стоп-лист) → `ERR-ROOMSERVICE-005`, страница
показывает новый итог, ничего не оформляется молча (P-9). Позиции заказа
хранят снимок названий на всех языках и цены: правка меню после заказа его
итог не меняет.

**Р-6. Языки.** Названия и описания — JSONB `{"en": …, "ru": …, "kk": …}`
под Pydantic-схемой `LocalizedText`: `en` обязателен, остальные языки — из
списка языков отеля (§4.4). Нет перевода на языке страницы — показывается
английский. Китайский позже = язык в настройках отеля + строки интерфейса
страницы (код), как у экрана согласия.

**Р-7. Источник заявки `guest_order`.** Новое значение `ServiceRequestOrigin`
(VARCHAR, без миграции значения — spec 0035 §4). Заказ с меню — работа без
участия ресепшена, поэтому числитель Exit-критерия Phase 1 становится
`guest_chat + guest_order`. Формулировку правит её владелец (spec 0035 §4) в
PR-1; решение принято сессией от имени основателя — строка в
[FOUNDER_REVIEW_QUEUE](../FOUNDER_REVIEW_QUEUE.md). Сводка дня (страница и
утреннее сообщение) получает строку «заказы с меню N»: сумма по источникам
обязана сходиться с «создано».

**Р-8. AI заказов не видит; адресация — по гостю, а не по диалогу.**
- Заказ не пишется в `request_origins`. Поэтому снапшот «мои заявки»
  (spec 0025) его не содержит, и AI не может ни отменить оплаченный заказ,
  ни пересказать его статус.
- Общий подписчик «заявка закрыта» (`notify_guest_on_request_closed`) по той
  же причине гостю о заказе ничего не шлёт.
- Сообщения о шагах заказа пишет свой подписчик в диалог веб-гостя. Диалог
  он находит по `guest_identity_id`, сохранённому в заказе.
- Персонал видит заказ иначе, чем заявку. Развилку по
  `origin == guest_order` делает одно место: `keyboard_for_request(request)`
  в `channels/telegram/keyboards.py`. Его зовут все четыре места, где сегодня
  строится клавиатура заявки. Плюс свой текст уведомления (§8.4).

**Р-9. Фото — порт файлового хранилища, адаптер «диск сервера».** FOUNDATION
§9: файлы — вне БД, в БД — только метаданные; провайдер объектного хранилища —
открытое решение §17.3, оно требует ADR в Phase 1. Решение (оформляется ADR в PR-6):
- порт `FileStoragePort` в kernel;
- обязательный `FakeFileStorageAdapter` (ADR-007);
- рабочий адаптер `LocalDiskFileStorageAdapter` на постоянном томе сервера:
  прод и так на одном сервере в РК (ADR-006), фото меню — не ПД, нового
  провайдера, договора и секретов не нужно;
- S3-совместимый адаптер появится, когда появится второй узел или файлы с ПД
  (реквизиты, Phase 2). Ядро при этом не меняется.

Почему не `bytea` в Postgres: прямое нарушение §9 ради экономии одного
адаптера. Почему не S3 сейчас: провайдер, договор и ключи на двух контурах
ради десятков картинок меню.

Загрузка проверяется декодированием и перекодированием (Pillow): принимаются
JPEG, PNG и WebP до 5 МБ. Сохраняется WebP со стороной не больше 960 px, без
метаданных (EXIF с геолокацией телефона не уезжает). Перекодирование и есть
проверка типа из §9: файл, который не декодируется как картинка, отклоняется,
а сохраняются только пиксели. Фото в бэкап не входят: ресторан загружает их
заново (строка в рунбуке восстановления, PR-6).

**Р-10. Гостевая страница — в `channels/web`, на её каноне сессии.** Маршруты
`/g/{slug}/{room}/menu…` живут в уже подключённом роутере веб-чата и стоят за
его зависимостью `_require_session`. Комната и проживание берутся из сессии,
комнату из пути канал игнорирует (README канала). Страница собирается
сервером из файлов пакета `channels/web/menu/` (шаблон, CSS, JS — отдельными
файлами ради R-3) и отдаётся одним HTML с инлайн-стилями и скриптом, как
страница чата. Нового статического маршрута и новой анонимной двери нет.
Каталог, итог и заказ страница берёт JSON-запросами (§5.4).

**Р-11. Флаг и настройки.**
- **Включён ли room service у отеля, сбор, валюта и языки** — конфигурация
  тенанта, раздел `TenantConfig.room_service` (§4.4). Задаёт оператор файлом
  профиля онбординга (P-11), а не F&B из кабинета: сбор — условие договора
  отеля, а не меню.
- **«Принимаем / не принимаем»** — оперативное состояние, его переключают
  каждый вечер. Поэтому это строка в БД модуля, а не конфиг: конфиг
  версионируется и пишется целиком (§6 FOUNDATION).
- **Флаг выключен** → маршруты меню отдают 404, кнопки «Меню» в чате нет.

**Р-12. «Хочу поесть» — данные, без правки промпта.** Боту хватает факта
справочника отеля (spec 0036), например: «Еду в номер заказывают в меню:
кнопка „Меню“ вверху страницы чата. Оплата — сотруднику при получении». Факт
добавляют в момент включения флага (§10). Текстовая заявка в `fnb` («уровень
ноль») работает как раньше: цены бот не называет, сумму считает код и только
на странице. Промпт и evals не меняются, платного прогона нет.

## 4. Данные

Все таблицы — тенантные, RLS по канону `0002` (ENABLE + FORCE + политика
`tenant_isolation`). FK между модулями не ставятся — по образцу
`request_origins` и `conversations.guest_identity_id`.

### 4.1. `service_requests` — новые колонки (PR-1)

| Колонка | Тип | Смысл |
|---|---|---|
| `payment_required` | `BOOLEAN NOT NULL DEFAULT false` | оплата при выполнении; ставится при создании |
| `paid_at` | `TIMESTAMPTZ NULL` | когда сотрудник отметил «Оплачено» |
| `paid_by_user_id` | `UUID NULL`, FK `users` ON DELETE SET NULL | кто отметил |
| `paid_by_display_name` | `VARCHAR(255) NULL` | снапшот имени (PII сотрудника) |

CHECK: `paid_at IS NULL OR payment_required`. Предикат spec 0035 расширяется:
`paid_by_user_id IS NOT NULL` ⟹ `paid_at IS NOT NULL`. Обратное тоже верно:
отметку ставит только человек (§5.1).

### 4.2. Меню (PR-2)

- `menu_sections`: `id`, `tenant_id`, `position` (INT), `names` (JSONB),
  `archived_at` (TIMESTAMPTZ NULL), `created_at`, `updated_at`.
- `menu_items`: `id`, `tenant_id`, `section_id` (FK `menu_sections`),
  `position`, `names` (JSONB), `descriptions` (JSONB, может быть `{}`),
  `price_minor` (INT, CHECK > 0), `is_stopped` (BOOLEAN NOT NULL DEFAULT
  false), `archived_at` (TIMESTAMPTZ NULL), `created_at`, `updated_at`.
  `photo_key` добавляет PR-6.
- `room_service_settings`: `tenant_id` (PK), `accepting_orders` (BOOLEAN NOT
  NULL DEFAULT false), `updated_at`. Строки нет → «не принимаем».

«Удалить» блюдо или раздел — это `archived_at`, а не DELETE: позиции старых
заказов ссылаются на блюдо. Раздел с живыми блюдами не архивируется
(`ERR-ROOMSERVICE-009`). Порядок — `position`, кабинет меняет его стрелками.
Под будущий POS (#418, вход 11) у блюда стабильный UUID, а заказ хранит снимок.
Внешний ключ POS — будущая аддитивная колонка. Источником истины меню станет
порт, а не правка этих таблиц.

### 4.3. Заказы (PR-4)

- `room_service_orders`: `id`, `tenant_id`, `request_id` (UUID UNIQUE, без
  FK), `stay_id`, `guest_identity_id` (без FK), `client_order_key` (UUID),
  `guest_language` (VARCHAR(2)), `currency` (VARCHAR(3)), `subtotal_minor`,
  `service_charge_percent` (NUMERIC(5,2)), `service_charge_minor`,
  `total_minor`, `cancel_reason` (VARCHAR(32) NULL — значение
  `OrderCancelReason`), `created_at`, `updated_at`. UNIQUE
  `(tenant_id, stay_id, client_order_key)` — защита «Оформить» от двойного
  нажатия (P-8).
- `room_service_order_lines`: `id`, `tenant_id`, `order_id` (FK, CASCADE),
  `menu_item_id` (FK `menu_items`, без каскада — блюда не удаляются),
  `position`, `names` (JSONB — снимок), `unit_price_minor`, `quantity`
  (1–20), `line_total_minor`.

Комната, номер `#N`, пожелания и все времена шагов живут в заявке, второго
экземпляра у заказа нет. Пожелания гостя — это `details` заявки: на них
работает обезличивание текстов заявок (spec 0032), отдельной копии ПД нет.
`summary` заявки — «Заказ в номер: Борщ со сметаной ×1, Чай ×2» по-русски
(фолбэк — en), обрезается до 500 знаков.

### 4.4. Конфигурация тенанта (PR-2)

`TenantConfig.room_service: RoomServiceConfig | None = None` — необязательное
поле, `schema_version` остаётся 1 (§6):

```python
class RoomServiceConfig(BaseModel):
    enabled: bool = False                      # фиче-флаг (§10)
    category_key: str = "fnb"                  # куда уходят заказы; категория обязана существовать
    currency: Literal["KZT"] = "KZT"
    service_charge_percent: Decimal = Field(ge=0, le=30, decimal_places=2)
    languages: tuple[str, ...] = ("en", "ru", "kk")   # en обязателен и первый
```

Числа пилота (процент сбора) в репозиторий не пишутся: они живут в файле
профиля отеля на сервере, как телефон ресепшена. Демо-отель на staging
получает `enabled=True`, сбор 10% и демо-меню из сида (§9, PR-2).

### 4.5. ПД и ретеншн

- `service_requests.paid_by_display_name` — строка в
  [PII_REGISTRY](../PII_REGISTRY.md) по образцу `claimed_by_display_name`
  (PR-1).
- Пожелания гостя — уже учтённое поле `service_requests.details` (обезличивание
  — spec 0032); новой строки реестра не нужно. PR-4 сверяет это тестом:
  обезличенная заявка-заказ теряет пожелания, позиции и суммы живут.
- Заказы без заявки (Р-3) старше суток удаляет джоба ретеншна
  (`channels/common/retention.py`, PR-4). Остальные заказы живут, пока живут
  их заявки: в них нет ПД гостя, а суммы нужны отчётам.

## 5. Контракты

### 5.1. `requests.api` (PR-1)

- `ServiceRequestCreate`: + `request_id: UUID | None = None` (идемпотентное
  создание, Р-3), + `payment_required: bool = False`.
- `ServiceRequestRead`: + `payment_required`, `paid_at`,
  `paid_by_display_name`, `closed_by_display_name`. Последнее spec 0035 наружу
  не отдавала за ненадобностью, теперь потребитель есть — карточка заказа
  показывает, кто доставил (§8.3).
- `mark_request_paid(request_id, *, acting_user: ActingUser) ->
  ServiceRequestRead`. Новый файл `payment.py`: `service.py` уже за границей
  R-3. `acting_user` обязателен: «Оплачено» ставит только человек (P-9).
  Допустимо только при `payment_required`, статусе `in_progress` и пустой
  отметке, иначе `ERR-REQUESTS-006` (409). Строка берётся FOR UPDATE.
  Публикует `request.payment_marked`.
- `change_request_status(…, only_from: RequestStatus | None = None)`: переход
  выполняется, только если текущий статус равен `only_from`, иначе
  `ERR-REQUESTS-003`. Проверка идёт под той же блокировкой FOR UPDATE —
  гонку «гость отменяет, сотрудник принимает» выигрывает один.
- Защита в `change_request_status`: переход в `done` при `payment_required`
  и пустом `paid_at` → `ERR-REQUESTS-005` (409).
- `ServiceRequestOrigin.GUEST_ORDER = "guest_order"`.
- Событие `RequestPaymentMarked` (`request.payment_marked`: `request_id`).

Заказы (PR-4):

```text
quote(lines: list[OrderLineInput]) -> OrderQuote

    # OrderPlace: stay_id, guest_identity_id, room_number, client_order_key,
    #             lines, expected_total_minor, comment ≤ 200, guest_language
```

Правила `place_order`:
- флаг включён, «принимаем»;
- все блюда живые и не в стоп-листе;
- от 1 до 30 позиций, от 1 до 20 порций каждая;
- итог совпадает с `expected_total_minor`;
- у проживания не больше 3 открытых заказов и не больше 10 заказов за сутки
  (числа — этой спеки). Защищает чат службы от потока «оформил — отменил»;
- категория `category_key` существует.

Нарушение — свой код из §5.5.

`remove_item_photo(item_id)`, `read_item_photo(photo_key) -> bytes`; в

## 7. Пересечения с основной очередью

- **#228 (`stay_id` в заявке)** — не пререквизит. Заказ сам хранит `stay_id`
  из сессии. Когда #228 появится, `place_order` передаст его в
  `create_request` одной строкой — это записано в README `room_service`
  (PR-4). Серия не ждёт #228, #228 не ждёт серию.
- **#370 (журнал изменений)** — не пререквизит. «Кто отметил оплату» уже
  хранится в заявке (`paid_by_*`, §4.1), отмена заказа — в `closed_by_*`.
  Журнал, когда появится, добавляет к списку действий заявок «отметил оплату»
  (событие `request.payment_marked`). Записано комментарием в #370.
- **#212 (часы служб)** — переключатель «принимаем» и есть «кухня работает»
  для заказов в номер. Заказ, принятый при включённом переключателе, ночной
  логикой #212 не откладывается до открытия службы: иначе гость ждал бы всю
  ночь заказ, который сам ресторан согласился принять. Спека #212 обязана
  исключить заявки с `origin=guest_order` из отложенной доставки. Записано
  комментарием в #212.
- **#384 (пилот по этапам)** — room service на пилоте включается не раньше
  этапа 3 (заявки): без включённых заявок F&B не получает уведомлений.
- **#124 (вода за деньги)** — переиспользует отметку оплаты (Р-2), сама серией
  не делается.
- **#82** — общий порт файлового хранилища (Р-9) появляется в PR-6.

## 9. Серия PR — ТЗ

Порядок строгий: каждый следующий PR — draft на ветке предыдущего, пока тот
не смержен; после merge — на `main`. Все PR серии остаются draft до своего
окна ревью (решение основателя 04.10: дорожка room service параллельна
основной очереди, основная сессия её PR не трогает). Smoke (spec 0019) на
черновиках не идёт; на «ready» и на push в `main` он идёт по уже одобренному
потоку и цене spec 0019. Новых платных проверок серия не вводит. Ориентир #418
— 3–5 PR. Серия из шести: без отдельного PR-3 второй PR вырос бы примерно до
2,5 тыс. строк, а такой diff ревью уровня A за один проход не удерживает
(правило 9).

У каждого PR одинаковые обязательные пункты:
- README затронутых модулей (R-4);
- `docs/runbooks/errors.md` для новых кодов;
- структурированные логи с `tenant_id` и метрики (P-10);
- тест изоляции тенанта для каждой новой таблицы и маршрута (P-4);
- `make check` зелёный;
- платных вызовов модели нет.

### PR-1. Заявка с оплатой при выполнении — уровень A

- **Входит:** колонки §4.1 (миграция — следующий номер), контракты §5.1,
  `requests/payment.py`, защита `done`, `only_from`, идемпотентное создание
  по `request_id`, `GUEST_ORDER`. Строка «заказы с меню» в
  `staff_portal/summary.py` и `channels/telegram/daily_summary.py`. Правка
  spec 0035 §4 (таблица значений и числитель), строка GLOSSARY «Источник
  заявки» (новые термины серии внесены PR спеки), PII_REGISTRY, errors.md.
- **Не входит:** модуль `room_service`, любые экраны и тексты гостю, правки
  Telegram-клавиатур (PR-5). Заявок с `payment_required` в этом PR не
  создаёт никто, кроме тестов.
- **Тесты:**
  - `done` без отметки → 005 из сервиса и из `POST /api/v1/requests/{id}/status`;
  - отметка → `done` проходит;
  - отметка неприменима → 006 (каждая из трёх причин);
  - повторная отметка → 006, а не вторая запись;
  - событие `request.payment_marked` публикуется в той же транзакции;
  - создание с тем же `request_id` возвращает ту же заявку: одно событие,
    один номер;
  - `only_from=NEW` на заявке `in_progress` → 003;
  - конкурентные «отмена с `only_from`» и «взять» → ровно один победитель;
  - CHECK и предикат имён §4.1;
  - сводка: сумма по четырём источникам равна «создано».
- **Приёмка:**
