# Spec 0041: журнал изменений в кабинете — кто что сделал с заявками и заселением

- **Статус:** черновик (PR #445)
- **Issue:** #370
- **Дата:** 2026-10-16
- **Решение:** основатель 27–28.09.2026 в теле #370: состав (заявки + заселение), срок
  (тот же, что у текстов гостей), видит менеджер. Остальное решено здесь.
- **Связано:** [spec 0032](0032-guest-text-retention.md) (срок и джоба ретеншна),
  [spec 0033](0033-staff-cabinet-v1.md) §3.3 и [RBAC.md](../RBAC.md) (роли),
  [spec 0035](0035-pilot-measurability.md) §3 (`claimed_*`/`closed_*`),
  [spec 0038](https://github.com/dikatapulta/HospitalityAIPlatform/pull/420) §7 (отметка оплаты).

## 1. Проблема

Менеджер не видит, кто из сотрудников что сделал. Действия кабинета сегодня видны только
в структурированных логах сервера. У заявки хранится последний «кто взял» и «кто закрыл»
(spec 0035 §3), но истории нет, а у заселения, выезда, переселения и нового кода не хранится
даже этого. В Opera у отеля есть экран Changes, и менеджер ждёт такой же.

## 2. Решение

### 2.1. Таблица `staff_action_log` — ядро, а не модуль

Действия рождаются в двух доменных модулях, `requests` и `guests`, а друг друга они не
импортируют (FOUNDATION, слои). Поэтому таблица и функции живут в ядре: модель в
`platform/models.py` по канону `TenantIsolationCanary`, функции в новом
`platform/staff_actions.py`. Оба модуля зовут ядро, это разрешённое направление.

Запись делается **той же сессией и той же транзакцией**, что и само действие (решение issue).
Откатилось действие, значит откатилась и строка, и журнал не врёт ни «было», ни «не было».
Outbox не годится: не каждое действие публикует событие (`move_stay`, `extend_stay`,
`reissue_access_code` его не публикуют), а срок outbox 30 дней.

| Колонка | Тип | Смысл |
|---|---|---|
| `id`, `tenant_id` | канон | RLS: ENABLE + FORCE + политика (ADR-003) |
| `occurred_at` | `UTCDateTime` NOT NULL | момент действия, `utc_now()` той же транзакции |
| `actor_user_id` | `Uuid` NULL, FK `users.id` ON DELETE SET NULL | кто; пара «FK + снапшот» как у `claimed_by_*` |
| `actor_login` | `VARCHAR(12)` NULL | снапшот логина отеля (spec 0037 §6); NULL — учётка без логина |
| `action` | `VARCHAR(32)` NOT NULL, StrEnum без CHECK (канон `StaffRole`) | §2.2 |
| `request_id`, `stay_id` | `Uuid` NULL, **без FK** | на что: ядро не ссылается на таблицы модулей |
| `request_daily_number`, `request_service_day` | `INTEGER`, `DATE` NULL | снапшот `#N` и его дня: номер уникален только внутри дня |
| `category_name` | `VARCHAR(255)` NULL | снапшот подписи службы (`request_categories.name`) |
| `room_number` | `VARCHAR(20)` NULL | снапшот комнаты; у переселения — откуда |
| `room_number_to` | `VARCHAR(20)` NULL | только у переселения — куда |
| `nights` | `SMALLINT` NULL | только у продления |
| `with_note` | `BOOLEAN` NOT NULL DEFAULT false | готово или отмена с примечанием |

Индекс — `(tenant_id, occurred_at DESC)`. Снапшоты, а не join: журнал — свидетельство «как
было в момент действия», и переименованная служба не должна менять прошлые строки.

**Текстов в таблице нет по построению**: ни `summary`/`details`/`resolution_note` заявки,
ни имени гостя, ни `display_name` сотрудника (решение issue). `with_note` говорит, что
примечание было, но само примечание не копирует. Иначе журнал продлевал бы жизнь ПД в обход
spec 0032.

### 2.2. Типы действий — пишется только действие с личностью

| `action` | Где пишется | Подпись в журнале | «Что» |
|---|---|---|---|
| `request_created` | `requests.create_request` с `acting_user` (форма «Новая заявка») | Создана вручную | `#15 · Уборка · 305` |
| `request_claimed` | `change_request_status` new → in_progress | Взята в работу | `#12 · Уборка · 305` |
| `request_done` | → done; `with_note` → «Выполнена с оговоркой» | Выполнена | `#12 · Уборка · 305` |
| `request_cancelled` | → cancelled | Отменена | `#14 · Инженер · 220` |
| `stay_checked_in` | `guests.check_in` | Заселение | `305` |
| `stay_checked_out` | `guests.check_out` | Выезд | `412` |
| `stay_moved` | `guests.move_stay` | Переселение | `305 → 412` |
| `stay_extended` | `guests.extend_stay` | Продление | `412 · на 2 ночи` |
| `stay_code_reissued` | `guests.reissue_access_code` | Новый код | `412` |

Строка пишется **только когда вызывающий передал личность сотрудника** (`acting_user`).
Путь без личности ничего не пишет: Telegram-суррогат (ADR-008 §7), отмена гостем,
заявка от ИИ, HTTP API. Журнал отвечает на вопрос «кто из сотрудников», и строка «кто-то»
на него не отвечает. У пилотного отеля персонал работает только в кабинете (решение
основателя 13.10, #384), поэтому дыры здесь нет.

**«Продление» добавлено сессией**: в списке issue его нет, но это то же действие с карточкой
Stay, что переселение. Менеджер, увидевший выезд позже срока, должен найти, кто продлил.

**Отметка оплаты** (`request_payment_marked`, подпись «Оплачено») входит в контракт журнала,
но кода у неё пока нет. Значение enum, подпись и вызов добавляет PR room service, который
добавляет кнопку «Оплачено» (spec 0038 §7). Этот PR их не добавляет, по P-1.

**Печать листка не пишется.** Она клиентская (`window.print()`), и сервер о ней не знает.
Отдельный запрос «напечатал» лгал бы при отменённом диалоге печати. Действие с последствиями
у листка — новый код, и он в журнале. Выдача ещё одного QR привязки без нового кода в v1
тоже не пишется (`docs/LATER.md`).

### 2.3. Личность: логин, а не имя

`ActingUser` (сегодня `modules/requests/schemas.py`) переезжает в ядро как
`platform.staff_actions.StaffActor(user_id, display_name, login)`. `requests` реэкспортирует
его под старым именем, `guests` принимает тот же тип новым kw-only аргументом
`acting_user: StaffActor | None = None` в пяти функциях из §2.2. `display_name` по-прежнему
идёт в `claimed_by_*`/`closed_by_*` (spec 0035), в журнал идёт только `login`.
`StaffContext.login: str | None` заполняет `require_role` из `user_identities` тем же способом,
что страница «Сотрудники» (`staff_credentials.parse_password_external_id`). `staff_portal`
передаёт `acting_user` во все пять действий заселения так же, как сегодня передаёт его в
действия заявок.

### 2.4. Страница `/staff/{slug}/changes`

- Маршрут — в `staff_portal/router.py`, роль `_manager_role` (RBAC.md, новая строка матрицы).
  Карточка «Журнал изменений» на главной видна только менеджеру, как «Сводка дня».
- Серверный рендер, GET-форма без JS. Фильтры:
  - **«День»** — дата по поясу отеля (`TenantConfig`, FOUNDATION §9), по умолчанию сегодня.
    Сервер переводит её в полуинтервал UTC `[00:00, 24:00)` отеля.
  - **«Сотрудник»** — «Все» и `DISTINCT actor_login` журнала тенанта.
  - **«Действие»** — «Все действия» и подписи из §2.2. Фильтр «Выполнена» включает и строки
    с оговоркой.
- Заявка не из выбранного дня (вчерашнюю `#12` взяли сегодня) показывается с датой:
  `#12 (15.10) · Уборка · 305`. Иначе её не отличить от сегодняшней `#12`.
- Сортировка — новые сверху, страница 200 строк, ссылка «Показать более ранние» (`offset`,
  канон `list_requests`). Время — `ЧЧ:ММ` по поясу отеля.
- Тексты страницы — §4.

### 2.5. Срок хранения

Своего числа у журнала нет: срок — `MESSAGES_RETENTION_DAYS` (владелец — spec 0032 §1).
Удаляет та же джоба: `enforce_guest_text_retention` для каждого тенанта зовёт
`platform.staff_actions.delete_staff_actions_before(cutoff) -> int`, а итоговый лог
`guest_text_retention_completed` получает счётчик `staff_actions_deleted`. Идемпотентность
та же, что у удаления сообщений: повторный DELETE по `occurred_at < cutoff` строк не находит.
Сбой — тот же `ERR-CHANNEL-004` по тенанту. Новых кодов ошибок нет.

## 3. Контракты

- `platform.staff_actions.StaffAction` (StrEnum §2.2), `StaffActor`, `StaffActionRecord`
  (Pydantic: поля таблицы без `id`/`tenant_id`/`occurred_at`).
- `record_staff_action(session: AsyncSession, actor: StaffActor, record: StaffActionRecord) -> None`
  делает только `session.add` и не открывает свою транзакцию.
- `list_staff_actions(*, day_start: datetime, day_end: datetime, actor_login: str | None,
  actions: frozenset[StaffAction] | None, limit: int, offset: int) -> list[StaffActionRead]`
  и `list_staff_action_logins() -> list[str]` открывают свой `session_scope()`.
- `delete_staff_actions_before(cutoff: datetime) -> int`.
- `requests.api.ActingUser` = `StaffActor` (реэкспорт); `create_request(data, *, acting_user=None)`.
- `guests.api.check_in/check_out/move_stay/extend_stay/reissue_access_code(..., *, acting_user=None)`.
- Миграция: таблица, индекс, RLS-блок по канону 0002, downgrade удаляет таблицу. Head-ревизия
  в `tests/test_db.py` — тем же PR.

## 4. Тексты (показаны основателю в чате 16.10 до спеки)

- Главная, карточка: «Журнал изменений» — «Кто что сделал с заявками и заселением».
- Заголовок: «Журнал изменений». Подзаголовок: «Действия сотрудников с заявками и заселением.
  Записи хранятся {N} дней.» N подставляется из `messages_retention_days`, в шаблон не пишется.
- Колонки: «Время», «Сотрудник», «Действие», «Что». Подписи действий и колонки «Что» — §2.2.
  Пустой логин — «без логина».
- Фильтры: «День», «Сотрудник» (первый пункт «Все»), «Действие» (первый пункт «Все
  действия»), кнопка «Показать».
- Пусто: «За этот день записей нет.» Пагинация: «Показать более ранние».

Подписи не зависят от рода («Выполнена», а не «закрыл/закрыла»): по логину не видно, кто
сотрудник, мужчина или женщина. Поэтому вместо фразы «BORM закрыл #12» из issue — таблица.

## 5. Что сознательно НЕ делаем

- Сотрудники, приглашения, роли и входы в кабинет — не в этой задаче (решение issue).
- Ресепшен журнал не видит (решение issue: расширение — отдельным решением).
- Экспорт в CSV и поиск по номеру заявки — NG-8, пока не попросят.
- Запись из путей без личности (§2.2).

## 6. План тестов

1. **Транзакционность:** каждое из девяти действий с `acting_user` даёт ровно одну строку с
   верными снапшотами. Отказ действия (недопустимый переход `ERR-REQUESTS-003`, занятая
   комната `ERR-GUESTS-002`) строки не оставляет.
2. **Без личности — без строки:** переход из Telegram-пути, отмена гостем, заявка от ИИ.
3. **Нет текста:** заявка с маркерами в `summary`/`details`/`resolution_note` и гость с именем;
   ни один маркер не встречается ни в одной колонке журнала. Маркеры латиницей (кириллица в
   JSON экранируется).
4. **Изоляция (P-4):** строки тенанта A не видны в контексте B; INSERT с чужим `tenant_id`
   отвергает RLS. Тест по образцу `tests/test_tenant_isolation.py`.
5. **Ретеншн:** строки старше срока удаляются, свежие остаются, счётчик в логе, повторный
   прогон даёт 0.
6. **Страница:** менеджер видит, `receptionist`/`staff` получают 403, карточки на главной у
   них нет. Фильтры «день» (граница суток по поясу отеля, а не UTC), «сотрудник», «действие»
   («Выполнена» с оговоркой и без). Пагинация 200.
7. **Миграция:** upgrade/downgrade на CI-базе, head-ревизия.
