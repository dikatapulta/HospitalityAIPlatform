# Spec 0043: просроченные проживания — автовыезд по сроку и список в кабинете

- **Статус:** принята сессией (PR по #225), ревью — вместе с кодом
- **Issue:** #225 (аудит 05.08, находки Г-1 и Г-2)
- **Дата:** 2026-10-21
- **Решение:** в теле #225 — джоба автовыезда через N часов после расчётного часа (запас —
  конфиг тенанта) и список «просроченные» на странице заселения. Остальное решено здесь;
  запас по умолчанию — строка в [FOUNDER_REVIEW_QUEUE](../FOUNDER_REVIEW_QUEUE.md).
- **Связано:** [ADR-008](../adr/) §3–§4 (доступ гостя производен от Stay),
  [spec 0033](0033-staff-cabinet-v1.md) §6 (страница заселения),
  [spec 0041](0041-staff-changes-log.md) (журнал изменений), #122 (PmsPort).

## 1. Проблема

Выезд оформляет только человек (`guests.check_out`). Забытый выезд держит Stay в `checked_in`
навсегда, а partial unique «один активный Stay на комнату» отказывает следующему заселению
(`ERR-GUESTS-002`). При 100–150 выездах в день это случается ежедневно, и обнаруживается
только отказом у стойки. Пометка «ПРОСРОЧЕН» есть лишь в CLI `tools/checkin --list`.

Гостевой доступ этой проблемы не имеет: `resolve_session` и привязка проверяют
`now < check_out_at`, поэтому чат гостя гаснет ровно в расчётный час, оформлен выезд или нет
(Q8, без грейса). Просроченный Stay мешает отелю, а не гостю.

## 2. Решение

### 2.1. Когда Stay закрывается сам

Новое поле `TenantConfig.stay_auto_checkout_grace_hours: int | None`, по умолчанию **2**,
пределы 1…72. Stay закрывается, когда `now ≥ check_out_at + grace`.

- **Расчётный час уже внутри `check_out_at`:** кабинет и CLI ставят 12:00 по поясу отеля из
  конфига тенанта (spec 0033 §6), в БД — UTC (§9). Запас прибавляется к этому моменту, а в
  кабинет время выводится снова по поясу отеля. Свой расчётный час (CLI `--check-out`)
  уважается: запас считается от него.
- **2 часа по умолчанию:** к 14:00, обычному часу заезда, комната свободна для следующего
  гостя. Поздний выезд в кабинете не выражается (продление — целыми ночами), поэтому
  длинный запас ничего не защищает: чат гостя всё равно погас в 12:00.
- **`null` — автовыезд выключен:** отель без него или с выгрузкой из PMS (§2.4).
- **Источник — файл профиля отеля** (`ops/onboarding/*.json`), как сроки напоминаний:
  онбординг берёт поле из профиля, поэтому повторный онбординг его не сотрёт. Поля нет в
  файле — действует умолчание.

Пока запас не вышел, просроченный Stay продлевается кнопкой «+N ночей», и старые код и QR
оживают вместе со сроком (ADR-008 §3). После автовыезда — только новое заселение с новым
листком: это и есть смысл запаса.

### 2.2. Джоба

`guests_api.close_overdue_stays() -> int` — шаг цикла воркера раз в
`worker_stay_auto_checkout_interval_seconds` (600, `.env.example`), канон периодической
задачи `remind_unclaimed_requests` (NG-8, планировщика нет). Список тенантов —
платформенной сессией; работа со Stay — внутри `tenant_context` каждого (P-4). Сбой одного
отеля логируется и не останавливает остальных; сбой прогона целиком — `ERR-GUESTS-007`, цикл
воркера живёт дальше. За прогон — до 500 Stay на отель (больше — WARNING, остаток в следующий
прогон).

Каждый Stay закрывается **своей транзакцией тем же путём, что ручной выезд** (`close_stay`,
P-12): статус `checked_out`, код, ссылки привязки и сессии гаснут, `stay.checked_out`
публикуется. Событие одно и то же: подписчикам неважно, кто закрыл.

**Гонка с сотрудником.** Джоба берёт строку `FOR UPDATE SKIP LOCKED` и в той же выборке
перепроверяет статус и срок. Выезд, продление и переселение (`_get_active_stay_or_raise`)
теперь тоже берут `FOR UPDATE`; перевыпуск кода — нет: его гонку по-прежнему разводит
partial unique активного кода (`ERR-GUESTS-003`). Итог: «Продлить» в ту же секунду либо успевает первым (срок
сдвинулся — джоба Stay не тронет), либо ждёт джобу и честно получает `ERR-GUESTS-001`
(«проживание уже закрыто»), а не «продлено» у закрытого Stay.

### 2.3. Веб-чат гостя и журнал изменений

- **Чат:** новых текстов нет. Гость потерял доступ ещё в `check_out_at`; автовыезд только
  гасит записи, которые уже не действовали. Новых ПД и новых мест хранения нет.
- **Журнал:** новое действие `stay_auto_checked_out`, подпись «Выезд по сроку», «Что» —
  комната, в колонке «Сотрудник» — «автоматически». Пишется без личности
  (`record_automatic_action`, `actor_*` = NULL). Это исключение из spec 0041 §2.2 «путь без
  личности не пишет»: там отсутствие строки значит «никто из сотрудников», здесь
  отсутствие строки оставило бы менеджера с вопросом «кто выписал 305?» без ответа.
  `VARCHAR` без CHECK — миграции нет.

### 2.4. Согласование с PmsPort (#122)

Когда появится выгрузка из PMS, источник истины о выезде PMS-Stay — PMS: сверка закроет Stay тем
же `check_out` ([ADR-004](../adr/ADR-004-pms-stay-source-opera-report-snapshot.md), правило 3).
Автовыезд при этом **остаётся включённым** (ADR-004, правило 8): он страхует ручные Stay, которых
PMS не ведёт, и день, когда выгрузка перестала приходить. Одновременно работающие выгрузка и
автовыезд не ломают данные: оба идут через `close_stay` под `FOR UPDATE`, второй находит Stay уже
закрытым. Порт этой спеке ничего не добавляет.

### 2.5. Список «Не выехали в срок» на странице заселения

Под формой заселения (форма у стойки главное) — блок, только если просроченные есть (`guests_api.list_overdue_stays()`:
`checked_in` и `check_out_at ≤ now`, по сроку выезда, до 100 строк). Роль — та же, что у
страницы (ресепшен и выше), нового права нет.

- Заголовок «Не выехали в срок — N».
- Пояснение: «Срок выезда прошёл, а выезд не оформлен: комната занята, гость уже не может
  писать в чат. Откройте карточку — продлите или оформите выезд.»
- Строка: «Комната 305 · выезд был 21.10 в 12:00 · закроется сам в 14:00» и кнопка «Открыть»
  (`?room=305` — существующая карточка). Автовыезд выключен — без «закроется сам…»; момент
  уже прошёл, а джоба ещё не дошла — «закроется сам в ближайшие минуты»; не сегодня — с датой
  («22.10 в 14:00»). Тенант без конфига джобой не обходится — обещания нет. После
  «Продлить» пометки просрочки на карточке гаснут сразу.
- Карточка просроченного Stay (плашка «просрочен» уже есть) получает строку «Срок выезда
  прошёл. Если не продлить, выезд оформится сам в 14:00.»

## 3. Контракты

- `TenantConfig.stay_auto_checkout_grace_hours`, `TenantConfig.stay_auto_checkout_grace()`
  → `timedelta | None`; `TenantProfile.stay_auto_checkout_grace_hours` (онбординг).
- `guests_api.close_overdue_stays() -> int`, `guests_api.list_overdue_stays() -> list[StayRead]`,
  `ERR_GUESTS_AUTO_CHECKOUT_FAILED = "ERR-GUESTS-007"`.
- `StaffAction.STAY_AUTO_CHECKED_OUT`, `staff_actions.record_automatic_action(session, record)`.
- Лог `stays_auto_checked_out` (тенант, число), `stay_auto_checked_out` (stay_id, комната);
  метрика `stays_auto_checked_out_total`.

## 4. Тесты

1. Stay за запасом закрывается: статус, код, ссылки, сессии погашены, событие и строка журнала
   «автоматически»; Stay внутри запаса и Stay другого тенанта не тронуты.
2. `null` в конфиге — ничего не закрывается; тенант без конфига пропущен, остальные обойдены.
3. Гонка: Stay, захваченный другой транзакцией (`FOR UPDATE`), джоба пропускает; продление
   после автовыезда — `ERR-GUESTS-001`.
4. Воркер: шаг на старте, по интервалу; сбой не роняет цикл.
5. Онбординг: поле из профиля, без поля — 2.
6. Кабинет: блок со строками и «закроется сам в …», без просроченных — блока нет; журнал
   показывает «Выезд по сроку / автоматически».

## 5. Не делаем

- Уведомлений персоналу в Telegram о закрытых Stay — сводка дня и журнал отвечают.
- Счётчика просроченных на главной кабинета и поздних выездов «до 18:00» — строки в
  [LATER](../LATER.md).
