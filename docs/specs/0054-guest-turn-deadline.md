# Spec 0054: потолок ожидания хода гостя

- **Статус:** черновик (PR #557)
- **Issue:** #271 (и дополнение аудита тихих отказов Д-5)
- **Дата:** 2026-10-30
- **Касается:** [ADR-017](../adr/ADR-017-llm-budget-reservation-and-retry-pause.md)
  (паузы между попытками остаются, потолок встаёт над ними), деградация
  FOUNDATION §7.8 (реплика и эскалация прежние, меняется только момент).

## 1. Проблема

Худший ход гостя складывался из настроек шлюза: `LLM_MAX_ATTEMPTS ×
LLM_TIMEOUT_SECONDS` плюс паузы — при умолчаниях 3 × 30 с + до 3 с ≈ 93 с.
Ход подтверждения, на котором гость передумал, зовёт шлюз дважды
(классификатор, затем новый запрос) — до ~3 минут. Всё это время гость в
веб-чате видит своё сообщение без ответа и без признака жизни, а Telegram
считает вебхук неотвеченным. Подъём `LLM_TIMEOUT_SECONDS`, который советовала
статья ERR-AI-001, растягивал ожидание дальше: с 42 с ход выходит за 125 с
Cloudflare, страница пишет «Не доставлено», и повтор гостя — второй ход и
вторая эскалация (аудит 04.10, Д-5).

## 2. Решение

Вариант 1 из #271 — общий потолок хода. Вариант 2 («меньше попыток») оставлял
потолок произведением двух настроек, которое разъедется при следующей правке;
вариант 3 (ответ сразу, ход фоном) меняет контракт каналов и требует ADR —
это Phase 1, не Gate B (строка #271 в очереди).

- **Потолок — 25 секунд на весь ход** (`GUEST_TURN_DEADLINE_SECONDS`,
  `channels/common/guest_turn.py`) — решение основателя 30.10 из трёх
  вариантов (25 с, 45 с, оставить как есть) с ценой, названной ниже. Самый долгий здоровый вызов на гостевой
  копии и staging за всё время — около 5 с (медиана 2–2,5 с, ~230 вызовов,
  журнал `llm_call_log` на 30.10), то есть запас пятикратный; 25 с — внутри
  окна повтора вебхука Telegram (около минуты) и далеко от 125 с Cloudflare.
- **Задаёт потолок гостевой канал, соблюдает шлюз.** Канал знает, сколько гость
  готов ждать; шлюз — единственное место, где идут попытки (§7.2).
  `orchestrator.handle_message(deadline=…)` передаёт один и тот же объект во
  все вызовы шлюза хода: второй вызов получает остаток, а не свежий потолок.
- **Шлюз** (`complete(..., deadline=…)`): попытка обрывается в момент потолка
  (`asyncio.timeout` вокруг вызова провайдера); после таймаута новая попытка
  не начинается, если пауза перед ней не меньше остатка; потолок уже вышел —
  провайдер не зовётся вовсе. Исход во всех случаях — тот же ERR-AI-001 и строка
  `timeout` в журнале, плюс лог `llm_call_deadline_reached`.
- **Обрывается только сетевой вызов.** Записи шлюза в БД (журнал, резерв) и
  исполнение инструментов хода (создание заявки) потолок не прерывает: он
  проверяется лишь вокруг обращения к провайдеру.
- **Что видит гость** — прежнюю деградацию: «Извините, сейчас я не могу
  ответить — уже зову сотрудника отеля» и эскалацию персоналу (или «позвоните на
  ресепшен», если звать некого, spec 0051), но не позже чем через 25 с.
- **Цена.** При умолчаниях (таймаут попытки 30 с) повтора после зависания
  внутри хода гостя нет: зависшую попытку обрывает потолок. Гость, которому
  вторая попытка ответила бы примерно на 35-й секунде, получает «зову
  сотрудника» на 25-й. Повторы остаются для быстрых таймаутов и для вызовов
  без потолка — наставник и фото реквизитов идут вне ожидания гостя.

Потолок — константа, а не настройка окружения: менять его — решение о том,
сколько гость ждёт, и оно проходит ревью PR'ом. Для этого есть признак —
`llm_call_deadline_reached` при живом провайдере (статья ERR-AI-001).

## 3. Контракты

- `gateway.Deadline` — момент по монотонным часам; `Deadline.after(секунды)`,
  `remaining_seconds()`.
- `gateway.complete(request, *, provider=None, deadline=None)`; без `deadline`
  поведение прежнее.
- `orchestrator.handle_message(..., deadline=None)`.
- Коды ошибок и тексты гостю не меняются; статья ERR-AI-001 описывает потолок.

## 4. Тесты

- `ai/gateway/tests/test_deadline.py` — зависший провайдер обрывается на
  потолке одной попыткой; пауза длиннее остатка — без повтора и без сна;
  времени хватает — повтор работает; исчерпанный потолок — провайдер не зовётся,
  строка `timeout` в журнале.
- `ai/tests/test_orchestrator_deadline.py` — оба вызова хода подтверждения
  получают один и тот же `Deadline`.
- `channels/common/tests/test_turn_deadline.py` — зависшая модель: гость
  получает реплику деградации, эскалация записана, провайдер вызван один раз.
