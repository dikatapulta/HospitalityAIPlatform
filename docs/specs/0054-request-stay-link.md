# Spec 0054: заявка знает своё проживание — `stay_id` из сессии веб-гостя

- **Статус:** черновик (PR #560)
- **Issue:** #228
- **Дата:** 2026-10-30
- **Меняет:** [spec 0032](0032-guest-text-retention.md) §2 — новая строка таблицы
  ретеншна.

## 1. Проблема

Заявка знает о госте только строку `room_number`. Одна комната за сутки — два
проживания: заявки вчерашнего и сегодняшнего гостя различимы лишь по времени на
границе выезда. Квота «на проживание» (#124) поверх строки комнаты не строится:
переезд (`move_stay`) меняет комнату, а счёт должен идти за гостем; новый гость
в той же комнате унаследовал бы чужой счёт.

## 2. Решение

Колонка `service_requests.stay_id` — UUID, nullable, с индексом (миграция
`0048`). Пустая у всех заявок, где проживание не проверено; старые строки не
заполняются (§4).

- **Без внешнего ключа на `stays`.** `stays` — таблица модуля `guests`, а схема
  модуля не ссылается на таблицу соседа (P-2): так же хранят непрозрачный id
  `room_service_orders.stay_id`, `act_requests.stay_id` и
  `request_origins.request_id`. В тексте issue — «FK»; отступление осознанное.
- **Пишет только проверенный вызывающий внутри процесса:**
  `create_request(data, *, stay_id=None, …)` — аргумент, а не поле
  `ServiceRequestCreate`. Схема — тело публичного `POST /api/v1/requests`, и
  внешний вызывающий не должен приписывать заявку чужому проживанию — довод,
  по которому там нет и `request_id` (ревью PR #497, Н-5). Лишнее поле в теле
  запроса Pydantic молча отбрасывает.
- **Читается** полем `ServiceRequestRead.stay_id`.
- **`room_number` остаётся** и по-прежнему ведёт очередь, уведомления и поиск:
  комната — где сделать, `stay_id` — для кого.

Кто заполняет:

| Путь | `origin` | `stay_id` |
| --- | --- | --- |
| Инструмент `create_service_request` в веб-чате | `guest_chat` | Stay сессии |
| Карточка эскалации из веб-хода (ЧП, ИИ не ответил, бот не смог) | `escalation` | Stay сессии |
| Заказ в номер (spec 0038) | `guest_form` | `room_service_orders.stay_id` |
| Запрос реквизитов для АВР (spec 0049) | `guest_form` | `act_requests.stay_id` |
| Гость в Telegram | `guest_chat`, `escalation` | пусто — привязки к Stay нет (spec 0027 §3.2) |
| Форма кабинета «Новая заявка» | `staff_manual` | пусто — сотрудник называет комнату, а не проживание: номер может пустовать, а поломку мог заметить сам персонал, и квоте гостя за неё не платить |
| HTTP API | `api` | пусто — довод выше |

Сквозная передача веб-хода — рядом с уже существующей комнатой из привязки:
канал `web` передаёт `session.stay_id` в `run_guest_turn(verified_stay_id=…)`,
дальше — `orchestrator.handle_message(verified_stay_id=…)` →
`ToolTurnContext.verified_stay_id` → инструмент, и `escalate(verified_stay_id=…)`
→ карточка эскалации. Инструмент исполняется на ходу подтверждения, и Stay
берётся из сессии этого хода; переезд Stay не меняет (`move_stay` правит
комнату того же Stay).

## 3. Персональные данные и срок

`stay_id` указывает на человека через Stay. Через 90 дней (срок —
[spec 0032](0032-guest-text-retention.md)) ретеншн обнуляет его той же джобой,
что обезличивает текст заявки (`anonymize_expired_request_texts`): обезличенная
заявка не ведёт к проживанию — так же поступает `room_service_orders.stay_id`.
`room_number`, категория, статус и времена остаются отчётам. Строка —
в [PII_REGISTRY](../PII_REGISTRY.md), строка таблицы — в spec 0032 §2.

## 4. Чего здесь нет

- Потребителей: квоты (#124) и отчётов по проживанию — у них свои issue.
- Показа «прошлый/нынешний гость» в очереди кабинета.
- Бэкфилла: Stay по комнате и времени восстановим, но на границе выезда
  неоднозначен, а потребителя у старых строк нет.

## 5. Тесты

- `requests`: заявка с `stay_id` отдаёт его в `ServiceRequestRead`, без —
  пусто; `stay_id` в теле `POST /api/v1/requests` не записывается; ретеншн
  обнуляет `stay_id` у старой заявки и не трогает свежую.
- Веб-ход: заявка инструмента и карточка эскалации несут Stay сессии; ход
  Telegram — пусто.
- `room_service` и `documents`: заявка заказа и запроса АВР несёт `stay_id`
  своей строки.
- Миграция: `alembic check`, head `0048` в `tests/test_db.py`.
