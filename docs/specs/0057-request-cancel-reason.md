# Spec 0057: причина отмены заявки — список, и гостю текст по причине

- **Статус:** черновик (PR #578)
- **Issue:** #54
- **Дата:** 2026-10-31
- **Решение основателя:** 06.08.2026, [аудит](../audits/2026-08-05-operational-audit.md) §12 п. 7 —
  3–5 типовых причин кнопками + «другое» со свободным текстом.
- **Меняет:** [spec 0033](0033-staff-cabinet-v1.md) §5 — «Отменить» спрашивает причину
  списком, а не заметкой; [spec 0021](0021-request-ux-staff-and-guest.md) П-4 — текст гостю
  об отмене зависит от причины.

## 1. Проблема

Сотрудник отменяет заявку и пишет причину словами; гость получает шаблон «пришлось отменить»
и под ним эти слова как есть — «От персонала: дубль». Это записка коллеге, а не ответ гостю
(тот же довод, по которому spec 0030 убрала такую склейку у «Готово»). У дубля хуже:
вторая такая же заявка уже в работе, и «вашу заявку пришлось отменить» — неправда.
Причину нельзя посчитать: «почему отменяем» отель не узнает из свободного текста.

## 2. Решение

**Домен.** `CancelReason` (`modules/requests/models.py`, экспорт — `requests.api`) и колонка
`service_requests.cancel_reason` — VARCHAR(16), nullable (миграция `0050`), CHECK
`cancel_reason IS NULL OR status = 'cancelled'`. Канон колонки — как у `origin`: VARCHAR
со значениями `.value`, состав меняется миграцией данных.

| Значение | Подпись персоналу | Гостю |
|---|---|---|
| `unavailable` | Нет в наличии | «К сожалению, вашу заявку «{summary}» выполнить не получится: этого сейчас нет в наличии. Если подойдёт что-то другое — напишите мне, пожалуйста.» |
| `guest_declined` | Гость отказался или уехал | «Заявку «{summary}» закрыли — как мы поняли, она больше не нужна. Если это не так, напишите мне, пожалуйста.» |
| `duplicate` | Дубль — такая заявка уже есть | ничего: вторая заявка уже в работе |
| `not_provided` | Отель такого не делает | «К сожалению, с заявкой «{summary}» отель помочь не может — такой услуги у нас нет. Если нужно что-то ещё — напишите мне, пожалуйста.» |
| `other` | Другое — напишу сам | как до этой спеки: «К сожалению, вашу заявку «{summary}» пришлось отменить. Если она ещё актуальна — напишите мне, пожалуйста.» + «От персонала: {текст}» |
| `by_guest` | Гость отменил сам | ничего (spec 0025: подтверждение он получил репликой модели) |

- «Не наша служба» из решения 06.08 названа «Отель такого не делает»: с spec 0042 у заявки есть
  «Передать», и причина «не наша служба» подталкивала бы отменить вместо передачи — гость
  остался бы без помощи. Список, подсказка и тексты гостю утверждены основателем 31.10
  («как предложено» — ответ окну через диспетчера пула).
- `change_request_status(…, cancel_reason=None)` пишет причину только на переходе в
  `cancelled`; на прочих — игнор с warning-логом, как `resolution_note`. Отмена с
  `initiator=guest` всегда получает `by_guest` — правило домена, вызывающие его не передают:
  ни путь, ни будущий канал не забудут его выставить.
- Требовать причину — дело входа персонала (как требовала заметку spec 0033 §5), а не домена:
  у заказа в номер причина своя (`room_service_orders.cancel_reason`, spec 0038), у запроса
  АВР заметка — «что уточнить» (spec 0049). Их колонка остаётся пустой, тексты гостю —
  у их собственных подписчиков, как сейчас.
- `cancel_reason` — класс, не ПД: ретеншн (spec 0032) её не трогает, и счёт «почему отменяем»
  живёт дольше 90 дней. `resolution_note` по-прежнему обнуляется.
- Событие `request.status_changed` не меняется: подписчики дочитывают заявку.

**Кабинет** (очередь, `/staff/{slug}/requests`). «Отменить» открывает форму: список причин
(первым — пустое «Выберите причину», без выбора форма не уходит) и поле «Причина — гость
прочитает её в чате», видимое и обязательное только при «Другое». Под списком — «Делает другая
служба — нажмите «Передать», а не «Отменить».» (если передать есть куда). `POST
/{slug}/api/requests/{id}/cancel` принимает `{reason, note}`: `reason` обязателен,
`by_guest` — 422, `other` без непустой `note` — 422, у прочих причин `note` отбрасывается.
Страница «Документы для АВР» шлёт `reason: other` со своей заметкой — её поведение не меняется.
Закрытая заявка в ленте показывает строку «Отменена: <подпись>»; у «Другое» — текст
сотрудника строкой «Примечание: …».

**Гостю** — подписчик `notify_guest_on_request_closed`: текст из таблицы, тем же переводом на
язык гостя, тем же ключом идемпотентности. Пустая причина (Telegram до PR 2, HTTP API, строки
до миграции) — прежний шаблон с примечанием.

**HTTP API.** `ServiceRequestStatusUpdate.cancel_reason` — необязательное поле (аддитивно).
`ServiceRequestRead.cancel_reason` — наружу.

**Telegram (PR 2 серии).** «❌ Отменить» под уведомлением заменяет кнопки списком причин и
«← Назад»; «Другое» задаёт вопрос с ForceReply («Заявка #5: почему отменяете? Гость прочитает
ответ. Ответьте на это сообщение.»), ответ закрывает с `other`. `/cancel <#N> текст` — `other`
с текстом; `/cancel <#N>` без текста — подсказка про кнопки. До PR 2 кнопка отменяет, как
сейчас, с пустой причиной — прежний шаблон гостю. У гостевой копии бота нет.

## 3. Гостевая копия

Заявки на копии выключены (этап 3, #384) — отменять там нечего. Причины приходят вместе с
включением заявок; отдельного флага не нужно.

## 4. Тесты

- Домен: причина пишется только на `cancelled`; на `done` — игнор; гость → `by_guest` даже без
  аргумента; CHECK отвергает причину у незакрытой заявки (прямой UPDATE).
- Кабинет: без причины, с `by_guest`, `other` без текста — 422 и заявка открыта; с причиной —
  `cancel_reason` в ответе и строка «Отменена: …» в ленте закрытых.
- Гостю: по тексту на каждую причину; `duplicate` — ни сообщения, ни записи `Message`; пустая
  причина — прежний шаблон с примечанием.
- Миграция: `upgrade` → `downgrade` → `upgrade` (общий тест миграций), head в `tests/test_db.py`.
