- **Статус:** принята сессией (PR спеки #709); код — один PR после снятия заморозки `main` (06.11)
- **Issue:** #700
- **Дата:** 2026-11-03
- **Решение основателя:** 02.11 после встречи с хаускипингом — вкладка и её тексты (тело issue);
  03.11 ночью — брать сейчас, код в очередь слияния после 06.11 (комментарий issue). Как
  запоминать отправителя, issue оставил спеке — §2.
- **Меняет:** [spec 0045](0045-services-and-levels.md) §3 — сотрудник, кроме заявок своих служб,
  видит без права действий заявки, которые его служба отправила другим (§3);
  [spec 0041](0041-staff-changes-log.md) §2.3 — у `StaffActor` появляются службы (§2).

## 1. Проблема

Создать заявку в любую службу может любой сотрудник (форма «Новая заявка», spec 0045 §3). Но
заявка чужой службы уходит из его очереди, и о ней отправитель больше ничего не узнаёт: у заявки
нет поля «кто создал», автор есть только в журнале изменений (spec 0041, `request_created`),
а журнал видят менеджер и старший. Хаускипинг отправил технику «в 704 течёт кран» и спрашивает
в WhatsApp «сделали?».

## 2. Отправитель — полем у заявки, а не из журнала

Журнал не годится как источник списка:

- в нём нет **службы** отправителя, только `actor_user_id` и логин. Службу пришлось бы брать из
  нынешнего членства: перевели сотрудника в другую службу — его прошлые заявки переехали бы
  вместе с ним, удалили учётку (`ON DELETE SET NULL`) — пропали бы;
- журнал — свидетельство для менеджера и старшего со своим сроком и своей границей видимости
  (spec 0041 §2.5, spec 0045 §3); рабочий список на нём связал бы две фичи, и правка одной
  ломала бы другую;
- журнал в ядре, заявки в модуле: выборка шла бы двумя запросами через списки id, а поиск и
  потолок ленты — в памяти, против канона очереди «все срезы — в SQL» (#221).

**Колонка** `service_requests.created_by_service_keys` — `VARCHAR(63)[] NOT NULL DEFAULT '{}'`:
снимок служб (`service_keys` членства) сотрудника, создавшего заявку формой, на момент создания.
Ключи строками, как на членстве (spec 0045 §2): ключ удалённой категории ничего не открывает.
`server_default` остаётся навсегда — старый образ вставляет строки без колонки (откат образа).
Пусто — заявка не из формы (гость, ИИ, HTTP API) или у создателя нет служб (менеджер).
Бэкфилла нет: снимок «из нынешнего членства» был бы выдумкой, а вкладка заполнится
первыми же заявками после деплоя.

Id и имени отправителя у заявки нет: вкладка — про службу, тексты основателя отправителя не
называют, «кто создал» менеджер видит в журнале. Поэтому `PII_REGISTRY.md` не меняется.

**Как снимок попадает в заявку.** `platform.staff_actions.StaffActor` получает поле
`service_keys: frozenset[str] = frozenset()`, его заполняет `StaffContext.actor()`.
`requests.create_request` пишет `created_by_service_keys` из `acting_user.service_keys`
(сортированным списком), без `acting_user` — пусто. Поле у личности, а не отдельным
аргументом: любой будущий путь с личностью сотрудника получит снимок сам, забыть его нельзя.
В журнал службы не пишутся — колонки spec 0041 §2.1 не меняются.

## 3. Что попадает во вкладку

Заявка R — в «Отправленных» сотрудника V, когда верно оба условия:

1. `R.created_by_service_keys ∩ V.service_keys ≠ ∅` — её создал тот, кто в тот момент был
   в одной из служб V;
2. ключ нынешней категории R ∉ `V.service_keys` — сейчас она в чужой для V службе. Переданную
   обратно в службу V заявку (spec 0042) вкладка больше не показывает — она в очереди V:
   одна заявка — одно место.

Следствия:

- **Ресепшен** (служба `reception`) видит, что ресепшен отправил по звонкам технике и уборке:
  очередь показывает ему всё, вкладка — фильтр «наши».
- **Менеджер** вкладки не видит: служб у него нет, весь отель он видит в очереди и журнале.
  Нет вкладки и у сотрудника без служб — очередь уже говорит ему, что делать.
- Заявки менеджера, гостя и ИИ не попадают ни в чьи «Отправленные».
- Сотрудник уборки и прачечной отправил в прачечную: коллега только из уборки увидит заявку
  в «Отправленных», сам отправитель — в своей очереди.

Порядок — новые сверху, без окна по времени: «что стало» спрашивают и про вчерашнюю. Потолок —
тот же `_QUEUE_LIMIT` (200) с той же строкой «Показаны 200 самых новых заявок — более старые
найдёт поиск…». Статусы — все четыре: закрытая заявка и есть ответ на «сделали?».

## 4. Страница «Заявки»

- Четвёртая вкладка после «За 7 дней»: `?tab=sent` (`QUEUE_TAB_SENT`), только у сотрудника
  со службами. Без служб `?tab=sent` открывает «Открытые» — канон `parse_queue_tab`: ссылка
  коллеги с чужими правами страницу не роняет.
- Строка — как в очереди (`_queue_list.html`): комната, суть, «#N · служба-получатель», статус,
  возраст, исполнитель или «Не назначен». Нажатие открывает панель заявки целиком: суть,
  детали, «Создана», исполнитель, причина отмены и примечание.
- **Только просмотр:** ни в строке, ни в панели кнопок нет (все `can_*` ложны). Право
  действовать вкладка не меняет: действие над заявкой чужой службы по-прежнему 403
  `ERR-REQUESTS-007` (spec 0045 §5).
- Поиск по комнате и `#N` — как во вкладках очереди, в SQL. Чипсы «Все / службы / Мои»
  на вкладке скрыты: они режут по своим службам, а вкладка свои службы исключает по
  определению. Кнопки «Искать за 7 дней» нет — она ищет в своей очереди.
- Лента обновляется тем же опросом фрагмента, что и другие вкладки (`fragment_path` несёт `tab`).
- Сборка вкладки — новый `staff_portal/sent_requests.py`: `queue.py` уже за пределом R-3.

## 6. Контракты

- `StaffActor.service_keys: frozenset[str] = frozenset()` (аддитивно); `StaffContext.actor()`
  передаёт свои `service_keys`.
- `ServiceRequest.created_by_service_keys: Mapped[list[str]]` — в `ServiceRequestRead` не
  выходит: наружу не нужно, HTTP API не меняется.
- `requests.api.list_requests_sent_by_services(service_keys: frozenset[str], *, limit: int,
  room_number: str | None = None, daily_number: int | None = None) -> list[ServiceRequestRead]`:
  `created_by_service_keys && :keys`, join `request_categories` с `key <> ALL(:keys)`,
  `ORDER BY created_at DESC LIMIT`. Пустой набор — `[]` без запроса.
- Миграция: колонка с `server_default`, downgrade удаляет колонку; номер — `ops/pool.sh reserve
  migration` при коде, head в `tests/test_db.py`. Индекса нет: при ~50–120 заявках в сутки
  (spec 0033 §1) выборка по тенанту дешёвая.
- Новых кодов ошибок нет. [RBAC.md](../RBAC.md) §2 — новая строка «Очередь заявок, вкладка
  «Отправленные»: смотреть без действий» (`staff`, `senior` — свои службы, ресепшен — ✅,
  `manager` — —); README `requests` и `staff_portal` — тем же PR кода.

## 7. Тесты

- **Снимок:** форма сотрудника уборки — `{housekeeping}`; двух служб — обе; менеджера и заявки
  без `acting_user` (ИИ, гость) — пусто.
- **Выборка:** уборка → инженерия видна другому сотруднику уборки и не видна инженерии во
  вкладке; переданная обратно в уборку из вкладки уходит и есть в очереди; случай двух служб
  из §3; ресепшен видит отправленное ресепшеном; заявка тенанта A не видна в B (RLS, P-4).
- **Страница:** вкладки нет у менеджера и у сотрудника без служб (`?tab=sent` → «Открытые»);
  во фрагменте вкладки нет `data-action`; «Взять» по заявке из вкладки — 403
  `ERR-REQUESTS-007`; поиск по комнате и `#N`; тексты пустой ленты из §5; чипсов нет.
- **Миграция:** upgrade → downgrade → upgrade (общий тест миграций), head.

## 9. Что сознательно не делаем

- Уведомление отправителю «вашу заявку #12 выполнили» — пуш на телефон (spec 0050) адресует
  исполнителей; отправитель смотрит вкладку.
- Ссылку на вкладку в плашке «Заявка #N создана и ушла в службу …» — новый текст персоналу,
  отдельно от этой задачи.
- «Кто отправил» в панели заявки у службы-получателя и «мои отправленные» у менеджера — нужно
  поле автора у заявки; появится просьба — тогда.
