## 1. Проблема

Группы на 30–40 человек подбирают турагенты и корпоративные клиенты из-за рубежа, не видя здания:
отдел продаж шлёт PDF и фото, агент спрашивает «а с какого этажа видно горы?» письмами. Частный гость
с сайта отеля хочет выбрать даты, посмотреть, где будет жить, и оставить запрос, который попадёт в
отдел бронирования, а не в почту. Нужна витрина, где посетитель сам смотрит здание, этажи, стороны и
номера, подбирает их словами («высокий этаж с видом на Кок-Тобе, двенадцать номеров»), а помощник
готовит запрос — отдел продаж или бронирования получает его карточкой, как любую заявку. Ограничения,
которые задают форму, — тело issue (NG-7, NG-2, NG-3, P-9, шлюз, ПД посетителей).

## 2. Решение

### 2.1. Модуль `showroom` и сцена — данные тенанта (NG-7, P-11)

Доменный модуль `modules/showroom/` (анатомия канона `requests`) владеет **сценой** и **запросами из
витрины**. Зависимость односторонняя: `showroom` → `requests.api` (карточка), как у `table_booking`.
Имя `showroom`, а не `showcase`: `tools/demo_showcase*` — скрипты демо к показу, это другое.

**Сцена** — один документ JSON на тенанта, таблица `showroom_scenes`, не конфиг: конфиг тенанта
читается на каждом ходу гостя, а сцена на 350 номеров — десятки килобайт. Просмотрщик общий и
параметрический: строит здание из чисел сцены (корпус, этажи, номера по сторонам), файла модели нет.
Схема (`SceneDocument`, `extra="forbid"`, JSON ≤ 512 КБ, ≤ 2000 номеров):

```python
class Building(BaseModel):
    floors_total: int                       # 1..60
    length_m: float; width_m: float         # корпус — прямоугольник
    orientation_deg: int                    # азимут длинной оси; стороны считаются от него
    rounded_ends: bool = False; facade_step: bool = False   # закруглённые торцы, фасад «гармошкой»
    podium_floors: int = 0; crown: bool = False
class SideInfo(BaseModel):   names: LocalizedText; view_keys: tuple[str, ...] = ()
class ViewInfo(BaseModel):   names: LocalizedText; azimuth_deg: int | None = None; distance_m: int | None = None
class RoomTypeInfo(BaseModel):
    names: LocalizedText; windows: Literal[1, 2] = 1; note: LocalizedText | None = None
    price_note: LocalizedText | None = None  # ориентир отеля («от 45 000 ₸ за ночь»); нет — «уточнит отдел бронирования»
class Room(BaseModel):       number: str; side: Literal["north", "east", "south", "west"]; type_key: str; view_keys: tuple[str, ...] = ()
class Space(BaseModel):      # помещение не-номер — на вырост (банкетные залы, идея основателя 04.11): формат, не просмотрщик
    key: str; kind: Literal["hall", "restaurant", "lobby", "spa", "office", "other"]; names: LocalizedText
    area_m2: float | None = None
    capacity: dict[Literal["theatre", "banquet", "classroom", "u_shape", "reception"], int] = {}
class Floor(BaseModel):
    number: int; kind: Literal["rooms", "lobby", "restaurant", "offices", "technical", "monthly", "closed"]
    sellable: bool = False; label: LocalizedText | None = None; rooms: tuple[Room, ...] = (); spaces: tuple[Space, ...] = ()
class SceneDocument(BaseModel):
    schema_version: Literal[1] = 1
    building: Building; sides: dict[str, SideInfo]; views: dict[str, ViewInfo]
    room_types: dict[str, RoomTypeInfo]; floors: tuple[Floor, ...]
```

Проверки схемы: номера и ключи помещений уникальны, `type_key`, `view_keys` и `side` — из словарей
сцены, `number` этажа — в пределах `floors_total`, продаваемый этаж (`sellable`) — только `kind = rooms`.
Имён, занятости и цен из PMS в сцене нет и быть не может; единственное число о деньгах — `price_note`
типа номера, ориентир, который задал сам отель (слово основателя 04.11: цены — только если отель их
задал в настройках). Помещения просмотрщик v1 не рисует — подписывает на этаже («Зал «Алатау», до 200
гостей банкетом»); расстановка столов — §9. Сцену загружает менеджер в кабинете файлом JSON
(«Загрузить сцену»); новая версия заменяет прежнюю (`scene_version + 1`), действие журнала
`showroom_scene_replaced` (spec 0041 §2.2). Файлы пилотного отеля — вне репозитория (`*.local`), на
staging к показу их загружает основатель кабинетом; в репозитории — вымышленное здание демо-тенанта.

### 2.2. Где видно: три режима — кабинет, по коду доступа, публично

Страница живёт на домене платформы — `https://<домен>/showroom/{slug}` (слово основателя 04.11:
«а почему он опубликован как артефакт а не на necturn?»); артефакт claude.ai — только к показу 05.11.

- **Кабинет** `/staff/{slug}/showroom` — менеджер, службы продаж и бронирования (`*_category_key`
  §2.5): просмотрщик, помощник, формы, «Загрузить сцену» (только менеджер). Пункт меню «3D-витрина»
  занимает место демо-ссылки «3D-модель ↗» (#792): модуль включён — ссылки `DEMO_3D_URL` в меню нет.
  Кнопка «Открыть страницу посетителя ↗» ставит cookie доступа под сессией кабинета — менеджер
  попадает на страницу без кода (слово основателя 04.11).
- **По коду доступа** (до публичного запуска; слово основателя 04.11: «пока страницу сделать приватной
  а потом и публичной… вход по коду для показа»): `enabled`, задан `access_code_hash` (§2.5),
  `public_enabled = false`. `GET /showroom/{slug}` без cookie — экран «Введите код доступа» (§5);
  сцена и остальные маршруты — 403 `ERR-SHOWROOM-005`. `POST …/access` `{code}` → bcrypt-сверка
  (канон кода заселения spec 0027 §1.2: в базе только хэш) → cookie `showroom_access` (`HttpOnly;
  Secure; SameSite=Strict; Path=/showroom/{slug}`, Max-Age 7 дней) со значением HMAC-SHA256 секретом
  приложения над `tenant_id:access_code_version` — таблицы сессий нет; новый код — версия +1, прежние
  cookies гаснут. Неверный код — 403 `005` без уточнения; попытки — `showroom_code_verify_ip` 20 за
  10 минут на адрес и `showroom_code_verify_tenant` 200 за 10 минут (две ступени канона spec 0027
  §3.3) — 429 `003`. Код один на отель, не короче 8 знаков; ставит основатель командой
  `python -m hospitality.tools.showroom_access_code set --tenant <slug>`: код читается из переменной
  окружения вызова, в базу ложится хэш, в вывод, журнал и репозиторий код не попадает (`.env` staging
  пишет только основатель). До письменного «да» отеля страницу по коду видит только сам отель (показ
  05.11) — не агенты и не гости.
- **Публично** — `public_enabled` (§2.5): та же страница без кода. Флаг ставит основатель через
  `mutate_tenant_config` после допсоглашения и письменного «да» отеля (§2.6) — шаг рунбука онбординга
  (PR г). Выключено всё или нет сцены — 404 `ERR-SHOWROOM-001` раньше остального.
- Страница — один HTML без сборки (инлайн CSS/JS, канон spec 0027 §3.4): просмотрщик `viewer.js` и
  библиотека three.js (MIT, версия закреплена) отдаются своими статическими файлами из пакета
  `channels/showroom/assets/`, как обои чата (`wallpaper.py`): кэш навсегда, версия в адресе — хэш
  содержимого. CSP `default-src 'self'`; ничего извне не грузится, аналитики нет, единственная cookie —
  доступ по коду (ADR-019: форма и cookie на публичной поверхности — через ADR-025). Календарь дат —
  родной `<input type="date">`. Надписи — en, ru, kk (en первым: агенты из-за рубежа); ответы
  помощника — на языке фразы посетителя.
- **Два входа на одной странице** (слово основателя 04.11): переключатель «Для групп» (агенты:
  компания, размер группы, номера с модели) и «Для гостей» (частный гость: даты календарём, гостей,
  желаемый номер или вид). Просмотрщик и помощник общие; различаются форма, карточка и служба.
- «Свободно / занято» на странице нет нигде (NG-2, правило 9): наличие уточняет служба, и страница
  говорит это прямо (§5); в настройках наличие не задаётся — его источник только PMS
  ([spec 0059](0059-stay-extension-availability.md), ADR-025 «Пересмотреть»). Цена у типа номера —
  только когда отель задал `price_note`, с подписью «ориентир, подтверждает отдел бронирования».

### 2.3. Навигация: сначала правила, потом модель через шлюз инструментом

`POST /showroom/{slug}/navigate` (и `/staff/{slug}/showroom/navigate` под сессией кабинета),
тело `{text ≤ 300 знаков, language?, audience: group|booking}` → `{commands, reply, source}`.
Композиция — `ai/showroom/` (как `ai/mentor`); модуль `showroom` модели не знает (FOUNDATION §5.1).

1. **Правила без модели** (`ai/showroom/rules.py`): «этаж 15 / floor 15 / 15-қабат», «номер 1507 /
   room 1507», «горы / mountains / тау», «город / city / қала», «сверху / top / жоғарыдан», «с улицы /
   street / көшеден», «выше / ниже», «сначала / reset» — ru, en, kk. Совпало — команды без вызова
   модели, `source = rules`. Это и запасной путь (§7.8): модель выключена или бюджет исчерпан —
   правила и кнопки, текст «Помощник отдыхает…» (§5), не ошибка.
2. **Модель** — `gateway.complete(purpose="showroom", forced_tool="navigate_showroom",
   max_tokens=300)`: назначение `showroom` в `purposes.py` (ADR-024 §1: своя модель
   `LLM_MODEL_SHOWROOM` — пусто = выключено на деплойменте, на staging — модель гостя, основатель
   хочет Sonnet; свой дневной бюджет тенанта `LLM_SHOWROOM_DAILY_BUDGET_USD`, умолчание $1).
   Системный промпт `showroom_navigate_v1` — инструкция, аудитория (`audience`) и **сводка сцены**
   (этажи с назначением, стороны и виды, типы номеров без цен; не список 350 номеров — поиск по
   условиям делает код). Фраза посетителя — недоверенный ввод (§7.6): модель отвечает только
   аргументами инструмента, свободного текста нет.
3. **Инструмент `navigate_showroom`** (`ai/tools/navigate_showroom.py`, канон `create_service_request`;
   класс `auto` — побочных эффектов нет, P-9):

   ```python
   Command = FocusFloor(floor) | FocusRoom(room) | SetView(preset: mountains|city|top|street)
           | FindRooms(floor_from?, floor_to?, side?, view_key?, type_key?, count? 1..60)
           | DraftRequest(kind: group|booking, guests?, check_in?, check_out?, room_numbers?, view_key?, type_key?, wishes?)
   class Navigation(BaseModel):
       commands: list[Command] = Field(max_length=4)
       reply: str = Field(max_length=200)      # на языке посетителя; без цен, наличия и обещаний
   ```

   `FindRooms` исполняет сервис ядра `showroom.api.find_rooms(RoomQuery)` — тот же, что у панели
   фильтров на странице (P-5: ИИ ничего не умеет эксклюзивно). **`DraftRequest` — «бот сам оформляет
   запрос» (слово основателя 04.11) с подтверждением посетителя, структурно, не промптом** (канон
   гейта spec 0015): команда лишь открывает карточку подтверждения (§5), заполненную по словам
   посетителя — даты, гостей, номера или вид, пожелания; контакты и согласие посетитель вписывает сам,
   запрос уходит только его кнопкой «Отправить запрос» тем же `POST …/requests` (§2.4). Инструмента,
   создающего запрос, у модели нет — реестр инструментов назначения `showroom` без побочных эффектов
   (тест §7). Этаж или номер вне сцены — команда отбрасывается с логом `showroom_command_dropped`,
   остальные идут. `reply` с валютой или числом с «тг/₸/$/€/USD» заменяется статическим «Подобрал
   варианты — смотрите на модели» (неправда посетителю дороже пустой реплики); evals стерегут это
   раньше (§7).
4. **Лимиты** (канон spec 0023, ступень по IP — spec 0027 §3.3, адрес — `shared/clientip.py`):
   `showroom_navigate_ip` 30 за 10 минут на адрес, `showroom_navigate_tenant` 600 в сутки отеля (правила
   и модель вместе); выше — 429 `ERR-SHOWROOM-003`. Деньги держит бюджет назначения: при $2/$10 за 1M
   токенов (прайс-лист шлюза) вызов без учёта схемы инструмента ≈ $0,005; замер 10.09 показал, что
   описания инструментов удваивают цену гостевого бота, а у `navigate_showroom` объединение из шести
   команд — реальную цену меряет PR (б) `count_tokens` по тому, что уходит в запрос (ревью PR #801,
   П-1); бюджету это не угрожает. Ошибки шлюза ERR-AI-001/002/003/006 — путь 1, не 5xx.
5. Фразы посетителей не хранятся (ПД нет — хранить нечего), но уходят в Anthropic (США): под полем
   помощника — подсказка не писать имена и контакты (§5; ревью PR #801, П-2). В логах — `tenant_id`,
   `source`, виды команд. Метрика `showroom_navigations_total{source=rules|model|fallback}`.

### 2.4. Запрос — заявка в службе продаж или бронирования, контакты в модуле

Два вида запроса, одна таблица (§3) и один `POST /showroom/{slug}/requests` →
`showroom.api.create_request(ShowroomRequestCreate)` — идемпотентно по `client_key`:

- **группа** (`kind = group`, вкладка «Для групп»): компания, контактное лицо, телефон, почта, размер
  группы (1–500), заезд и выезд (до 400 дней вперёд), выбранные на модели номера (только из сцены,
  ≤ 60), пожелания (≤ 500), язык, строка согласия (§2.6) → заявка в службе `sales_category_key`;
- **бронирование** (`kind = booking`, вкладка «Для гостей»; слово основателя 04.11 «как система
  бронирования через сайт но с 3д моделью»): заезд и выезд календарём, гостей (1–`booking_max_guests`),
  имя, телефон, почта, желаемый номер или вид (`room_numbers` ≤ 3, `view_key`, `type_key` — из сцены,
  необязательно: форма обязана позволить назвать желаемый номер или вид — задел под допродажу выбора,
  DISCUSSION_LOG «Не решено»), пожелания, язык, согласие → заявка в службе `booking_category_key`
  (не задана — в службе продаж).

Общее: строка `showroom_requests` (§3) и `ServiceRequest` с `origin = showroom_form` (новое значение
`ServiceRequestOrigin`, влезает в VARCHAR(16)): посетитель — не проживающий гость, поэтому запрос **не
входит ни в числитель, ни в знаменатель** доли «без участия ресепшена» — одна строка в spec 0035 §4
тем же PR; `details` заявки — вид, даты, гостей, номера или вид, компания; **контактов в заявке нет**:
карточка берёт их из модуля (`requests_for_requests`, как `bookings_for_requests` spec 0064) — у
контактов один срок хранения (§3), а не два; дальше — обычный цикл заявки: номер `#N`, очередь службы,
сигнал, пуш (spec 0050), лестница невзятой заявки (spec 0045 §4). Служба отвечает посетителю сама —
телефоном или почтой, вне платформы; «Готово» на карточке — «ответили». **Это запрос, а не бронь**
(P-9, NG-2, NG-3, NG-4): наличие, цену, бронь и депозит подтверждает человек в Opera; своей системы
бронирования и оплаты нет; исходящей почты посетителю нет. Лимиты: `showroom_request_ip` 5 в час на
адрес, `showroom_request_tenant` 50 в сутки — 429 `003`; скрытое поле-ловушка (`website`) заполнено —
200 без записи и без заявки (боты).

### 2.5. Настройки — конфиг тенанта (P-11, NG-7)

```python
class ShowroomConfig(BaseModel):
    enabled: bool = False                   # витрина в кабинете (сцена нужна отдельно)
    access_code_hash: str | None = None     # bcrypt; задан — страница по коду (§2.2); код ставит команда, не руки
    access_code_version: int = 0            # +1 при смене кода — прежние cookies гаснут
    public_enabled: bool = False            # без кода — только после допсоглашения и письменного «да» отеля (§2.6)
    sales_category_key: str                 # служба продаж — обязана быть категорией отеля (как у ресторана, spec 0064)
    booking_category_key: str | None = None # служба бронирования; None — запросы гостей в службу продаж
    booking_max_guests: int = 10            # 1..30
    assistant_enabled: bool = True          # False — только правила и кнопки, модели нет
    contact_note: LocalizedText | None = None   # «Отдел продаж отвечает в рабочие часы…» под формами
```

Поле аддитивное, переносится в `build_config` (иначе онбординг его сотрёт); создаёт его целиком PR (а),
чтобы (б) и (в) `config.py` не трогали. Деплоймент: `LLM_MODEL_SHOWROOM`,

### 2.6. ПД посетителей, договор с отелем и юрдокументы (тем же PR, что миграция — правило 9 плана)

Посетитель — не гость, политика гостевого чата к нему не относится (она про чат и проживание).
Поэтому отдельная короткая страница `GET /legal/showroom-privacy` из `docs/legal/showroom-privacy.md`
(kk/ru/en: кто обрабатывает, какие данные — контакты, даты и пожелания из формы, зачем — ответ на
запрос, срок — §3, кому передаются — тот же перечень субоператоров, что у гостя, кроме мессенджеров;
права, контакт privacy@necturn.com) и строка согласия на обеих формах (§5) с версией
`SHOWROOM_CONSENT_VERSION` (`channels/showroom/consent.py`, дрейф с файлом ловит `tests/test_legal.py`);
версия и время — в строке запроса. Текст согласия и политика — юридический текст: в спеке это вариант
окна, слово основателя — до кода PR (в) (ответ диспетчера 03.11 в founder-review). Фразы помощника
уходят в Anthropic (США) — подсказка под полем (§5) и строка политики; они не хранятся. Строки
[PII_REGISTRY](../PII_REGISTRY.md), раздел «Посетители витрины» в `docs/runbooks/subject-requests.md`.

**Пилотный договор** (вне репозитория, `исходник/contract.md`; ревью PR #801, Н-1): контакты
посетителей — новая категория субъектов, которой нет в составе данных пп. 4.2.1 и 4.2.5, п. 4.2.2 прямо
говорит, что телефон и e-mail не запрашиваются, а срока 365 дней нет в п. 4.6; по п. 7.3 эти пункты
письмом не меняются. Поэтому абзац [pilot-copy.md](../runbooks/pilot-copy.md) — по образцу
**«Выгрузка Opera»**, не «Квоты бесплатного»: в конфиге копии `showroom` нет; любой режим с формой (по
коду или публичный) у пилотного отеля включается только по слову основателя **после допсоглашения
(п. 7.3) и письма отелю по п. 1.2** (пишет основатель). Письменное «да» отеля на публикацию планировки
входит в то же допсоглашение; юристу — вместе с политикой витрины. Кабинетный режим (`enabled` без
кода и без `public_enabled`) формы не имеет, ПД посетителей не собирает — его допсоглашение не ждёт.

## 7. Тесты

1. Сцена: лишнее поле, дубль номера или ключа помещения, номер на этаже вне `floors_total`, `type_key`
   не из словаря, `sellable` у офисного этажа, > 512 КБ — `002` с путём; помещение с вместимостью
   проходит; версия растёт; изоляция тенантов.
2. `find_rooms`: этажи, сторона, вид, тип, `count`; порядок; пустой результат — пустой список.
3. Код доступа: верный — cookie и 200 на сцене; неверный — 403 `005` без причины; без cookie сцена,
   навигация и запрос — 403; `public_enabled` — без cookie 200; смена кода (версия +1) — прежняя cookie
   403; cookie менеджера под сессией кабинета; команда не печатает код; лимиты по адресу и тенанту —
   `003`; кабинетный режим без кода и без флага — страница 404.
4. Правила: таблица фраз ru/en/kk → команды без модели (`source = rules`); незнакомая фраза — модель;
   модель выключена (ERR-AI-006) и бюджет исчерпан (ERR-AI-002) — `fallback` с текстом, не 5xx; команда
   с номером вне сцены отброшена; `reply` с валютой заменён; `forced_tool` стоит в запросе шлюза;
   `DraftRequest` не создаёт ни строки, ни заявки; в реестре инструментов назначения `showroom` нет
   инструмента с побочным эффектом (структурный инвариант P-9).
5. Лимиты: IP и тенант — `003`; fail-open по канону 0023.
6. Запрос: повтор `client_key` — та же заявка; `004` на датах (заезд раньше сегодня, выезд не позже
   заезда, дальше 400 дней), гостях (группа 1–500, бронирование 1–`booking_max_guests`), чужом номере
   или виде; ловушка — 200 без строк; группа — в `sales_category_key`, бронирование — в
   `booking_category_key`, без него — в продажи; `origin = showroom_form`; в `details` нет контактов;
   карточка берёт контакты из модуля; доля spec 0035 §4 запрос не считает; обезличивание через 365 дней;
   согласие записано с версией; ключ службы не из категорий отеля — ошибка конфига; онбординг поле не
   стирает.
7. Страницы: выключено или без сцены — 404 и нет пункта меню; кабинет — 403 чужой службе; CSP и
   отсутствие внешних загрузок (как `tests/test_site.py`); cookies нет, кроме доступа по коду;
   `price_note` виден только когда задан, в `reply` помощника цен нет и при заданном `price_note`.
8. **Evals** `python -m hospitality.ai.evals.showroom_navigate [--repeat N]` — 36 фраз en/ru/kk/zh
   (агенты и гости, не демография проживающих) на вымышленной сцене: ожидаемые виды команд, даты и
   гостей в `DraftRequest`, язык `reply`, ни одной валюты и слов «свободно / available / бос» в `reply`.
