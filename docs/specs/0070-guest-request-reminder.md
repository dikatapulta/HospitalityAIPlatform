# Spec 0070: гость напоминает о заявке — код считает напоминания и зовёт ресепшен и менеджера

- **Статус:** принята (PR #838); код — PR 1 (домен и кабинет) — PR #842. Код — двумя PR после показа 05.11, в `main` — не раньше 06.11:
  правка промпта гостя меняет поведение бота в отрепетированных сценариях (слово основателя 04.11,
  строка #834 в [QUEUE.md](../QUEUE.md)).
- **Issue:** #834. Решение основателя 04.11 ~13:00 (чат окна-консультанта), дословно в теле issue:
  «ну как сделай, заведи очередь» на направление консультанта. Остальное решено здесь.
- **Дата:** 2026-11-04
- **Меняет:** [spec 0025](0025-guest-request-status-and-cancel.md) §2 — на вопрос о заявке модель
  отвечает по-прежнему из снапшота, но зовёт инструмент; [spec 0045](0045-services-and-levels.md) §4 —
  четвёртое «сразу на третью ступень»; [spec 0028](0028-unclaimed-request-reminders.md) §8 — список
  «долго в работе» берёт и взятую заявку, о которой напомнил гость.

## 1. Проблема

Гость пишет второй раз: «я уже второй раз прошу полотенца!» Промпт `concierge_v7` («The guest's
active requests») велит ответить статусом из списка и «Do not call any tool for that and do not
escalate to staff». Заявку не теряет лестница по времени (spec 0045 §4, spec 0028), но то, что гость
ждёт и недоволен, не узнаёт никто: ни служба, ни ресепшен, ни менеджер.

## 2. Решение в одном абзаце

На каждый вопрос гостя о своей открытой заявке модель зовёт инструмент `remind_about_request`
с id заявки из списка. Модуль `requests` считает напоминания на самой заявке. Кого звать, решает
лестница кабинета — кодом, по настройке отеля (P-5): со второго напоминания, или с первого, если
заявка уже просрочена, она звучит ресепшену и менеджеру. Новой карточки нет: счётчик стоит на той
же заявке. Гость получает тот же честный статус без обещания срока (spec 0039 §6, как у spec 0040).

## 3. Домен — `modules/requests`

- Колонки `service_requests`: `guest_reminder_count INTEGER NOT NULL DEFAULT 0` (CHECK `>= 0`)
  и `guest_reminded_at TIMESTAMPTZ NULL` — время последнего напоминания, UTC. Миграция — номер через
  `ops/pool.sh reserve migration` в PR 1; `server_default` остаётся (откат). Таблица уже под RLS
  (P-4), новых ПД нет: число и время — не текст гостя, PII_REGISTRY и ретеншн spec 0032 не меняются.
- `ServiceRequestRead` — оба поля, с умолчаниями `0` / `None`.
- `record_guest_reminder(request_id) -> ServiceRequestRead | None` — новый файл
  `modules/requests/reminders.py`, экспорт через `api.py`. Один атомарный
  `UPDATE … SET guest_reminder_count = guest_reminder_count + 1, guest_reminded_at = now()
  WHERE id = :id AND status IN ('new', 'in_progress') RETURNING …`; `None` — заявки нет или её
  уже закрыли. Событий нет: сигнал кабинета опрашивает заявки сам (spec 0039 §3).
- Сервис обычный (P-5): кнопка кабинета «Гость напомнил» по звонку в номер — запись в
  `docs/later/`, не этот скоуп.

## 4. Гость — инструмент, оркестратор, промпт `concierge_v8`

**Инструмент** `ai/tools/remind_about_request.py`, класс `auto` (P-9: не деньги, не документы,
не бронь; эффект — звук в кабинете). Схема — как у `cancel_service_request`: собирает реестр,
только при непустом снапшоте; `request_id` — enum id открытых заявок диалога. Флаг заявок его не
выключает — как отмену: заявки, созданные до выключения флага, гость вправе торопить.
Описания — по-английски (язык аргумента, #342):

- инструмент — «Record that the guest is asking about, or reminding you of, one of their open
  requests from the Active service requests list. Call it on every message where the guest asks how
  such a request is going or says it is still not done. Pick request_id ONLY from the allowed
  values. It does not create, cancel or speed up anything by itself.»;
- `reply_to_guest` — «Your whole reply to the guest, in the language of the guest's last message:
  that you have noted the reminder, the request's #N and its status in plain words. Promise no time,
  and never say that a manager or anyone else was alerted.»

**Оркестратор.** Напоминание — сопутствующий вызов, как сигнал «факта нет» (spec 0036 §6): все
его вызовы вынимаются из вызовов хода до выбора действия, независимо от позиции, и у действия не
выигрывают. Иначе «где полотенца? и принесите воды» теряло бы заявку на воду, если модель поставила
напоминание первым. Код — в модуле инструмента (`take_reminders`), в `orchestrator.py` — вызов
и склейка реплики:

- каждый различный `request_id` из снапшота хода — один `record_guest_reminder`; id вне снапшота
  и `None` от домена (закрыли между ходами) — пропуск с warning-логом, без эскалации: гость
  спрашивал о статусе, а не просил действия;
- реплика напоминания (аргумент → свободный текст модели → трёхъязычный резерв §7) — первым
  абзацем перед репликой хода, как у сигнала; других вызовов нет — ход `REPLY` с ней одной;
- исход-эскалация (`escalate_to_staff`, сбой): гостю — только её текст, напоминание всё равно
  записано. «Позовите менеджера, я второй раз прошу!» — это `escalate_to_staff`, правило v7 остаётся.

**Промпт `concierge_v8`** — копия v7, правится только первый пункт «The guest's active requests»:

> - When the guest asks how one of these requests is going or reminds you about it ("where are my
>   towels?", "I asked an hour ago!"), you MUST call `remind_about_request` on that same message with
>   that request's id. The hotel's system records the reminder and itself decides whom to alert —
>   never tell the guest that a manager or anyone else was alerted. Write your whole reply into its
>   `reply_to_guest`: say that you have noted the reminder, name the request (its #N number if
>   present) and its status in plain words — `new` means staff has been notified and will pick it
>   up, `in_progress` means staff is on it. Never promise a time. A thank-you or a passing mention
>   of the request is not a reminder.

Промпт растёт на ~80 токенов, схема инструмента — ~200 на ходах с открытыми заявками; цену smoke
(spec 0019) это заметно не меняет.

## 5. Кабинет — лестница, сигнал, карточка

**Правило подъёма** — чистая функция `guest_raised(...)` в `staff_portal/ladder.py`, одна на
сигнал, очередь и главную (P-12). Заявка «поднята гостем», если `guest_reminded_at` задан,
порог отеля не выключен и:

- `guest_reminder_count >=` порога (§6), **или**
- напоминание пришло уже просроченной: у `new` — `guest_reminded_at − created_at >= d` (та же
  граница, что метка «просрочена», `step_by_time`); у `in_progress` — не меньше срока «долго
  в работе» от взятия (spec 0028 §8; срок по умолчанию выключен — тогда только по числу);
- у `in_progress` напоминание к тому же не раньше взятия (`claimed_at`): поднятая и тут же взятая
  заявка не звучит заново в момент взятия; следующее напоминание после взятия — звучит.

**Сигнал** (spec 0039 §3, spec 0050 §6):

- невзятая поднятая — четвёртое «сразу на третью» в `ladder_step`: звучит ресепшену и менеджеру
  вместе со службой;
- взятая поднятая — в список `stalled`, даже при выключенном сроке «долго в работе»; адресаты те
  же: служба, ресепшен, менеджер. Запрос — `requests_api.list_guest_reminded_requests(category_ids=,
  limit=)`: открытые с `guest_reminded_at IS NOT NULL`, свежие напоминания сверху;
- у обоих видов поля `guest_reminders` и `is_guest_raised`; ключ «уже прозвучало» (`signal.js`
  и рассылка пуша) несёт число напоминаний: каждое новое напоминание после подъёма звучит один раз,
  новой карточки нет. Текста гостя в сигнале по-прежнему нет — только номер, комната и служба.

**Карточка очереди** — бейдж с первого напоминания (видит каждый, кто видит заявку), поднятая —
красный бейдж и красная рамка, как «просрочена». **Главная** — поднятая стоит во вкладке «Требует
внимания» той же группой, что просроченные и «долго в работе».

## 6. Настройка отеля

`TenantConfig.guest_reminder_raise_after: int | None = 2` — с какого напоминания заявка поднимается,
1–10; `None` — подъёма нет совсем (бейдж и счёт остаются). Схема аддитивна, `schema_version` = 1.
`onboard_tenant.build_config` переносит поле из прежнего конфига — иначе повтор онбординга вернёт
умолчание. Меняет — `python -m hospitality.tools.request_reminders --guest-raise-after 3`
(или `off`) — у одного отеля, `--tenant-slug` как у прочих флагов команды; вывод называет оба
правила подъёма.

## 7. Тексты (показ основателю — файлом диспетчеру; запись в `docs/founder-review/`)

Кабинет, на русском:

| Где | Текст |
|---|---|
| Бейдж, 1 напоминание | «Гость напомнил» |
| Бейдж, N | «Гость напомнил 2 раза» · «… 5 раз» (склонение по числу) |
| Уведомление, заголовок | «Гость напоминает второй раз: #12» · «Гость напоминает уже 3-й раз: #12» · подъём с первого (просрочена): «Гость напоминает о заявке #12» |
| Уведомление, текст | невзятая — «Комната 512 · Хаускипинг · ждёт 40 мин»; взятая — «Комната 512 · Хаускипинг · в работе 40 мин» |
| Главная, строка | «Гость напоминает» |

Гостю реплику пишет модель (образец, ru): «Отметил ваше напоминание в заявке #12 — полотенца
в номер 512. Сотрудники о ней знают и возьмут её в работу.»; взятая — «…Сотрудники уже ею
занимаются.» (решение диспетчера за основателя 04.11, запись в `docs/founder-review/`). Резерв без аргумента и текста, kk/ru/en с новой строки (#224): «Еске салуыңызды
өтінімге белгіледім — қызметкерлер оны көреді.» / «Отметил ваше напоминание в заявке —
сотрудники его видят.» / «I've added your reminder to the request — the staff can see it.»

## 10. Что сознательно не делаем

- **Жалоба на закрытую заявку** («полотенца так и не принесли», а заявка «Готово») — её нет
  в снапшоте, правило «не вижу такой заявки — предложить сотрудника» v7 остаётся. Запись в `later/`.
- **Сообщение в Telegram-чат службы о подъёме** — у пилота Telegram персонала нет (spec 0028 §8).
- **Другая реплика гостю после подъёма** («сообщил менеджеру»): модель пишет реплику до решения
  кода, а две версии реплики на выбор удвоили бы её работу ради слов, которых issue не просит.
- **Защита от «где? где? где?» за минуту** — три сообщения подряд и есть недовольный гость;
  ложные подъёмы на пилоте — повод поднять порог флагом §6, а не код.
