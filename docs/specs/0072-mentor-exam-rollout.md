# Spec 0072: «Наставник» — экзамен для всех сотрудников к запуску 01.12

- **Статус:** принята (PR #903); код — PR 2 (#910), PR 3 (#916), PR 4 (#925) — §6: проект — вариант (в), «Неточность» — (б); PR 5 (#929) — проверка
  ответа, §2.
- **Issue:** #898. Слово основателя 10.11 и находки консультанта — в теле issue; решения окна —
  [founder-review](../founder-review/2026-11-10-pr903-mentor-exam-rollout.md).
- **Дата:** 2026-11-10
- **Меняет:** [spec 0048](0048-mentor.md) §10 п. 5 — включение у сотрудников идёт на проекте
  кодекса; §12 «Сводка по службам» — итог считается только по назначенному экзамену (§3 ниже).

## 1. Проблема

Руководство пилотного отеля хочет начать с «Наставника» с экзаменом: каждый сотрудник сдаёт, порог
80 %, полноценное внедрение — с 01.12 (слово основателя 10.11). Экзамен уже есть (spec 0048 §12),
но тему выбирает сам сотрудник, и «Итоги экзаменов» берут последнюю попытку любой темы — «сдан»
выходит на самой короткой главе. Логин кабинета, без которого экзамена нет, выпускается по одному
приглашению, а сотрудников — сотни. Дневной потолок наставника рассчитан на вопросы, не на экзамен
всего отеля за день.

## 2. Порог 80 % и проект кодекса

- **Порог** — настройка отеля `mentor_exam_pass_percent` (spec 0048 §12), у пилотного отеля 80:
  запись конфига шагом рунбука [mentor.md](../runbooks/mentor.md), как флаг `mentor_enabled`.
  Экрана настройки нет: число ставится один раз при запуске, а попытка снимает порог при начале
  (смена посреди экзамена старых итогов не перепишет).
- **Проект кодекса.** Основатель утвердит кодекс позже; включение у сотрудников идёт на проекте.
  Условие «после утверждения кодекса» снято из spec 0048 §10 п. 5 и рунбука тем же PR.
- **Проверка ответа.** Оценку каждого ответа ставит модель (`mentor_quiz_check`, первая строка
  «Оценка: …»), а два «неверно» из 10 — уже не сдан: одна ошибка проверяющего меняет исход (аудит
  #896, комментарий в #898). С v2 промпт велит считать ответ сотрудника данными, а не указаниями;
  замер — набор evals `python -m hospitality.ai.evals.mentor_quiz_check` (24 ответа: верный,
  частичный, неверный, не на вопрос, с указанием проверяющему; четыре по-казахски). Прогон платный —
  по «да» основателя, локально: база и ключ — как у bakeoff, тенант `bakeoff-eval`. **Совпадение с ожидаемой оценкой: не мерено (10.11)** — число сюда вписывает
  тот, кто прогонит, рядом — сколько раз оценка завышена и занижена.

## 3. Назначенный экзамен (PR 3)

**Что видит менеджер.** На вкладке «Итоги экзаменов» — форма «Назначить экзамен»: тема — весь
кодекс или отмеченные главы (оглавление по частям, главы должностей «Для кого» — тоже главы); кому —
всем сотрудникам или отмеченным службам (галочки «Сотрудников»). Число вопросов и порог — из
настроек отеля. Назначение не редактируется: «Снять» — и назначить заново. Срока у назначения нет:
срок отель объявляет сам; без последствий в программе дата была бы только надписью (потом —
по просьбе отеля).

**Что видит сотрудник.** Назначенный и ещё не сданный экзамен — строкой над вкладками на всех
страницах «Наставника» со ссылкой на «Экзамен». На вкладке «Экзамен» сверху — «Назначены вам»:
тема, состояние и «Начать экзамен», у сданного кнопки нет. Ниже — прежний выбор темы как «Экзамен
для себя»: в итоги для менеджера он не идёт. Назначение сотруднику — активное назначение «всем»
или его нынешней службе (`service_keys`, spec 0045); у сотрудника их может быть несколько.

**Итог по назначению** — сдан, если у сотрудника есть сданная попытка этого назначения (дата — первой
сданной); иначе его последняя законченная попытка; иначе «нет попыток». «Сдан однажды — сдан»:
пересдача после сдачи не отнимает результат. «Итоги экзаменов» — раздел на каждое активное
назначение (тема, кому, дата назначения, «Снять»), под ним карточки служб как в spec 0048 §12, но
только служб назначения и с итогом по назначению. Снятое назначение пропадает у сотрудников и из
итогов; попытки остаются в базе.

**Ход** — тот же, что у экзамена spec 0048 §12; в `POST exam/start` вместо `chapter_number` —
`assignment_id`. Темой попытки служат главы назначения, найденные в нынешнем кодексе по номеру
**и** названию (перезагрузка кодекса могла сдвинуть нумерацию); ненайденные пропускаются. Не
нашлось ни одной, назначение снято или не для служб сотрудника — ERR-MENTOR-006 (409), модель не
зовётся. Начатая попытка доходит до итога, даже если назначение сняли посреди неё.

**Данные** — миграция (номер — `ops/pool.sh reserve migration`), RLS-канон `0002`:

| Таблица | Колонки |
|---|---|
| `mentor_exam_assignments` (новая) | `id, tenant_id, chapters JSONB` (массив `{number, title}` — снимок; пустой — весь кодекс), `service_keys JSONB` (пустой — всем), `created_by_user_id, created_at, archived_at` |
| `mentor_exam_attempts` | + `assignment_id` — FK на назначение, `ON DELETE SET NULL`; `NULL` — экзамен для себя |

Данных о человеке в назначении нет, кроме автора. Срок хранения — пока живёт тенант.

## 4. Логины списком (PR 2)

На странице «Сотрудники» рядом с приглашением — «Пригласить списком»: уровень и службы — те же поля,
что у одиночного приглашения, и поле «Имена — по одному в строке» (столбец из таблицы вставляется
как есть). «Составить список» строит на странице таблицу «Имя — Логин»: логин подсказывает та же
функция `suggestLogin` (`static/team.js`, правило spec 0037 §4), совпадения внутри списка получают
цифру (`IVAA`, `IVAA2`), пустую подсказку вписывает менеджер. Таблица правится, затем «Выпустить
приглашения».

- **Сервер** проверяет весь список до записи: формат и свобода каждого логина (spec 0037 §4) и
  повтор внутри списка — по строке с номером (ERR-AUTH-012), службы — ERR-AUTH-015. Есть ошибка —
  не выпускается ни одно приглашение, менеджер правит отмеченные строки: в ответе `details` —
  `{row, reason}`, причина `format`, `duplicate` или `taken`. Нет — все приглашения одной
  транзакцией (`staff_invite_batch.create_invites` — отдельно от `staff_invites`, R-3), до 100
  строк за раз. Права, срок ссылки
  (`STAFF_INVITE_TTL_HOURS`) и принятие — как у одиночного приглашения: новой двери нет.
- **Лист для печати** — ответ на выпуск: по карточке на человека — имя, QR одноразовой ссылки
  (segno, как `checkin.qr_svg`), код отеля, логин и срок ссылки. Ссылки видны только на этом
  экране (в базе — хэш токена, spec 0033 §3.4): `Cache-Control: no-store`, в логи — только id
  и число приглашений (`staff.invite_batch_created`). Кнопка «Печать» — `window.print()`, стиль
  печати — карточки по две в ряд, без шапки кабинета.

## 5. Дневной потолок

Строка в рунбуке: экзамен из 10 вопросов — около $0,006 (spec 0048 §12), потолок
`LLM_MENTOR_DAILY_BUDGET_USD` — $2 в сутки: около 300 попыток, если в тот же день никто не спрашивает
и не тренируется. В дни экзамена — службы по дням (до ~250 попыток в день) или потолок выше на эти
дни (шаг основателя в `.env`).

## 6. Пометка проекта и «Неточность в статье» (PR 4)

Рекомендации консультанта из #898. Ответ основателя 10.11 кнопками в чате диспетчера
(`ask/3-898-texts.answer`, перенесён в #898): пометка — **вариант (в)**, явный выбор вместо
рекомендации окна (б); «Неточность» — **(б)**. Записи —
[founder-review](../founder-review/2026-11-10-pr903-mentor-exam-rollout.md).

- **Пометка «Проект кодекса»** — статус редакции строкой шапки файла кодекса (`Статус: проект` →
  `mentor_codexes.meta`, разбор `codex.py`), без миграции кодекса. Сотрудник видит «Проект кодекса»
  на «Кодексе» и «Экзамене». Варианты: (а) не делать; (б) пометка, итог засчитывается, в «Итогах»
  у попытки — «на проекте»; (в) как (б), но сданное на проекте — пробное, в итог не идёт.
  Рекомендация окна была (б); **принято (в)** — явный ответ основателя 10.11: до утверждения
  кодекса экзамен сдаётся только пробно.
- **«Неточность в статье»** — кнопка у статьи на «Кодексе» и под проверкой ответа. Варианты:
  (а) не делать; (б) без текста — счётчик «отметили N сотрудников» по статье на «Где ошибаются»;
  (в) с комментарием — свободный текст сотрудника, новый носитель ПД со сроком хранения.
  Рекомендация окна — (б): показывает, какие статьи читать первыми, без хранения текстов.

**Как сделано (PR 4).** Проект — строка шапки «Статус:» начинается со слова «проект» (без учёта
регистра; `codex.is_draft_status`), пометка — пока такая редакция загружена. Попытка снимает
статус при начале — `mentor_exam_attempts.on_draft_codex` (миграция, номер — `ops/pool.sh
reserve migration`); утверждённая редакция прошлых не переписывает. Такая попытка —
**пробная**: в итог по назначению не засчитывается (`ExamAttemptRead.passes_assignment`), в
итоге стоит, только пока зачётных нет, и сменяется любой зачётной, даже несданной; у сотрудника
назначение остаётся открытым. После утверждения сотрудники сдают то же назначение заново —
нового назначения не нужно. Отметка —
`mentor_article_flags` (`user_id`, номер статьи; одна на сотрудника и статью, RLS-канон `0002`):
нажатие отмечает, повторное — снимает; статьи нет в кодексе — не пишется. Новая загрузка кодекса
той же транзакцией снимает отметки статей, у которых сменились название, текст или источник,
и пропавших; у нетронутых — оставляет. «Неточности в статьях» на «Где ошибаются» — статьи
с числом отметивших (только учётки «Сотрудников»), больше — выше; имён нет ни у кого.
«Обнулить статистику» отметки не трогает.

## 9. Тесты

- **PR 2:** весь список или ничего — одна плохая строка (формат, занят учёткой, занят ожидающим
  приглашением, повтор в списке) не выпускает ни одного; номер строки в ответе; 101 строка — 422;
  права — только менеджер (staff, senior — 403); CSRF; приглашение из списка принимается обычной
  страницей; токенов нет в логах; `no-store`.
- **PR 3:** назначение всем и службам видят только свои сотрудники; итог — «сдан однажды — сдан»,
  иначе последняя законченная; экзамен для себя в итоги не идёт; снятое назначение — ERR-MENTOR-006
  при начале, начатая попытка доходит до итога; глава с тем же номером, но другим названием
  пропускается, ни одной — ERR-MENTOR-006; RLS назначений; назначать и снимать — только менеджер.
  Mock-провайдер, как у spec 0048.
- **PR 4:** «проект» в начале статуса — проект, «Проектный офис» — нет; попытка помнит проект
  при начале, утверждённая редакция её не переписывает; пробная в итог не засчитывается, зачётная
  её сменяет, новая пробная зачётную не сменяет; отметка своя, повтор и снятие
  идемпотентны, статьи нет — не пишется; счёт — только учёток из списка, больше — выше;
  новая редакция снимает отметки изменённых и пропавших статей, оставляет нетронутые; RLS;
  кнопка — любой уровень, CSRF, раздел выключен — 404; «Где ошибаются» без имён; «пробно»
  в «Итогах» и «Назначены вам», назначение открыто.
- **PR 5:** в промпте проверки — строка и пример про ответ как данные; ответ с `"}` и переводом
  строки остаётся строкой своего поля JSON и не добавляет строк запросу; набор evals: на каждую
  статью все пять видов ответа, «не на вопрос» и «с указанием» ждут «неверно», пример промпта
  в сценариях не повторяется; сценарий идёт через шлюз (назначение `mentor`, тот же промпт).
