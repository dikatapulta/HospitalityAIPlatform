# Spec 0076: гость оценивает выполненную заявку — модуль `feedback/`

- **Статус:** черновик (PR #914); код — три PR по §9.
- **Issue:** #899. Решение основателя 10.11.2026 (чат окна-консультанта) «тогда давай делать по твоим
  рекомендациям» — в теле issue. Основа — рекомендация Ф-5 операционного аудита 05.08
  ([audits/2026-08-05-operational-audit.md](../audits/2026-08-05-operational-audit.md)): 👍/👎 и
  необязательный комментарий после «выполнено». Решения окна —
  [founder-review](../founder-review/2026-11-10-pr914-guest-feedback.md).
- **Дата:** 2026-11-10
- **Опирается на:** [spec 0039](0039-cabinet-only-staff-alerts.md) §2 (карточка в службе эскалаций),
  [spec 0032](0032-guest-text-retention.md) (срок текстов гостя), [spec 0027](0027-guest-web-chat.md)
  (веб-чат), [spec 0035](0035-pilot-measurability.md) §4 (источник заявки).

## 1. Проблема

Гость не может сказать отелю, хорошо ли выполнена заявка. Плохой опыт отель узнаёт отзывом в
интернете после выезда, когда исправить уже нечего. У руководства нет числа качества по службам,
а в отчёте пилота нет числа «гости довольны». Модуль `feedback/` стоит в плане Phase 1, но его нет.

## 2. Решение в одном абзаце

Под сообщением веб-чата «заявка выполнена» гость видит «Как всё прошло?» и две кнопки — палец
вверх и палец вниз. Одно касание сохраняет оценку. Палец вниз сразу заводит карточку в службе
эскалаций (у пилота — ресепшен), пока гость в отеле, и открывает необязательное поле «что не так»:
написанное дописывается в карточку. Сводка дня кабинета показывает оценки по службам. Модели на
этом пути нет: промпт не меняется, платных проверок нет. Включает отель выключателем (§4.4).

## 3. Когда спрашиваем

- **Под итогом `done`** — с примечанием персонала или без (частичное выполнение, spec 0030).
  Такое сообщение получает только заявка, принятая ботом в чате (`request_origins`, ADR-011).
  Под отменой кнопок нет: оценивать гостю нечего.
- **Без отдельного сообщения и без напоминаний.** Кнопки стоят под уже отправленным итогом; не
  нажал — ничего не происходит. Сколько выполненных заявок, столько и оценок; потолка нет.
- **До выезда.** После выезда чат закрыт (ADR-008 Q8), и оценить нельзя. После перезагрузки
  страницы виджет показывает сохранённое состояние.
- **Оценка окончательная.** Первое касание фиксирует её: иначе карточку пальца вниз пришлось бы
  снимать, когда гость передумал. Комментарий один, тоже окончательный.
- **Только веб-чат.** Гости копии пишут только через него (spec 0039 §2.2). Telegram — когда бота
  подключат к копии (#484), запись в [later/](../later/2026-11-10-pr914-feedback-telegram.md).

## 4. Домен — `modules/feedback`

### 4.1. Таблица `request_feedback`

Тенантная по канону `TenantIsolationCanary` (P-4, RLS): `id`, `tenant_id`, `request_id`
(уникален в тенанте: одна оценка на заявку), `category_id` (служба заявки на момент оценки — для
сводки без чужого SQL, P-2), `rating` (`up` / `down`, VARCHAR(8), `native_enum=False`),
`comment` (Text NULL, ≤ 500 знаков), `comment_at`, `card_request_id` (NULL — карточки нет),
`created_at`, `updated_at`. Тем же миграционным файлом: `messages.request_id` (UUID NULL) — заявка,
итог которой сообщает это сообщение. Пишет её только `notify_guest_on_request_closed`.

### 4.2. Публичный API (`api.py`)

- `rate_request(request_id, *, stay_id, rating) -> FeedbackRead`. Оценить можно заявку `done`,
  у которой `stay_id` совпадает со Stay сессии гостя. Повтор той же оценки возвращает прежнюю
  (двойное касание, P-8). Другая оценка — 409. У `down` после записи —
  карточка (§4.3).
- `add_comment(request_id, *, stay_id, comment) -> FeedbackRead`. Только к `down` без комментария:
  атомарный `UPDATE … WHERE rating='down' AND comment IS NULL`. Номера карт маскируются до
  записи (`shared/pii.mask_payment_card_numbers`, NG-3, spec 0031).
- `feedback_states(request_ids, *, stay_id) -> dict[UUID, FeedbackState]` — для виджета: только
  заявки, которые можно оценить, с текущей оценкой и признаком комментария.
- `count_feedback(*, start, end, category_ids=None) -> list[FeedbackCount]` — `up` и `down`
  по службам за окно сводки.
- `clear_expired_comments(cutoff) -> int` — для джобы ретеншна (§4.5).
- Схемы — Pydantic (R-6). Событий модуль не публикует: подписчиков нет.

### 4.3. Карточка пальца вниз

Через `requests_api.create_request`: служба — `TenantConfig.escalation_category_key`, комната и
Stay — из оценённой заявки, не срочная. Источник — новое `ServiceRequestOrigin.FEEDBACK =
"feedback"` (VARCHAR(16), без миграции). Как у `escalation`, он входит в знаменатель
Exit-критерия: ресепшену понадобилось работать (формула spec 0035 §4 не меняется). Лестница —
обычная лестница службы, без особого пути эскалации. Тексты — §8.

- Комментарий дописывается в карточку `requests_api.append_request_details`. Карточку уже взяли,
  закрыли или она полна — заводится вторая, по канону spec 0039 §2.5.
- Шаг карточки — best-effort: оценка уже записана. Сбой — `feedback_card_failed` с кодом ошибки
  (ERROR, дойдёт до Sentry), гостю — прежний ответ.

### 4.4. Выключатель

`TenantConfig.guest_feedback_enabled: bool = False`, аддитивно (`schema_version` прежний). Его
переносит `build_config` (иначе повторный онбординг сотрёт поле). Валидатор не даёт включить
выключатель без `escalation_category_key`: «передадим сотрудникам» гостю должно быть правдой.
Выключен — виджета нет, маршруты отвечают 404 `ERR-FEEDBACK-001`, плитки сводки нет.

### 4.5. Срок и реестры

Комментарий — текст гостя: срок у [spec 0032](0032-guest-text-retention.md), затем `comment` →
NULL той же часовой джобой ретеншна. Оценка, служба и время остаются для сводки, как категория и
статус заявки. Строки в `docs/PII_REGISTRY.md` и коды в `docs/runbooks/errors.md` — PR 1:
`ERR-FEEDBACK-001` оценки выключены (404), `-002` заявку нельзя оценить (404: нет, не `done`, не
этого Stay), `-003` заявка уже оценена иначе (409), `-004` комментарий не к `down` или уже есть (409).

Логи: `feedback_rated` (request_id, rating, category_key), `feedback_commented` (request_id,
appended / new_card), `feedback_card_created`, `feedback_card_failed` (error_code) — без текста гостя.

## 5. Веб-чат — `channels/web`

- Poll и история: у `ChatMessage` — поле `feedback: {request_id, rating, commented} | None`. Его
  заполняет `feedback_states` по `messages.request_id` сообщений страницы.
- `POST /g/…/feedback` `{request_id, rating}` и `POST /g/…/feedback/comment` `{request_id,
  comment}` — под `require_guest_session`, Stay берётся только из сессии. Пустой комментарий или
  длиннее 500 знаков — 422. Отдельный лимитер не нужен: одна оценка и один комментарий на заявку.
- Виджет — `assets/feedback.js` (в `chat.js` 331 строка, R-3) и стили в `chat.css`: под пузырём
  итога, иконки пальца — линейные, как у иконок чата (#754). Надписи — в `CHAT_TEXTS` (kk, ru, en),
  по языку надписей чата. Вид — уровень гостевых экранов; превью — основателю в PR 2.
- Модель оценок не видит: виджет — не сообщение диалога. Гость написал жалобу в строку ввода —
  это обычный ход гостя.

## 6. Кабинет — `staff_portal`

- Сводка дня: плитка «Оценки гостей» — итог и строки по службам за то же окно, что у
  `day_summary` (одно окно на странице, spec 0035 §6). Старший службы видит свои службы
  (`category_ids`, spec 0045 §3), менеджер — все.
- Источник `feedback` — слагаемым подписи «Создано» на странице и в утреннем сообщении Telegram
  (`daily_summary.py`), только ненулевым: сумма источников обязана сходиться (#313).

## 7. Юртексты и включение на копии

- **Политика гостя** (`docs/legal/privacy-policy.md`, kk/ru/en) — PR 1. В §2 — оценка
  выполненной заявки и комментарий к ней, если гость их оставит. В §7 — комментарий по сроку
  текстов сообщений, оценка — вместе с заявкой. Номер версии — `ops/pool.sh reserve policy`.
  Согласие заново не запрашивается: оценку гость ставит сам, отдельным действием (довод версии
  1.1). Это решение окна, проверяет юрист РК. Шаблон DPA (`dpa-hotel-template.md` N.2.1, N.2.4) —
  тем же PR.
- **Договор** (вне репозитория): п. 1.2 требует согласовать новую функцию письмом. В п. 4.2.1
  есть «тексты сообщений гостя в чате» — под это подходит комментарий, но не оценка. Поэтому
  включение на копии — как у выгрузки Opera ([pilot-copy.md](../runbooks/pilot-copy.md)):
  по слову основателя, после письма по п. 1.2 и после допсоглашения (п. 7.3) или вывода юриста,
  что оно не нужно. PR 3 дописывает абзац в `hotel-letter-staff-features.md` и строку в
  `pilot-copy.md`. К 01.12 функция не обязательна.

## 10. Тесты

- **PR 1:** коды §4.5 (чужой Stay, не `done`, выключено); двойное касание — одна строка; `up`
  после `down` — 409; `down` — карточка `origin=feedback` с комнатой и Stay, службы нет — оценка
  без карточки и лог; комментарий — в невзятую карточку или вторая, к `up` — 409, номер карты

- **PR 2:** `feedback` под итогом `done`, под отменой нет; без сессии — 401, Stay из сессии, а не
  из тела; 422 по длине; выключено — 404 и виджета нет.
- **PR 3:** плитка по службам, срез старшего; выключено — плитки нет.

## 11. Что сознательно не делаем

- **Звёзды 1–5 и NPS:** для числа пилота хватает доли «хорошо» (аудит Ф-5), а «3» и «4» отелю мало
  что говорят. **Общая оценка при выезде:** чат гаснет на выезде (ADR-008 Q8).
- **Оценки по сотрудникам:** палец вниз часто не про исполнителя («долго ждал»), а такое число легко
  превратить в наказание. Кто закрыл — только в карточке, чтобы ресепшен знал, у кого спросить.
- **Перевод комментария персоналу** — [later/](../later/2026-11-10-pr914-feedback-comment-translation.md).
  **Заказ в номер и бронь столика** — у них свои экраны и свой итог. **Смена оценки, напоминание,
  страница всех комментариев** — пилоту хватает карточек и сводки.
