# ai/ — AI-слой: оркестратор, инструменты, промпты, evals (Task 0015/0017.1)

## Назначение

Композиционный слой (FOUNDATION §5.1, §7): превращает сообщение гостя в ответ
или действие ядра. Бизнес-логики не содержит (P-5): каждая способность AI —
тонкая обёртка над сервисом доменного модуля. Весь LLM-трафик — только через
`ai/gateway` (§7.2, см. его README).

## Публичный API

- `orchestrator.handle_message(*, message, history=None, pending_action=None,
  active_requests=(), provider=None) -> OrchestratorTurn` — единая точка
  обработки сообщения гостя; вызывается внутри `tenant_context(...)` (P-4).
  Историю диалога и `pending_action` хранит вызывающая сторона (канал; ADR-011
  — `conversations.pending_action`). `active_requests` — снапшот открытых
  заявок диалога (spec 0025): канал резолвит его по `request_origins` на
  КАЖДЫЙ ход; оркестратор кладёт блок в системный промпт (статусные ответы,
  анти-дубли) и отдаёт инструменту отмены как allowed-список id.
- `OrchestratorTurn` (P-7): `kind` (`reply` / `awaiting_confirmation` /
  `action_done` / `needs_human`), `reply_text`, `pending_action?`,
  `created_request_id?` (только у создающих инструментов — по нему канал пишет
  `request_origins`; отмена его не заполняет), `escalation?`
  (`EscalationContext`, задан ⟺ `needs_human` — spec 0022: по нему канал
  публикует `conversation.escalated`, и staff-чат реально узнаёт о госте,
  issue #36), `unanswered_question?` (вопрос гостя, не покрытый справочником
  отеля, — spec 0036 §6: по нему канал пишет строку `unanswered_questions`;
  читать её менеджеру будет страница «Справочник отеля» — #335).
- Ошибки провайдера (ERR-AI-001/002/003) пробрасываются — деградация §7.8
  забота канала. Ошибка исполнения инструмента (ERR-AI-004 и т.п.) — исход
  `needs_human`, не 5xx.

## Гейт подтверждения P-9 (`confirm_guest`) — структурный, детерминированный

Класс подтверждения — свойство контракта инструмента (`ai/tools`), гейтит
оркестратор, не текст промпта. Два хода (spec 0017.1):

1. **Предложение.** Модель вызывает инструмент класса `confirm_guest` →
   оркестратор НЕ исполняет его: возвращает `awaiting_confirmation` +
   `pending_action` (`tool_name` + `arguments`). Канал сохраняет его между
   вебхуками и задаёт гостю подтверждающий вопрос.
2. **Ход подтверждения** (`pending_action` передан). Оркестратор не полагается
   на повторный tool_use модели (issue #31: Haiku ре-эмитит нестабильно —
   заявка молча терялась). Вместо этого — структурная классификация ответа
   гостя: один вызов gateway с единственным служебным инструментом
   `resolve_confirmation` и `forced_tool` (модель обязана вернуть вердикт,
   свободный текст невозможен). Дальше детерминированно:
   - `confirm` → исполнить **сохранённый** `pending_action` → `action_done`;
   - `decline` → ничего не исполнять → `reply`; гейт гаснет (канал очищает
     `pending_action` на всех исходах, кроме `awaiting_confirmation`);
   - `other` (передумал/правка/другая тема) → старое предложение снимается,
     сообщение обрабатывается как новый запрос (обычный ход).

   Реплику «готово/отменил» пишет классификатор на языке гостя (`reply`);
   текст «передал в службу» появляется только ПОСЛЕ фактического исполнения.
   `resolve_confirmation` — механизм гейта, не AI-способность: в реестре §7.3
   его нет.

**Снятие гейта на срочной заявке (ADR-018, spec 0034 §5).** Единственное
исключение: вызов `create_service_request` с `is_urgent` исполняется сразу, без
хода подтверждения — сообщение «в номере течёт» и есть подтверждение, а гость с
аварией второго сообщения не пишет (аудит А-3). Класс инструмента при этом не
меняется: оркестратор спрашивает `registry.confirmation_waived(name, arguments)`
отдельно от `confirmation_class(name)` — и **засчитывает снятие только у
объявленного класса `CONFIRM_GUEST`**: `confirmation_waived → True` в
инструменте класса `auto` или `confirm_staff` не делает ничего (граница
ADR-018 держится кодом, а не намерением автора инструмента). Реплику гостю на
таком ходу даёт сам инструмент (`done_text(arguments)` — утверждённый абзац на
языке гостя), а свободный текст модели отбрасывается: промпт требует от неё
вопроса, и вопрос о уже созданной заявке был бы ложью. Отмена заявки гейт не
снимает никогда.

## Вопрос без ответа — служебный сигнал модели (spec 0036 §6)

Справочник отеля заполняет отель, а знает, чего в нём не хватает, только гость.
Детерминированного признака «модель не знала ответа» в системе нет — текстовая
реплика структурно неотличима от любой другой, — поэтому признак объявляется
контрактом, ровно как вердикт гейта: служебный инструмент
`report_unanswered_question(question, reply_to_guest)`. В реестре §7.3 его нет
(сервиса ядра не зовёт, в отеле ничего не меняет), схему собирает оркестратор,
исполнения у него нет.

- **Эскалацией это НЕ является** (spec 0022). «Во сколько завтрак» не требует
  человека **сейчас**, а отель на 310 номеров, получающий уведомление на каждый
  неизвестный факт, выключит уведомления к концу первой недели. Причины
  эскалации — отказы, и «не знаю ответа» среди них нет.
- **Реплика гостю — из аргумента**, а не из свободного текста: модель часто
  отдаёт tool_use с пустым текстом, и гость получил бы молчание. Приоритет:
  аргумент → свободный текст модели → статическая заглушка на языке
  демо-тенанта (канон `_ESCALATION_TEXT`). С `confirmation_question` общие
  только первые две ступени — третья там вопрос из `summary`. На снятом гейте
  вторая ступень пропускается: свободный текст там — вопрос «оформить?» о уже
  созданной заявке.
- **На ходу без действия `reply_to_guest` — весь ответ гостю**, включая то, что
  покрывают факты: свободный текст рядом с сигналом гость не видит. Описания
  схемы говорят это дважды (в описании инструмента и первым словом аргумента) —
  замер ревью PR #344 показал, что без этого ход «пароль Wi-Fi и есть ли утюг»
  теряет ответ из факта 17 раз из 20. Там же «один вызов на ход, все
  непокрытые вопросы — в нём».
- **Разбираются все вызовы сигнала**, а не первый: «один вызов» — просьба к
  модели, и на двух вопросах она звала сигнал дважды. Вопросы сводятся одной
  строкой справочника (` / `), различающиеся реплики — абзацами, повтор
  пишется в лог (`unanswered_question_signal_repeated`).
- **Сигнал никогда не выигрывает у действия.** Оркестратор вынимает его вызовы
  из списка вызовов хода **независимо от позиции** и работает дальше с первым
  оставшимся: исполняется `tool_calls[0]`, и «есть ли утюг и принесите
  полотенца» иначе теряло бы заявку из-за порядка вызовов у модели.
- **Смешанный ход — обе части доезжают.** Реплика сигнала встаёт первым абзацем
  перед репликой хода (вопрос-подтверждение гейта P-9 или текст инструмента на
  снятом гейте), через пустую строку; склейку делает оркестратор, поэтому промпт
  велит модели не повторять ответ внутри `confirmation_question`. Исключение —
  эскалация: гостю уходит только текст эскалации (человек уже идёт), а вопрос
  записывается всё равно.
- **Описания аргументов — по-английски**, в отличие от боевых инструментов
  реестра: `reply_to_guest` читает гость, а язык аргумента тянется за языком его
  описания (замер, issue #342). Заводить новое поле гостевого текста с этим
  дефектом незачем.
- **Строку пишет канал**, а не `ai/`: оркестратор кладёт вопрос в поле исхода
  `OrchestratorTurn.unanswered_question`, а `channels/common` пишет строку
  `unanswered_questions` — буква в букву канон `escalation`. Держит это канон, а
  не линтер: направление `ai → channels` контрактом импорт-линтера сегодня не
  закрыто (сиблинги через «:» в контракте слоёв `pyproject.toml`).

## Промпты (§7.5)

- `concierge_v5.md` — активный системный промпт обычного хода
  (`orchestrator.PROMPT_NAME`). v5 (spec 0036, issue #333) добавляет раздел
  «What you know about this hotel» — правила чтения блока «Hotel facts»:
  отвечать из факта коротко; числа, цены, часы, коды и пароли воспроизводить
  ДОСЛОВНО, переводя только слова вокруг них; факт с пометкой `temporary,
  until <дата>` называть временным состоянием, а не правилом отеля; не выводить
  ответ из соседних фактов. Плюс правило смешанного хода: если ход и отвечает
  на покрытый фактом вопрос, и предлагает действие, ответ идёт ПЕРВЫМ внутри
  `confirmation_question` инструмента — свободный текст на таком ходу гость не
  видит (гейт P-9 отдаёт ему именно аргумент), и без правила ответ пропал бы
  молча.
  Вторую половину v5 привёз PR серии #334: ветка «факта нет» — сказать честно,
  указать на РЕСЕПШЕН и на том же ходу вызвать `report_unanswered_question`.
  Сотрудника ветка не обещает намеренно: обещать некому (#101 открыт), а после
  #101 обещание сделало бы эскалацией каждый неизвестный факт — ровно то, против
  чего построен §6 спеки. Тем же изменением переписан первый буллет раздела
  `# What you must not do`: он обещал сотрудника ровно на тех вопросах (цены,
  правила отеля, часы работы), которые теперь отвечает раздел знаний, — модель
  получала два указания на один вопрос, а приоритета у правил промпта нет.
  «Check with a staff member» осталось за тем, чего справочник не покрывает по
  природе: статус и детали брони, деньги, документы.
  **Справочник перетягивает язык ответа — это измерено, а не предположено.**
  Факты написаны на языке отеля и лежат между правилом «отвечай на языке
  гостя» (первая строка файла промпта с v2) и репликой гостя. Прогон evals
  07.09.2026 на Sonnet 5: гость-англичанин получал ответ по-русски в 3
  сценариях из 4. Поэтому правило языка стоит ТРИЖДЫ: хвостом внутри блока
  фактов (`_hotel_facts_block`), отдельным блоком `# Before you reply` в самом
  конце системного промпта (`_guest_language_reminder`) и предложением в
  буллете смешанного хода самого файла `concierge_v5.md` (единственное из трёх,
  что видно в тексте промпта; первые два собирает оркестратор). Решают тут
  позиция И форма: прогон 10.09.2026 показал, что абстрактный запрет
  («translate the wording into the guest's language») правило не удерживает —
  2–3 отказа из 4, — а **рабочий пример перехода «факт → ответ»** удерживает:
  0 из 3 простых сценариев на трёх прогонах. Остаётся смешанный ход: там текст
  гостю живёт в аргументе `confirmation_question`, чьё описание написано
  по-русски, и это дефект старше справочника (воспроизведён без блока фактов
  вовсе — **#342**). Разбор трёх мест, полные тексты и запрет их переставлять —
  spec 0036 §8.2.
- `concierge_v4.md` — предыдущая версия (история). v4 (spec 0025, issue #40)
  добавила правила работы с блоком «Active service requests» (его дописывает
  оркестратор из снапшота диалога): статус — только из списка, просьба, уже
  покрытая открытой заявкой, — не дубль; отмена — только инструментом
  `cancel_service_request` и только для заявок из списка; о заявке не из
  списка — честное «не вижу». Эти правила v5 не трогает.
- `concierge_v3.md` — предыдущая версия (история). v3 закрыл баг #71: v2 учил
  модель, что вызов инструмента = отправка заявки службе («the request is only
  submitted after the guest confirms»), поэтому Haiku придерживал `tool_use` до
  «да» — а на ходе «да» `pending_action` уже не было, и заявка не создавалась
  **никогда** (на английском гейт не вооружался в 0/4 прогонов, kk 3/4). v3
  переформулирует: вызов инструмента — лишь ЧЕРНОВИК заявки, ничего не
  отправляет (подтверждение и отправку делает система), поэтому модель обязана
  звать инструмент на том же ходу, где предлагает заявку. Замер на Haiku 4.5:
  v3 — 24/24 на 6 языках пилота.
- `concierge_v2.md` — история. v2 закрыла два дефекта bake-off'а
  (DISCUSSION_LOG): промпт целиком на английском с жёстким правилом «отвечай на
  языке последнего сообщения гостя» первой строкой (утечка языка) и требованием
  формулировать предложение действия вопросом.
- `confirmation_gate_v2.md` — промпт классификатора хода подтверждения
  (`orchestrator.CONFIRMATION_PROMPT_NAME`). v2 (spec 0025) генерализует
  реплику подтверждения под второе действие: «заявка отменена», а не только
  «передана службе» (v1 писался под единственный инструмент создания).
- Смена промпта = новый файл `<name>_v<N+1>.md` + смена константы + прогон
  evals (§7.7). Старые версии остаются в репозитории как история.

## События

Не публикует и не потребляет доменных событий (события заявок публикует
`modules/requests` при исполнении инструмента).

## Таблицы

Своих нет. `llm_call_log` — у `gateway` (его README).

## Зависимости

Внутренние: `modules/requests` (публичный API — категории, создание заявки),
`platform/config` (`TenantConfig.hotel_facts` — справочник отеля в системном
промпте, spec 0036; `TenantConfig.category_hints` — типовые предметы службы в
описании enum'а инструмента, issue #123), `shared` (errors, logging, tenancy,
db). Направление слоёв (R-5): `ai/` зависит от доменных модулей, обратное
запрещено; каналы зависят от `ai/`.

Конфиг тенанта читает ОДИН раз за ход оркестратор и передаёт потребителям:
блок промпта собирает сам, подсказки служб отдаёт в
`tools.registry.build_tool_specs(context, config)`. До spec 0036 конфиг читал
реестр инструментов; с появлением второго потребителя это дало бы два
одинаковых запроса к БД на каждую реплику гостя. Конфиг недоступен (онбординг
не завершён, дрейф схемы) — `None` и WARNING: ход идёт без справочника и без
подсказок, диалог гостя ценнее обоих.

## Типовые сценарии изменения

- **Новый AI-инструмент** — копировать канон `tools/create_service_request.py`
  (контракт модуля: `NAME`, `CONFIRMATION_CLASS`, `CREATES_REQUEST`,
  `DONE_TEXT`, `build_spec(...)`, `execute(arguments, context)`,
  `confirmation_waived(arguments)`, `done_text(arguments)`) + запись в
  `_TOOLS` и строка в `build_tool_specs` (`tools/registry.py`) + тест.
  Инструмент класса `confirm_guest` автоматически проходит гейт — отдельного
  кода подтверждения писать не нужно. Пример инструмента, зависящего от
  контекста хода, — `tools/cancel_service_request.py` (spec 0025).
- **Новая служба отеля или её типовые предметы** — это ДАННЫЕ тенанта, а не
  правка `ai/`: категории и `category_hints` задаёт онбординг
  (`python -m hospitality.tools.onboard_tenant`,
  docs/runbooks/tenant-onboarding.md). Enum категорий и список предметов
  собираются под тенанта в `tools/registry.build_tool_specs`.
- **Правка промпта** — новая версия файла + evals; см. §«Промпты».
- **Смена модели рантайма** — `LLM_MODEL` + прайс-лист gateway; выбор — только
  по bake-off (`python -m hospitality.ai.evals.bakeoff`, нужен
  `ANTHROPIC_API_KEY`).
