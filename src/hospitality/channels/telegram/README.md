# channels/telegram — канал Telegram (Task 0016, 0017)

Первый реальный вход гостя в систему и первый полный проход скелета (Task 0017):
приём вебхука Telegram Bot API, нормализация в общий контракт канала, идемпотентная
запись диалога, вызов AI-оркестратора, уведомления службе о заявках и подтверждения
гостю. Канал — композиционный слой (§5.1), **не порт ядра** (§8): обязательного
Fake-адаптера нет, в тестах он воспроизводится payload'ами вебхука.

> **Сквозная сборка (Task 0017, ADR-011).** На текст гостя канал зовёт оркестратор
> (`guest.py`) и хранит между ходами историю диалога и `pending_action` (гейт P-9).
> Создав заявку, публикует событие `request.created` (через `modules/requests`) —
> уведомление службе и подтверждение гостю идут **подписчиками событий** (P-6,
> `notifications.py`), а не прямыми вызовами. Персонал закрывает заявку командами в
> staff-чате (`staff.py`). Обратная адресация «заявка → чат гостя» — таблица
> `request_origins` (композиционный слой владеет ею, домен не тронут, ADR-011).

## Контракт нормализованного сообщения (`channels/base.py`, P-7)

`NormalizedMessage` — единственный формат, который канал отдаёт наверх; выше по
стеку неизвестно, из какого канала пришло сообщение. Зарезервировано поле
`reply_to` (ответ на конкретное сообщение): Telegram присылает полный объект —
заполняется сразу; WhatsApp (Phase 1) даст только id и восстановит текст по
`external_message_id` из истории (DISCUSSION_LOG «Контракт … reply-to»).

## Поток обработки (`service.process_update`)

1. **Проверка секрета** (`router.verify_telegram_secret`, §8.4): Telegram шлёт
   `secret_token` из `setWebhook` в заголовке `X-Telegram-Bot-Api-Secret-Token`.
   Неверный/пустой секрет → **403 `ERR-TELEGRAM-001`**, до разбора тела. Пустой
   `TELEGRAM_WEBHOOK_SECRET` = вебхук закрыт (fail-closed, §11). `allowed_updates`
   при `setWebhook` обязан включать `callback_query` — иначе Telegram не доставляет
   нажатия inline-кнопок и они молча не работают (ставит `deploy.sh`, проверяет
   там же по `getWebhookInfo`).
2. **Нормализация** (`normalize.py`): не-сообщение (edited_message и т.п.) → no-op
   200; текст → `TEXT`; не-текст (фото/голос/стикер) → `UNSUPPORTED`.
3. **Маппинг чата на тенанта**: Phase 0 — один бот = демо-тенант, по slug из
   `TELEGRAM_TENANT_SLUG` (как сервисный токен в `platform/auth.py`). Пер-чатовый
   маппинг (несколько отелей за одним ботом) — Phase 1.
4. **Развилка гость / персонал** (`service.py`): чат входит в МНОЖЕСТВО
   staff-чатов тенанта (дефолтный `TELEGRAM_STAFF_CHAT_ID` + чаты служб из
   конфига, spec 0026) → команда персонала (`staff.py`); иначе — реплика гостю.
   Это граница безопасности: строгое равенство в множестве, конфиг не
   прочитался → деградация в сторону гостя (персонал = только дефолтный чат).
5. **Consent-gate гостя** (`consent.py`, spec 0029, issue #127): согласие
   диалога (`conversations.consent_at/consent_version`) не равно текущей версии
   → гость получает экран согласия с inline-кнопкой и НЕ идёт дальше: ни
   `insert_inbound_message` (содержимое его сообщений до согласия не хранится),
   ни оркестратора, ни заявок. Нажатие кнопки записывает согласие, снимает
   клавиатуру и отвечает приветствием (`greeting.py`, issue #39). Экран
   показывается один раз на (диалог, версия) — кроме `/start`/`/help`, которые
   показывают его всегда; поток спама упирается в общий rate-limit (spec 0023).
   Тексты и версия — общий канон каналов `channels/common/consent.py` (дословная
   копия `docs/legal/consent-text.md`); язык — `from.language_code`, неизвестный
   → все три версии. Персонала гейт не касается.
6. **Идемпотентная запись** (`channels/common/store.py`, spec 0027 §2, P-8):
   диалог — по `(tenant, channel, chat_id)`; входящее — под уникальным ключом
   доставки `(tenant, idempotency_key)`.
   Повторный вебхук с тем же `update_id` не создаёт второй `Message` и не влечёт
   второй эффект (общая опора и для гостя, и для команд персонала). У гейта
   опора своя — ключи ИСХОДЯЩИХ (`guest:consent_prompt:…`,
   `guest:consent_granted:…`): входящей строки до согласия нет.
7. **Обработчики** — что делать с сохранённым сообщением:
   - **Гость** (`guest.py` — транспортная обвязка; сам ход — общий
     `channels/common/guest_turn.py`, spec 0027 §2): не-текст → вежливый отказ;
     `/start`/`/help` → детерминированное приветствие с именем отеля БЕЗ вызова
     LLM (`greeting.py`, issue #39; payload deep-link принимается, но не
     разбирается); прочий текст → **rate-limit ДО оркестратора** (issue #41, spec 0023: две ступени,
     ключ Telegram — `chat_id` —
     всплеск `GUEST_CHAT_RATE_LIMIT_MESSAGES`/`…_WINDOW_SECONDS` и дневной
     потолок `…_MESSAGES_PER_DAY`; счётчики — канон `shared/ratelimit`,
     fail-open при недоступном Redis; превышение → статический двуязычный
     отказ БЕЗ вызова LLM, один раз на окно, лог `ERR-CHANNEL-003` + метрика
     `guest_rate_limited_total`; входящее уже сохранено — история честная);
     дальше — оркестратор (история + `pending_action` + **снапшот открытых
     заявок диалога**, spec 0025: канал резолвит их по `request_origins` →
     `requests.list_open_requests_by_ids` и передаёт `active_requests` — по
     нему модель отвечает о статусе, не плодит дубли, а инструмент
     `cancel_service_request` получает допустимые id), ответ гостю. Заявка
     создана → привязка `request_origins`. Ошибка провайдера LLM → деградация
     §7.8 (честный фолбэк).
     Обещание «зову сотрудника» правдиво (spec 0022, issue #36): исход
     `NEEDS_HUMAN` и деградация публикуют `conversation.escalated` в outbox
     **до** реплики гостю — упала публикация → гость получил молчание, не ложь.
   - **Персонал** (`staff.py`): бот реагирует **только на команды** (текст с
     ведущим «/»), **нажатия inline-кнопок** и **ответы-реплаи на свой вопрос
     о примечании** — всё остальное (обычная переписка группы, не-текст)
     остаётся без ответа (S-2, #38 п.4). Пути (все зовут
     `requests.change_request_status`, P-5):
     - команды `/start · /done [текст] · /cancel [текст] <#N>` (ADR-013:
       `/assign` упразднён — подсказка «сразу /start»); аргумент — дневной
       номер `#N` (неоднозначность — просьба уточнить полным id; UUID тоже
       принимается); хвост после номера у `/done`/`/cancel` — примечание
       закрытия (spec 0021 П-4). Разбирается команда из **сырого** текста
       (`NormalizedMessage.raw_text`): маскирование карт калечило uuid заявки
       раз на ~500 (issue #172); сырым текст остаётся только внутри разбора, и
       **наружу из него уходит только пережившее канон плюс дневной номер не
       длиннее потолка** — ничего сверх. Примечание закрытия (оно хранится и
       уходит гостю) маскируется каноном; аргумент в ответе «Не разобрал»
       цитируется, только если он **дословно пережил канон** в `normalized.text`
       (ответ пишется строкой в `messages`) — иначе цитаты нет вовсе: разбор рвёт
       строку по пробелу раньше канона, и `4111-1111-1111 1111` дало бы в цитате
       12 цифр PAN, для канона слишком короткие. Сама цитата всё равно проходит
       канон — общий текст он изредка проносит. Числовой аргумент отсекается
       **потолком** `_MAX_DAILY_NUMBER_DIGITS` (5 цифр: номер живёт в пределах
       суток одного отеля): ряд длиннее в `int()` не уходит, поэтому в поиск по
       `daily_number` не попадают ни слитный PAN, ни его кусок (`/done 41111111
       11111111`), ни телефон — последний ронял вебхук на 500 (issue #203).
       Остаток инварианта: карта по четвёркам даёт «Заявка #4111 … не найдена» —
       4 цифры BIN, в пределах отраслевого усечения. Всё — spec 0031 §2;
     - команда **ответом на уведомление** — заявка резолвится по
       `external_message_id` уведомления (обратный поиск по ключам `messages`,
       #38 п.3), номер не нужен. Поиск ограничен диалогом самой команды:
       `message_id` в Telegram нумеруется внутри чата, и с маршрутизацией по
       службам (spec 0026) номера шести групп совпадают постоянно — без этого
       условия `/done` реплаем в чате уборки закрывал бы заявку инженерии
       (issue #206);
     - **кнопки** под уведомлением (`keyboards.py`): «Взять в работу» →
       «Готово / Готово частично / Отменить»; ошибки отвечаются тостом
       (`answerCallbackQuery`), успех — тост + строка в чат + перерисовка
       кнопок; «Готово частично» задаёт вопрос (ForceReply), ответ-реплай
       персонала становится `resolution_note` и закрывает заявку.
6. **Уведомления** (`notifications.py`, подписчики событий, P-6): `request.created`
   → в staff-чат (**маркер «🚨 СРОЧНО ·» первым**, если заявка срочная — spec 0034 §5;
   **номер `#N`** в шапке, **номер комнаты**, категория, **суть
   по-русски** через `ai.translation` + оригинал строкой «Гость написал» — персонал
   читает русский, оригинал рядом как эталон, баг #71; номер и комнату подписчик
   дочитывает из заявки, событие их не несёт, #37/#38; подсказка команд — с `#N`);
   `request.status_changed(done|cancelled)` → сообщение гостю об итоге (адрес — по
   `request_origins`; доставка канал-осознанная, spec 0027 §2: диалог telegram —
   push через sender, иной канал (web) — только запись исходящего `Message`,
   гость заберёт poll'ом) **на языке гостя** (spec 0021 П-1): канонический русский текст,
   при нерусском целевом языке — один вызов `ai.translation.translate_for_guest`
   (язык — `guest_language` заявки, фолбэк — `default_language` тенанта, issue #66;
   сбой перевода → канонический текст; **частичное выполнение** (`done` +
   `resolution_note`) идёт другим путём — текст гостю СОБИРАЕТ модель из сути
   заявки и пометки персонала сразу на его языке (`ai.closing_message`,
   spec 0030), деградация — шаблон «выполнена частично» + «От персонала: …»;
   склейка «выполнена» + записка персонала врала гостю, issue #58;
   **исключение** — отмена самим гостем,
   spec 0025: при `initiator=guest` гостя НЕ извещают — «пришлось отменить» в
   ответ на собственную отмену абсурдно, подтверждение он получил репликой
   модели); `request.status_changed(cancelled, initiator=guest)` → «🚫 Гость
   отменил заявку #N» в staff-чат + снятие кнопок исходного уведомления
   (ключ дедупа `staff:request_cancelled_by_guest:<request_id>`, без LLM);
   `conversation.escalated` → «🆘 Гостю нужен
   сотрудник» в staff-чат (spec 0022: чат, комната и суть — если известны из
   аргументов инструмента, последняя реплика гостя, причина; **без LLM** — при
   `llm_unavailable` причина эскалации и есть недоступность ИИ; ключ дедупа —
   `staff:escalated:<inbound_message_id>`, P-8; staff-чат не настроен → warning
   `ERR-TELEGRAM-002`, без ретрая). У причины `emergency` (ЧП-перехват,
   spec 0034) свой заголовок — «🚨 ЧП: сообщение гостя»: такое сообщение обязано
   читаться в ленте с первого символа.
   **Адресат уведомления о заявке — чат СВОЕЙ службы** (spec 0026, issue #80):
   `TenantConfig.staff_chats_by_category[category_key]`, фолбэк — дефолтный чат;
   создание и «гость отменил» идут в один и тот же чат категории, кнопки
   перерисовываются в чате самого уведомления (`load_staff_notification_target`).
   Эскалация — всегда в дефолтный чат («уровень выше»): категории у неё нет.
   Конфиг недоступен или категория незнакома → дефолтный чат + warning
   `staff_routing_config_unavailable` (§7.8: уведомление важнее маршрутизации);
   след маршрутизации — лог `staff_notification_routed`.
   Регистрируются composition root воркера
   (`hospitality/worker.py`).

## Напоминание о невзятой заявке (`reminders.py`, issue #57, spec 0028)

Уведомление о новой заявке уходит один раз; если его никто не прочитал, заявка
пропадает из поля зрения. Поэтому воркер раз в `WORKER_REMINDER_INTERVAL_SECONDS`
зовёт `remind_unclaimed_requests`: заявки в статусе `new` (ADR-013 — «никто не
взял») старше срока тенанта получают повторное сообщение в чат СВОЕЙ службы
(тот же адресат, spec 0026) — с номером `#N`, комнатой, сутью, возрастом и
кнопками статуса. Реплай-команда на напоминание резолвит заявку так же, как на
исходное уведомление.

- **Срок — конфиг тенанта** (P-11): `request_reminder_after_minutes`
  (по умолчанию 30 мин, `null` = выключено) и пер-категорийный
  `request_reminder_minutes_by_category` (уборка ≠ прорыв трубы). Задаёт
  `python -m hospitality.tools.request_reminders`.
- **Одно напоминание на заявку** (P-8): ключ `staff:request_unclaimed:<id>`.
  Лестница эскалаций и `in_progress`-висяки — Phase 1 вместе с владельцем
  заявки (ADR-008); SLA-движка здесь нет намеренно.
- **Без LLM**: суть — оригиналом гостя (перевод персонал видел в исходном
  уведомлении), фоновая задача не тратит токены и не зависит от модели.
- **Изоляция сбоев**: сбой по одной заявке (`ERR-TELEGRAM-004`) не отменяет
  остальные и повторится следующим прогоном (ключ пишется только после успешной
  отправки); падение прогона целиком — `ERR-TELEGRAM-005`, цикл воркера жив.
- **Мультитенантность**: тенанты обходятся списком
  `platform.config.list_configured_tenant_ids`, вся работа — под
  `tenant_context` каждого (P-4).

## Таблицы (живут в `channels/common/models.py`; миграции `0008`, `0009`, RLS — копия канона `0002`)

- `conversations` — `id`, `tenant_id` (FK+индекс), `channel`, `external_id`
  (уникальны в тройке с `tenant_id`, `channel`), `pending_action` (JSONB, NULL —
  состояние гейта P-9 между ходами, Task 0017), `consent_at`/`consent_version`
  (NULL — согласия нет; доказательная запись consent-gate, миграция 0016,
  spec 0029), `created_at`, `updated_at`.
- `messages` — `id`, `tenant_id` (FK+индекс), `conversation_id` (FK+индекс),
  `direction` (inbound/outbound), `content_kind` (text/unsupported), `text`,
  `external_message_id`, `idempotency_key` (уникален в паре с `tenant_id`;
  NULL у исходящих реплик; у уведомлений — ключ дедупа `staff:…`/`guest:…`),
  `correlation_id`, `created_at`.
- `request_origins` (Task 0017, ADR-011) — `id`, `tenant_id` (FK+индекс),
  `request_id` (уникален в паре с `tenant_id`, **без FK** на `service_requests`),
  `conversation_id` (FK+индекс), `created_at`. Привязка «заявка → диалог-источник»
  для доставки подтверждения гостю; в Phase 1 вытесняется идентичностью гостя.

Все три таблицы под RLS (ENABLE + FORCE + политика `tenant_isolation`); изоляция
покрыта тестами (`tests/test_tenant_isolation.py`).

Про `conversations.consent_at/_version` есть строка в `docs/PII_REGISTRY.md` (§9):
это доказательная запись согласия, а не техническое поле.

## Аутентификация вебхука

Вебхук **не** использует сервисный токен `/api/v1/*` (Task 0013) и зависимость
`require_authenticated_tenant`: он аутентифицируется секретом вебхука Telegram
(§8.4), а тенанта ставит сам по маппингу чата. Роутер подключает composition root
(`hospitality/app.py`) отдельно от роутеров API.

## Конфигурация окружения (`shared/config.py`)

- `PUBLIC_BASE_URL` (spec 0029) — внешний адрес инсталляции: из него собирается
  ссылка на политику конфиденциальности в тексте согласия. Локальный дефолт
  `http://localhost:8000`; на staging/проде обязан быть реальным — иначе гость
  получает нерабочую ссылку в юридически обязательном тексте.
- `TELEGRAM_WEBHOOK_SECRET` — секрет вебхука (пустой = закрыт).
- `TELEGRAM_BOT_TOKEN` — токен бота для отправки ответов (пустой валиден для тестов).
- `TELEGRAM_TENANT_SLUG` — маппинг чата на тенанта (по умолчанию `demo-hotel`).
- `TELEGRAM_API_BASE_URL` — база Bot API (по умолчанию `https://api.telegram.org`).
- `TELEGRAM_STAFF_CHAT_ID` (Task 0017) — chat.id **дефолтного** staff-чата:
  уведомления о заявках без своей службы, эскалации, команды закрытия; пустой =
  служба-канал выключена. **Нужен и воркеру** (уведомления шлёт он) — см.
  `ops/deploy/docker-compose.staging.yml`. Чаты отдельных служб — не окружение,
  а конфиг тенанта (`staff_chats_by_category`, spec 0026): это свойство отеля,
  а не инсталляции.
- `WORKER_REMINDER_INTERVAL_SECONDS` (issue #57, spec 0028) — как часто воркер
  ищет невзятые заявки. Сам СРОК — конфиг тенанта, не окружение (P-11).
- `GUEST_CHAT_RATE_LIMIT_MESSAGES` / `…_WINDOW_SECONDS` / `…_MESSAGES_PER_DAY`
  (issue #41, spec 0023) — ступени rate-limit гостевого чата; ≤0 отключает
  ступень. Пер-тенантные значения — конфиг тенанта, Phase 1 (P-11).

Регистрация вебхука и секретов на staging — `docs/runbooks/telegram.md`.

## События (Task 0017, P-6)

Публикует: `conversation.escalated` (`events.py`, spec 0022) — гостю пообещали
человека (`NEEDS_HUMAN` оркестратора / деградация §7.8); нагрузка: диалог,
входящее сообщение (естественный ключ идемпотентности), чат, последняя реплика,
причина/код, суть и комната (если известны). Заявки и их события создаёт
`modules/requests` через оркестратор/инструмент. Потребляет (подписчиками
`notifications.py`, регистрирует `hospitality/worker.py`): `request.created` →
уведомление службе; `request.status_changed` → итог гостю при `done`/`cancelled`
(кроме отмены самим гостем) и «Гость отменил заявку» в staff-чат при
`cancelled` + `initiator=guest` (spec 0025); `conversation.escalated` →
эскалация в staff-чат (своё же событие: публикация — вебхук-процесс,
доставка — воркер).

## Зависимости

Внутренние: kernel — `hospitality.shared` (db, tenancy, errors, logging, config,
middleware, events) и `hospitality.platform.models`; доменный `modules/requests`
(через `api.py`: сервис + события) и композиционный `ai` (оркестратор + gateway) —
канал выше них по слоям (§5.1). Внешние: `httpx` (Bot API). Импортируется
composition root'ами: `hospitality/app.py` (`router`), `hospitality/worker.py`
(`notifications`), `alembic/env.py` (`channels/common/models`). Сиблинг
`channels/common` — общее ядро гостевых каналов (spec 0027 §2).

## Типовые сценарии изменения

- **Новый тип входящего (фото/голос с разбором)** — тип в `MessageKind` +
  обработка в `normalize.py`/`guest.py` + тесты; таблицы не трогаются.
- **Новая staff-команда** — глагол → статус в `_STATUS_BY_VERB` (`staff.py`) + тест.
- **Другой канал уведомлений (не только гостю в Telegram)** — вынести подписчиков в
  общий `notifications/` над портом отправки (ADR-011, «Последствия»).
- **Новая фоновая задача канала** — функция в своём файле + вызов по интервалу в
  `hospitality/worker.py` (канон `reminders.py`/`cleanup_terminal_events`);
  отдельная джоба или планировщик не заводятся (NG-8).
- **Идентичность гостя (`guests/`, Phase 1)** — заменить `request_origins` резолвом
  идентичности; ADR-011 → superseded.
- **Несколько отелей за одним ботом** — заменить маппинг по slug на пер-чатовую
  таблицу привязки (`_resolve_tenant` в `service.py`); Phase 1.
- **Новый канал (WhatsApp/Email)** — новый пакет `channels/<name>`: транспорт по
  этому образцу, персистенция и ход гостя — из `channels/common` (spec 0027 §2);
  контракт `NormalizedMessage` не меняется, WhatsApp лишь реализует сборку
  `reply_to.text` по `external_message_id` из истории.
