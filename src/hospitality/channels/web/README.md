# channels/web — гостевой веб-чат по QR (spec 0027, issue #79)

## Назначение

Второй гостевой канал: гость сканирует статический QR в номере
(`https://<хост>/g/{tenant_slug}/{room}`), вводит код заселения с карточки
ресепшена (ADR-008 §3) и общается с тем же AI-консьержем, что в Telegram.
**Строгий auth-only с рождения** (Q7, решение 22.07): без валидной
`GuestSession` — статический ответ `ERR-WEB-002` без единого вызова LLM и без
заявок; после выезда — то же (Q8, валидность перепроверяется на каждом
действии). Транспорт — HTTP JSON + одна статическая страница; ход гостя —
общий `channels/common/guest_turn` (spec 0027 §2).

## Маршруты (`/g/{tenant_slug}/{room_number}` и `/w/{tenant_slug}/b/{token}`)

| Маршрут | Auth | Что делает |
| --- | --- | --- |
| `GET /g/…/` | нет | HTML-страница чата (надписи kk, ru, en — #224, инлайн CSS/JS, `page.py`); кнопка «🛎 Заказать в номер» — только у отеля с включённым room service, видна после входа |
| `POST /g/…/session` | нет, rate-limit по IP и по комнате | `{code}` → тройка тенант+комната+код → Set-Cookie `guest_session`; отказ — 403 `ERR-WEB-003` без причины; комната длиннее 20 символов или пустая — 422 до лимитера; лимит по IP или по (tenant, room) — 429 `ERR-WEB-004` (#483) |
| `GET /g/…/menu` | сессия (без неё — 303 на чат) | Страница «Заказать в номер» (spec 0038, `menu/page.py`) |
| `GET /g/…/menu/data` | сессия | Каталоги в виде гостя, «принимаем», сбор, заметка о доставке, открытые заказы проживания, языки отеля, комната из сессии |
| `POST /g/…/menu/quote` | сессия | `{catalog, lines}` → итог по ценам сервера (Р-5) |
| `POST /g/…/orders` | сессия | «Оформить»: 201 — новый заказ, 200 — повтор того же `client_order_key`; 409 `ERR-ROOMSERVICE-003…005`, 429 — `006` |
| `GET /g/…/orders/{id}` | сессия | Заказ этого проживания (стадия, состав, суммы, время шагов); чужой — 404 `008` |
| `POST /g/…/orders/{id}/cancel` | сессия | Отмена гостем, пока «Отправлен»; принятый — 409 `007` |
| `POST /g/…/messages` | сессия | `{text, client_message_id}` → общий ход гостя → `{replies}` синхронно; повтор `client_message_id` — `duplicate: true` (P-8) |
| `GET /g/…/messages?after=` | сессия | история/новые сообщения (poll раз в ~5 с; так доезжают подтверждения заявок от подписчика) |
| `GET /g/…/documents` | сессия (без неё — 303 на чат) | Форма «Реквизиты для закрывающих документов» (spec 0049); приём выключен — 404 `ERR-DOCUMENTS-005` |
| `GET /g/…/documents/data?language=` | сессия | Номер и даты проживания словами в поясе отеля, язык гостя (Р-9) |
| `POST /g/…/documents` | сессия | Multipart: `client_key`, `language`, `bill_to`, `note`, до 5 `files` → запрос АВР и карточка «Реквизиты получены» в чат; повтор ключа — тот же ответ; отказ файла — код узла и `details: [{file_position}]` |
| `GET /w/{slug}/b/{token}` | нет | Страница ссылки привязки с листка (spec 0033 §6): consent-строка v3 + кнопка; сессии не рождает |
| `POST /w/{slug}/b/{token}/session` | нет, rate-limit по IP | Нажатие кнопки-согласия: `start_guest_session_by_bind_link` (тот же путь, что код, P-12) → cookie + `chat_url`; ссылка многоразова до выезда (#354); погашена или Stay погас — 403 `ERR-GUESTS-006`; токен длиннее 128 символов — 422; лимит — 429 `ERR-WEB-005` |

Короткий префикс `/w` — ради ёмкости QR; отдельный `bind_router` подключает
composition root рядом с основным. Маршруты меню и заказов — свой `menu/router.py`
под тем же `/g`: room service у отеля выключен (`TenantConfig.room_service`, spec 0038
Р-10) — любой из них отвечает 404 `ERR-ROOMSERVICE-002` раньше проверки сессии.

Контекст тенанта канал ставит САМ по slug внутри маршрутов (ADR-008 §6):
ни QR-slug, ни гостевая сессия НЕ входят в общий `TenantResolver` — гостевая
сессия на `/api/v1/*` конструктивно даёт 401 (тест-инвариант). Cookie:
HttpOnly + Secure + SameSite=Strict + Path=/g/{slug}; атрибуты — не граница
безопасности, границу держит `guests.resolve_session` на каждом действии.
`{room}` из пути на аутентифицированных операциях игнорируется — комната
только из сессии (несовпадение логируется `web_path_room_mismatch`).

## Ключевые решения

- **Комната — из привязки, не из текста** (issue #79): `verified_room_number`
  Stay уезжает в ход (`ToolTurnContext`) — `create_service_request`
  перезаписывает комнату из аргументов модели; системный промпт получает блок
  «verified room» (модель не переспрашивает номер). Эскалации web-гостя несут
  комнату — персоналу есть куда прийти.
- **Ключ чат-лимита — `stay_id`** (spec 0027 §3.2): повторный ввод кода рождает
  новую идентичность и не должен обнулять лимиты spec 0023.
- **Доставка исходящих — только запись** в `messages` (poll забирает);
  канал-осознанный подписчик — `channels/telegram/notifications.py`.
- **Экран входа = экран согласия** (spec 0029): кнопка ввода кода и есть
  согласие на обработку ПД. Тексты и версия — общий канон каналов
  (`channels/common/consent.py`, дословная копия `docs/legal/consent-text.md`),
  во всех трёх языках: до входа язык гостя неизвестен всегда. Факт пишется на
  сессию (`guest_sessions.consent_*`) — своё согласие на каждую привязку;
  telegram хранит своё на диалоге, правило актуальности версии общее.
  Страница ссылки привязки — тот же канон: сессия рождается ТОЛЬКО по нажатию
  кнопки-согласия (открытие страницы — не согласие).

## Таблицы

Своих нет: диалог — общие `conversations`/`messages` (`channel='web'`,
`external_id` = UUID идентичности клиента; `conversations.guest_identity_id`
заполняется при создании — миграция 0015); доступ — таблицы `modules/guests`.

## Конфигурация

- `GUEST_CODE_VERIFY_RATE_LIMIT_ATTEMPTS` / `…_WINDOW_SECONDS` — лимит ввода
  кода по (tenant, room); `GUEST_CODE_VERIFY_IP_RATE_LIMIT_ATTEMPTS` — вторая
  ступень по IP за то же окно, проверяется первой (аудит 26.10 К-1, #483:
  поток выдуманных комнат с одного адреса гонял bcrypt на каждую); ≤0
  отключает ступень. Чат-лимиты — общие `GUEST_CHAT_RATE_LIMIT_*` (spec 0023).
- `GUEST_BIND_LINK_CONSUME_RATE_LIMIT_*` — лимит привязок по ссылке с листка
  по IP (spec 0033 §9); просторный — гости за NAT отеля делят один адрес. Сам
  адрес — канон `shared/clientip.py` (issue #207): за туннелем `request.client`
  указывает на соседний контейнер, и лимит был бы общим на всех гостей сразу.
- `TenantConfig.reception_phone` — телефон в статическом auth-only ответе.
- `PUBLIC_BASE_URL` — из него собирается ссылка на политику конфиденциальности
  в тексте согласия на экране входа (spec 0029 §2).

## Реквизиты для АВР (spec 0049, PR 4 серии #493)

Скрепка в строке ввода чата → форма: «На кого выставить», до 5 файлов (PDF, DOCX,
JPG, PNG, WebP), текст; номер и даты — из проживания сессии. Где работает (Р-7):
выключатель контура `ENABLE_GUEST_DOCUMENTS` **и** служба «Бухгалтерия»
(`accounting`) у отеля (`documents/hotel.py`) — иначе скрепки нет, маршруты 404.

- **Тело** читает только `platform/upload_form.read_upload_form` (CANONICAL):
  потолок 51 МБ до разбора, файлы в памяти, `/tmp` контейнера — tmpfs. Фото
  больше 5 МБ страница уменьшает в браузере до 2400 px (JPEG), HEIC в `accept` нет.
- **Отказы**, которые маршрут ждёт, — `AppError`, лог WARNING: ERROR-лог унёс бы
  поля формы в Sentry, пока открыт #433 (ревью PR #500, Н-1).
- **Сообщения гостю** (Р-2, `documents/messages.py`): «Реквизиты получены» пишет
  маршрут (ключ на запрос), «Готово» (ключ на проживание — дубль второго не даст)
  и «Вернули» с примечанием бухгалтера (ключ на заявку) — подписчик
  `request.status_changed`, регистрирует `worker.py`. Текст статический, на языке
  запроса, примечание — как написано; отмена гостем не пишет. Общий уведомитель
  гостя запрос не видит: у него нет `request_origins`.
- Логи: `act_request_form_opened`, `act_request_file_rejected` (код и номер файла),
  `act_request_message_recorded` / `…_skipped_duplicate`,
  `act_request_received_message_failed` (WARNING: запрос принят, карточки нет).

## «Заказать в номер» (spec 0038, PR 5)

Гость жмёт «🛎 Заказать в номер» в чате: вкладки «Ресторан» и «Магазин» (какие
открыты у отеля), разделы и карточки, корзина своя у каждого каталога, лист товара
снизу. «Далее» берёт итог у сервера (`…/menu/quote`), «Оформить заказ» шлёт его как
`expected_total_minor` и ключ кнопки (`client_order_key`): двойное нажатие и повтор
после сбоя — один заказ. Экран заказа опрашивает `…/orders/{id}` раз в 8 с, пока
заказ открыт; отменить можно, пока он не оплачен («Отправлен», «Идём за оплатой»):
заказ принят только после оплаты. Вид — по прототипу-эталону spec
0038, светлая и тёмная темы; шрифты системные (без Google Fonts — IP гостя никуда
не уходит). Всё, что пришло с сервера, скрипт выводит через `esc()`: названия
вносит персонал. Язык — kk/ru/en из языков отеля, переключатель в шапке, выбор
помнит `sessionStorage`. Корзины — тоже в `sessionStorage` вкладки.

Сообщения в чат (`menu/messages.py`) — на языке заказа, статическими текстами без
модели: «Оформлен» (`request.created`), «Иду за оплатой» (`new → in_progress`),
«Оплачено» — заказ принят (`request.payment_marked`), «Доставлено» (`done`; примечания персонала
гостю нет — ревью PR #520, Н-9), «Отменён» сотрудником с причиной (нет причины — «Другое»).
Отмена гостем в чат не пишется. Ключ — на шаг, повторное «Иду за оплатой» после возврата в
очередь второго сообщения не даёт. Адрес — веб-диалог по `guest_identity_id`
заказа; страница чата заберёт сообщение опросом. Подписчика подключает воркер.

## Типовые сценарии изменения

- **Публичные вопросы неавторизованным** (Phase 2, Q7) — per-channel конфиг
  тенанта; auth-only здесь остаётся дефолтом.
- **WebSocket/SSE вместо poll** — деталь транспорта; API и ход не меняются.
- **Финальные тексты согласия (юрпакет)** — `page.py` + `CONSENT_VERSION`.
- **Auth-only в Telegram** — тот же `guests.start_guest_session` с
  `identity_kind=telegram`; этот канал не меняется.
